# 决策制定流程

Jupyter Frontends Council 遵循 Jupyter 全局治理文档中的决策指南，采用**共识优先、投票兜底**的决策模式。这一模式贯穿从日常 PR 合并到重大架构决策的所有决策场景。

## 决策两步法

```
┌─────────────────────────────────────┐
│  第一步：寻求非正式共识（informal    │
│  consensus）                         │
│  - 在会议/Issue/PR中开放讨论         │
│  - 倾听不同观点，尝试达成一致         │
└──────────────┬──────────────────────┘
               │ 达成共识？
        ┌──────┴──────┐
        │ 是          │ 否
        ▼             ▼
┌──────────────┐ ┌────────────────────┐
│  直接执行     │ │ 第二步：正式投票    │
│              │ │ - 活跃成员发起投票  │
│              │ │ - 遵循Jupyter投票   │
│              │ │   流程（7天投票期） │
└──────────────┘ └────────────────────┘
```

### 第一步：非正式共识

绝大多数决策通过非正式共识完成：

- **讨论空间**：GitHub Issue/PR、周会讨论、Zulip/Discourse
- **核心原则**：充分讨论、倾听异议、寻求共赢方案
- **无硬性流程**：不设时间限制、不要求正式动议
- **PR 合并场景**：合并者运用最佳判断，确保代码质量、有测试、留足讨论时间后即可合入

共识不是"全票通过"，而是"没有持续的反对意见"。如果讨论中没有成员持续反对，即可认为达成共识。

### 第二步：正式投票

当无法达成明确共识时，任何活跃 Council 成员可以发起正式投票。投票流程遵循 Jupyter 官方治理文档中规定的指导方针，核心要素包括：

| 要素 | 规范 |
|------|------|
| **投票期** | 至少 7 天，给成员充分时间参与 |
| **法定人数** | 需达到 50% 以上活跃成员参与 |
| **通过标准** | 通常为简单多数（具体取决于事项类型） |
| **投票通知** | GitHub 自动 ping 所有 Council 成员 |
| **参与率要求** | 成员每年须参与至少 2/3 的投票 |

## Council 规模原则

Frontends Council **不设人数上限**。这遵循 Jupyter 治理模型中的明确指导：

> "新治理模型和决策指南旨在支持大型、高参与度的决策机构。即使目前已有明确决策机构的子项目，也可能希望扩大该机构以纳入更多贡献者。"

这一原则的核心信念是：**更多的参与带来更好的决策**。不设上限意味着任何持续贡献的社区成员都有机会进入决策层，而不必等待"空位"。

## 决策文化

Frontends 团队的决策文化可以概括为以下几点：

1. **信任判断**：团队信任成员的判断力，不设置繁琐的审批流程
2. **慢讨论快执行**：复杂议题多给几天讨论时间，达成共识后快速行动
3. **不要害怕合并**：大多数变更可以直接合入，不要让指南成为开发速度的负担
4. **公开优先**：尽量在公开空间（Issue/PR/会议）讨论，离线重要对话需向团队汇报
5. **团队共担**：无论对错，团队而非个人承担后果——"我们同舟共济"

## 与 Jupyter 全局治理的衔接

Frontends Council 的决策权限限于 JupyterLab 前端子项目范围内的事务。涉及跨子项目或 Jupyter 整体方向的决策，通过 SSC 代表（Jérémy Tuloup）上升到 Software Steering Council 层面处理。

```
Frontends Council 内部决策
  ├─ 前端技术方向、PR合并、Issue分类 → 自行决策
  └─ 跨子项目/影响Jupyter整体 → SSC代表提交SSC讨论
```
