# CodeBuddy 产品矩阵核心洞察

## 洞察一：三态一体——IDE、插件、CLI 共享同一套 AI 核心能力

### 陈述

CodeBuddy 以三种产品形态交付同一套 AI 编程能力：IDE（产设研一体的独立桌面端）、插件（即插即用于 VS Code/JetBrains/Xcode 等主流 IDE）、CLI/Code（终端命令行）。三者并非割裂的产品，而是同一 AI 核心在不同交互载体上的投影——Plan 模式、Subagents、Skills、Hooks、MCP、记忆、规则、智能提交等高级能力在三种形态间保持一致。

### 证据

- CodeBuddy 明确提供三种形态：IDE、插件、CLI/Code（F-009）。
- 三种形态共享高级功能清单：Plan 模式、Subagents、Skills、Hooks、MCP、模型配置、检查点、记忆、规则、智能提交（F-018）。
- 插件兼容 VS Code 1.82+、JetBrains 2022.2+、Android Studio Flamingo、微信开发者工具 1.06+、Xcode 14.0+、VS 2022（F-019 ~ F-024），说明核心能力以插件协议形式嵌入宿主。
- CLI 同样具备 Sub-agents、MCP 客户端/服务器、长期记忆、Skills 等能力（F-032 ~ F-034），与 IDE 文档列出的高级功能一一对应。
- IDE 基于 VSCode 架构（F-008），CLI 通过 npm 包 `@tencent-ai/codebuddy-code` 分发（F-025, F-027），印证底层共享同一 AI 引擎。

### 反常识

通常 AI 编程工具的"桌面 IDE"和"插件"是两套独立代码库，能力差异显著。CodeBuddy 的 IDE 基于 VSCode 架构，意味着它本身可以被视为"预装了 CodeBuddy 插件并深度集成产设研链路的 VSCode 发行版"，而非从零构建的独立 IDE。这降低了三态之间的能力漂移风险——插件能做的，IDE 天然能做；IDE 独有的产设研链路（Figma 转码、CloudBase 部署）则作为增值层叠加。

### 行动

- 选择形态时，交互载体是首要决策因素：需要产设研一体选 IDE，已有 IDE 工作流选插件，服务器/无头场景选 CLI。
- 学习 Skills、Hooks、MCP、Subagents 等高级能力具有跨形态迁移性，在一种形态掌握后可直接复用到其他形态。
- CLI 的 `/init` 生成的 CODEBUDDY.md 项目手册是跨形态共享上下文的关键载体。

## 洞察二：产设研全链路闭环——从自然语言到部署的垂直整合

### 陈述

CodeBuddy IDE 的核心差异化在于将产品（PRD）、设计（原型/Figma）、研发（编码/测试/审查）、部署（沙箱/公开链接）四个阶段整合进同一条自然语言驱动的流水线，而非仅做代码补全。这条链路依赖腾讯云生态（CloudBase、CloudStudio、EdgeOne Pages）与第三方服务（Supabase、Figma、TDesign/MUI/Shadcn）的深度预置。

### 证据

- 全流程链路：自然语言 → PRD → 设计原型 → 前后端代码 → 部署（F-003）。
- 四阶段能力明确划分：产品阶段（需求分析/PRD）、设计阶段（原型/草图转高保真/组件库）、研发阶段（Figma 转码/智能补全/单测生成/代码审查）、部署阶段（沙箱/公开链接）（F-010 ~ F-013）。
- 后端集成 Supabase + 腾讯 CloudBase（BaaS）（F-004, F-014）。
- 部署集成 CloudStudio 与 EdgeOne Pages（F-015）。
- 组件库预置 TDesign、MUI、Shadcn（F-006, F-016）。
- 多模型支持混元与 DeepSeek（F-017）。

### 反常识

多数 AI IDE 聚焦研发阶段的代码生成，将设计稿转换和部署视为外部工具的职责。CodeBuddy 把 Figma 转码、BaaS 后端、托管部署全部内置，本质上是在销售"一条从想法到上线的最短路径"，而非一个更聪明的编辑器。这种垂直整合的代价是对腾讯云生态的绑定（CloudBase/EdgeOne Pages），但 Supabase 的并列引入又保留了一定的厂商中立性。

### 行动

- 快速验证产品想法时，可直接用自然语言生成 PRD 与原型，再借 Figma 转码和 CloudBase 一键部署完成 MVP。
- 团队已有 Supabase 后端时，IDE 同样支持，无需强制迁移到 CloudBase。
- 组件库选型可优先考虑 TDesign/MUI/Shadcn，以获得最佳的自然语言修改体验。

## 洞察三：NPC 云端 AI 员工——从本地辅助到自主交付的范式跃迁

### 陈述

NPC 是 CodeBuddy 从"本地编程助手"向"云端 AI 员工（Cloud Agent）"演进的关键产品。它基于 CodeBuddy 核心能力打造，但运行在 CNB 平台（cnb.cool）上，以目标驱动（定义 What 而非 How）方式自主完成从需求到 PR 的全流程，并支持多 NPC 并行与协同。这标志着 AI 编程从"人驱动工具"转向"人验收产出"。

### 证据

- NPC 定位为研发流程中的 AI 员工，基于 CodeBuddy 打造，与 CNB 平台深度融合（F-039, F-040）。
- 理念为"给 NPC 定下目标，下班前验收 Ta 的产出"（F-041）。
- 目标驱动：用户定义 What 而非 How（F-042）。
- 自主获取上下文：CNB 仓库、ISSUE、流水线（F-043）。
- 全流程：规划 → 编码 → PR → 构建 → 预览环境 → 验收合入（F-045）。
- 并行指派：多 NPC 云端并行（F-044）；多 NPC 协同：NPC Team 按职能分工（F-046）。
- 自主修复构建报错直至门禁通过（F-047），自动解决合并冲突（F-048）。
- 支持职能、SOP、Skill 定制（F-049）。

### 反常识

传统 AI 编程工具在本地运行，上下文局限于当前工作区，且需要人逐步驱动。NPC 将 Agent 部署到云端，直接对接代码仓库、Issue 跟踪和 CI/CD 流水线，使其能自主跨系统行动。更关键的是"自主修复构建报错直至门禁通过"——这意味着 Agent 拥有对 CI 反馈的闭环响应能力，而非仅生成一次代码。多 NPC 按职能分工组队（NPC Team）则引入了组织协作维度，单个 Agent 的局限性被团队互补性弥补。

### 行动

- 适合 NPC 的任务是目标明确、可验收的独立工作单元（如修复特定 Issue、实现带测试的功能）。
- 复杂任务应拆解后并行指派给多个 NPC，或组建 NPC Team 按职能分工。
- 通过定制 SOP 和 Skill 可将团队工程规范固化到 NPC 行为中。
- 计费按 Agent 执行 Token 消耗，需关注大规模并行任务的成本。

## 洞察四：对抗性安全审查——多 Agent 证伪与 PoC 动态验证重构 SAST

### 陈述

CodeBuddy Security 不是传统 SAST（静态应用安全测试）工具的 AI 包装，而是以"对抗性审查"为核心的新范式：先假设告警为误报再证伪，多 Agent 独立论证消除幻觉，并自动生成 PoC 在隔离沙箱中实际运行验证。验证后的漏洞反哺为静态规则，形成自增强闭环。

### 证据

- 基于腾讯云代码分析 TCA-Xcheck 与 AI 安全 Agent 多引擎驱动（F-062）。
- 六步闭环：威胁建模 → 漏洞发现（Xcheck 静态分析 + AI 深度审计多引擎并扫）→ 对抗审查（先假设误报再证伪，多 Agent 独立论证）→ 动静验证（自动生成 PoC 隔离沙箱运行）→ 自动修复（针对性补丁，建议人工复核）→ 人工审核（F-064 ~ F-069）。
- AI 规则反哺闭环：验证后漏洞沉淀为静态规则（F-071）。
- 战绩：18 个漏洞、14 个严重/高危、18 个 CVE 编号，覆盖 11 个开源项目（F-075 ~ F-077）。
- 相比传统 SAST 的优势：高召回率、低误报率、可发现未知漏洞、低规则维护成本、PoC 动态验证、针对性修复补丁（F-078）。

### 反常识

传统 SAST 的核心痛点是高误报率——安全团队淹没在大量假阳性中。CodeBuddy Security 的"对抗审查"反直觉地先假设自己是错的，再通过多 Agent 交叉论证和 PoC 实际运行来证伪。这种"自我怀疑"机制反而比"自信报告"更可靠。更关键的是动静验证：静态分析怀疑有漏洞不够，必须生成 PoC 在沙箱中真实触发，这从根本上区分了"看起来可疑"和"实际可利用"。CVE 编号战绩证明该方法能发现人工审计遗漏的真实漏洞。

### 行动

- 安全审计应将 AI 审查结果作为辅助线索，最终以 PoC 动态验证结果为准。
- 自动修复补丁建议人工复核后再合入（F-068 明确建议人工复核）。
- 团队可利用 AI 规则反哺机制，将发现的漏洞模式沉淀为团队自定义静态规则。
- 智能成本优化（多档模型 + 缓存）适合大规模代码库审计时控制成本（F-074）。

## 洞察五：分层记忆与 Sub-agent 架构——CLI 的企业级可定制性

### 陈述

CodeBuddy CLI 虽定位为终端工具，但其架构具备企业级可定制性：长期记忆通过 CodeBuddy.md 分三层（项目级、用户级、企业级）继承；Sub-agents 拥有独立上下文、专属提示词和工具权限；MCP 同时支持客户端与服务器；配置本身也分层并支持 CLI 参数覆盖。这套设计使 CLI 既能服务个人开发者，也能满足企业统一规范管控。

### 证据

- 长期记忆基于 CodeBuddy.md 分层：项目级、用户级、企业级（F-033）。
- Sub-agents 具备独立上下文、专属提示词、工具权限（F-034）。
- MCP 客户端/服务器双能力（F-032）。
- 高度自定义：分层配置 + CLI 参数（F-035）。
- `/init` 生成 CODEBUDDY.md 项目手册（F-030），是项目级记忆与规则的载体。
- `/doctor` 提供故障排查（F-037）。
- 跨平台 macOS/Linux/Windows，50+ 编程语言（F-036）。

### 反常识

终端 AI 工具通常被视为轻量级个人工具，企业治理能力薄弱。CodeBuddy CLI 通过三层记忆（项目 < 用户 < 企业）实现了与企业管理体系对齐的继承模型——企业级规则可作为底线统一下发，项目级规则可在此基础上细化。Sub-agents 的独立上下文和工具权限则解决了单 Agent 上下文膨胀和权限过大问题，使复杂任务可以安全委派。MCP 服务器能力意味着 CLI 不仅能消费外部工具，还能向其他 Agent 暴露自身能力。

### 行动

- 企业团队应在企业级 CodeBuddy.md 中定义统一编码规范和安全底线，项目级再补充特定约定。
- 复杂任务使用 Sub-agents 委派，为每个子 Agent 配置最小必要工具权限。
- 通过 `/init` 为每个项目生成 CODEBUDDY.md，作为新成员和 AI 的共同项目手册。
- 遇到环境问题优先运行 `/doctor` 诊断。
