# 01 规则文件格式：后缀、精确与正则三节

## 1. 物理结构

`proxy.list` 是纯文本，UTF-8 无 BOM，**全文件 0 行非 ASCII**（F-017）。结构只有三层：

```text
# skylinevpn-proxylist                      ← 第 1 行：固定标题
# License: Skyline Networking Tech LLC      ← 第 2 行：固定许可行
                                            ← 第 3 行：空行
## domain_suffix                            ← 第 4 行：节标题
000webhost.com
01.org
...
## exact                                    ← 第 26,453 行
85.17.73.31
1password.drift.click
...
## regex                                    ← 第 26,539 行
(^|\.)13mei[5-7]\.buzz$
...
```

节标题固定为 `## <section>`，节名取自 `merge.py` 的元组 `("domain_suffix", "exact", "regex")`（F-014、F-032）。解析器遇到未知节名会直接 `sys.exit`（F-038），因此**三节之外不可能有第四条通道**。

## 2. 三节的语义

文件本身不声明语义，下面三条是从 `merge.py` 的生成与归约代码反推的（F-033 ~ F-042）：

| 节 | 条目形如 | 匹配语义（反推） | 谁会产生它 |
|----|---------|----------------|-----------|
| `domain_suffix` | `example.com` | 主机等于该值**或以 `.example.com` 结尾** | `\|\|host`、裸关键词（F-037） |
| `exact` | `85.17.73.31`、`1password.drift.click` | 主机**严格等于**该值 | `\|http://host` 单竖线规则（F-037） |
| `regex` | `(^|\.)13mei[5-7]\.buzz$`、`^hses[1-7]?\.akamaized\.net$` | 对主机名做**正则匹配**，锚定方式由条目自带 | 上游通配符与少量 URL 正则（F-034、F-036） |

关键点：`domain_suffix` 与 `exact` 的差别**不在字符串形态**（两者都可能是普通域名），而在**是否包含子域**。`a4e8s8k3.map2.ssl.hwcdn.net` 放在 `exact` 里表示「只匹配这一个主机」，若放进 `domain_suffix` 就会连它的子域一起匹配（F-019）。

这也是 [03 归约算法](03-reduction-algorithm.md) 中 `covered()` 函数的语义基础：既然后缀包含子域，任何已被父后缀覆盖的子域条目都属冗余。

## 3. 规模与分布

| 节 | 条目数 | 占比 |
|----|-------|------|
| `domain_suffix` | 26,447 | 99.06% |
| `exact` | 84 | 0.31% |
| `regex` | 167 | 0.63% |
| **合计** | **26,698** | 100% |

（F-015；统计口径为「非空且非 `#` 开头」的行。）

这个分布本身就是设计意图的证据：**绝大多数规则都能用后缀表达**。`exact` 只有 84 条，说明「只拦一个主机、不拦子域」是少数派需求（其中还包含 IP 形态条目，如 `85.17.73.31`）。`regex` 的 167 条主要来自上游的通配符规则，覆盖 `*.buzz`、`*.icu` 这类批量域名（F-020）。

## 4. 排序与大小写

- 三节内部**均按 `sorted()` 升序**输出，等价于按码位排序（F-042）。
- `domain_suffix` 与 `exact` 条目一律**转小写**；`regex` 保持原样（F-039）。
- 排序的意义不是美观，而是**让 diff 可读**：每周的变更在 GitHub 上就是若干行插入，评审者能一眼看出新增了哪些域名（F-011 的 `+1`、`+8`、`+5`）。

若不做排序，集合迭代顺序在不同 Python 版本/哈希种子下可能变化，每次构建都会产生全文件级 diff，自动化提交将失去可审性。

## 5. 缺失的东西：版本号与格式说明

数据文件内部**没有 schema 版本、没有生成时间戳、没有条目总数**（F-022）。文件头只有两行固定注释，内容里也只有三节标题。

这意味着：

1. 消费端无法从文件判断「这份表是哪一版解析规则生成的」；
2. 若将来 `merge.py` 改变语义（例如把 `domain_suffix` 改成严格相等），旧客户端不会得到任何提示；
3. 唯一的时间信号是 **Release 的 tag**（`vYYYYMMDD`），而不是文件内容本身。

对应地，`README.md` 只有下载命令与许可指向，**不解释三节格式**（F-064、C-4）。因此「格式文档」在本仓是缺失的一环——它被隐含在 `merge.py` 里，只有读代码才能获得。

## 6. 消费端的解释责任

由于仓内不含匹配器，消费端必须自己实现三节语义。从归约逻辑可以推出**最低实现要求**：

```text
domain_suffix: host == e 或 host.endswith("." + e)
exact:         host == e
regex:         re.search(pattern, host)      # 条目自带锚点，不要额外加 ^...$
```

如果消费端把 `domain_suffix` 实现成严格相等，那么归约阶段被「吸收」掉的子域条目就会真的失效——**归约的正确性依赖消费端的语义与之匹配**。这是一条隐式契约，也是 D-5 的核心。
