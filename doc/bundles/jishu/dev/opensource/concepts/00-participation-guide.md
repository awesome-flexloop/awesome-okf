# 开源参与指南

> **时点说明**：本文基于 2020 年前后教程（简书连载《开源的世界》第 1.1 篇《1.1 开源项目指南》）整理，学习资料为开源软件指南（Open Source Guides，opensource.guide/zh-cn/）。**注意**：原文为部分抓取，正文在「你提交贡献之后发生了什么 -> 没有人响应你」章节的"每个人都会遇到这样的情况。"处截断，后续章节未获取，本概念仅覆盖已抓取内容（F-260~F-265）。

## 为什么会有人为开源做贡献（F-261）

为开源贡献力量，得到的回报是能够学习到很多、受教很多、锻炼各种经验。文章列举的动机包括：

- **巩固现有技能**——无论是撰写代码、设计界面、撰写文档还是组织活动，都能在开源项目里找到实践位置
- **遇见志同道合的人**——开源项目一般有和谐、热心的社区，很多人的深厚友谊通过共同参与开源建立
- **寻找导师，并且尝试帮助他人**——相互学习和彼此教学让每位参与者满载而归
- **在公众间建立声誉（职业口碑）**——开源下的所有工作都是公开的，是很好的展示实力的地方
- **学习领导和管理的艺术**——实践解决冲突、组织团队、优先级排列等管理技能
- **鼓励作出改变，哪怕改变是很微小的**——不必是资深人士，看到网站的拼写错误，直接改掉即可

## 开源贡献意味着什么：不需要编码能力（F-262）

为开源做贡献不一定需要编码能力，代码固然重要，但项目中不需编码的重要部分经常被忽视。文章列出的非编码贡献类型：

| 兴趣类型 | 贡献形态 |
|---------|---------|
| 规划事件 | 组织研讨会或线下分享、组织大型会议、帮助社区成员寻找技术会议并提交演讲拟稿 |
| 设计 | 重新布置布局、进行用户研究、整理风格指南、创建 t 恤或新标志 |
| 写作 | 撰写和改进文档、以实例展示项目用法、撰写新闻稿、撰写教程、翻译项目文档 |
| 组织活动 | 链接重复问题、建议新标签、阐述清晰开放问题以推动讨论 |
| 享受编码乐趣 | 解决开放问题、写新功能、自动化项目设置、改进工具和测试 |
| 帮助他人 | 回答 Stack Overflow 与 reddit 上的问题、帮助缓和讨论板或对话渠道 |
| 在编码方面帮助他人 | 审核他人代码、撰写教程、为其他贡献者做导师 |

开源也不必一定是软件项目：可以是图书、食谱、列表等任何可以开源的项目类型（如"惊奇"列表 awesome、前端面试题清单等）。

## 分析感兴趣的开源项目（F-263）

一个典型的开源项目通常包含如下角色：

- **作者**：项目的创始人或创始组织
- **归属者**：代码仓库或组织的管理员（不一定和作者是同一个人）
- **维护者**：负责项目未来走向和组织管理的贡献者
- **贡献者**：只要为项目做出了贡献就算
- **社区成员**：使用项目的人们

靠谱的开源项目一般有文档，通常在代码仓库顶级目录列出：

- **LICENSE**：根据开源软件的定义，每个开源项目必须拥有开源许可协议——源码开放但没有任何许可协议就不能叫做开源
- **README**：介绍性说明文件，解释项目有何用处、为何发起、如何快速入门
- **CONTRIBUTING**：帮助人们了解如何对项目做贡献，解释项目需要什么类型的贡献者、社区流程如何
- **CODE_OF_CONDUCT**：参与社区时的礼仪、说话方式、行为规范，帮助形成友好氛围
- **其它文档**：如教程、导游、治理规则，大型项目中常见

开源项目的组织工具：**问题追踪**（Issue tracker）、**Pull requests**、**论坛或邮件列表**、**即时在线聊天**（Slack 或 IRC）。

## 找合适的项目做贡献（F-264）

可利用以下资源找到合适的新项目：

- GitHub 探索（github.com/explore/）
- Open Source Friday
- First Timers Only
- CodeTriage
- 24 Pull Requests
- Up For Grabs
- 像忍者一样贡献（contributor.ninja）

## 贡献前检查列表（F-265）

在进一步行动前，快速扫描项目以确保项目接受贡献，评估是否适合新贡献者：

- **符合开源的定义**：有许可协议吗？通常在根目录有一个 `LICENSE` 文件
- **提交活跃度**：最后一次提交在什么时候？有多少贡献者？提交是否频繁？
- **issue 情况**：有多少开放 issue？维护者响应是否迅速？是否有活跃讨论的 issue？issue 是否近期产生？有没有已关闭的 issue？
- **PR 情况**：有多少开放 PR？提交 PR 后维护者响应是否迅速？是否有活跃讨论的 PR？近期有多少 PR 合并？
- **项目受欢迎程度**：维护者回答是否有帮助？社区是否友好？PR 是否被 review？维护者是否对贡献者道谢？

## 有效沟通建议（F-265）

在开启 issue 或 PR 之前，或在聊天室提问之前，牢记以下建议：

- **给出上下文**——解释你是如何做的、如何再现错误现象，或解释新想法的理由（"当我做 Y 的时候 X 不能工作"，而非"X 出问题! 请修复它"）
- **做好准备工作**——阅读项目的 README、文档、问题、邮件列表并搜索网络，展现你尝试过、努力过
- **保持请求短小直接**——每一次贡献都需要他人查阅，保持简洁能大大增加获得帮助的机会
- **让所有沟通都在公开场合进行**——不要给维护者发私信，除非是分享敏感信息（如安全问题或严重过失）
- **大胆提问但要谨慎**——每个人进入新项目都是新手，给维护者同样的耐心
- **尊重社区决定**——可积极讨论并寻求妥协；如无法同意可保持自己的分支或另起炉灶
- **保持优雅**——跨语言、文化、地理位置与时区会丢失上下文，书面交流难以传达语气，善意理解对方意图

创建 issue 与 pull request 的适用情形（F-265）：

- 报告自己无法解决的错误、讨论高级主题或想法、期望实现新特性 → **创建 issue**
- 提交补丁（纠正拼写错误、损坏链接等）、开始别人请求的任务 → **创建 pull request**；PR 不意味着工作已完成，可尽早开启并标记为 WIP（正在进行中）以获取反馈
