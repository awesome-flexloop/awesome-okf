# 核验与对抗审查

> **结论**：`status: stable`。本束不做运行时实测，全部结论限定为「仓库内文档与源码可证」；运行时行为以 F 编号标注为「文档口径」。
> **核验强度**：L1 一手（直接读取被解读仓库），非二手转述；但**信源单一**——所有口径最终仍由官方自己书写，缺少第三方复现。

## 一、核验方法

| 步骤 | 做法 | 目的 |
|------|------|------|
| 1 元信息锚定 | `git rev-parse`、`git log -1`、`go.mod`、`CHANGELOG.md`、`LICENSE` | 固定版本坐标，避免「以最新版为准」的漂移 |
| 2 文档三角互证 | README ↔ `docs/` 架构与参考手册 ↔ `internal/` 目录与包名 | 识别文档内部矛盾 |
| 3 清点复核 | 目录计数（internal 包、skills 产品、docs 篇数、事件数） | 把「很多」换成可复核的数字 |
| 4 口径冲突登记 | 见第二节 | 保留冲突，不强行抹平 |
| 5 对抗审查 | 见第四节 | 主动寻找本束结论的薄弱点 |

## 四、对抗审查（四视角）

### 4.1 魔鬼代言人：这套「静态命令面」是否只是把复杂度换个地方？

**意见 D-1**：静态展开把 MCP 的动态发现换成了构建期生成，代价是**发版与接口变更强耦合**。一旦服务端新增参数而 CLI 未重生成，用户会遇到「文档有、命令无」的错位。仓库用 `git diff --exit-code` 守护生成物（F-029），说明作者知道这个风险，但该守护只保证「生成物与生成器一致」，不保证「生成器与服务端一致」。
**处置**：在 [02-static-endpoint-pipeline.md](../concepts/02-static-endpoint-pipeline.md) 显式写入「版本滞后」这一代价，不把静态化描述成纯粹优点。

**意见 D-2**：`dws api` 允许直连开放平台（F-058），等于在受控命令面旁边开了一扇后门。仓库用「raw 不进 Agent Schema」（F-060）缓解，但人类用户仍可绕过 dry-run 与安全元数据。
**处置**：在安全概念中把 raw 通道标注为「逃生舱」，并给出使用纪律（先 dry-run、再小流量、域名白名单）。

### 4.2 新人视角：读完能否跑通第一条命令？

**意见 D-3**：原文 README 的信息密度极高（安装、登录、20 个服务、事件、raw API、skills 全在一页），新人容易在「装完之后做什么」处掉队。
**处置**：本束提供三条递进示例（安装登录 → 日常操作 → Agent 工作流），每条示例给出预期输出形态与失败时的退出码判读。

**意见 D-4**：`profile switch <corpId:userId>` 需要用户先知道自己的 corpId，而文档未在首次登录处回显获取方式。
**处置**：示例中要求先执行 `dws auth status --format json` 读取身份，再做切换，避免让读者猜 ID。

### 4.3 老板视角：这套东西的业务价值能否一句话说清？

**意见 D-5**：若只讲「钉钉的命令行」，容易被理解为运维脚本工具；真正的差异点是「同一份声明同时产出人类 CLI 与 Agent Schema」，这让 AI 调用具备**可审计的接口契约**。
**处置**：概念 00 与 02 均以「双表面同源」作为价值主张，而非罗列命令数量。

**意见 D-6**：安全章节强调审计与确认，但未给出合规映射（等保、SOC2 等）。本束不应替官方宣称合规。
**处置**：只陈述机制（JSONL 哈希链、域名白名单、HTTPS 强制），明确「不构成合规认证结论」。

### 4.4 未来视角：半年后哪些内容会过期？

**意见 D-7**：版本号、命令数量、事件数量、skills 数量四类数字最易腐烂；已全部收敛到 F 编号，正文只引用编号不复制数字者优先。
**处置**：正文出现的数字均带 F 编号或标注「快照」；`log.md` 记录核验时点。
