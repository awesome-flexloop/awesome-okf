# 核验报告

本文件回答三个问题：仓库里哪些数字/说法彼此不完全一致（C）、这份教程最容易被怎样反驳（D）、哪些结论本包明确没有资格给出。

## 一、口径冲突（C）

| 编号 | 冲突 | 两侧依据 | 裁决 |
|------|------|----------|------|
| C-1 | **安装期校验锚点有两套**：安装器内嵌 SHA-256（F-019、F-049），Release 页另有 `SHA256SUMS.txt`（F-060） | README 安装节 vs `build_release.py` | 两者不是替代关系：安装器校验的是**它即将安装的那个包**，`SHA256SUMS.txt` 校验的是**你在 Release 页下载到的文件**。本包不主张任何一方「更权威」，只按用途分别引用 |
| C-2 | **Windows 两个平台共用构建号**：v3.0.1 表中 Windows 10+ x64 与 Windows 11 ARM64 的 Build 均为 `20261027-123045` | `CHANGELOG.md` | 构建号标识一次 CI 构建批次，不等同于「一个平台一个构建」；平台数（2）与构建批次（1）是不同维度，不可互相推算 |
| C-3 | **tag 与 app version 是弱约束**：tag 格式被强校验（F-045），但 tag 版本号与安装器内 `APP_VERSION` 不一致时只打印提示，不中止（F-054） | `build_release.py` | 对外表述版本时应以 `CHANGELOG.md` 的 Release 版本为准，不要把 tag 名当作唯一事实源 |
| C-4 | **Release 资产数少于 CI 束内容物**：macOS 束内同时含 `.pkg` 与 `.tar.gz`，只发布 `.pkg`（F-051）；Windows 束含内部测试脚本，不发布（F-043） | `build_release.py`、`RELEASING.md` | 讨论「每个平台几个资产」必须以 `dist/<tag>` 输出为准，不能按 CI 束解包结果计数 |
| C-5 | **架构命名两套写法**：README 写 `x64`，构建脚本与包名写 `amd64`（F-013、F-052） | README、`build_release.py` | 同一架构的不同命名习惯；本包统一在涉及包名处用 `amd64`，涉及平台表时保留 README 原写法 |

## 二、对抗审查（D）

> 视角：魔鬼代言人（D-1、D-4）、新人（D-2）、老板/风险（D-5、D-6）、未来维护者（D-3、D-7）。

| 编号 | 意见 | 影响 | 本包的处理 |
|------|------|------|-----------|
| D-1 | **校验和不等于签名**：SHA-256 只证明「文件没变」，而 `SHA256SUMS.txt` 与被校验资产由同一次流水线生成，未使用 GPG/cosign 等签名机制 | 发布账号或仓库失陷时，校验和会与恶意包一同被替换 | 在 [06 信任模型](concepts/06-trust-model-and-boundaries.md)中明确：本链提供**完整性**与**发布流程一致性**，不提供**抗发布方失陷**的密码学保证 |
| D-2 | **一键安装本身是信任链最弱一环**：`curl … \| sudo bash` 把远端脚本直接交给 root，`--check` 也只校验包、不校验脚本自身 | 教程若把一键安装写成「安全默认」，会误导读者 | [演练 00](examples/00-install-verify-uninstall.md)把「下载后本地查看/离线安装」列为高风险环境的推荐路径 |
| D-3 | **禁止词清单在仓库外**：缺失即拒绝运行（F-057），换机/新维护者若无该文件则整条流水线不可用 | 可用性换保密性；新人首次发布极易卡住 | 明确写为「设计取舍而非缺陷」，并在 [05 身份与泄漏门](concepts/05-identity-and-leak-gates.md)给出前置准备清单 |
| D-4 | **泄漏正则既有误伤也有漏检**：邮箱、裸 `CI` 等宽泛模式会命中正常文本；编码/加密/自定义压缩格式则可能漏检 | 门禁给人「已彻底扫描」的错觉 | 明确扫描的**格式覆盖面**（F-058）与**不覆盖面**（加密容器、未知压缩、网络侧内容） |
| D-5 | **身份锁依赖本地钩子**：`install-hooks.sh` 需克隆后手动执行一次（F-070），仓库内未展示服务端分支保护配置 | 未装钩子的克隆可提交违规提交，直到发布前全量检查才暴露 | 在 [05](concepts/05-identity-and-leak-gates.md)指出「本地钩子是早期反馈，`publish-release.sh` 的门才是硬门」 |
| D-6 | **「只保留最新 release」牺牲可回滚性**：旧 tag 保留但资产删除（F-040） | 老用户无法再安装历史版本；出问题不能快速回退到上一版 | 在 [02 发行拓扑](concepts/02-distribution-topology.md)把它记为**策略代价**，不写成纯粹优点 |
| D-7 | **本包未执行任何二进制或安装器**：分流行为、TUN 建立、DNS 处理、服务守护、实际下载体积全部缺席 | 所有运行时结论都只是文档口径 | 根 `index.md`、演练索引与每篇演练顶部均标注来源性质 |

## 三、明确的不可核验边界

1. **产品实现**：仓库不含任何产品源码（F-007），协议、加密、路由策略、节点调度均不可从本仓推断。
2. **服务端行为**：账号体系、订阅校验、节点可用性、限速与计费不在仓库范围内。
3. **Release 实况**：本包未访问 GitHub Release 页面，资产清单与上传者核验（F-039）是**流程要求**，不是本次实测结果。
4. **安装器内部逻辑**：`skyline-{linux,macos}-install.sh`、`skyline-windows-install.ps1` 位于 CI 束内，本仓只引用其变量名与步骤标记（F-046 ~ F-053、F-062 ~ F-064），未逐行审阅。
5. **运行平台**：未在 Ubuntu / Debian / macOS / Windows 任一实机执行安装，故障排除条目均为 README 口径（F-026 ~ F-028）。

## 四、复核触发条件

出现以下任一情况，应重读仓库并更新本束：

- 新增 tag 或 `CHANGELOG.md` 出现新版本条目；
- `LEAK_PATTERNS`、`MSG_LEAKS`、`AGENT_FILES` 任一正则变更；
- `build_release.py` 的步骤标记期望值（`stage_total`、`sub()` 计数）变更；
- 发布策略变化（例如恢复保留多个历史 release、引入签名）；
- README 平台矩阵或命令表变化。
