## 2. 机制层（Mechanism Layer）——执行者洞察

> 以下洞察基于本篇**单一公众号文章** + 官方架构事实推导，标记为 hypothesis。

### 洞察 1：体积差距的根本——「内核编译期捆绑」vs「运行期复用」
- **现象（phenomenon）**：Electron 应用动辄上百 MB，Tauri 应用只有几 MB 到十几 MB（F-005/F-010）。
- **工作原因（working cause）**：Electron 在**编译/打包期**把完整 Chromium + Node.js 落入每个应用（F-004）；Tauri 在**运行期**复用操作系统已安装的系统 WebView 渲染引擎（F-008），本地只放业务代码与轻量 Rust 二进制（F-009）。
- **影响（impact）**：应用体积与首包下载、安装占地直接挂钩；Electron 的「自包含」换来跨平台一致性，Tauri 的「复用」换来轻量却依赖目标机系统 WebView 版本。
- **建议（recommendation）**：选型时把「体积敏感度」作为首要权重——面向消费端、讲究安装体验的工具优先 Tauri；面向追求渲染一致性、需锁定渲染版本的内网企业应用，Electron 依然有其价值。
- **反常识（counterintuitive）**：「轻量」与「全平台一致性」在此二者间存在权衡，并非「越轻越好」——Tauri 轻量部分的代价是渲染引擎版本差异风险。

### 洞察 2：移动端支持是 1.0→2.0 的质变拐点
- **现象（phenomenon）**：Tauri 2.0 将目标平台从桌面扩展到 iOS/Android（F-014）。
- **工作原因（working cause）**：1.0 的短板是跨端（仅桌面三系统）与开发体验，2.0 补上移动端与 CLI/配置简化（F-015），形成「一套前端 + Rust 后端 → 桌面 + 移动」的统一代码库。
- **影响（impact）**：对已熟悉 Web 前端的团队，同一套代码可覆盖桌面与移动，缩短多端交付成本；但需注意 iOS/Android 与桌面在 WebView 能力、权限模型上的差异（F-016）。
- **建议（recommendation）**：若团队有「桌面 + 移动」双端诉求且愿投资 Rust，Tauri 2.0 的「一套代码多端」是现实的竞争力；纯桌面轻量工具则入门更简单。

### 洞察 3：性能数字需「去营销化」阅读理解
- **现象（phenomenon）**：文章给出启动 <0.5s、内存 30-50MB、体积最小 3.5MB 等鲜明数字（F-012/F-013/F-010）。
- **工作原因（working cause）**：这些是对**特定演示场景**（如基础 Markdown 编辑器）的测量；真实应用体积/内存/耗时取决于业务复杂度与依赖（见 [verification.md](verification.md) 单源标注）。
- **影响（impact）**：若读者把演示数字当作普适绝对值，会在选型时产生「性能幻觉」。
- **建议（recommendation）**：以「量级/趋势」看待这些数字（Tauri 显著轻于 Electron 量级成立），落到具体项目时用自己最小可运行样例实测再决策。

## 3. 迁移层（Transfer Layer）——可迁移实践

> 以下实践中立、可逆、尊重边界，可用于读者自己的桌面应用选型。

1. **按「内核捆绑 vs 运行期复用」评估体积**：任何桌面跨平台选型，先判断是否接受「每应用携带完整渲染引擎」的代价。
2. **用最小样例实测**：不轻信营销数字，以最小可运行 App 实测体积/内存/启动，作为决策依据（呼应洞察 3）。
3. **关注权限模型**：选择「敏感权限默认关闭、显式授予」的框架（如 Tauri 2.0 的 capability），降低安全暴露面（F-016）。
4. **生态成熟度权衡**：复杂场景/强插件依赖下，成熟生态（Electron）仍具优势；轻量高体验优先新框架（Tauri 2.0）。该权衡独立于技术优劣，取决于需求场景。
