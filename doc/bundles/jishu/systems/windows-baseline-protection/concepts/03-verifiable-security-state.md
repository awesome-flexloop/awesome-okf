# 03 · 可验证安全状态

微软 IT Pro Blog 用的词是 **a versioned, attestable device security state**——一个可版本化、可证明的设备安全状态。这一节把三个词拆开。

## 一个答案，三类消费者

平台把散落的独立设置收敛成**一个 `true`/`false`**：全部满足为 `true`，否则 `false`（F-028）。结果由平台计算、以硬件为根，同时供三方读取：

| 消费者 | 拿到结果做什么 |
|---|---|
| 使用这台电脑的人 | 在设置页看缺哪项、按指引开启 |
| IT 管理员 | 通过 Microsoft 365 管理中心的 baseline security mode 管理受管理设备（F-043） |
| **应用与服务** | 自行决定是否据此调整功能（见[04 · 应用侧策略](04-app-side-policy.md)） |

第三类消费者是这次变化的实质。前两类只是把原本分散的开关放到一个页面里，第三类把内部状态变成了**对外接口**。

## 启动时测量 + 关闭需重启 = 只需查一次

官方给的机制约束（F-030）：

- 状态由**安全处理器在启动时测量**；
- 每一项要求**自启动起强制执行**；
- 关闭任一项都**需要重启**，因此状态不会在系统运行过程中悄悄改变。

这条容易被忽略，但很关键：正因状态在一次开机周期内稳定，用户和应用**查询一次即可**，不必反复轮询，也不必担心「刚查完就被改了」。

## 版本化：这是地板，不是天花板

官方原句 `This is the floor, not the ceiling`（F-031）。含义有三层：

1. 首版 8 项只是起点，标准会随威胁演进增加；
2. 因为状态是**版本化**的，依赖方知道自己面对的是哪一版门槛；
3. **通过当前版本的设备，可能不通过后续版本**。

因此本包所有提到 8 项的地方都带「首版」限定。官方称版本增项与演进规则将在后续博客说明，截至 2026-11-20 尚未发布（缺口 G2）。

## 三种读出形式

| 形式 | 回答什么 | 典型用途 |
|---|---|---|
| **简单状态查询** | 基线是否激活？是 / 否 | 应用启动前的快速判断 |
| **详细报告** | 若为否，**缺哪几项** | 让结果可行动：用户知道该去开哪一项 |
| **硬件支持的证明令牌** | 用密码学凭证证明该状态，由安全依赖方在服务端验证 | 银行、在线考试、反作弊等需要防本地伪造的场景 |

第三种是源文提到的「硬件生成的证明令牌把结果放到服务端验证和记录」（F-039）的官方对应物（F-034）。差别在于：前两种是本地回答，第三种把信任锚从本机搬到服务端，**对本地绕过制造更多限制**——这部分源文判断与官方一致。

## 别把状态当成安全评分

`true` 只表示首版清单全部启用，不等于「这台电脑不会中毒」，微软也没有这样声称。它是一个**设备信任信号**，用途是让依赖方做策略判断，不是安全能力的完整度量。
