# I 阶段洞察 · E 阶段模式

> 洞察全部引用 F 编号，证据可回溯到[事实台账卷一](article-source.md)、[卷二](facts-mechanism-and-claims.md)。
> 模式经[四视角对抗审查](adversarial-review.md)（A2、A6）收紧后入库，成熟度 **L1：单案例待验证**。

---

## 一、I 阶段：3 条核心洞察

### 洞察 1 · 变化不在「检查什么」，而在「谁能读结果」

| 四元组 | 内容 |
|---|---|
| **陈述** | 基线保护没有新增任何一项安全防护；它新增的是一个**对外读出接口**——把原本散落的独立设置，变成应用可查询的单一状态。 |
| **证据** | F-027（官方：每一项都是现有能力，新的是一起评估为一个可证明结果）、F-028（true/false 对用户、IT、应用三方可读）、F-033（源文亦强调「不是给系统自己用的」）、F-034（三种读出形式）。 |
| **反常识** | 读者默认把「新的安全功能」理解为「新增了更严的防护」。实际防护清单一个没加，变的是**结果的消费者**——从系统自己，扩展到每一个应用开发商。 |
| **行动** | 读这类平台变更时，先问「这个结果谁能读、读完能做什么」，再判断影响面；不要从检查项数量推断严格程度。 |

### 洞察 2 · 平台把裁决权外包，风险与责任同时转移

| 四元组 | 内容 |
|---|---|
| **陈述** | 微软提供状态与四档动作，但**不决定用哪一档**；设备能否运行某软件，从「操作系统说了算」变成「每个应用自己说了算」。 |
| **证据** | F-036（allow/warn/limit/block 四档，平台不裁决）、F-037（Bray：you own the policy）、F-034（证明令牌可由服务端验证）、F-039（源文亦注意到服务端验证）。 |
| **反常识** | 标题式叙事是「微软收紧了」。机制事实恰好相反：微软在**退出**逐设备裁决，把它下放给应用。所谓「更严」是潜在结果的分布，不是平台策略。 |
| **行动** | 评估影响时按**应用逐个**查其公开策略，不按 Windows 版本一刀切；在伙伴公布档位前（缺口 G3），任何「某软件会被拦」都是推测。 |

### 洞察 3 · 越具体的数字，越要先问口径

| 四元组 | 内容 |
|---|---|
| **陈述** | 本例中三处「看起来最硬」的数字/日期都带口径：8 项与 7 类、11/18 与 11/17、三家具名与五家具名。数量具体不等于无歧义。 |
| **证据** | F-029（两条驱动规则拆/合 → 8 项 vs 7 类）、F-018/F-019/F-022（官方宣布 11/17、媒体转述 11/18）、F-040/F-041（伙伴名单）、核验报告 E1/E2/E5。 |
| **反常识** | 直觉是「数字冲突说明有一方写错」。这里 8 与 7 **都对**，差别只是分类粒度；真正写错的反而是不带数字的一句「检测不通过就拒绝启动」（E4）。 |
| **行动** | 把「数量」当成需要追问拆分方式的字段，不是可直接搬运的事实；把「能力清单」与「已采用策略」分栏登记。 |

## 二、E 阶段：模式「读出方优先」

| 项 | 内容 |
|---|---|
| **模式名** | 读出方优先（5 字） |
| **一句话** | 识别平台类变更时，先定位「谁能读这个状态、读完能做什么」，再判断影响面。 |
| **成熟度** | **L1 · 单案例待验证**（仅本例；需 ≥2 个独立案例才升 L2） |
| **适用于** | 平台/操作系统/开放 API 把内部状态开放给第三方消费的变更；媒体报道与官方口径混杂时。 |
| **不适用于** | 纯本地功能改动（无外部读出方）；已有明确强制策略且官方公布执行规则的变更；需要实际兼容性测试才能回答的工程问题。 |

### 核心做法（6 步）

1. **三问拆解**：把变更拆成「测什么 / 谁来读 / 读完能做什么」，三者分别登记，不合并成一句「更严了」。
2. **锚定官方一手**：查厂商官方博客、产品文档、支持页、版本发行说明，确认结果形式（简单状态 / 明细 / 可验证令牌）。
3. **定位策略归属**：分清平台、应用、管理员三方谁裁决；「平台能报」不写成「平台会拦」。
4. **能力／策略分栏**：把「厂商参与测试」与「厂商已承诺某档策略」放在两栏，不合并叙述。
5. **数字问口径**：遇到数量与日期，先查是谁拆分、谁合并、谁的时点；并列登记，不裁决单一对错。
6. **影响面按消费者列举**：输出结论时逐个列出读出方及其已公开策略，不做全平台一刀切推断。

### 反模式（4 个，均来自本例实际教训）

| # | 反模式 | 本例表现 |
|---|---|---|
| 1 | **能力当策略** | 把「开发者可选 block」写成「Adobe 检测不通过就拒绝启动」（E4，本包唯一实质勘误） |
| 2 | **时点当发布** | 把媒体转述日 11/18 当作官方发布日，忽略官方博客与构建说明的 11/17（E1） |
| 3 | **数字裁决** | 把 7 类与 8 项当成「谁写错了」，忽略支持页合并了两条驱动规则（E2） |
| 4 | **操作放大** | 把「在安全中心内单独关闭 SAC」写成「禁用 Windows 安全中心」（E3） |

### 检验标准

读完任一平台变更材料，能不加推测地回答五问：**测什么 / 谁读 / 谁裁决 / 读出后有几档动作 / 有无官方或厂商的公开承诺**。五问齐备且每问有信源，才算读完；缺任一问登记为缺口，不以推测填空（本例缺口 G1~G6）。

### 跨领域迁移（≥1 个非当前领域）

- **知识库治理（本仓自身）**：OKF 的 `status: flagged` 是内部状态。若把它开放给下游消费者，消费者可自行决定「拒绝引用 / 降权展示 / 仅提示」，不能写成「知识库禁用了该包」——与「平台报告状态、策略由开发者决定」同构。本例的 `flagged` 用法可在[核验报告](verification.md)与[bundle 根](../index.md)就地对照验证。
- **支付风控**：平台把风险分开放给商户，商户决定「放行 / 二次验证 / 拒绝交易」，媒体标题写成「平台封禁了某类交易」即为反模式 1。
- **内容平台信用分**：把账号信用分开放给创作工具，工具决定限流还是仅提示，不等于「平台限流」。
