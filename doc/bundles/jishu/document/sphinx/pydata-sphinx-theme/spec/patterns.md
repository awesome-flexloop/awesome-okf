# 可复用模式（E 阶段）

> 从事实与洞察中抽象出的可迁移模式。每个模式给出触发场景、结构、步骤、反模式与迁移验证。

## 模式 P-001：构建期导航计算 + 运行期交互

**触发场景**：文档站需要在服务端生成稳定的层级导航，同时保留浏览器端的折叠、高亮与快捷键。

**结构**：

```text
Sphinx toctree（唯一事实源）
    │
    ├── 构建期：解析祖先/子树 → 生成带 current/aria-current 的 HTML
    │             → 缓存可共享部分 → 按页搬运当前标记
    └── 运行期：只处理滚动、开关、焦点、快捷键
```

**步骤**：

1. 以 `root_doc` 的 toctree 作为顶部导航唯一来源，不在模板里硬编码链接。
2. 侧栏按“当前顶层祖先”解析子树，而不是渲染全站树。
3. 在 HTML 中一次性写入 `current/active` 与 `aria-current`，避免前端猜测。
4. 对可共享的子树做缓存，缓存键包含祖先、输出目录、展开层级与参数。
5. 前端只做状态切换与滚动同步，不重建导航结构。

**反模式**：

- 用 JavaScript 在浏览器里根据 URL 重新计算整棵树（慢、易错、SEO 不友好）。
- 每个页面都从全站根节点渲染侧栏（大站点构建爆炸）。
- 缓存 HTML 却不迁移 `current` 标记（高亮错页）。

**迁移验证**：任选一个非文档站点（如后台管理菜单），检查是否满足“服务端产出结构 + 客户端只改状态”；若客户端仍在拼菜单，则不适用。

## 模式 P-002：模板列表 + 空渲染剪枝的可插拔布局

**触发场景**：页面有多个区域，需要让用户通过配置增删组件，且组件可能因上下文无内容而自动隐藏。

**结构**：

```text
section config: [template_a, template_b, ...]
    → 补全后缀
    → 逐个渲染
    → 空白结果剔除
    → 渲染最终区段
```

**步骤**：

1. 把每个区域建模为“有序模板名列表”，而不是布尔开关集合。
2. 统一模板命名与后缀规则（可省略 `.html`）。
3. 渲染前用当前页面上下文试渲染，剔除空白结果。
4. 对渲染昂贵的模板提供跳过检查的白名单。
5. 允许用户用 `!` 前缀继承并覆盖内置模板的单个块。

**反模式**：

- 为每个组件写一个 `enable_xxx` 开关（组合爆炸、顺序不可控）。
- 组件缺数据时抛错（应渲染为空并让位）。
- 把“是否显示”硬编码在布局模板里（用户无法重排）。

**迁移验证**：把该模式套到一个邮件模板系统或仪表盘卡片布局，检查能否仅靠“模板列表 + 空剪枝”完成增删与排序；若必须改中心代码，则不适用。

## 模式 P-003：单一 DOM 状态驱动的双主题

**触发场景**：站点需要 light/dark 两套视觉，但不想维护两份页面或两套构建。

**结构**：

```text
<html data-theme="light|dark">
    ├── CSS 变量按 data-theme 定义
    ├── 高亮 CSS 双前缀（light/dark）
    ├── 图片用 only-light / only-dark / dark-light 声明
    └── JS 只切换 data-theme 并持久化
```

**步骤**：

1. 把所有颜色收敛为语义变量，按 `html[data-theme=...]` 定义两套值。
2. 对无法用变量的属性，使用 `light-dark()` 或分主题选择器。
3. 构建期生成双前缀的代码高亮 CSS，而不是依赖媒体查询。
4. 首屏内联脚本恢复用户选择，避免闪烁。
5. 为主题相关资源提供显式类，避免运行时猜图片。

**反模式**：

- 生成两套 HTML/两套路由（SEO 重复、维护翻倍）。
- 只用 `prefers-color-scheme`（用户无法手动覆盖）。
- 在 `:root` 上定义颜色（被更高特异性的主题规则覆盖）。

**迁移验证**：把模式套到一个 Web 应用的设计系统，检查是否能用“一个根属性 + 变量”完成主题切换；若需要重建组件树，则不适用。

---

## 模式选择速查

| 问题 | 模式 |
|---|---|
| 导航结构复杂、页面多 | P-001 |
| 布局需要用户可配置、组件可插拔 | P-002 |
| 需要明暗主题且不想双份构建 | P-003 |
