## 核心原则：共识优先，投票兜底

Jupyter Server 团队的决策遵循一个简单而有效的两级机制：

1. **寻求非正式共识**：首先通过讨论达成非正式的一致意见
2. **投票作为升级机制**：如果无法达成明确共识，活跃成员可以发起正式投票

投票不是日常决策手段，而是共识无法达成时的兜底方案。这体现了 Jupyter 社区"讨论先于投票"的治理文化。

## 共识阶段

在共识阶段，团队成员通过公开讨论（GitHub Issues、会议、Discourse 等渠道）交换意见，尝试达成一致。共识不意味着所有人完全同意，而是"没有无法解决的反对意见"。

共识阶段的特征：
- **开放性**：讨论在公开渠道进行，任何人可以参与
- **耐心**：给复杂议题充分的讨论时间
- **善意推定**：默认他人的意见出于善意
- **寻求共同点**：聚焦于大家能接受的方案，而非每个人最理想的方案

## 投票阶段

当共识无法达成时，进入投票阶段。投票流程遵循 Jupyter 全局治理文档中规定的标准流程，包括：

- **谁可以发起投票**：任何活跃团队成员
- **谁可以投票**：所有活跃团队成员
- **法定人数**：活跃成员计入法定人数
- **投票规则**：遵循 Jupyter 治理模型的规定

> 📖 详细的投票规则（包括多数比例、投票期限、排序复选制等）在 [Jupyter 全局治理文档](../../governance/concepts/09-decision-making.md)中定义，本 Team Compass 不重复这些规则，而是引用全局标准。

## 团队规模原则：无上限、高参与

Jupyter Server 团队**不设人数上限**。这遵循 Jupyter 新治理模型的设计理念：

> 新治理模型和决策指南旨在支持大型、高参与度的决策机构。因此，即使今天已有明确决策机构的子项目，也可能希望扩大该机构的规模以纳入更多贡献者。

这一原则的含义：
- **欢迎新成员**：不会因为"团队已经够大了"而拒绝合格的新成员
- **扩大参与**：鼓励更多贡献者参与决策，而非集中在少数核心成员手中
- **分布式权威**：决策权随团队规模扩大而分布，避免核心团队瓶颈

## "We sail together"在决策中的体现

决策机制与团队的"同舟共济"理念紧密相关：

- 决策成功是**团队的成功**，不是某个人的胜利
- 决策失误时，**团队共同承担**责任，而非归咎个人
- 鼓励所有成员（尤其是新成员）参与讨论和投票
- 尊重不同意见，但一旦做出决策，团队整体支持

## 与全局治理的衔接

Jupyter Server Team Compass 的决策机制嵌套在 Jupyter 三层治理模型中：

```
┌──────────────────────────────────────────────┐
│ Jupyter 全局治理 (jupyter/governance)         │
│ - EC（执行委员会）: 全维度治理                 │
│ - SSC（软件指导委员会）: 软件方向              │
│ - Foundation（基金会）: 法律/商标/财务        │
└──────────────────┬───────────────────────────┘
                   │ 遵循全局决策规则
                   ▼
┌──────────────────────────────────────────────┐
│ Jupyter Server Team Compass（本文档）          │
│ - 共识优先 → 投票兜底                         │
│ - 团队规模无上限                              │
│ - 日常运作自主管理                            │
└──────────────────────────────────────────────┘
```
