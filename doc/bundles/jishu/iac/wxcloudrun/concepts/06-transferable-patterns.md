# 可迁移模式：平台约束下的交付与成本治理

上一章把微信云托管的安全边界与迁移陷阱逐条摊开。本章换一层视角：把其中具有机制共性的事实抽成**可迁移模式**——换到别的平台、换到别的技术栈，模式本身仍然成立，只有其中的阈值需要替换。

每条模式都由五个要素组成：**触发条件**（用平台事实作为判定依据，标注 F 编号）、**步骤**（3～7 步有序动作）、**反模式**（失败做法与后果）、**检验标准**（可用是/否或数字门槛判定）、**跨域迁移示例**（用到微信云托管之外的场景，并说明为何可迁移）。

需要先说清方法论立场：**可迁移性恰恰依赖具体事实**。脱离 F 编号的「通用建议」不可判定、不可复用；把事实抽象成「机制属性」之后，才既保留判定依据，又能跨平台搬运。

## 模式一：「封板发布单 + 单点流量切换」式灰度发布

微信云托管的发布语义是串行的：部署发布采用发布单形式，流程包含新建版本、测试、灰度上线 3 个子流程（F-053），一个服务同一时间点只能存在 1 张发布单，如需发布其他版本需先取消发布或者结单（F-023）。把它抽成机制，可得三个属性：

| 属性 | 平台事实 | 机制含义 |
|---|---|---|
| **工作台唯一** | 同一时间点只能存在 1 张发布单（F-023） | 发布进度是串行的，不存在并行发布线；发布单一旦进入下一阶段就不可回退 |
| **状态不可回退** | 进入灰度上线步骤后测试阶段的测试配置失效且不可再回到上一步骤（F-059）；回退操作只能向前回退，即高版本回退到低版本，不可反向回退（F-062） | 「回退」是版本之间的向下移动，不是流程步骤的倒退 |
| **用户粘滞分配** | 流量路由规则为用户首次进入时按照流量比例随机进入某一个有流量的版本，非首次进入时该用户将一直进入到首次进入的版本中（F-058） | 灰度不是「随机分流」，而是首次分配后固定；老用户不会自动迁移到新版本 |

配套的比例语义是粒度化的：灰度上线时按 10% 粒度加减流量比例，只支持最多 2 个版本有流量，支持将灰度流量比例回调（F-057）；一个服务下最多 2 个版本有流量，其余版本可以存在但没有流量接入（F-024）。官方推荐节奏是「先 50%，然后隔 3-5 分钟结束灰度」，版本切换空窗期流量切换出现空白一般持续 1 分钟自动恢复（F-066）。

> **勘误 E-003**：版本下线后的缩容时长，`guide/service/online.html` 正文写作「下线半小时内缩容到 0」，同页举例写作「缓存 2 分钟后缩容为 0」。官方文档不同页面口径不一致，本处采信「**2 分钟缓存期 + 半小时缩容**」的并列描述——二者分别对应缓存与缩容两个阶段：旧版本发布成功后还会缓存 2 分钟，期间控制台会看到新旧版本同时都有实例，且部分请求还会走到旧版本（F-061）；线下版本会无视配置信息，在下线半小时内缩容到 0（F-060）。

### 触发条件

满足以下任一条即适用本模式：

- 服务的任何一次上线都要在有流量的状态下逐步放量，且无法接受「一次性全量」——此时需要「单点流量切换」机制（F-057：最多 2 个版本有流量，按 10% 粒度调整比例）。
- 已有生产流量在跑，需要在不停服的前提下替换版本——此时必须依赖「只向前回退」的语义做故障处置预案（F-062）。
- 服务需要区分「测试流量」与「生产流量」——此时测试配置的失效点（F-059）就是必须提前排期的分界点。

### 步骤

1. **清理发布单**：确认当前服务没有未结单的发布单；一个服务同一时间点只能存在 1 张发布单，如需发布其他版本需先取消发布或者结单（F-023）。
2. **固定候选版本**：确认有流量的版本不超过 2 个（F-024、F-057），把新版本作为唯一候选，其余版本保持无流量接入状态。
3. **预置测试配置**：先用 OpenID 白名单或 URL 参数完成测试验证；选择 URL 参数测试方式时至少配置 1 个 key 和 value 条件，value 支持 Glob 表达式（F-056）。此步必须在进入灰度之前完成——进入灰度上线步骤后测试阶段的测试配置失效且不可再回到上一步骤（F-059）。
4. **按粒度放量**：以 10% 为粒度把流量切到新版本，不要跳过前几个观察点（F-057）。
5. **按推荐节奏收口**：先切到 50%，然后隔 3-5 分钟结束灰度（F-066）；切换空窗期的流量空白一般持续 1 分钟自动恢复（F-066），不应把这段空窗误判为故障。
6. **观察覆盖缓存期**：观察窗口至少覆盖旧版本的 2 分钟缓存期再收流量与下线旧版本，期间仍会有部分请求走到旧版本（F-061、F-060）。
7. **预置向前回退路径**：回退时先把目标版本的实例数保持到版本创建时的最小副本数，再接入现网；回退只能向前回退，不可反向回退（F-062）。

### 反模式

- **把灰度当成可自由跳转的开关**：在灰度阶段试图回到测试配置或反向回退到更高版本 → 流程被锁死在当前阶段且不可逆，只能等发布单结单重来（F-059、F-062）。
- **跳过比例粒度直接全量**：一次性把 100% 流量切到新版本 → 爆炸半径等于全量（流水线推送触发只能全量发布现网，F-064；CLI 发布版本后直接 100% 接入现网，F-068），出事后的回退成本按 F-062 的「向前回退」规则被放大到不可接受。
- **按流量比例估算会话一致性**：以为「新老版本各 50%」意味着老用户会有一半迁移到新版本 → 用户粘滞（F-058）使老用户始终停留在首次进入的版本，新版本实际承载的是新进用户，行为差异排查方向会被带偏。
- **结束灰度过快**：切换完成即认定旧版本无流量 → 2 分钟缓存期内仍有部分请求走到旧版本（F-061），表现为「已经发布成功却还有老版本报错」。
- **并行推进多条发布线**：试图同时为两个功能各开一张发布单 → 一个服务同一时间点只能存在 1 张发布单（F-023），第二条发布线必须等待结单或取消。

### 检验标准

- 是否有流量版本数 ≤ 2？（是/否，F-024、F-057）
- 发布前是否确认过同一服务同时只有 1 张未结单发布单？（是/否，F-023）
- 灰度比例是否以 10% 为粒度推进，且最终落在「先 50%、隔 3-5 分钟结束」？（是/否，F-057、F-066）
- 观察窗口是否 ≥ 2 分钟以覆盖旧版本缓存期？（≥2 分钟，F-061）
- 故障预案是否写明「只能向前回退」并指定了目标版本的最小副本数保持方式？（是/否，F-062）
- 测试配置是否在进入灰度之前完成、且已确认此后不可返回上一步骤？（是/否，F-056、F-059）

### 跨域迁移示例

**传统 CI/CD 的金丝雀发布（如 Argo Rollouts、Spinnaker）**。把本模式的三个属性映射过去：平台侧的「10% 粒度」换成流水线的 weight 步长，「2 分钟缓存期」换成各自的连接排空/优雅下线时间，「最多 2 个版本有流量」换成策略允许的 canary+stable 双版本约束。之所以可迁移，是因为这三条属性刻画的是**发布机制本身**——串行工作台、状态单向推进、用户粘滞分配，与容器平台无关；任何支持多版本并存的发布系统都可以套用「一个发布单一条发布线、进入放量后不可回头、老用户粘滞」这三条纪律。

## 模式二：「能力边界清单化」交付模式

这条模式来自平台的**否定性事实**。微信云托管暂不支持的场景包括：仅支持 HTTP 协议通过域名调用服务、不支持 tcp/udp/mqtt 等协议、不支持通过公网 IP 访问服务、不支持部署 Docker Compose、不支持接入 WAF、不支持一个服务开启多个监听端口、不支持用来部署数据库/Redis 等有状态服务（F-163）。配合单端口与端口的硬约束（F-027：一个服务只能设置一个端口；F-025：监听端口必须为 1~61000 之间的整数且不能为 9100）、仅 HTTP 协议（F-070），以及迁移改造项（F-164、F-180），可以得到一套完整的迁移方法：**先列不支持清单 → 再逐项映射存量系统 → 再切分服务边界**。

### 触发条件

- 存量系统存在多端口暴露、TCP/UDP/MQTT 协议依赖、公网 IP 直访、Compose 编排、外部 WAF 依赖、或容器内自建有状态服务中的任意一项（F-163）。
- 存量系统把本地目录或容器内进程当作持久化存储（F-164、F-181）。
- 项目的数据库连接地址或端口配置在迁移后会失效（F-180）。
- 项目依赖在容器内运行守护进程（docker daemon）的运行时假设（F-182）。

### 步骤

1. **抄录边界基线**：以平台「不支持清单」为基线逐条落纸，共 7 条（仅支持 HTTP 协议通过域名调用服务、不支持 tcp/udp/mqtt 等协议、不支持通过公网 IP 访问服务、不支持部署 Docker Compose、不支持接入 WAF、不支持一个服务开启多个监听端口、不支持用来部署数据库/Redis 等有状态服务，F-163），另补协议、端口与状态三条延伸边界（F-070、F-025、F-027）。
2. **逐项映射存量系统**：对每条边界标注「命中 / 不命中」及命中位置——协议层、寻址层、编排层、状态层、防护层，每条命中都必须给出确定的处置结论，不允许留空。
3. **做出「拆分 / 改造 / 放弃」三选一决策**：多端口命中走拆分（F-180：项目若暴露多个端口需拆分成多个子服务）；编排命中走改造（不支持 Docker Compose，F-163、F-034）；不可迁移的部分直接放弃——CMS 管理系统属于云开发环境定制的项目，完全迁移难度巨大，文档建议放弃迁移，改用其他数据库基础在云托管支持范围中的内容管理系统（F-172）。
4. **切分服务边界并各自登记端口**：每个子服务在控制台登记唯一端口（端口号由业务项目自行设定，必须通过新建版本时在控制台填写来告知云托管，F-026），项目暴露的端口要和控制台配置的端口保持一致（F-180）；端口取值落在 1~61000 且避开 9100（F-025）。
5. **外置状态**：把数据库、存储迁移到对象存储和云数据库（F-181）；服务是计算型的，扩缩过程中数据无法持久化保存，多实例共享只能使用数据库、存储等媒介沟通（F-164）；Redis 暂未支持，可以在腾讯云或其他云厂商购买（F-164）。
6. **修正连接与依赖假设**：数据库连接地址必须是线上可访问的外网地址或内网地址，而不是 `localhost:3306`（F-180）；补全环境变量 `MYSQL_ADDRESS`、`MYSQL_PASSWORD`、`MYSQL_USERNAME`，否则会引发无法连接数据库并导致部署失败（F-189）。
7. **复核运行时与构建假设**：清除依赖 docker daemon 守护进程的运行时假设——k8s 底层使用 docker，而 podman 不需要守护进程，因此 podman 上能运行的程序迁移到云托管可能启动不起来（F-182）；构建方式改用流水线、上传代码包、上传镜像 3 种发布方式之一，不依赖 Compose（F-016、F-034、F-064）。

### 反模式

- **直接把生产 Dockerfile 推上去就完事** → 依赖 docker daemon 的程序在云托管上可能根本起不来（F-182），且问题只在该组件被触发时才暴露。
- **保留 `localhost:3306` 连接串** → 容器内 `localhost` 指向自身，数据库连接失败并导致部署失败（F-180、F-189）。
- **期望用 Compose 编排多容器** → 平台不支持部署 Docker Compose（F-163、F-034），多容器编排必须拆成多个服务，多端口应用同时受单端口限制（F-027、F-180）。
- **把容器内目录当持久化存储** → 服务是计算型的，扩缩过程中数据无法持久化保存（F-164），实例暂未支持挂载硬盘（F-181）。
- **沿用云开发的 CMS 做内容管理** → CMS 完全迁移难度巨大，官方建议放弃迁移（F-172），硬迁的代价远高于换一套。

### 检验标准

- 平台「不支持清单」的 7 条是否逐条给出「命中/不命中 + 处置动作」？（7/7，F-163）
- 每个子服务的监听端口是否为 1 个、是否落在 1~61000 且避开 9100、是否与控制台填写一致？（是/否，F-025、F-027、F-180）
- 数据库连接地址是否已从 `localhost:3306` 改为线上可访问地址？（是/否，F-180）
- 容器内是否仍存在「依赖 docker daemon」「挂载硬盘」「本地目录持久化」三类假设？（是/否，F-182、F-181、F-164）
- 环境变量 `MYSQL_ADDRESS` / `MYSQL_PASSWORD` / `MYSQL_USERNAME` 是否在每次部署前确认存在？（是/否，F-189）
- 是否明确记录了「放弃迁移」的部分及其替代方案？（是/否，F-172）

### 跨域迁移示例

**任何「单容器 + 单一编排格式」的托管平台准入评审**，例如 Serverless 容器平台的单服务单入口约束、内部平台的中间件白名单准入、以及把传统 VM 化应用改造为容器化交付的评审清单。之所以可迁移，是因为这条模式的主体是**一份「不支持清单」加一套逐项映射流程**，平台只提供清单内容，映射与切分方法由迁移方掌握；把清单从「云托管的 7 条」替换为「目标平台的 N 条」，步骤 1～7 的骨架完全不变。

## 模式三：「静默销毁风险」的成本与可用性治理模式

托管平台最容易被忽略的失败模式不是崩溃，而是**平台单方面发起的、用户不主动触发的事件**：闲置冻结与自动销毁（F-044）、欠费冻结与删除（F-045、F-153）、服务缩容到 0（F-151、F-065）、版本下线后缩容（F-060）、数据库自动暂停（F-150）、内网域名下线（F-165）。这些事件都有一个共同点：用户无法阻止、无法感知、且恢复能力由平台单方定义。

把它们从「平台特性」升级为「显式风险项」，需要三件事：**登记触发条件 → 绑定观测指标 → 绑定响应动作**。

### 触发条件

- 业务存在非请求驱动的运行单元：异步任务、定时任务、批处理，且实例最小副本数被设为 0（F-177、F-178）。
- 环境可能被闲置：长期无请求调用会触发冻结甚至自动销毁（F-044）。
- 账号余额可能不足：欠费会冻结乃至删除全部环境（F-045、F-153）。
- 存在版本级别的流量切换与下线操作，需要评估下线后的资源回收（F-060、F-061）。
- 服务使用平台开通的数据库并开启了自动暂停（F-150）。

### 步骤

1. **枚举平台隐式事件**：把会由平台单方发起的事件登记为清单条目，逐条写明触发条件与时间窗——环境 30 天内未产生任何请求调用即被冻结，冻结时间超过 180 天系统自动销毁并删除环境且不支持恢复（F-044）；账号欠费时所有环境都将被冻结，欠费超过 7 天所有环境都将被删除且无法恢复，环境删除后环境内所有资源将被释放、不可恢复（F-045）；欠费 12 小时内正常使用且继续扣费，欠费大于 12 小时小于 7 天所有环境停服但存储类继续扣费、数据保留，欠费大于 7 天资源销毁无法找回（F-153）。
2. **登记缩容与回收类事件**：服务下版本的实例最小副本数为 0 且当前服务连续半小时没有任何访问时会触发缩容到 0（F-151）；实例副本数最小值设为 0 时，服务在 30min 内无流量后台会将实例副本数缩容为 0（F-065）；版本下线后无视配置信息、在下线半小时内缩容到 0（F-060）；开启数据库的自动暂停后，连续 10 分钟内没有任何读写和运算操作数据库即进入暂停状态（F-150）。
3. **绑定观测指标**：按官方建议在「告警设置」中选择指标「调用次数」+「平均实例个数」，参考服务正常运行时的值扩大 2～5 倍设置告警（F-162）；同时在腾讯云侧设置余额告警能力（F-162）；资源到期通知在资源到期前 7 天开始推送，账号欠费通知的对象为小程序管理员（F-043）。
4. **绑定响应动作**：需要保活的服务把最小实例副本数设为大于 0（定时扩容的实例副本数不能设置小于最小实例副本数且不可设置为 0，F-031）；异步任务按「半小时内触发更新的实例直到任务执行完毕」设计保活节奏，过程中每 15 分钟发起请求防止容器缩容，服务规格需设置内存/CPU 条件大于 95% 以降低突刺导致扩容的概率（F-177、F-178）。
5. **收敛代码内的后台任务**：不在请求处理程序范围之外启动后台线程或例程，并确保在传送响应之前完成所有异步操作——用户无法控制实例服务的重启、新增、销毁，这些权限都由云托管集群自己控制（F-179）。
6. **按「重建 + 备份」而非「等待恢复」编写恢复预案**：环境销毁与欠费删除均不可恢复（F-044、F-045、F-153），所以恢复路径是重建环境 + 从备份恢复数据，而不是等待平台恢复。
7. **用结算日作为复盘时间界**：费用当前为按天结算，异常用量要到第二天早晨结算时才会产生高额费用并可能触发欠费通知（F-160），因此成本异常复盘必须跨到结算日之后。

### 反模式

- **依赖「平台会保活」** → 最小实例为 0 时，半小时内没有访问请求，长达 2 小时的异步任务会直接缩容到 0 而中途被杀（F-177、F-151、F-065）。
- **把长任务写在请求处理器之外的后台线程里** → 实例被销毁时任务静默中断，且用户无法控制实例的重启、新增、销毁（F-179）。
- **只配容器告警、不配余额告警** → 欠费停服发生在欠费 12 小时之后，停服期间数据库存储、对象存储容量、静态资源存储容量继续扣费（F-153、F-162）。
- **指望环境「休眠保活」** → 30 天无请求即冻结、冻结超 180 天自动销毁且不支持恢复，环境里的资源一并释放且不可恢复（F-044、F-045）。
- **看到当日用量正常就认为成本安全** → 按天结算让异常当日不可见，代价在次日结算才显现（F-160）。
- **以为缩容等于「闲置不花钱」就忽略可用性** → 缩容到 0 确实不产生容器相关用量和费用（F-151），但同时意味着下次请求要承担冷启动，且异步任务会被中断（F-177）。

### 检验标准

- 是否有一份显式登记的「平台隐式事件清单」，且每项含触发条件、时间窗、观测指标、响应动作四要素？（是/否，F-044、F-045、F-151、F-153）
- 需要非请求驱动的服务，其最小实例副本数是否 > 0？（>0，F-177、F-031）
- 是否同时配置了「调用次数 + 平均实例个数」告警（阈值按正常值 2～5 倍）与腾讯云侧余额告警？（是/否，F-162）
- 是否确认过资源到期前 7 天通知的推送与欠费通知的接收人（小程序管理员）？（是/否，F-043）
- 恢复预案是否按「重建 + 数据备份」而非「等待平台恢复」编写？（是/否，F-044、F-045、F-153）
- 是否存在「在请求处理程序范围之外启动的后台线程或例程」？（是/否，F-179）

### 跨域迁移示例

**任何支持缩容到 0 的无服务器平台的成本治理**，例如函数计算平台的空闲回收、云原生 Serverless 服务的 min-instances=0 策略、边缘函数平台的实例回收；也适用于传统 CI/CD 中预览环境/临时环境的回收策略与通用云成本治理。之所以可迁移，是因为模式的核心动作是**把「平台隐式回收/停服」从特性说明转成风险登记项**，这一动作不依赖任何具体平台；换平台时只需替换触发条件与阈值（把「30 天无请求」换成目标平台的空闲回收阈值），四要素结构保持不变。

## 洞察

### 洞察 A：模式不是事实的复述，而是事实的「可迁移抽象层」

- **陈述**：三条模式都从编号事实出发，但抽取的是**机制属性**而不是平台参数——模式的可搬运对象是步骤与检验标准，平台事实只作为触发判据。
- **证据**：模式一由 F-023、F-057、F-058、F-059、F-062、F-066 抽象出「工作台唯一 / 状态不可回退 / 用户粘滞分配」；模式二由 F-163、F-025、F-027、F-070、F-164、F-180 抽象出「列边界 → 映射存量 → 切服务」；模式三由 F-044、F-045、F-150、F-151、F-153、F-165、F-177 抽象出「登记 → 观测 → 响应」。
- **反常识**：直觉上「可迁移方法论」应当抽象到没有具体数字为止，但那样就失去了判定依据——「灰度比例 10%」「3～5 分钟」「2～5 倍」这些阈值恰恰是模式可执行的原因；抽象掉阈值，模式会退化成无法检验的常识。
- **行动**：迁移到新平台时只替换阈值与动作名，保留 F 编号作为「这条判据从哪来」的溯源锚点；同时保留检验标准里的数字门槛，避免新平台上的执行退化为凭感觉。

### 洞察 B：否定性事实比肯定性事实更值得沉淀

- **陈述**：平台文档中的「不支持什么」比「支持什么」更稳定、也更容易被忽略，恰恰是模式抽象最可靠的原料。
- **证据**：F-163（7 条不支持项）、F-034（不支持 Docker Compose）、F-164 与 F-181（无持久化、不支持挂载硬盘、Redis 暂未支持）、F-182（podman 与 docker daemon 差异）、F-179（不要在请求处理器外启动后台线程）。
- **反常识**：肯定性表述（支持什么协议、支持哪些指标）会随平台迭代被覆盖更新，而否定性边界一旦被写进架构，往往成为长期约束；只读「功能特性」章节的迁移者，会在改造期才第一次撞上这些边界。
- **行动**：把否定性事实整理成一份独立的「能力边界清单」基线，并在每次架构评审中逐条过一遍——清单条目只增不减，新增项必须给出处置结论。

### 洞察 C：三条模式覆盖了交付生命周期的三个断面

- **陈述**：模式一管「版本怎么放出去」，模式二管「放出去的东西是什么形态」，模式三管「放出去之后它会不会被平台收走」——三者分别对应发布期、改造期、运行期。
- **证据**：模式一的时间锚点是发布单与灰度（F-053、F-062、F-066）；模式二的时间锚点是迁移改造（F-180、F-189、F-182）；模式三的时间锚点是运行期的隐式事件（F-044、F-153、F-177）。
- **反常识**：直觉上「安全与成本」属于上线后的运维话题，与发布流程无关，但云托管的发布单不可逆语义（F-059、F-062）恰恰决定了故障时能不能退——发布机制本身就是可用性机制；同样，成本治理的失败点也不在账单，而在缩容与欠费这两个平台代劳的动作上。
- **行动**：把三条模式编成同一份交付检查单：发布前过模式二，发布中过模式一，上线后过模式三；三者共享同一份 F 编号引用体系，不重复维护。
