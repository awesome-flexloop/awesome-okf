# 从传统服务迁移到云托管并核对成本

迁移到云托管真正的成本不在「把服务跑起来」，而在两处：**不可迁移项的处置**（平台明确不支持的能力）与**账单口径的换算**（按规格计费而非按使用率）。本文档先走完迁移侧的检查与改造，再按刊例价把成本算一遍。

## 目标与前置条件

**目标**：完成一次可验收的迁移判定——对官方不支持项逐条给出处置结论、对状态型依赖完成外置改造，并按刊例价口径给出首月的成本量级。

**前置条件**：

| 前置条件 | 说明 | 依据 |
|---|---|---|
| 账号已开通 | 必须先有微信小程序/公众号才可以开通微信云托管 | F-010 |
| 依赖 Docker 运行时 | 云托管的 k8s 底层使用的是 docker，需要在提供的镜像启动时运行一个守护进程（docker daemon） | F-182 |
| 端口模型可拆分 | 不支持一个服务开启多个监听端口 | F-163 |
| 状态可外置 | 不支持用来部署数据库/Redis 等有状态服务 | F-163 |

## 步骤

### 步骤 1：先过「不支持清单」这一关

**操作**：逐条比对现有架构，任何一条命中且无处置方案，就不应进入迁移排期。

| # | 不支持项 | 官方表述 | 迁移处置方向 |
|---|---|---|---|
| 1 | 调用协议 | 仅支持 HTTP 协议通过域名调用服务 | 非 HTTP 调用形态需先改造 |
| 2 | 传输协议 | 不支持 tcp/udp/mqtt 等协议 | TCP 长连接、MQTT、UDP 类服务需改造或留在原平台 |
| 3 | 公网 IP | 不支持通过公网 IP 访问服务 | 统一改为域名调用；自定义域名需已备案（F-006） |
| 4 | 编排格式 | 不支持部署 Docker Compose | 多容器编排拆成多个服务（F-034） |
| 5 | 防护层 | 不支持接入 WAF | 自建防护能力落在业务侧 |
| 6 | 端口 | 不支持一个服务开启多个监听端口 | 多端口应用拆分服务（F-027、F-180） |
| 7 | 有状态服务 | 不支持用来部署数据库/Redis 等有状态服务 | 状态外置到数据库与存储（F-164） |

**关键配置**：以上七类表述来自官方「暂不支持的场景」清单（F-163），逐条与该清单的 7 项一一对应。

**依据**：F-163、F-034、F-027、F-180、F-006、F-164

### 步骤 2：执行官方迁移检查清单

**操作**：对下面三项逐条核对，这是官方给出的迁移检查清单原文。

**关键配置**：迁移检查清单包含——微信云托管目前不支持同一个服务多个端口，项目若暴露多个端口需拆分成多个子服务；迁移时须确认项目中数据库连接地址是线上可访问的外网地址或内网地址而不是 `localhost:3306`；项目暴露的端口要和控制台配置的端口保持一致（F-180）。

**依据**：F-180

### 步骤 3：补全数据库环境变量

**操作**：手动新建服务并部署时，在「服务设置」中补全 `MYSQL_ADDRESS`、`MYSQL_PASSWORD`、`MYSQL_USERNAME`；若此前用过控制台模板部署，二次部署前先确认这三个变量是否已被清空。

**关键配置**：不补全会引发无法连接数据库并导致部署失败；控制台部署模板成功后这三个环境变量会消失，二次部署前需先补全（F-189）。这三个变量仅在模板部署自动开通数据库时产生（F-089）。

**依据**：F-189、F-089

### 步骤 4：把状态从容器里搬出去

**操作**：容器内不保留任何需要跨实例共享的数据；本地目录不作为存储方案。

**关键配置**：微信云托管服务是计算型的，扩缩过程中数据无法持久化保存；微信云托管服务挂载硬盘目前还不支持，多实例共享暂时只能使用数据库、存储等媒介沟通；Redis 暂未支持，可以在腾讯云或其他云厂商购买（F-164）。微信云托管服务实例暂未支持挂载硬盘，需要在容器化改造时将数据库、存储等迁移到对象存储和云数据库中（F-181）。

**依据**：F-164、F-181

### 步骤 5：云函数代码的四处改造

**操作**：按下表逐处改造云函数代码，再决定数据库形态。

| 迁移对象 | 现状与改法 | 依据 |
|---|---|---|
| `wx-server-sdk` | 迁移到云托管后基本失效 | F-170 |
| 获取用户身份 | 云函数通过 `cloud.getWXContext()` 获取 openid 等信息，在云托管中直接从请求的 `req.headers` 中读取 | F-170 |
| `wx.cloud.CloudID` | 在云托管中不做自动解析，需自行通过 API 完成信息置换 | F-170 |
| 云开发数据库 | 属于 mongo 协议的 flexdb 数据库，云托管没有与其对应的数据库类型 | F-171 |
| CMS 管理系统 | 是云开发环境定制的项目，完全迁移难度巨大，文档建议放弃迁移，改用其他数据库基础在云托管支持范围中的内容管理系统 | F-172 |
| 数据库连接数 | 云函数的一次执行对应一次请求，云开发业务无需考虑连接数问题，放在云托管中就需要考虑 | F-173 |

**关键配置**：flexdb 的三条出路分别是——保留云开发数据库形态并使用 `cloudbase-node-sdk` 操作、迁移到云托管 mysql 数据库、或在腾讯云购买 mongo 数据库（F-171）。

**依据**：F-170、F-171、F-172、F-173

### 步骤 6：Django migration 的两步法与触发方式取舍

**操作**：migration 同步分两步执行，再决定在什么时机触发。

**关键配置**：Django migration 同步分两步——`python manage.py makemigrations` 生成 migrations 文件对比新旧 Model 找出差异，`python manage.py migrate` 根据 migrations 执行 SQL 并依据 django_migrations 表只执行没有执行过的步骤（F-174）。

| 触发方式 | 机制 | 取舍 | 依据 |
|---|---|---|---|
| Dockerfile `RUN` 中执行 | 构建期执行 | 构建环境不在数据库 VPC 内网中，只能使用外网地址；文档不建议这种用法，migration 操作非常多时会增加构建耗时 | F-175 |
| Dockerfile `CMD` 或 `ENTRYPOINT` 中集成 | 容器启动时执行 | 多个实例同时创建出来需要注意竞争处理 | F-176 |
| 通过 webshell 进入实例执行 | 人工介入 | webshell 进入的实例都处于同一数据库 VPC 内网环境 | F-176 |

**依据**：F-174、F-175、F-176

### 步骤 7：容器化改造的运行时陷阱

**操作**：核查镜像启动脚本是否依赖 docker daemon；本地用 podman 验证通过不等于云托管可跑。

**关键配置**：微信云托管的 k8s 底层使用的是 docker，需要在提供的镜像启动时运行一个守护进程（docker daemon），而 podman 不需要，因此 podman 上能运行的程序迁移到云托管可能启动不起来（F-182）。

**依据**：F-182

### 步骤 8：优化构建耗时

**操作**：调整 Dockerfile 的分层顺序；需要时指定加速源。

**关键配置**：Docker 构建缓存对 ADD 和 COPY 指令会检查镜像中文件内容并为每个文件计算校验标识，校验标识通常不考虑文件的最后修改时间和最后访问时间；缓存无效后所有后续命令都会重新构建（F-183）。先 `COPY ./package*.json` 再执行 `npm install` 最后 `COPY . .` 的写法，在不变更 package*.json 时打包时间基本都在 1 秒左右（F-184）。线上构建的 Docker 镜像源已经是腾讯加速源，所以不需要自己设置 registry-mirrors；Dockerfile 内可自行指定 alpine（mirrors.tencent.com）、NPM（mirrors.tencent.com/npm/）、Python（mirrors.cloud.tencent.com/pypi/simple）加速源（F-185）。另需注意构建阶段无报错日志、空白，大概率是构建超时（> 10 分钟）（F-034）。

**依据**：F-183、F-184、F-185、F-034

### 步骤 9：确认计费依据与用量口径

**操作**：先认清「按什么计费」，再谈优化。

| 维度 | 事实 | 依据 |
|---|---|---|
| 计费依据 | 容器规格是计费依据，无论容器实际使用率多少都按所声明的容器规格计费；弹性伸缩只产生容器实例数量的变化，单个容器的规格不会改变 | F-015 |
| 结算精度 | 微信云托管按实际使用量计费，精确到 100 毫秒 | F-017 |
| 资源量算法 | 实例消耗的资源量为规格乘以运行时间（精确到秒） | F-148 |
| 免费边界 | 只创建服务没有创建版本不会产生费用；服务下版本的实例最小副本数为 0 且当前服务连续半小时没有任何访问时会触发缩容到 0，不产生任何容器相关用量和费用 | F-151 |
| 数据库常驻成本 | 开通数据库之后就会创建出 3 个系统数据库用于创建系统表，预计占用数据库 28M 内存，每天都会产生微量的数据库存储费用；如无需使用数据库请及时销毁 | F-152 |
| 抵扣顺序 | 先抵扣免费资源，再进行资源包的用量抵扣，抵扣完成后再计算按量计费费用 | F-145 |
| 资源包归属 | 资源包为环境级别购买，不支持转移到其他环境；到期后不可再用于抵扣按量计费的用量 | F-146 |

**关键配置**：按量计费结算时的抵扣顺序为「先抵扣免费资源，再进行资源包的用量抵扣，抵扣完成后再计算按量计费费用」；当有多个资源包时可叠加使用，一个资源包中某个指标用量耗尽后其他指标仍可继续抵扣（F-145）。资源包均为一次性购买，不可续费，可反复购买；为环境级别购买，不支持转移到其他环境（F-146）。

> **口径澄清（计费依据 vs 计量粒度）**：上表「计费依据」（F-015）与「结算精度」（F-017）**不是同一层面的两套规则**，并列出现容易被误读为「按使用率计费」：
> - **F-015 说的是单价基准**——单价由**声明的容器规格**决定，实际使用率高低不改变单价；弹性伸缩只改变实例数量，不改变单个实例的规格。
> - **F-017 说的是用量计量粒度**——用量按实际运行时间计量，精度到 100 毫秒；单位时间的用量 = 规格 × 运行时间（F-148）。
>
> 合起来的口径是「**按声明规格的单价 × 按实际运行时长的用量**」：想降费只有两条路——降规格（降单价）或缩容/缩短运行时间（降用量），压低 CPU 使用率本身不产生降费效果。

> **勘误说明（E-009）**：官方文档资源包抵扣示例章节的正文与同页举例算术不一致——正文称「CPU 12 核*小时由 B 抵扣后剩余 702 核*小时」，而同页举例写出的算式是 `720 − 12 = 708`（源文档未说明该 720 对应哪一个资源包额度）。本处采信源文档正文原值 **702 核*小时**，并标注**源文档算术存疑**，不以推算值 708 替代原文；引用该场景剩余量时按原值表述并保留此标注。

**依据**：F-015、F-017、F-148、F-151、F-152、F-145、F-146

## 成本估算示例（按刊例价估算）

以下估算**按刊例价进行**，不考虑折扣、特惠活动、资源包、优惠券等——官方文档称这类费用预估可理解为理论上的最高价（F-156）。

**场景**：工具类小程序，每日 8:00～24:00 维持 1 个 0.25 核 0.5GB 实例。这是官方计费示例中的口径（F-154）。

| 步骤 | 计算 | 结果 |
|---|---|---|
| 容器 CPU | 120（核*小时）× 0.055 元/（核*小时） | 6.6 元 |
| 容器内存 | 240（GB*小时）× 0.032 元/（GB*小时） | 7.68 元 |
| 月度合计 | 6.6 + 7.68 | **14.28 元/月** |

该场景的每月 CPU 120（核*小时）、内存 240（GB*小时）与月度费用总计 14.28 元，与官方计费示例一致（F-154）。

**三个换算要点**：

- **规格不同，账单相同**：1 核 2GB 实例运行 1 小时与两个 0.5 核 1GB 实例运行 1 小时消耗的资源量完全相同（F-148）。因此「用小实例多开几份」并不省 CPU 与内存费用，只改变并发能力与扩缩容粒度。
- **拆到最小档也一样**：0.25 核 0.5GB 实例运行 4 小时消耗 CPU 1（核*小时）、内存 2（GB*小时）（F-148）。最小规格是 F-013 规定的 0.25 核 0.5G。
- **数据库是另一笔账**：开通数据库后即创建 3 个系统数据库，预计占用数据库 28M 内存，每天都会产生微量的数据库存储费用；如无需使用数据库请及时销毁（F-152）。开启数据库的自动暂停后，连续 10 分钟内没有任何读写和运算操作数据库即进入暂停状态，暂停状态不会产生数据库算力资源用量，但还会有数据库存储用量（F-150）。

**其它官方计费示例**（同一刊例价口径）：活动类小程序每月费用总计 28.3545 元；社区论坛类小程序每日费用总计 4.7264 元、每月费用总计 141.792 元（F-155）。

## 已知边界

- **七个不支持项无法用配置绕过**：这是迁移评审的一票否决项来源（F-163）。
- **容器不是存储**：扩缩过程中数据无法持久化，挂载硬盘不支持，Redis 暂未支持（F-164、F-181）。
- **podman 通过 ≠ 云托管可跑**：依赖 docker daemon 的程序在 podman 上能运行，在云托管可能启动不起来（F-182）。
- **构建期执行 migration 不在 VPC 内网**：只能用外网地址，且会拖长构建（F-175）。
- **计费按规格而非使用率**：压低使用率不会降费，只有降规格或缩容才会（F-015、F-151）。
- **开通数据库即刻产生成本**：28M 系统表占用与每日微量存储费用从开通当天起算（F-152）。
- **资源包不能跨环境转移**：为环境级别购买，跨环境使用无效（F-146）。
