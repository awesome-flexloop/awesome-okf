# 核心公式：Agent = LLM + 上下文 + 工具

> 博文用整节"一个公式，贯穿全书"介绍本公式（F-010/F-011）。经对原书第一章核验，博文转述准确但做了简化，本文补足原书的两条精确边界与 Harness 主张（F-034/F-038）。

## 一、公式的精确表述

原书第一章原文（F-010 核验）：

> 现代 Agent 的最小工程实现：**Agent = LLM（大语言模型，Large Language Model）+ 上下文 + 工具**。

博文称"不是比喻，是架构定义"（F-010），原书对该"等号"有两条博文未展开的限定（F-038）：

1. **加号是工程组件的组合**，不是强化学习中的形式化定义；
2. **公式只描述 Agent 边界之内的实现，不包含 Agent 与之交互的 Environment（环境）**——在经典 RL/控制论视角下，环境向 Agent 返回观察、Agent 的行动改变环境状态，二者闭环交互但互不为组成部分。

| 直觉理解 | 实现组件 | 学术概念 | 含义 |
|---------|---------|---------|------|
| 大脑 | LLM | 策略（Policy） | 面对当前信息，从可选行动中挑出最合适的一个：理解意图、思考规划、做出判断 |
| 眼睛 | 上下文构造 | 观察与历史 | 将环境返回的观察与已有历史组织成当前决策所需的信息表示 |
| 手脚 | 工具与适配器 | 观察/行动接口 | 规定 Agent 可以读取哪些观察、发出哪些行动，以及接口格式 |

博文的通俗版（F-011）与原书一致：LLM 决策、规划、判断；上下文是"当前任务里能看到的全部信息"；工具执行代码、调 API、操控浏览器、调用子 Agent。

原书给出一个关键推论：**在底层模型固定时，提升 Agent 表现最主要的系统工程手段，是重新定义或扩展观察空间与动作空间**——许多看似需要"更聪明模型"的问题，其实只是接口问题（把所需数据纳入上下文、把所需操作封装成工具）。

## 二、Model–Harness 结构：书的真正主张

博文结尾"底层的逻辑变化没那么快"（F-023，作者对书主旨的转述）对应的是原书第一章的 **Harness 工程**主张（F-038）：

- **Model**：负责策略决策；
- **Harness**：Agent 边界内环绕模型的运行与治理层——构造上下文、暴露工具接口、维护循环和状态、实施权限/验证/纠正。工程公式中 LLM 对应 Model，"上下文 + 工具"构成最小 Harness，生产系统再加入约束、验证和纠正。
- Harness 原指马具：模型是强大但不可预测的马，Harness 把力量引导成可靠的任务执行，而非限制其奔跑。
- 书的立场（借 Rich Sutton《苦涩的教训》立论）：方向上认同模型会持续"吃掉"Harness（工具调用、长程规划都曾靠外部编排，如今已是原生能力）；节奏上这个过程远比想象中慢——**"模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿"**。这是对"框架是否会被模型吃掉"争论的工程时间尺度回答。

## 三、工具分类：博文三类 vs 2.0 五类

博文按 1.4 版第 4 章写"感知/执行/协作三类工具"（F-014），与博文时点的官方口径一致（F-035）。2.0 版第一章已把广义工具体系扩为**五类**：

| 类别 | 作用方向 | 代表场景 |
|------|---------|---------|
| 感知工具 | 环境 → Agent | 搜索引擎、文件读取、API/数据库/企业数据 |
| 执行工具 | Agent → 环境 | 代码执行、文件操作、系统命令、外部 API |
| 协作工具 | Agent ↔ Agent/人 | 委托子 Agent、关键决策点请求人类确认、多 Agent 协调 |
| 事件触发工具（2.0 新增） | 环境 → Agent（非主动调用） | 新邮件、定时时间点、Webhook 回调驱动任务启动 |
| 用户沟通工具（2.0 新增） | Agent → 用户 | 文字消息、语音通话、邮件等主动关怀与进展传递 |

工具调用（Tool Calling/Function Calling）四步循环：声明工具 → 模型决定调用（名称/参数）→ 结果追加到上下文 → 模型据此决定下一步；这是 ReAct 的基础。书同时给出工具设计原则：**通用基础能力用于组合与探索（隔离沙箱、权限/资源上限）；专用工具用于约束高风险和强业务规则操作（支付、删除、发邮件、部署——参数明确、权限受限、全程可审计、必要时预览+人工确认）**。

## 四、现代 Agent 产品三维对比表（原书完整版）

博文称"第 1 章里的一张对比表，值得反复看"并转述了 5 行（F-019）。核验确认原书 2.0 第一章确有此表，博文为压缩转述，下表按原书完整版呈现（F-034）：

| Agent 产品 | 眼睛（感知） | 手脚（行动） | 策略 |
|-----------|-------------|-------------|------|
| **Cursor 等 Coding Agent** | 需求、读取到的代码片段、目录列表、终端输出 | 开放式：代码搜索、文件读写、执行命令等 | 增量开发：理解需求→搜索相关代码→编辑代码→测试验证→调试修复 |
| **Deep Research 等搜索 Agent** | 搜索结果、网页内容、论文摘要与引用 | 开放式：搜索查询、网页读取、生成报告等 | 迭代深化：根据已有信息调整搜索方向，逐步综合出完整报告 |
| **Browser Use 等电脑操控 Agent** | 屏幕截图、DOM 或无障碍树、操作结果 | 开放式：点击、输入、滚动、截图、执行代码等 | 视觉感知+操作：观察屏幕→识别目标元素→执行操作→验证结果 |
| **豆包等手机助手 Agent** | 手机截图、App 界面状态、系统反馈 | 开放式：点击、滑动、输入、打开 App 等 | 意图理解+App 操控：理解需求→定位目标 App→执行操作→确认完成 |
| **Pine AI 等个人办事 Agent** | 经授权读取的账户记录、账单结果、服务商资料 | 开放式：打电话、发邮件、填表单、与用户确认 | 多步骤任务执行：收集信息→制定协商策略→联系服务商→谈判→汇报结果 |

（博文压缩版把感知/行动列简化为"需求文档、代码库、终端环境"/"文件读写、执行命令"等，语义一致但粒度更粗。）

原书总结这些系统的三个共同特征：**开放式的动作空间**（不是从有限按钮中选择，而能生成任意自然语言和代码）、**内部思考**（行动前先规划推演）、**持续交互**（根据环境反馈调整策略）。
