# 插件生态

> Fact index：本篇声明对应 [信源与事实登记](../references/article-source.md) 的 F-033~F-042、F-052~F-056、F-063、F-064、F-066~F-068。

内核被限制得越窄，插件层承担得越多。本页把官方四类插件清单（F-052）摊开，并重点讲清两个最容易被二手文章带偏的地方：**支持范围分三档**、**用量与合规提示博文完全没提**。

## 一、四类插件总览（官方清单 F-052）

| 类别 | 官方列出的实现 | 博文对应 | 在五步流程中的位置 |
|------|---------------|---------|-------------------|
| 事件 | GitHub Webhook、GitLab Webhook、HTTP、定时、Issue 轮询 | F-033 | 第 1 步：把外部发生的事变成统一格式事件 |
| Agent | Claude Code、Codex、ACP、DeepSeek Harness、通用 `command` | F-034、F-035 | 第 3 步：接活、干活、在最后一条回复里交代结果 |
| 通道 | 桌面通知（默认开启）、飞书、钉钉·企微·Slack·Discord 模板 | F-036 | 第 4 步：需拍板时推卡片、收点选 |
| 交付 | `delivery` | F-037 | 第 4 步自动闭环分支：审代码、等 CI、合并、等发布、线上确认 |

官方措辞是插件**主动连进内核**，账号凭据留在各自插件里（F-058）；第三方插件通过 `agent-autoloop add <git 地址>` 安装（F-053）。

---

## 二、事件插件：把「发生了一件事」翻译成统一格式

博文列出的三类入口：GitHub Issue/PR、定时任务，以及面向**无法主动推消息的系统**的轮询脚本——后者无新内容就直接退出，不叫醒大模型、不花 Token（F-033）。自有消息格式可以写一个小插件翻译成标准事件。

官方清单补上 Webhook 与 HTTP 两类（F-052），并给出运维预演命令 `agent-autoloop emit <类型> --dry-run`：预演这条事件会派给谁，**不连接中台、不写日志**（F-048）。这条命令很适合在接真实 Webhook 之前用。

> ⚠️ 但「内置」不等于「连过真实服务」：官方明确四种 Webhook 模板**只在本地模拟服务验证过**，GitLab Webhook 按官方文档格式测试、**没连过真实 GitLab**（F-055）。分级见本页第五节。

---

## 三、Agent 插件：一个约定 + 一段回执

中台对 Agent 只有一个约定：**在最后一条回复里交代结果**（F-020、F-034）。需要提问、通知、结卡片、约复查或触发新事件时，在回复末尾附一个 `agent-autoloop` 代码块。不用装 SDK，也不用改 Agent 源码——这正是 [01 内核与五步流程](01-kernel-and-loop.md) 里「不写死产品名」禁令兑现后的效果。

博文给出的 `ask` 回执示例（F-034）：

````text
```agent-autoloop
{
  "ask": [{
    "title": "怎么发货？",
    "text": "两种方式今天都能发出。",
    "options": ["快递", "自提"],
    "key": "shipping"
  }]
}
```
````

官方 README 把回执协议细化为五类（F-051）：

| 回执 | 作用 |
|------|------|
| `ask` | 发卡片请人拍板 |
| `notice` | 通告；只告知的通告标 `fyi`，不带按钮 |
| `resolve` | 结卡片 |
| `later` | 约定稍后复查 |
| `events` | 触发新事件 |

两条容易忽略的容错设计（F-051）：JSON 写错时**只让在原会话重写最后一段回复，不重做已完成的业务**；`"resume": true` 表示接续上一轮会话。可照做的写法见 [规则与回执实战](../examples/02-rules-and-receipts.md)。

第三方 Agent 用 `use: "command"` 传命令数组接入，`{prompt}` 作为**独立参数**传递、不当作 shell 代码执行（F-053）——这是指令数据分离在插件接口层的延伸。

## 四、通道与交付插件

**通道**（F-036）：桌面通知默认开启（Mac 与 Linux）；飞书卡片为作者自用，可发卡片、点按钮、卡片改状态；钉钉、企业微信、Slack、Discord 也可接。官方把后几者标为「模板」（F-052）。飞书是官方唯一明确写「跑通发送、按钮回调、卡片更新」的通道（F-055）。

**交付流水线**（F-037）：由「定时查看 GitHub 标签的小脚本 + 专门负责上线的 Agent」组成。给 PR 打 `deliver` 标签后，跟完审代码 → 等检查通过 → 合并 → 等发布完成 → 线上确认新版本。官方补充了两条硬约束（F-056）：**审查与交付配置只从 `main` 读取**，**绝不在接单电脑上检出或运行 PR 里的代码**；排队、并发与重试复用内核。

- 博文提到「只想审不上线再打 `deliver-review` 标签」（F-037），但**官方 README 只列出 `deliver`**，未列 `deliver-review`（F-068）→ 仅博文单源，动手前以仓库配置手册为准。
- 官方场景模板中另有「PR 自动交付」与「交付 PR」两套模板（F-063）。

## 五、支持范围三档（本包最重要的分级）

博文「装好就能直接用的有 Claude Code、Codex、支持 ACP 的 Agent」容易让人读成「插件表里这些都验证过了」（F-035）。按官方 F-054、F-055、F-067 应分三档：

| 档位 | 内容 | 依据 |
|------|------|------|
| **A. 实测跑通** | Claude Code、Codex、ACP（官方 Codex ACP 适配器）跑通多轮问答与**跨进程会话续接**；飞书跑通发送、按钮回调、卡片更新 | F-055 |
| **B. 内置但只在本地模拟验证** | 四种 Webhook 模板只在本地模拟服务验证；GitLab Webhook 未连真实 GitLab | F-055 |
| **C. 仅提供接入命令，未逐个验证** | DSH（`dsh --profile headless {prompt}`）、pi（`pi --print {prompt}`）、OpenClaw、Hermes、Cursor、WorkBuddy / CodeBuddy——官方原话「**我们还没有逐个跑过**」 | F-054 |

再加一层：官方注明**场景模板样例数据均为虚构，脚本与回执只用本地 HTTP 与假飞书 CLI 验证，未在真实账号跑过完整业务**（F-067）。所以「七套场景模板 + 三套扩展模板」（F-063）应理解为**可照着改的配方**，不是「已在生产验证的方案」。

## 七、用量与合规：动手前必须知道

官方 README 专设「用量与合规说明」（F-064），**博文完全未提**：

- 中台调用的是**本机已安装并登录的 CLI**，**不读取或转存账号凭据**；
- 模型调用消耗算在**用户自己账号**，额度与使用范围遵循各厂商服务条款；
- **高频自动化场景下，厂商通常更建议使用 API Key**——官方原话是个人订阅额度主要为**日常人工交互**设计；
- **对外提供服务请使用 API Key**；
- 项目是**独立开源项目，与相关厂商无隶属或背书关系**。

> ⚠️ 这一条对「定时巡检 / 每晚批量跑」的用法有直接影响。可以理解为：本教程教你把流程接起来，但「用订阅账号跑高频自动化是否符合条款」是账号侧问题，需自行按厂商条款判断，不能从「项目开源可用」推出「额度用法合规」。

另外两条安全口径（F-066）：安装器与中台启动时把数据目录设为 `0700`；`agent-autoloop uninstall` 默认保留规则、密钥与记录，卸载不等于清除数据。

## 八、公司虚实中台案例（作者自述，单源）

博文列举的案例（F-041、F-042）：作者称国庆节给公司搓了一个工作台，与公司飞书数据和权限打通，各岗位同事在近半个月自行搓应用；同事对中台的意见通过飞书私聊机器人触发 Claude 评估、修改、上线并回复。数字口径为「同事已提八十多条意见、Claude 自主修改将近 70 条、作者拍板十几条；可自动处理的需求 1 小时内改完并收到反馈后上线」。

> ⚠️ 以上为**作者自述、官方仓库无对应记载、无独立佐证**（F-042）。本包按案例叙事收录，不作为成效结论，也不据此推断系统能力上限。详见 [P0 核验报告](../references/verification.md)「成效数字溯源表」。
