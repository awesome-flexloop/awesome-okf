## 逐项核验

### 1. 项目开源与命名 — ✅ 通过

- 博文给出仓库 `github.com/KKKKhazix/agent-autoloop` 与项目名 Agent-Autoloop（F-003），官方 README 同名（F-043），MIT 许可证（F-065）。
- 博文自述「周一未开源、收到反馈后花两天重写」（F-004/F-005）为作者叙事，官方仓库无对应记载，标为作者自述单源。

### 2. 内核 + 插件架构与四个方向 — ✅ 通过

- 博文：中台内核 Autoloop + 外围插件，四方向为事件 / Agent / 通知通道 / 代码交付流水线（F-010/F-011）；内核只做四件事（F-012）。
- 官方 README 插件表逐项对应，并细化为 GitHub Webhook、GitLab Webhook、HTTP、定时、Issue 轮询 / Claude Code、Codex、ACP、DeepSeek Harness、通用 command / 桌面、飞书、钉钉·企微·Slack·Discord 模板 / `delivery`（F-052）；仓库目录 `kernel/`、`host/`、`protocol/`、`worker/` 分层印证内核边界（F-059）。
- 内核确定性约束（F-015/F-016）由官方「不读系统时钟、不用随机数、不向外发请求、凭据留插件」进一步细化（F-058）。

### 3. 内核规模与性能数字 — ⚠️ 口径差异（取官方值）

| 指标 | 博文口径（F-013/F-014） | 官方口径（F-061） | 结论 |
|------|------------------------|------------------|------|
| 内核行数 | 大概 1600 行 | 约 1650 行（**含空行和注释**） | 统计口径不同，正文取官方值 |
| 启动 | 不到 0.1 秒 | 冷启动 88.78 ms；110 万条事实时 99.8 ms | 一致，官方给出数据量条件 |
| 空闲内存 | 60MB 左右 | 59.94 MB RSS | 一致 |
| 1000 连接 | 170MB 出头 | 170.49 MB RSS（**1000 个同时等待的长轮询**） | 一致，官方给出连接形态 |
| 派活耗时 | 基本在 1.5 毫秒以内 | **派活 p99 1.82 ms** | ⚠️ 最大的口径差异：博文把「1.5ms 以内」写成上界，官方是 p99 统计值，二者不可等同 |
| 依赖 | 没有第三方依赖 | 运行时依赖 0；但需 Node.js 24+、Git、curl（F-044） | 「零依赖」指运行时依赖，非「装个 Node 就能跑」 |

- 官方实测环境：Apple M5 Pro、24 GB、Node 24.21.0，写入逐条提交、事务落盘后才应答（F-061）。**该组数字为作者单环境自测，无第三方独立复现**，正文引用时须保留环境与「作者自测」标注。
- 官方补充历史增长边界（F-062）：状态汇总变慢、日志索引继续占盘，格式变化后首次启动全量重建，110 万条用时 43.1 秒。

### 4. 平台支持与前置依赖 — ⚠️ 博文未提的重要边界

- 官方支持 **macOS / Linux**，需 Node.js 24 或更新、Git、curl 与一个已登录的命令行 Agent（F-044）。
- **Windows 版待定**：作者称 11 月 7、8 日回家后开发并做兼容性测试，进度在 issue #17（F-045）；WSL2 按 Linux 安装可跑，但需 systemd / `--no-service` / `loginctl enable-linger`，桌面通知到不了 Windows 桌面，`command` 接入的 Agent 不上报用量，WSL2 自身约占 1GB 内存。
- 博文「电脑上装个 Node 就能跑」（F-013）未区分平台，容易误导 Windows 读者；教程正文以官方口径为准。

### 5. 五步流程与规则配置 — ✅ 通过

- 博文五步（F-018~F-022）与官方「一件事怎么转起来」五步（F-043 及 README 上手段）逐条对应。
- `rules.json` 派活（F-019）由官方两份规则示例细化：定时规则 `name`/`when.cron`/`to`/`cwd`/`prompt`，外部事件规则 `when.source`/`types`/`to`/`cwd`/`skill`/`parallel`（F-049）；并补充「几秒内生效、改错继续按旧规则跑并发卡片提醒」（F-050）。
- 「最后一条回复交代结果」（F-020/F-034）由官方回执协议细化为 `ask`/`notice`/`resolve`/`later`/`events` 五类、`fyi` 通告、JSON 错只重写末段、`"resume": true` 续会话（F-051）。

### 6. 内核四机制与可靠性边界 — ⚠️ 一处可靠性表述需收窄

| 机制 | 博文 | 官方（F-057/F-058/F-060） | 结论 |
|------|------|--------------------------|------|
| 挂起零消耗 | 发完卡片就下班，三天不回「一分钱 Token 都不花」（F-024） | 等待状态存数据库、Agent 进程退出；「**只有很轻的中台在后台等着**」 | ✅ 机制一致，官方保留残余成本 |
| 事件溯源 | 断电或程序被强杀，已记进去的也还在（F-026） | 进程被强杀已确认的事不丢；**整机断电没有单独测过**；日志与索引同一事务写盘、写完才应答 | ⚠️ 博文把「强杀未丢」外推到「断电也不丢」，官方未测 |
| 指令数据分离 | 外部内容单独放文件、标为资料（F-029） | 类比 SQL 参数化；提示词里只有校验过的类型、编号、链接；事件带 `cwd`/`agent`/`access` 字段直接拒收 | ✅ 官方更具体 |
| 跳数熔断 | 超过 8 层自动停（F-031） | 类比 TTL；超 8 层只记录、不再派活并发卡片；**经过人工提问与定时复查不清零，Agent 改不了** | ✅ 官方补充关键约束 |

- 官方提供可复现的自测命令（F-060）：`agent-autoloop why 1`、`node sim/random.ts 24301 200000`、`node sim/crash.ts 1000 12648430`、`npm run benchmark`。

### 7. Agent / 通道 / Webhook 支持范围 — ⚠️ 需分级呈现

- 博文「装好就能直接用的有 Claude Code、Codex，还有支持 ACP 的 Agent」（F-035）与官方实测范围一致（F-055）：这三者跑通多轮问答与跨进程会话续接，飞书跑通发送、按钮回调、卡片更新。
- ⚠️ 但官方明确：**四种 Webhook 模板只在本地模拟服务验证过，GitLab Webhook 按官方文档格式测试、没连过真实 GitLab**；README 整理的 DSH / pi / OpenClaw / Hermes / Cursor / WorkBuddy·CodeBuddy 接入命令「**我们还没有逐个跑过**」（F-054）。
- 官方另注明场景模板样例数据均为虚构，脚本与回执只用本地 HTTP 与假飞书 CLI 验证、未在真实账号跑完整业务（F-067）。
- → 教程须把「内置且实测跑通」「内置但未连真实服务」「仅提供接入命令未验证」分成三档，不可笼统写成「都支持」。

### 8. 交付流水线与标签 — ✅ 主流程通过（含 1 项单源附注）

- `deliver` 标签 → 审代码 → 等 CI → 合并 PR → 等部署 → 核对线上版本（F-037）与官方 README 完全一致；「审查和交付配置只从 `main` 读取，绝不在接单电脑上检出或运行 PR 里的代码」亦获官方逐字佐证（F-056）。
- ⚠️ 子项：博文提到的 `deliver-review` 标签在官方 README **未列出**（F-068），仅博文单源；教程中标注「仅博文单源，以仓库配置手册为准」。该子项非文章主结论，不影响大项结论与 bundle 状态。

### 9. 安装、试跑与场景模板 — ✅ 通过

- 博文「让 Agent 自己读 README 和 INSTALL.md 装好并试跑」（F-038/F-039）与官方一致：INSTALL.md 标题即「安装说明（写给 Agent）」，给出安装命令、目录、`try` → `answer 1 2` → `status` 的真实终端输出（F-046/F-047/F-068 相关段）。
- 官方补充完整运维命令组（F-048）、七套场景模板与三套扩展模板（F-063）、数据目录 `0700` 与卸载保留数据（F-066）。
- 作者自用 7 场景（F-040）中的 AIHOT / GEO 巡检属作者业务实例，官方模板表未逐项对应，正文列为「作者实践举例」而非「内置模板」。

### 10. 用量合规、许可证与安全 — ⚠️ 博文完全未提

- 官方「用量与合规说明」（F-064）：中台调用本机已登录 CLI，**不读取或转存账号凭据**；模型调用消耗算在用户自己账号，额度与使用范围遵循各家厂商服务条款；**高频自动化场景下厂商通常更建议使用 API Key**（个人订阅额度主要为日常人工交互设计）；对外提供服务请使用 API Key；项目为独立开源项目、与相关厂商无隶属或背书关系。
