# 选型矩阵、生产就绪与成本

原文最有价值的部分不是五个框架的介绍，而是把问题改写成“什么约束最卡你”（F-005、F-054）。下面把它拆成可以直接用于评审的四张表。

## 1. 按主导约束选

| 你的主导约束 | 首选 | 为什么 |
|-------------|------|--------|
| 精确控制、失败恢复、逐步审计 | LangGraph | checkpoint/resume + 确定性路由（F-018~F-020、F-023） |
| 角色型任务的团队速度 | CrewAI | 角色抽象压低搭建成本（F-024~F-026） |
| 已标准化在微软/.NET/Azure | MAF | .NET/Python 对齐、会话状态、企业中间件（F-033~F-035、F-039） |
| 类型安全与输出校验 | Pydantic AI V2 | capability 组合 + schema 校验 + Harness（F-041~F-045） |
| 对索引私有数据做推理 | LlamaIndex Workflows | 检索与事件驱动工作流同处（F-050~F-052） |

> 使用方法：先写“如果这次失败，损失是什么”，再从第一列找最接近的一行。不要从第二列反推需求。

## 2. 生产就绪对比

| 框架 | 持久执行 | MCP | 语言 |
|------|---------|-----|------|
| LangGraph | checkpoint + resume（F-018~F-020） | 有集成 | Python、JavaScript（F-009） |
| CrewAI | 通过平台运行时 | 有集成 | Python（F-010） |
| MAF | 会话状态（F-033） | MCP 原生；A2A 1.0 支持待补齐（F-036、F-074） | .NET、Python（F-035） |
| Pydantic AI V2 | 通过 Harness capability（F-043、F-077） | 原生集成（F-044） | Python（F-046） |
| LlamaIndex Workflows | 事件驱动 + 状态序列化/恢复（F-076） | 有集成 | Python、TypeScript（F-049） |

两点比表格更重要：

1. **MCP 降低了工具迁移成本**：按 MCP 建的工具集成可以跨框架复用（F-058）。但“支持 MCP”不等于“支持程度相同”，客户端/服务端/工具发现能力需逐框架查文档（F-058 的口径降级）。
2. **没有框架默认安全**：提示注入、工具误用、未校验输出仍是你的责任（F-081）。护栏、输入校验、工具权限应作为独立设计层，而不是指望框架开关。

## 3. 成本：免费的是框架，贵的是 token

原文的成本段落值得单独记住（F-059~F-064）：

1. 框架本身免费；模型按 token 计费（F-059）。
2. 多步推理 + 工具调用会显著放大 token 消耗（F-060）。
3. 每一步都重发完整上下文的“话痨型”crew 最容易产生意外账单（F-062）。
4. 控制成本的三条杠杆：prompt caching、限制每步推理、用结构化状态压上下文（F-063）。
5. 增长的费用项通常是模型成本，不是框架许可（F-064）。

原文给出的“每 100 万输入 token 1~5 美元”是 2026 年中期的宽区间，随模型、缓存、批处理与输入/输出计价变化，不能直接做预算（F-061、F-080）。正确做法是用目标模型现价 × 预估步骤数 × 重发系数做测算。

## 4. 双框架分层：原型层与记录系统层

原文的默认建议是“双框架立场”（F-065）：

1. **原型层**：CrewAI 或 Pydantic AI V2，目标是尽快学会问题。
2. **记录系统层**：Python 优先用 LangGraph；.NET/Azure 用 MAF。
3. **数据层**：产品本质是私有数据检索时，用 LlamaIndex Workflows（F-066）。

这套分层的真正理由是成本结构：迁移与评测 harness 才是主要成本，而不是框架许可（F-067）。所以越早判断“这是 Demo 还是 system of record”，后面越省（F-056、F-065）。

## 5. 一个可执行的评审顺序

1. 标注负载类型：`demo` / `internal tool` / `system of record`。
2. 写失败代价：一次失败损失多少钱、多少时间、是否触发合规/审计。
3. 定状态归属：状态必须持久化在哪里（内存/Postgres/平台运行时）。
4. 定审计粒度：是否需要逐步解释“哪一步跑了、为什么”。
5. 再选框架：按第 1 节的表，而不是按 Star 数或“功能最多”。

## 6. 区域约束（印度市场段落中可保留的部分）

原文针对印度团队给了三条约束（F-068）：

1. **人才**：Python 供给深，LangGraph/CrewAI/Pydantic/LlamaIndex 招聘池大；MAF 适合已标准化 .NET/Azure 的企业。
2. **成本**：卢比偏弱时，美元 token 支出更敏感，应优先支持 prompt caching 与推理上限的框架/模式。
3. **数据保护**：Agent 日志与检索到的客户数据属于个人数据，受 DPDP Act 2023 管辖；状态存储尽量在境内、最小化保留、校验每个工具输入。

这三条对中国团队同样有参考价值：把“人才栈、汇率/成本、数据驻留”换成本地条件即可。

## 7. 安全边界（必须单独说）

原文明确写“none of them makes your agent safe by default”（F-081）。具体风险：

1. **提示注入**：检索内容、网页、邮件都可能携带指令。
2. **工具误用**：高权限工具需要审批与最小权限。
3. **未校验输出**：进入下游系统前必须有 schema/业务校验。

Pydantic AI 与 MAF 提供更多护栏脚手架，但没有一个能替代你自己的控制层。把护栏、输入校验、工具权限当成独立设计层，是这份对比文里最不应该被忽略的一句。
