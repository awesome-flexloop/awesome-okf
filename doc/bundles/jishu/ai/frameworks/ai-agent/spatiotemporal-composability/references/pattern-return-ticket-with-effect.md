# 回程同源

> 一句话：**去程和回程必须在同一个表达式里生成**。清理逻辑一旦与创建逻辑分居两地，完整性就只能靠人记得写。

## 触发场景

**适用于**：需要在运行期装载、卸载、替换组件的插件系统、扩展点、Agent 工具/技能热插拔、可热更新的服务实现；这些系统共享一个会被多方修改的上下文。

**不适用于**：编译期完成装配且运行期不变的系统；无共享可变状态的纯函数服务；所有外部副作用都跨越系统边界、无法被 reify 的场景（见 F-066）。

## 核心做法（5 步）

1. **把共享位置登记为带类型的键**：所有组件可能修改的位置先 reify 成 coeffect key，键携带值类型与允许的操作集；未被任何键绑定的位置不允许组件触碰（F-034、F-050）。
2. **修改处同时返回逆**：每次上下文变换返回「新状态 + 就地逆」，逆在看到具体状态的那一刻产生，而不是事先固定一个全局逆（F-024、F-030）。
3. **运行时按 LIFO 累积并绑定到生命周期**：把逆折叠进组件专属的 accumulator，卸载时逆序执行；中间态始终满足 `φ(γ) = γ₀`（F-029、F-032）。
4. **依赖变更分类驱动生命周期，撤回前等待依赖方**：上下文每次变化对照依赖规范分为 activating / deactivating / neutral；提供者先停止供给、依赖方完成自身的异步拆卸后，才允许应用 accumulator（F-037、F-049）。
5. **把配置当唯一真相源**：在前提成立时，任意插拔顺序都收敛到「一次性静态装配」的状态，因此不必维护带顺序的迁移脚本（F-056）。

## 反模式（均来自论文引用的实际教训）

| # | 反模式 | 后果 | 论文依据 |
|---|---|---|---|
| 1 | 用 `deactivate` 之类的独立钩子做清理，与 `activate` 中的创建分离 | 违反 locality of concern，完整清理难以验证；VSCode 因此只能重启整个 extension host | F-012、F-016 |
| 2 | 用进程重启 / 容器编排替代细粒度回退 | 丢弃进程内累积状态、引入冗余副本与网络开销，粒度与组件粒度错配 | F-018 |
| 3 | 把资源安全交给组件作者手写回调 | OSGi / iPOJO 的停用回调是手写的，漏写一个就静默泄漏；且同步回调无法等待异步拆卸 | F-065、§7.4 |
| 4 | 把不可交换的键当作可交换 | 有序中间件链、要求返回最低可用描述符的 `open` 都不满足交换性，独立性证明失效 | F-043、§3.4.2 |
| 5 | 把已经越界的 emission 也当成可回滚 | 已发出的字节 / 消息不可撤回；恢复只到观测等价 `≃`，不是物理状态复原 | F-042、F-066 |
| 6 | 把「运行时不校验见证」忘了 | 逆是否真能回退、键上操作是否可交换，运行时都不检查，是作者义务；误以为框架会自动验证等于没有保证 | F-059 |

## 检验标准

- 卸载任意组件后，其余组件的表状态与「该组件从未加载」同构（Theorem 68 / Corollary 69 的形状）。
- 以任意顺序重复插拔同一组组件，最终静止状态一致（Theorem 80）。
- 组件作者不需要写任何卸载路径，只需要在产生副作用的地方返回逆。
- 提供者被移除时，所有声明其键的依赖方先完成停用，提供者才执行 accumulator（Theorem 70）。
- 失效组件的错误不传播到父组件，兄弟组件继续运行（§4.4 Failure）。

## 跨领域迁移示例

**操作系统驱动卸载**：Nooks 在 Linux 内核与可加载扩展的调用边界上插入 object tracker，shadow drivers 从另一侧记录请求与配置，二者都靠「运行时保存回收记录」而不是驱动作者手写清理（论文 §7.3 Interposed reclamation）。这与第 2、3 步同构：差别只在记录由平台按资源类型固定，而 Cordis 让组件自带每个原子效应的逆。

**CI 流水线热插拔**（非论文场景的推演）：把「注册一个 runner / 挂载一条 webhook / 占用一个并发槽」建模为带逆的键，取消某一步时按 LIFO 释放其占用的槽与钩子，后续步骤无需感知曾存在该步。此处能否套用，取决于并发槽是否可被 reify 为独占位置——这正是第 1 步的判据。
