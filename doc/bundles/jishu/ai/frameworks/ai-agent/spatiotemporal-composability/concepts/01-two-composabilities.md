# 01 · 两个可组合性：为什么现有插件框架不够

> 一句话：编译期由作用域和模块系统免费提供的两条性质，到了运行期热插拔场景双双失效，而现有方案要么靠重启、要么靠组件作者手写清理。

## 1. 两个定义

**时间可组合性（temporal composability）**：组件被移除时，它对共享环境所做的修改必须完整且安全地回退。论文明确把「资源分配、事件注册、状态变更」都算进需要追踪与有序回收的范围（F-009）。

**空间可组合性（spatial composability）**：组件必须能声明、发现并解析彼此的依赖；系统要管理依赖拓扑，并在依赖变化时协调各组件的生命周期（F-010）。

注意两个定义都落在**共享环境**上。如果组件之间不共享任何可变状态，问题自动消失——这也是后面「系统边界」判据的伏笔（F-066）。

## 2. 静态世界里的对应物

论文给了一个很有用的归约（F-011）：

| 运行期问题 | 静态对应物 | 谁来保证 |
|---|---|---|
| 时间维度：离开时要恢复 | 词法作用域、RAII、bracket pattern | 编译器 + 作用域规则 |
| 空间维度：找到依赖 | 模块导入解析 | 链接器 / 模块系统 |

归约的意义不是说「把静态机制搬到运行期」就够了，而是指出：运行期装配把这些保证的承担者从**编译器**换成了**框架运行时**。框架若没有等价机制，保证就完全落空。

## 3. 反例一：VSCode 扩展宿主

论文 §1.2.1 用 VSCode 作为主要动机案例（F-012–F-017）：

- 所有扩展运行在**同一个共享 extension host** 中，宿主不提供在运行时卸载单个扩展代码的机制（F-012）。
- 按安装量排序的**前 100 个扩展中，87 个**包含可执行代码，移除时需要重启整个 extension host（F-013）。
- 同一批前 100 个扩展中，**仅 7 个**声明了对非内置扩展的 `extensionDependencies`（F-014）。
- 这组数据取自 Visual Studio Code Marketplace，日期 **2026-06-09**（F-015，脚注 1）。

> ⚠️ 口径提醒：二手解读常写成「87% 的热门扩展含可执行代码」。论文原文是**个数**（87 个 / 100），且同时给出「7 个」这一第二项数据与取数日期。本包全文按原文口径书写，见勘误 [E-01](../references/verification.md)。

两个具体缺口：

1. **清理与创建分离**（F-016）：`deactivate` 是 host 进程终止时的优雅关闭回调，用途不是细粒度卸载。效应在 `activate` 里创建、却在 `deactivate` 里销毁，违反 locality of concern，完整清理无法局部验证。
2. **依赖不可检**（F-017）：`vscode.extensions.getExtension(...).exports` 默认返回 `any`，依赖方拿不到受检接口，空间可组合性只能靠文档和约定。

## 4. 反例二与三：靠进程、容器兜底

§1.2.3 指出操作系统在**进程粒度**提供时间可组合性，容器编排器在**服务粒度**提供空间可组合性，但两者与组件粒度错配（F-018）：

- 重启会丢弃进程内累积的状态；
- 重建耗时数秒至数分钟；
- 为隔离而引入的冗余副本与网络开销，与「换掉一个插件」这个动作不成比例。

换句话说，粗粒度机制确实「能恢复」，代价是把无关状态一起丢掉。论文要的是**与组件同粒度**的恢复。

## 5. 把问题收束成两个可执行判据

读后续形式化章节时，随时用这两问检验是否真的解决了问题：

- **时间判据**：卸载任意组件后，剩下的组件能否通过任何操作序列，区分「它曾被加载过」和「它从未出现」？论文用观测等价 `≃` 来形式化这一点（F-042、F-052）。
- **空间判据**：某个键的提供者被替换时，声明该键的依赖方是否**自动**停用并按新解析重新启用，且不需要作者写迁移脚本（F-053、F-056）？

再补一条来自实践的限制：已经越出系统边界的 emission（发出的字节、消息）不可撤回，恢复只能到**观测等价**，不是物理状态复原（F-066）。把「可回滚」理解成「什么都没发生过」是本主题最常见的过度宣称。
