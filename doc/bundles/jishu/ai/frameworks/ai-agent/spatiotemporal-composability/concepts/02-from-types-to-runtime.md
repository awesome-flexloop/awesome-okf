# 02 · 从静态类型到运行时：论文的立场

> 一句话：effect 与 coeffect 原本是类型判断上的两个标注维度，论文不打算再造一个类型系统，而是把这两个概念的**结构**做成运行时可直接操作的一等对象。

## 1. 两个判断的两条延伸线

论文 §2 先把 familiar 的两条线并排摆出来（F-020、F-021）：

| 概念 | 判断形式 | 关注点 | 谱系 |
|---|---|---|---|
| 效应 effect | `Γ ⊢ t : T^effect` | 计算**对外做了什么** | 单子式效应源于 Moggi、Wadler（Haskell 普及）；代数效应源于 Plotkin & Power；效应处理器源于 Plotkin & Pretnar，Koka / Eff / OCaml 5 采纳 |
| 协同效应 coeffect | `Γ^coeffect ⊢ t : T` | 计算**需要从环境拿什么** | 余单子式源于 Uustalu & Vene、Petricek 等 |

一句话对照：**effect 描述输出侧的影响，coeffect 描述输入侧的需求**。插件场景里，「注册了一个定时器」是 effect，「声明依赖 `database` 键」是 coeffect。

## 2. 分级协同效应

§2.2 提到分级协同效应用预序半环 `(S, ≤, +, ×, 0, 1)` 刻画需求用量（F-021）：`0` 未用、`1` 线性、`n` 有界、`∞` 无限制。这套装置服务于静态资源分析——在编译期回答「这段计算最多读几次环境」。

论文自己的方案**不走这条路**。它要的不是「用几次」，而是「这个键现在由谁提供、变了以后通知谁」。所以后面的 `Σ` 是一个键到值的有限偏函数，而不是一个用量半环（F-034）。

## 3. 关键取舍：reify，不是标注

§2.3 的立场句值得原样记住（F-022）：论文把 effect / coeffect 的**概念结构 reify 出来供运行时直接操作**，而不是给静态类型系统增加标注。

这个取舍决定了后面全部设计：

- **效应成为值**：一次变换返回「新状态 + 逆」，逆是可以在运行时保存、累积、调用的实体，而不是类型上的标签（F-024）。
- **依赖成为键表**：需求被登记成带类型的键，运行时能枚举、能比较前后变化、能据此通知（F-034、F-037）。
- **装配成为演算**：因为所有信息都在运行时数据里，插拔顺序、生命周期状态、解析结果都能写成状态转移规则并证明性质（F-047、F-051）。

代价同样明确：静态类型系统能在编译期拒绝的程序，这里只能靠运行时机制与组件作者的约定。**运行时不校验 witness**（F-059）——逆是否真能回退、键上操作是否可交换，都是作者义务。把这一点忘掉，就会把「结构性保证」误读成「框架自动验证」。

## 4. 局部保证的边界

§3 开篇给了一个很克制的前提（F-023）：单看一个组件，局部保证是容易的；问题出在**其他组件进入之后**。

因此 §3 的后半程专门处理「多个组件的效应交织在一起还成不成立」：§3.3 统一两类上下文，§3.4 建立效应独立性与协同效应交换性。这也解释了为什么论文需要观测等价 `≃S`——当多个组件同时修改上下文，逐字相等太强，只能用「无操作序列可区分」来读等式（F-042）。
