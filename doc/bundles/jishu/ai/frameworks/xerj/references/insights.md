# XERJ 架构洞察与知识地图

> 本文件是 I 阶段产出：每条洞察按「陈述 / 证据 / 反常识 / 行动」四元组组织，证据均引用事实清单编号（F-xxx）。

## 洞察 1：ES 兼容是传输层，不是产品身份

- **陈述**：XERJ 的产品面是「零配置摄取 + 自我描述 + 长期记忆」三件套，Elasticsearch 8.x 线协议只是让既有客户端与工具链免改造接入的传输层。评估 XERJ 时，先跑旗舰回路（`autoindex` → `autoindex map` → 查询），再谈 DSL 覆盖度。
- **证据**：F-006、F-008、F-009、F-010（`WHY_XERJ.md` 把 ES 兼容类比为 CockroachDB/Neon 讲 Postgres 协议）、F-011（三类 AI 特有问题：Onboarding / Orientation / Continuity）、F-012（`llms.txt`：ES wire compatibility is the transport, not the product）、F-014（autoindex 流水线 80/81 对抗验证）。
- **反常识**：一个通过 ES 8.x YAML 一致性套件 1366/1369 的引擎，最容易被读成「Rust 写的 ES」。但一致性命中的只是**语法面**；XERJ 真正稀缺的是 ES 没有的那三件（无映射设计的摄取、面向智能体的目录与字段图、命名空间记忆）。
- **行动**：接手一个「想用 XERJ 替掉 ES」的需求时，第一步不是跑兼容性测试，而是把**数据入库路径**画出来——若入库仍由人写 Logstash/pipeline，那 XERJ 的差异化价值一点没兑现。

## 洞察 2：`semantic` 是名字，不是能力

- **陈述**：默认嵌入模式是词法特征哈希，不是神经语义。「按意义搜索」在默认配置下等于「词/子词重叠 + BM25」；真正的语义需要 `--embed-mode neural`（或 `--embed-mode proxy`），且**该选择在首次索引前就要做**。
- **证据**：F-108（384 维）、F-109（FNV-1a 64 位）、F-110（有符号哈希）、F-111（一元组权重 1.0 + 字符三元组 0.35）、F-112（L2 归一化）、F-113（源码注释自陈 "not a neural model"）、F-115、F-116（`--embed-mode` 在摄入时生效，切换不重嵌入）、F-117。
- **反常识**：工具名 `xerj_semantic_search`、字段名 `semantic_text`、以及 `hybrid` 融合，都在语义上强烈暗示「理解语义」。而默认配置下，这些名字描述的是**字段类型与检索形状**，不是模型能力。这个命名与实现之间的落差，是这个项目最容易让人误判的地方。
- **行动**：向用户承诺「按意思搜」之前，先确认三件事：节点是否以 `--embed-mode neural` 启动、语料是否在**该模式生效后**才被索引、向量臂覆盖的索引比例（混合检索中向量臂只覆盖映射了 `semantic_text` 的索引）。

## 洞察 3：机器可读面比人读面更新

- **陈述**：仓库存在定向的文档漂移——**由工具生成的机器可读面（`mcp-tools.json`、`tools/list`）永远是最新的，人手写的人读面（README / AGENTS.md / WHY_XERJ.md）会滞后**。
- **证据**：F-060（crate 文档写 17 个工具）、F-062（测试函数名 `tools_list_has_all_seventeen`）、F-063（已发布 schema 的 `tools[]` 长度 17），对照 F-200（`AGENTS.md` 写 "Thirteen tools"）、F-201（`README.md` 写 "Thirteen tools are exposed"）、F-202（README 写 "eight detectors"，注册表实际 9 个）、F-203（`WHY_XERJ.md` 写 "13 format families"，代码侧 25 个抽取器 / 28 个 `Family` 变体）。
- **反常识**：一个以「诚实的坑清单」为卖点的项目，人读文档却比代码旧。这不矛盾——`llms.txt` 里被逐条维护的是**能力边界**（成本、隐私、质量），而工具**清单数量**属于会被 CI 漂移门禁覆盖、不需人肉维护的低风险事实。
- **行动**：任何关于「XERJ 有哪些工具 / 多少种格式 / 多少个检测器」的陈述，一律以**代码或已发布 schema** 为准，人读文档只用于理解意图与边界。

## 洞察 4：autoindex 是独立客户端，不是引擎内置管线

- **陈述**：`xerj autoindex` 是一个不链接引擎的纯 ES 兼容 HTTP 客户端，它既能被 XERJ 引擎使用，也能被真实 Elasticsearch 使用，且无法拖垮服务端。
- **证据**：F-027（`xerj-autoindex/src/lib.rs` 头部：纯 HTTP 客户端、不链接 `xerj-engine`、不对任意端点工作）、F-055（索引名 `<prefix>-<dataset-slug>`）、F-166（autoindex 是唯一无 HTTP 等价物的操作）、F-027 与 F-092 共同说明「显式 mappings + 幂等 `_id`」是客户端职责。
- **反常识**：直觉上「一键索引」像是引擎的一个功能模块；实际上它是一个**可独立部署的客户端**——这也解释了为什么它能同时对真实 ES 工作：它只依赖 ES 线协议这一层契约。
- **行动**：评估 XERJ 时可以把它拆成两个问题分别验证——「摄取客户端好不好用」与「检索引擎准不准」。用 autoindex 去索引一个真实 ES 实例，是一个成本极低、信息量极高的对照实验。

## 洞察 5：内容驱动识别 + 字段来源标记 = 可预测的数据集边界

- **陈述**：XERJ 的数据集划分不是按目录、也不是按扩展名，而是按**文件里读出来的字段名**；且只有「来自数据本身」的字段名才参与聚类键，抽取器发明的字段名被排除在外。
- **证据**：F-028（永不信任扩展名）、F-029（28 个 `Family` 变体）、F-030（25 个抽取器模块）、F-033（`FieldOrigin::Data` / `Extractor`）、F-034（issue #178：提取器字段名进入聚类键会静默搬家文档并孤立已写入文档）、F-035～F-039（分段与截断常量）。
- **反常识**：把 `data.csv` 改名成 `data.pdf` 不会改变识别结果；而**修改 CSV 的表头**却会改变它落到哪个索引——这是设计选择，不是 bug。同理，抽取器版本升级不会让旧文档搬家，因为 `title`/`body` 这类抽取器字段名不参与聚类。
- **行动**：规划语料布局时，把「同 schema 的文件放在一起、schema 演进时新建目录」当作硬约束；否则一次表头变更就会把语料劈成两个索引，历史查询静默缺数据。

## 洞察 6：参考编码的收益受「记忆门控」，不是普适最佳实践

- **陈述**：让智能体「先检索再写」只在**模型没记住的代码**上获胜；对模型已掌握的公共库，检索是净开销甚至最差的一臂。
- **证据**：F-188（7 个专用库 21 次运行：原生与 xerj 都 21/21，xerj 少 1.5 倍输出 token；纯记忆失败 1/21 且多花 6.5 倍成本）、F-189（已记忆代码上检索是 overhead，注入大段参考可能是最差臂）、F-190（33 个受测语料：裸提示 20%，带语料 98%）、F-204～F-206（grep 式 agent 最多拉入 1.06M 输入 token）。
- **反常识**：行业里「RAG 优先」的口号容易让人以为检索总是不亏。XERJ 的实测把边界划得很清楚：**收益来自「模型答不出来的细节」**，这正是内部 API、专有实现、小众库、训练截止后的新代码；热门公共库恰好是模型最熟的地方。
- **行动**：把「是否用参考编码」当成一个**按语料判断**的决策，而不是全局开关。判定式：这段代码的答案，模型凭记忆能给出具体、可验证的实现吗？能，就别检索；不能（契约、算法细节、私有 API），就检索。
