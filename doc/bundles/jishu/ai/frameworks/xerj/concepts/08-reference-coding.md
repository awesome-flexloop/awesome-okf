# 参考编码与语料库

「参考编码」（reference coding）是 XERJ 的旗舰用例：让编码智能体在动手前，先把**已经解决过这个问题**的开源实现捞出来读，而不是靠记忆猜或用 grep 反复试错。

## 闭环

```
xerj corpus add <name> <git-url>...   # 克隆参考仓库（一次一个领域）
xerj corpus add --from <manifest>     # 或重建别人定义好的语料
xerj corpus build <name> --recipe <r> # 或把结构化记录收割成可移植包
xerj corpus index <name>              # 用 autoindex 建索引（一次一个语料）
xerj code <name> "<what you need>"     # 检索后再写（每个任务）
```

（F-174）状态随时可查：`xerj corpus list` 显示每个语料的索引前缀、**是否加载在本节点**、以及任何 INCOMPLETE 标记。

## 语料的定义是可分享的

克隆是浅克隆（`--depth 1`），落在 `~/.xerj-code/corpora/<name>/`；每次构建在旁写一份 `corpus.json`——URL、完整 commit SHA、许可证，几百字节，不含源码（F-175）。**那份文件就是可分享的语料定义**：交给别人，对方执行

```sh
xerj corpus add --from their-corpus.json
```

就在自己的机器上重建同样的 commit（已存在的克隆会被移动到记录的 SHA，两棵树一致）。

语料名与仓库名在**触碰文件系统之前**校验：含 `/`、`*`、前导 `.` 或保留字的名字在解析阶段被拒（因为固定克隆检出会执行 `git checkout --force`）（F-176）。

仓库内已定版的语料定义有 5 份（F-195）：

| 语料 | 覆盖 | 用途 |
|---|---|---|
| `xerj-search` | lucene、tantivy、meilisearch、quickwit、sonic、elasticsearch | FTS、BM25、倒排、合并策略、容错、分段布局、ES 线语义 |
| `xerj-vector` | qdrant、usearch、instant-distance、hnswlib | HNSW 构建、邻居启发式、量化、过滤 k-NN |
| `xerj-storage` | sled、fjall、redb | WAL、flush epoch、崩溃恢复、压实、页分配 |
| `xerj-columnar` | clickhouse | 列式存储、聚合执行、压缩编解码、向量化扫描 |
| `xerj-blogposts` | —— | 上游自家博文语料 |

`--from` 读**本地文件**；v1.0.0-rc.95 起不抓取 URL，传 URL 会得到 `no such manifest`（F-197）。

## 检索返回「定义」，不是字节窗口

这是 `xerj code` 与普通全文检索的关键差异（F-177）：

```
─── valkey/src/networking.c  (score 12.68, BSD)
    [function addBulkStringToReplyIOV @ line 2635 — 366 of 272,498 chars]
static void addBulkStringToReplyIOV(char *buf, size_t buf_len, ...) {
```

**行号就是全部意义所在**。一个记录是整个文件，所以排序只能告诉你「哪个文件匹配了」；定义是从索引已经携带的 `symbols[]` 里定位出来的。

上游记录了没有这一步时的惨状：一次关于空回复的查询正确地排到了 `networking.c`，然后返回了它的许可证横幅——因为 `addReplyNull` 在第 1460 行。8 KB 的切片落在 272 KB 的文件里，答案是不是在切片内纯靠运气。

两个输出控制项：

- `--full N` 把每段落限到 N 字符（`--full 0` 打印文件头并说明如何拿到匹配定义）；
- `--no-symbol` 退回原始窗口（只对完全没有符号的数据文件有意义）。

## 退出码契约

`xerj code` 刻意区分「没匹配到」与「坏了」（F-178）：

| 码 | 含义 | 该做什么 |
|---|---|---|
| 0 | 有命中（段落打到 stdout） | 引用它们 |
| 1 | **无匹配**（含 `--json` 的空 `hits.hits`） | 回退到常规工作，**不要重试** |
| 2 | 用法错误、节点不可达、传输失败、30 天过期拒绝、独立语义失败 | 修问题 |
| 3 | 语料在 `state/` 中但**本节点 0 个存活索引** | 重新索引，或把 `XERJ_URL` 指向持有它的节点 |

> 退出码 3 的措辞值得注意：「这**不是**『没匹配』——语料只是没加载在这台服务器上」。

对比：**`xerj search` 在空结果时退出 0**（F-179）。不同工具、不同契约——写脚本时必须分开处理。

## 检索模式：默认是 BM25

默认检索模式是 `bm25`。两个语料、十二个手标查询的实测（F-180）：

| 模式 | rust-text top-1 / top-3 | kv-oss (C) top-1 / top-3 | 合并 top-1 / top-3 |
|---|---|---|---|
| **bm25** | 3/6 · **6/6** | **6/6** · 6/6 | **9/12** · **12/12** |
| hybrid | **5/6** · 6/6 | 2/6 · 4/6 | 7/12 · 10/12 |
| semantic | 4/6 · 4/6 | 2/6 · 3/6 | 6/12 · 7/12 |

**top-3 才是有效指标**——智能体读的是 k 个段落，不是一个。BM25 在 top-3 上两个语料都满分，且在任何语料上都不是最差的一臂，还快约 5 倍（无向量往返、无映射查找）。

### hybrid 为什么曾经是默认，又被撤回

上游把这段历史写得毫不掩饰（F-181）：

> hybrid 此前是默认，**选择它只基于 rust-text 一个语料**（在那里它赢 top-1）。那是一个语料特异的结果：在 C 语料上向量臂只触达 **407 个索引中的 5 个**（issue #173），于是融合把一个好的排名与一个看不见 98.8% 材料的排名混在了一起。

自 #977 起，hybrid 是**服务端融合**（F-182）：单个原生顶层 `hybrid` 查询，`{"fusion":{"method":"rrf","k":60}}`，没有客户端排名合并。代价是每命中每臂的排名不再暴露（服务端不提供），改为每次混合检索开头一行「实际跑了哪些臂」的说明。

向量臂**只对映射了 `semantic_text` 的索引有效**；语义查询作用于未映射索引时**不降级**，而是让整个请求 400 并连带拖垮通配符下的其他索引（F-183）。`xerj code` 会先读 mapping，只把向量臂瞄准有能力的索引。

## 三个不能省的纪律

### 一、绝不请求 `highlight`

`xerj code` 从不请求 `highlight`（F-184）：在本引擎上 highlight 块会**改变 `_score` 并重排命中**（issue #177）——同一查询，top-1 无 highlight 是 6/6，有 highlight 是 1/6。段落已改从 `symbols[]` 取得，highlight 不带来收益，只带来排序损失。

### 二、许可证分档

`tools/xerj-code/hub/README.md` 把语料源分三档，每个 manifest 的 `review.use` 字段记录仓库属于哪一档（F-196）：

| 档 | 含义 | 例子 |
|---|---|---|
| 可直接借鉴 | 许可证允许 | MIT / Apache-2.0 |
| **仅可参考思路** | 需改写，不得复制 | elasticsearch（AGPL-3.0 / SSPL-1.0 / Elastic-2.0）、sonic（MPL-2.0） |
| 禁止复制 | — | — |

运行时强制：受限许可证（AGPL、SSPL、Elastic、BUSL、GPL 系、MPL、未知）命中的段落下方会打印（F-185）：

```
!! <licence>: adapt the APPROACH, do not copy the code
```

对 ES 还有额外理由：把它的源码贴进 Apache-2.0 的 XERJ 除了许可证问题，还会**证伪项目公开的「与 ES 不共享任何代码」这一主张**。

### 三、过期索引比没有索引更糟

超过 **30 天**的索引被拒绝作答，除非传 `--stale-ok`（F-186）——它会返回已经不存在的代码，带着虚假的自信把智能体带进死路。

## 重建与状态管理

### `--fresh` 是重建，而且从不牺牲可用索引

`xerj corpus index <corpus> --fresh`（F-191）：

1. 在现有索引**旁**构建替代索引（命名 `xc-<corpus>-b<stamp>-*`，有独立的 autoindex `--state-dir`）；
2. 校验它（autoindex 退出码为 0 或 3 **且** `_count > 0`）；
3. 以**原子改名**把 `state/<corpus>.json` 切到新构建；
4. 只在这一切之后，按精确名字删除旧索引。

失败的构建会被删除，旧索引、旧状态文件与旧状态目录**原样保留**。

> 注意它**不是** `xerj autoindex --fresh`——后者只丢弃 autoindex 的续跑日志，且一旦某个语料代际已提交就会被直接拒绝（这正是 `--fresh` 过去在每个已索引语料上都失败的原因，#930）。

### 记录数是三态

一个数字、404（无匹配索引，即真零）、或 **Unknown**（超时、5xx、无法解析）（F-192）。**Unknown 不授权任何删除或切换**：如果节点数不出已有索引，就假定它是一个能用的索引，不把失败的构建留在它上面；如果数不出新构建，就什么都不删、什么都不切。只有数字或 404 才授权删除或切换。

### 状态文件有两个前缀

`prefix` 恒为 `xc-<corpus>`（整个命名空间，这样任何 `xc-<corpus>*` 通配在重建前后都继续有效）；`index_prefix` 是**已验证的那次构建**，也是 `xerj code` 实际查询的索引（F-193）。因此半成品不会在重建期间泄漏进答案。

代价：重建期间两个构建同时存在，节点会短暂持有两份语料，大语料要预留磁盘。

### 中断的首次构建被保留

首次构建失败但已写入记录、且没有可回退的工作索引时，该构建被**保留**而不是让语料完全消失，状态文件记 `salvaged: true` 与真实的 `autoindex_exit`（F-194）。这样的构建可能是部分的，所以 `xerj code` 每次查询都在 stderr 警告**覆盖不完整**——

> 此时「未命中」**不是**「代码不存在」的证据。

普通的 `xerj corpus index <corpus>`（无 `--fresh`）会续跑它（同前缀、同状态目录），完成后清除标记。

## 没有 shell 时的等价物

`xerj_code_search` 这个 MCP 工具跑同一条管线，**文本输出与 `xerj code` 的散文输出逐字节相同**（同样的命中、同样的 `!!` 许可证警告、同样的页脚）（F-198）。差别只在失败契约的映射：

- 拒绝类（30 天过期、语料不在账本、语料未加载在本服务器、传输失败）→ `isError: true`，正文带补救办法；
- **无匹配 → `isError: false`**——一次未命中是**指引**，不是工具失败。

另有 `licence_policy: "strict"`：从受限许可证命中里**剥掉段落正文**，只保留定位符、许可证与「仅可参考」的警告。

## MEATL：给机器读的输出

给智能体对智能体、智能体对工具的交换用 `--meatl`，每条命中一行（F-187）：

```
@ok f=<file>:<line> score=<12.34>[ why=<licence>]   # 一条命中
@ok f=<file>:<line> rrf=<0.1234>[ why=<licence>]    # 原生 hybrid 分数
@no q="<query>" why=no-match-in-corpus              # 未命中（退出码 1）
@mode <arms-ran note>                               # hybrid/semantic 说明行
```

`f` 是溯源定位符 `path:line`，与散文块打印的一致；`why` 是该命中所属仓库在 `corpus.json` 中记录的许可证（未知时省略）。MEATL 的未命中保留退出码 1 与未命中记录。

它**明确不是**给人看的：给人读的散文仍然是散文。上游的判断是——把总结压缩成箭头链，对读者来说比省下的预算更贵。

## 收益的记忆门控（最重要的一节）

「先检索再写」**不是**普适最佳实践。上游的实测给出了边界：

### 在模型没记住的代码上：赢

7 个专用构造库、21 次运行（F-188）：

| 臂 | 结果 |
|---|---|
| 原生（自己 grep 语料树） | 21/21 |
| XERJ（注入检索到的段落） | 21/21，**输出 token 少 1.5 倍，成本低 1.3 倍** |
| 纯记忆 | **失败 1/21**，并多花 **6.5 倍**成本在瞎试上 |

上游的解读很锋利：**编译器可以在重试循环里泄漏一个 API 的「名字」，但永远不会泄漏它的「契约」**（F-188）。

语料级实测（F-190）：裸提示在 33 个受测语料上正确率 **20%**，带语料 **98%**。

### 在模型已经记住的代码上：输

上游对已记忆代码的判断（F-189）：

> 检索是**净开销**。纯记忆最便宜；注入一大段参考甚至可能是**最差的一臂**，因为模型会把它拿到的东西再吐一遍。

### 完整的 token 对比

上游的三臂实测（F-204）：

| 臂 | 输出 token | 成本 | 解出 |
|---|---:|---:|---:|
| 仅凭记忆 | 260,916 | $11.18 | 11/16 |
| grep 驱动 | 26,477 | $3.27 | 16/16 |
| XERJ | 9,982 | $1.58 | 16/16 |

即比 grep 少 **2.7 倍**输出 token、比仅凭记忆少 **26 倍**，单个 Java 任务上最多 278 倍（F-205）。参照物是 grep 式智能体在某个语料上最多拉入 **1.06M 输入 token**（F-206）。

> **行动**：把「是否用参考编码」当成**按语料判断**的决策，不是全局开关。判定式很简单：**这段代码的答案，模型凭记忆能给出具体、可验证的实现吗？** 能（热门公共库）就别检索；不能（契约、算法细节、私有 API、训练截止后的新代码）就检索。

## 测量的方法学

上游把测量纪律也写进了 skill（F-188 上下文）：

1. **用客观判定**——生成的代码能编译且通过模型从未见过的隐藏测试；
2. **跑三臂**——`bare`（仅记忆）、`native`（自己 grep 语料树）、`xerj`（注入检索到的段落）；
3. **报中位数而非均值**——一次 flailing 试次可能是另一次的 5 倍；
4. **先验证任务本身**——注入参考正确解（必须通过）与一个貌似合理的错解（正确但平方复杂度，或缺了契约；必须失败）。**一个让错代码也能通过的基准什么也测不出来**；
5. **不要在模型已记忆的代码上测量**——它连一张 256 值的表都能凭记忆复现，检索于是显示为纯开销。

## 三条不可破的规则

1. **检索到的代码是证据，不是权威**。它证明的是**那个项目**在其约束下如何解决了问题。依赖它时引用 `file:line`，并明说你是改写而非复制。
2. **复制之前查许可证**。`corpus add` 在 `corpus.json` 里记录每个仓库的许可证，受限许可证的命中会带警告行。许可证不兼容时，**借鉴思路并自己写**。
3. **永远不要把工作仓库索引进共享语料**。参考语料是给别人的代码用的；混进自己的，会让检索把自己的错误当先例返回。
