# 代码分析工作流

Codebase Knowledge Generator 的核心价值在于将"理解代码库"这个模糊的人类认知过程，分解为四个 LLM 驱动的分析步骤：**抽象识别 → 关系分析 → 章节排序 → 逐章写作**。每个步骤都有精心设计的 Prompt 和严格的输出验证。

## 分析全流程

```
源码文件 ──→ [1.识别抽象] ──→ [2.分析关系] ──→ [3.排序章节] ──→ [4.逐章写作] ──→ 教程文档
              Identify         Analyze          Order           Write
              Abstractions     Relationships    Chapters        Chapters
                  │                │                │               │
                  ▼                ▼                ▼               ▼
           核心概念列表      关系图+概述      教学顺序       Markdown章节
           （name/desc/     （from/to/label  （索引列表）    （含代码示例、
            files索引）      + summary）                      Mermaid图）
```

这四个步骤的设计遵循**渐进式理解**原则——先让 LLM 建立全局概念地图，再分析概念间的联系，然后确定教学顺序，最后基于前面所有信息撰写详细内容。

## 阶段1：识别抽象（IdentifyAbstractions）

**目标**：从代码中提取 5-10 个核心抽象概念。

**输入**：所有源码文件拼接成的上下文字符串。

**Prompt 策略**：
1. 将全部源码附在上下文中，每个文件标注索引编号（`--- File Index {i}: {path} ---`）
2. 要求 LLM 识别"最重要的核心抽象"，每个抽象提供：
   - `name`：简洁名称
   - `description`：约100字的新手友好描述，**必须包含类比**
   - `file_indices`：相关文件的索引编号
3. 输出格式严格约束为 YAML 列表

**验证机制**：
- YAML 解析后必须是列表
- 每项必须包含 `name`（字符串）、`description`（字符串）、`file_indices`（列表）
- 文件索引必须在有效范围内（0 到文件总数-1）
- 索引去重排序

**关键设计决策**：要求 LLM 使用类比（analogy），这是让初学者理解复杂概念的关键手段。

## 阶段2：分析关系（AnalyzeRelationships）

**目标**：理解抽象之间如何交互，生成项目全局概述。

**输入**：阶段1产出的抽象列表 + 所有相关文件的代码片段。

**Prompt 策略**：
1. 提供所有抽象的名称、描述、相关文件索引
2. 提供相关文件的代码片段（不是全部文件，只取抽象引用的文件）
3. 要求产出两部分：
   - `summary`：项目核心功能的新手友好概述（支持 Markdown 加粗/斜体）
   - `relationships`：抽象间的有向关系列表，每项含 `from_abstraction`、`to_abstraction`、`label`
4. **关键约束**：每个抽象必须至少参与一个关系（不允许孤立节点）

**验证机制**：
- YAML 解析后必须是包含 `summary`（字符串）和 `relationships`（列表）的字典
- 每个关系必须包含三个键，索引必须在有效范围
- label 必须是字符串

**输出用途**：
- `summary` 用于生成教程首页的项目介绍
- `relationships` 用于生成 Mermaid 关系图和章节间交叉引用

## 阶段3：排序章节（OrderChapters）

**目标**：确定教学顺序——先讲什么，后讲什么。

**输入**：抽象列表 + 关系数据（summary + 关系详情）。

**Prompt 策略**：
1. 提供完整的抽象列表（索引+名称）
2. 提供项目摘要和所有关系（格式化为"从X到Y: 关系标签"）
3. 要求 LLM 像教材作者一样思考排序：
   - **先基础后深入**：最重要的、最基础的概念在前（用户面向的入口点）
   - **依赖前置**：被依赖的概念在依赖它的概念之前
   - **渐进展开**：从高层概览到低层实现

**验证机制**：
- YAML 解析后必须是列表
- 索引必须在有效范围、无重复
- **完整性检查**：列表长度必须等于抽象总数（不遗漏任何抽象）

## 阶段4：逐章写作（WriteChapters）

**目标**：为每个抽象生成一章完整的教程内容。

**输入**：每个章节独立接收：抽象名称/描述、相关代码片段、完整章节目录、前后章节信息、之前已写章节的摘要。

**Prompt 策略**（最复杂的 Prompt）：
1. **上下文累积**：之前所有章节的完整内容作为 `previous_chapters_summary` 传入
2. **交叉引用**：提供完整章节目录和文件名映射，要求引用其他章节时使用 Markdown 链接
3. **前后过渡**：非首章必须链接前一章；每章结尾必须链接下一章
4. **代码块限制**：每个代码块**不超过10行**，长代码必须拆分并逐段讲解
5. **Mermaid 图表**：内部实现讲解推荐使用 sequenceDiagram（最多5个参与者）
6. **类比驱动**：大量使用类比和示例
7. **由表及里**：先讲"解决什么问题"（动机），再讲"如何使用"（API），最后讲"内部实现"（源码）

**渐进式上下文机制**：

```
第1章写作时：previous = "This is the first chapter."
  → LLM 写第1章
  → chapters_written_so_far = [第1章内容]

第2章写作时：previous = 第1章完整内容
  → LLM 写第2章（知道第1章讲了什么）
  → chapters_written_so_far = [第1章, 第2章]

第3章写作时：previous = 第1章 + "---" + 第2章完整内容
  → LLM 写第3章（知道前两章讲了什么）
  → ...
```

这种设计确保了教程的**叙事连贯性**——每一章都知道前面已经讲过什么，避免重复，做好铺垫。

## YAML 作为 LLM 输出协议

四个阶段都使用 YAML 作为结构化输出格式，而非 JSON 或自由文本。原因：

1. **可读性**：YAML 比 JSON 更适合在 Prompt 中展示示例
2. **容错性**：YAML 对尾随逗号、引号的要求比 JSON 宽松，LLM 更容易生成正确的格式
3. **Python 原生支持**：通过 `yaml.safe_load()` 直接解析

每个阶段都有严格的**格式验证**：提取 ` ```yaml ... ``` ` 代码块 → 解析 → 类型检查 → 值范围检查 → 去重/排序。验证失败时抛出异常，触发 PocketFlow 的重试机制（最多5次），给 LLM 自我纠正的机会。

## 多语言支持

多语言通过在 Prompt 中注入语言指令实现。当 `language` 不为 `"english"` 时：
- IdentifyAbstractions：要求 name 和 description 使用目标语言
- AnalyzeRelationships：要求 summary 和 label 使用目标语言
- WriteChapters：要求**全部内容**（解释、示例、技术术语、代码注释）使用目标语言
- OrderChapters：排序本身与语言无关，但输入的抽象名称可能已翻译

注意：CombineTutorial 中的固定页面结构文字（"Source Repository"、"Chapters"、"Generated by..."）保持英文，不翻译。

## LLM 缓存策略

所有四个 LLM 调用都支持 prompt 级别的缓存（通过 `llm_cache.json` 文件）：
- **缓存键**：完整的 prompt 字符串（精确匹配）
- **首次尝试使用缓存**：`use_cache and self.cur_retry == 0`
- **重试时跳过缓存**：重试时需要获取新的 LLM 响应
- **缓存粒度**：每次 LLM 调用独立缓存，相同 prompt 直接返回缓存结果

这对于开发调试非常有用——调整后一个节点的 Prompt 不会导致前序节点重复调用 LLM，节省时间和费用。

## 最终组装（CombineTutorial）

四个分析阶段完成后，CombineTutorial 做最终组装：
1. 根据关系数据生成 Mermaid flowchart TD 图
2. 生成首页 index.md（标题 + 摘要 + 源仓库链接 + 关系图 + 章节目录）
3. 为每章追加页脚归属信息
4. 写入输出目录
