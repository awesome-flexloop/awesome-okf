# 自测闭环

## 厂商基准只负责给起点

公开的 SWE-bench Pro、Terminal-Bench、FrontierCode 数字能帮你挑出两三个候选模型，但不能替你做决定（F-075）。原因有三：任务分布不同、最难任务占比不同、缓存与上下文结构不同。

博文给出的收尾动作很明确：在提交之前，把候选模型放到自己的任务上跑一遍。

## 四步流程

**第一步，抽真实任务并写结果校验。** 从待办里抽一批真实任务，为每个任务写一个可判定的结果检查：测试通过、工单关闭、行数正确等（F-075）。没有校验器的任务不适合进入对比。

**第二步，每个候选模型跑两到三个 effort 档位。** 每次跑在独立会话里，避免共享缓存污染成本数据；从响应的 usage 字段记录每个已完成任务的花费（F-075）。

**第三步，画得分-花费图。** 横轴是每完成任务成本，纵轴是通过率。只有当多模型方案在图上严格优于所有单模型点时，才保留它（F-075）。

**第四步，影子运行。** 上线前在真实流量的一小片上并行跑冠军方案，对比结果与成本，再切流（F-075）。

## 快速版：Claude Code 里的十分钟对比

不想搭完整评测时，可以先用 Claude Code 做一次粗测（F-076）：从待办里挑一个任务，用 `/model` 在两个模型上各跑一次，比较 `/usage` 报告的成本与结果。这不能替代正式评测，但足以排除明显不合适的档位。

完整可照做的步骤见 [双模型成本对比实验](../examples/01-two-model-cost-comparison.md)。

## 怎么读得分-花费图

图上有四种典型形状，对应四种决策：

1. 便宜模型在左下、贵模型在右上，且斜率平缓 → 按任务价值选点，不必上最贵。
2. 便宜模型的点被贵模型的点支配（更贵且更差）→ 直接淘汰便宜模型。
3. 两个点几乎重合 → 选便宜的那个，或选延迟更低的那个。
4. 多点构成凸包 → 只有凸包上的点值得保留，其余都是被支配的配置。

博文的经验是：多数团队最后保留两到三个点——一个高频低成本档、一个日常主力档、一个困难任务档。这与四模型矩阵天然对应。

## 常见误区

**只看平均分。** 最难任务吃掉大部分预算（F-039），平均值会掩盖长尾失败。

**共享缓存跑对比。** 第二个模型命中第一个模型的缓存，成本会虚低；必须独立会话。

**用列表价代替实测成本。** 缓存命中率、输出长度、重试次数都会改变账单，usage 字段才是证据。

**忽略延迟。** 交互路径上，用户等待时间与成本同样是约束（F-016）。

**一次定终身。** 模型与价格在变，评测集也应随业务变化更新；本文的数值快照到 2026-12-31。

## 与其他概念的关系

选型矩阵（[按任务选型](01-task-to-model.md)）给候选，任务经济学（[每完成任务成本](02-task-economics.md)）给比较口径，本节的流程给最终证据。三者缺一，选型就会退化成“看 benchmark 拍脑袋”。
