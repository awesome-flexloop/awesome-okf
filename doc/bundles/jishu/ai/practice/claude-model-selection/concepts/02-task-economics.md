# 每完成任务成本

## 单价与任务成本是两件事

更大的模型单位 token 更贵、能力更强，但“贵 token”不必然等于“贵任务”。如果大模型用更少轮数、更少返工完成任务，它的每任务成本可能低于更便宜的小模型（F-036、F-037）。

博文给了两个反直觉例子：

1. Terminal-Bench 3.0 上，Fable 5.1 在 `max` 得 58.0%，Opus 5.5 在 `high` 得 58.9%，且 token 用量减半（F-036）。
2. FrontierCode 2.0 上，Fable 5.2 在 `high` 与 Opus 5.5 在 `max` 基本持平（45.3% vs 45.5%），每任务成本约为一半（F-037）。后者已由 Fable 5.2 发布文原文确认。

实践含义：在困难任务上，先把“上一级模型的低 effort”与“下一级模型的高 effort”放在一起比，而不是按 token 单价排座次。

## 最难的任务吃掉大部分预算

成本不是均匀分布的。博文提到，某个 20 题搜索基准里，2 道题占了 43% 的开销（F-039）。这意味着平均值会严重低估真实账单：如果只按典型任务估算，长尾任务会把预算打穿。

所以比较模型时，样本里必须包含你业务中最难的那一档任务，否则结论会系统性偏向便宜模型。

## 上下文与缓存经济学

四个模型都有 1M 上下文（F-031），但上下文不是免费的：每一轮都会重发，长任务里大部分输入按缓存读取计费（F-045）。博文引用的实测是：150K 上下文时一轮缓存读取约 `$0.03`，20K 时约 `$0.004`（F-046）。

这带来两个直接策略：

1. 主模型越大，越要精简主上下文；把昂贵上下文留给决策，把冗长阅读交给便宜子代理（F-047）。
2. 长跑任务的成本主要由缓存读价与未缓存输入决定，而不是标价牌上的输入单价（F-030）。

Haiku 的分档计价在这里是双刃剑：短提示极便宜，但一旦跨过 100K，输入与输出都跳到 5 倍（F-026、F-048）。如果每次调用都需要长提示，应比较 Haiku 与 Sonnet 的每完成任务成本，而不是列表价。

## 低 effort 加失败重跑

当输出可以自动校验时，更省钱的策略不是“全部用高 effort”，而是“低 effort 全量跑，只把失败项用高 effort 重跑”。博文的实测是：同一 SWE-bench Pro 子集，通过率约 97%、`$0.17`/题；全 `high` 则是 95.3%、`$0.29`/题（F-043）。

这个策略成立的前提是“失败可自动识别”。没有校验器时，低 effort 的失败会静默通过，省下的钱会以返工和错误的形式还回去。

## effort 档位的边际收益

SWE-bench Pro 上 Opus 5.5 的档位曲线可以作为量级参考（F-041）：

| 档位 | 相对 `high` 的分数 | 相对 `high` 的成本 |
|---|---|---|
| `low` | 约低 8 分 | 约三分之一 |
| `medium` | 约低 2.5 分 | 约 70% |
| `high` | 基准 | 100% |
| `xhigh` | 约高 1.4 分 | 约 2.5 倍 |

`medium` 是明显的甜点：用七成成本换两分半的差距。`xhigh` 只在“多一分就决定成败”的任务上才划算，这也解释了博文为什么建议超过 `high` 后先试上一级模型的低档，而不是继续堆 effort（F-011）。

## 延迟也是成本

对交互式产品，用户等待时间与 token 账单一样真实。博文的建议是按“人能等多久”反推模型与 effort：人正在等的回复从 Sonnet 5.5 的 `low`/`medium` 起步（F-016）。如果确实需要同模型的更快输出，Opus 5.5 与 Fable 5.2 的 fast mode 可以用溢价换最高 2.5 倍速度（F-044），但这不该成为后台批处理的默认选择。

## 一张决策清单

1. 先写清“完成”的判定标准，能自动校验的优先自动校验。
2. 用最难的任务样本估成本，不用平均值。
3. 比较“上一级低 effort”与“下一级高 effort”，而不是单价。
4. 长上下文任务单独估算缓存读取，不只看输入单价。
5. 有校验器时采用低档全量 + 失败重跑。
6. 交互路径与后台路径分开选型。
