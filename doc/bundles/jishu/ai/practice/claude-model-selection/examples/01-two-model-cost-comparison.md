# 双模型成本对比实验

## 目标

在自己的任务上回答一个问题：**Opus 5.5 `medium` 与 Sonnet 5.5 `medium`，哪个每完成任务更划算？** 产出是一张得分-花费表和一个可复述的选型结论。

对应博文“Measure on your own work”的四步流程（F-075）。

## 前置条件

1. Claude Code 可用，且能切换 Opus 5.5 与 Sonnet 5.5（所需版本分别为 v2.1.280、v2.1.284 以上）。
2. 选 3–5 个真实任务，每个都有可自动或半自动判定的完成标准。
3. 任务难度要覆盖长尾：至少包含一个你平时觉得“最容易翻车”的任务，因为最难任务吃掉大部分预算（F-039）。

## 步骤

**1. 写任务卡。** 每个任务记录四件事：

| 字段 | 示例 |
|---|---|
| 任务 | 修复 `billing` 模块的空指针 |
| 输入 | 仓库快照 + 失败测试名 |
| 完成判定 | `pytest tests/test_billing.py` 全绿 |
| 允许动作 | 只改 `src/billing/` |

**2. 固定跑法。** 每个模型、每个任务都在独立会话里跑，避免第二个模型命中第一个模型的缓存（F-075）。提示词保持一致，只改 `/model`。

**3. 跑并记录。** 每个组合跑完，从 `/usage` 抄三件事：输入/输出 token、缓存读写 token、总成本。同时记录通过与否。

建议记录表：

| 任务 | 模型 | effort | 通过 | 成本（USD） | 轮数 | 备注 |
|---|---|---|---|---|---|---|
| T1 | Opus 5.5 | medium | 是 |  |  |  |
| T1 | Sonnet 5.5 | medium | 是 |  |  |  |

**4. 画图。** 横轴是每完成任务成本（总成本 ÷ 通过任务数），纵轴是通过率。四个点以内手画即可，不必上工具。

**5. 判读。** 按 [自测闭环](../concepts/05-measurement-loop.md) 的四种形状决策：

1. 一个点被另一个点支配 → 淘汰被支配者。
2. 两点接近 → 选便宜或低延迟者。
3. 多点构成凸包 → 只保留凸包上的配置。
4. 多模型方案只有在严格优于所有单模型点时才保留。

## 快速版

时间不够时，先做博文给的十分钟版本（F-076）：挑一个待办任务，`/model` 切到 Opus 5.5 跑一次，记 `/usage`；再切 Sonnet 5.5 跑同任务，记 `/usage`。如果 Sonnet 通过且成本明显更低，它就是这个任务类型的起点；如果它失败或反复返工，Opus 的溢价就是必要的。

## 预期产出

一份两行结论，例如：

```text
T1–T3：Sonnet 5.5 medium 3/3 通过，成本约为 Opus 的 45%，作为日常档保留。
T4（跨模块重构）：Sonnet 1/2 通过，Opus 2/2；T4 固定走 Opus medium。
```

## 常见错误

**只跑一个任务就下结论。** 单任务方差极大，至少三个，且包含一个困难任务。

**用平均成本掩盖失败。** 失败任务也要计入成本，否则便宜模型会因“没做完所以没花钱”而虚胜。

**共享缓存。** 同一会话里切模型会复用缓存，成本失真；必须独立会话。

**忘记 effort 变量。** 比较的是“模型 × effort”组合，不是模型本身；Sonnet `high` 与 Opus `medium` 才是同量级对手（F-017、F-041）。

**把厂商 benchmark 当验收。** 厂商数字只用来挑候选，最终证据必须是自己的任务（F-075）。

## 验收清单

1. 至少 3 个真实任务，含 1 个困难任务。
2. 每个组合独立会话、同一提示词。
3. 成本来自 usage 字段，不是估算。
4. 有一张得分-花费表。
5. 结论能回答“哪个任务类型用哪个档位”。
