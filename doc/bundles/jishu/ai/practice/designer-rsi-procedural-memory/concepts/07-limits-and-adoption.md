# 边界与落地：什么时候该用外部程序记忆，什么时候不该

## 本章要点

1. 论文自己列了六条边界：回放只保局部、自动评测不等于人类偏好、文本不能强制偏好、像素几何仍是瓶颈、长流程保真损失、数据治理是前提（F-098–F-103）。
2. 个性化是第三条轴，且光靠“把偏好写进技能”不够，需要偏好条件化检索与工具面约束（F-100、F-105）。
3. 这套方法适合**流程重复、可回放、失败可归因到技能**的任务；不适合**一次性、强实时、无法构造对照**的任务。
4. 落地时最该先建的不是“自动加技能”，而是**可回放的评测集与门控**。
5. 以下落地清单是工程推演，不是论文结论；论文没有给出部署方案。

## 六条边界

| # | 边界 | 论文证据 | 对实践的意味 |
|---|---|---|---|
| 1 | 回放安全不是全流量安全 | R4 低端完整度 90% vs 94%；簇外误触发（F-079、F-098） | 门控通过≠上线安全；需要灰度与线上监控 |
| 2 | 自动评测进步不等于人类偏好进步 | 同一 judge 既演化又报告；未招募用户（F-060、F-099） | 内部指标只能做回归，不可做用户价值证明 |
| 3 | 自然语言技能不能强制模型遵守偏好 | 雪花案例：写入技能后模型仍回退到默认方法（F-100） | 偏好需要检索条件化 + 工具面约束，不能只靠“写清楚” |
| 4 | 像素级几何是感知、执行、验证的共同瓶颈 | Droste 案例：数值验证能发现错位，Agent 仍不能精确放置（F-101） | 精度关键任务保留人工复核或确定性原语 |
| 5 | 长 prose skill 无法解决长程序保真损失 | 数百步完整图案只保住大致布局（F-102） | 超长流程应拆成单元块，或改用宏/计划级编排 |
| 6 | 数据治理是生产部署前提 | 演化数据来自既有产品流量；组织治理与访问控制（F-103） | 先有数据分级、脱敏、权限、审计，再谈自动演化 |

## 个性化：第三条轴

论文把个性化单列，并给出三种失败模式（F-105）：

| 模式 | 案例 | 为什么技能不够 | 需要什么 |
|---|---|---|---|
| 方法偏好 | 用户要“分层噪点+模糊+阈值”做雪，模型却用粒子场 | 模型认为自己“已经会”，回退到默认实现 | 偏好条件化检索 + 禁用默认捷径的工具面 |
| 感知与精度 | Droste 画中画的内框对齐 | VLM 看不见细几何错误，文本技能不改变感知 | 数值验证 + 确定性放置原语 + 人工兜底 |
| 复杂手绘目标 | 完整几何拼贴图案 | 标注、蒸馏、执行三处都泄漏保真度 | 确定性宏、计划级编排，或更新模型 |

这三类失败共同说明：**程序记忆擅长“短小、自包含、可复用”的流程**，不擅长“精确几何、超长构造、默认偏好覆盖”。

## 适用性判据

### 适合

| 判据 | 说明 |
|---|---|
| 流程重复 | 同一类子任务反复出现，缺口值得铸造技能 |
| 可回放 | 能冻结输入、资产与上下文，构造双臂对照 |
| 失败可归因 | 能记录“这一轮检索了哪些技能”，否则无法归因 |
| 有稳定评测 | 至少有可重复的自动判分，哪怕不完美 |
| 短流程为主 | 单技能 5–10 个工具步骤，模型能可靠跟随 |
| 允许离线演化 | 不需要在线即时更新技能库 |

### 不适合

| 判据 | 说明 |
|---|---|
| 一次性任务 | 缺口不会复发，铸造不划算 |
| 强实时 | 离线回放与评分成本无法接受 |
| 无法构造对照 | 没有稳定输入或无法成对比较，门控失效 |
| 精度关键且无人工 | 像素级/数值级精度仍需确定性原语 |
| 超长确定性流程 | 自然语言技能会逐步偏离，应改用代码或宏 |
| 数据不可治理 | 用户数据无法脱敏/授权，不能进入演化 |

## 落地检查表（工程推演，非论文结论）

### A. 先建评测，不先建演化

- [ ] 固定一个与演化数据不相交的 held-out 集，并锁定版本。
- [ ] 定义成功判定（超时、无效产物、崩溃都算失败）。
- [ ] 把质量分与成功率分开存储，禁止合成一个“准确率”。
- [ ] 为 judge 做漂移测试：同一批图重复评分，记录方差。
- [ ] 至少准备一个跨家族 judge 作为抽查后端。

### B. 技能库最小规范

- [ ] 一个技能一个文件，文件名等于技能名。
- [ ] `description` 只写触发短语与操作词，200–600 字符。
- [ ] `tool_sequence` 控制在 5–10 步；超长流程拆成多个技能。
- [ ] 正文五节齐全，尤其要有 error handling 表。
- [ ] 统计、版本、失败计数放在外部 store，不写进技能文件。

### C. 检索与注入

- [ ] 先把 brief 蒸馏成操作词，明确忽略主体/地点/品牌/形容词/颜色。
- [ ] 用与冷启动相同的 tokenizer 做排序，保证“写作—路由”一致。
- [ ] 只把 catalog 放系统提示，全文走按需加载。
- [ ] 记录每轮“检索了哪些技能”，否则失败无法归因。
- [ ] 把“无技能命中”记为覆盖缺口，而不是静默返回空。

### D. 演化循环

- [ ] 缺口需复发 N 次再铸造；N 从 3 起，按流量调整。
- [ ] 失败阈值与修订阈值分开配置（论文为 0.6 与 2）。
- [ ] 每轮修订数量设上限，避免一次性大改。
- [ ] Reflector 必须同时拿到成功轨迹与失败理由。
- [ ] 先定向编辑，连续失败再整体重写。
- [ ] 修不好的记录回流缺口池，不要直接丢弃。

### E. 门控

- [ ] 同一批、同上下文、双臂重放；禁止跨批比较。
- [ ] 重写回放同时覆盖高分与低分轨迹。
- [ ] 成对判定并随机交换顺序。
- [ ] 逐 prompt 多数获胜，再做“无退化 + 至少一改进”的总体判定。
- [ ] 设置平局带，全部打平拒绝。
- [ ] 拒绝也留档：提案、before/after、拒绝原因。

### F. 治理与上线

- [ ] 用户数据分级、脱敏、访问控制、保留期限。
- [ ] 技能库变更可审计、可回滚、可灰度。
- [ ] 线上监控“簇外误触发”：新技能上线后看邻近意图的失败率。
- [ ] 精度关键环节保留人工复核。
- [ ] 对外表述避免“模型自我进化”“全面提升”等过度承诺。

## 最小可行闭环（推演）

若要从零验证这套思路，建议先做一条**单应用、单技能类型**的窄闭环：

```mermaid
flowchart LR
    A["固定 200 条历史 brief"] --> B["人工标注 20 条要求"]
    B --> C["无技能基线"]
    C --> D["跑 1 轮：只做 Deepening"]
    D --> E["4 条回放：2 高 2 低"]
    E --> F["门控"]
    F --> G["上线 1 个版本"]
    G --> H["held-out 复测"]
    H --> I{"低端是否退化？"}
    I -- "是" --> J["回滚并查误触发"]
    I -- "否" --> K["再开 Widening"]
```

理由：

1. Deepening 比 Widening 更容易验证——它有明确的旧版对照。
2. 单应用可以避免跨应用检索干扰。
3. 4 条回放成本低，足以暴露“修好失败、破坏成功”的典型问题。
4. 先验证门控，再验证“自动加技能”，风险更低。

## 仍未解决的问题

| 问题 | 现状 | 可验证方向 |
|---|---|---|
| 词重叠检索能否处理同义改写 | 论文未量化 | 在自有语料上测 recall@k 与误触发率 |
| 新技能上线的簇外影响 | 只有 R4 的间接证据 | 上线后监控邻近意图失败率 |
| 人类偏好是否同步提升 | 未做用户研究 | 小规模盲评，与自动分对照 |
| 超长流程如何保真 | 论文建议宏/计划级编排 | 单元块 + 确定性原语组合 |
| 跨领域迁移 | 仅图形设计 | 先在流程化强的领域试点（如报表、批处理） |

## 常见误读

| 误读 | 纠正 |
|---|---|
| “这套方法可以自动让 Agent 变强” | 只在特定任务、特定评测下有效；边界由论文自述（F-098–F-103） |
| “技能写清楚，模型就会照做” | 强默认偏好会覆盖文本；需检索条件化与工具约束（F-100） |
| “回放通过就能全量上线” | 只保证回放集内不退化（F-059） |
| “美学也会跟着提升” | 美学基本不变（F-096） |
