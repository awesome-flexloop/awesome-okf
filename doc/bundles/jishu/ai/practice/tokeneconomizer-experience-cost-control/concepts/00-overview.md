# 速览：经验驱动的黑盒成本控制

> **⚠️ 先读这一条**：论文里的 TokenEconomizer 是**三条元策略全开的实验控制器**；开源插件默认只开两条（micro-skills 默认关闭），且从不自行停止卡住的 turn（F-096、F-100、F-110）。装上插件并沿用默认值，**并不等于**复现了 18.4–30.9% 的结果。逐项差异见 [参数分账台账](../references/parameter-ledger.md) 与 [核验报告 D-3](../references/verification.md)。

## 性质声明

本束是**机制解读 + 官方文档转述型教程**，不是源码精读，也不是实测报告。事实基础为微软研究院博客（2026-11-16，F-001）、arXiv:2610.22732v1 全文（2026-10-15，F-002~F-004）、项目页与 `microsoft/TokenEconomizer` README 四个信源（F-014）。本环境未安装插件、未运行 `experiments/` harness；所有安装与配置步骤均标注为「官方文档转述，未实测」。

## 一句话结论

TokenEconomizer 把「降低 token 成本」从**单任务内的压缩**改写成**跨任务的策略学习**：在每个仓库里读已完成会话的轨迹，更新三套策略（注入哪些事实、加载哪些工具、何时打断卡住的 turn），再只通过 agent 已经暴露的三个接口施加控制，不改模型、不改 agent 代码（F-041、F-042、F-045）。

## 为什么值得读

多数降本手段按「单个任务」评估，而开发者是在**同一个代码库里日复一日**用 agent（F-015、F-016）。论文的核心提问是：仓库里的历史经验能不能让后续任务更省？三条可复用的观察（详见 [成本剖析](01-cost-profiling.md)）是：

| 观察 | 数字 | 对应元策略 |
|---|---|---|
| 事实被反复重新发现 | 仓库积累 ≥5 个任务后 30% 工具调用重复本仓早期动作；跨仓对照仅 7% | 微技能注入 |
| 为用不上的工具付费 | 每轮展示 23 个工具 schema，16 个从未被调用 | 工具剪枝 |
| 卡在失败上 | 17% 的失败任务占 32% 花费 | 失败循环干预 |

对应事实：F-018、F-019、F-022、F-023、F-026。

## 三条元策略速查

| 元策略 | 作用面 | 触发时机 | 可逆性 |
|---|---|---|---|
| 微技能注入 | 指令前缀（知识） | 任务之间 | 事实被后续证据反驳即永久退休（F-057） |
| 工具剪枝 | 已加载工具集（接口） | 每个任务之前 | 每 5 个任务全目录复审；手动 `toolprune restore`（F-063、F-101） |
| 失败循环干预 | 实时 rollout（控制） | 轨迹运行期间 | 先 redirect，再由人决定是否停止（插件侧，F-100） |

四条设计原则（仓库 README「How it works」）：**走 agent 已经读的接口**、**按实际计费口径算成本**、**保护任务成功率**、**每个动作可撤销**。

## 三条核心洞察（I 阶段）

1. **陈述**：成本控制的对象是「环境」而不是「任务」。证据：F-018/F-019 的 30% vs 7%、F-031~F-038 的逐仓反转。反常识：把「更省 token」当成模型或提示词的属性，会忽略同一手段在不同仓库效果相反。行动：先按仓库分组记录成本，再决定策略。
2. **陈述**：省得多不等于砍得狠。证据：F-082（降推理强度 Pass@1 掉 1.8–10.3 点）与 F-084（TE 在 30/30 cell 降本）。反常识：最直接的省钱办法是降低推理强度，但那是以质量为代价。行动：把「质量不低于默认」写成约束，而不是事后检查。
3. **陈述**：可逆性比正确性更关键。证据：F-057、F-063、F-106、F-072。反常识：三条元策略都会误判，论文不追求零误判，而是给每个误判配恢复路径。行动：任何由历史数据驱动的削减动作，都要同时设计反证通道与恢复路径。
