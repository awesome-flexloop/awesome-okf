# 成本剖析：三类可回收浪费与固定策略的反证

## 账是怎么被反复记的

每一轮 agent 请求都要重新付三样东西的费用：系统指令、全部已加载工具的描述、截至当前的会话历史（F-015）。仓库 README 补了一句很关键的话：**session 里大部分 token 是缓存重读**，所以成本必须按缓存计价口径算，否则会把省下来的钱算错（F-049）。

剖析实验在未修改的 Claude Code 上跑 60 个 SWE-Bench 任务，6 个仓库各 10 个，按仓库内顺序执行（F-016、F-017）。

## 浪费一：事实被反复重新发现

| 指标 | 数值 | 事实编号 |
|---|---|---|
| 仓库已有 ≥5 个任务后，重复本仓早期动作的工具调用占比 | 30% | F-018 |
| 与其他仓库完整历史对照的匹配率 | 7% | F-019 |
| 重复率变化 | 第 2、3 个任务 14% → ≥5 个前置任务后 30% | F-020 |
| 在至少半数任务中复现的动作，占工具调用收发字节 | 12–28% | F-021 |

30% 与 7% 的落差是整套方法的起点：**可复用的经验是仓库专属的**，不是通用编程常识。典型例子（仓库 README）：这个仓库要用 `python -m pytest` 而不是 `pytest`、要用 `npx tsc` 而不是 `tsc`、某条命令需要先设环境变量、生成文件落在哪个目录。跨仓匹配的那 7% 主要是通用 setup 与测试命令。

## 浪费二：为用不上的工具付费

| 指标 | 数值 | 事实编号 |
|---|---|---|
| 每轮展示的 tool schema 数 | 23 | F-022 |
| 从未被调用的工具数 | 16 | F-023 |
| 单个仓库最多调用的工具数 | 7 | F-024 |
| 占全部调用 98% 的工具数 | 3 | F-025 |

工具描述随每一轮请求一起发送，因此一个从不调用的工具是**按轮数重复计费**的。论文由此指出：固定地削减接口能去掉共同开销，但也会误伤某个仓库恰好需要的工具，所以剪枝必须有证据、且能恢复（F-060、F-063）。

## 浪费三：卡在失败上

| 指标 | 数值 | 事实编号 |
|---|---|---|
| 失败执行数 / 任务占比 | 10 次 / 17% | F-026 |
| 失败执行占总花费 | 32% | F-026 |
| Matplotlib 失败 vs 成功轮数 | 45 vs 20 | F-027 |
| Sphinx 失败 vs 成功轮数 | 36 vs 31 | F-027 |
| 重复更早失败签名的轨迹数 | 45 | F-028 |
| 首次重复之后发生的花费占比 | 51% | F-028 |
| 成功轨迹中也重复签名的比例 | 36 / 50 | F-029 |

这一组数字最容易被误读。**简单的全局轮数上限行不通**：Matplotlib 失败轨迹明显更长，Sphinx 失败轨迹只比成功长一点（F-027）。**重复也不等于失败**：50 条成功轨迹里有 36 条同样重复了失败签名，且重复后花费中超过一半来自最终成功的运行（F-029）。所以守卫需要两样东西：与「本仓库成功轨迹的轮数分布」比较得到的预算，以及一个能区分「还在推进」和「真卡住」的 judge。这正是 [失败循环干预](05-failure-loop.md) 的设计。

## 固定策略为什么不够

论文用同一套配置在 6 个仓库上比较三种流行的开源降本插件（F-030）：

- **RTK**：把 shell 命令输出压缩后再交给 agent，工具与提示词不变。
- **Serena**：基于 language server 的 MCP 服务，增加符号级导航工具，并要求 agent 优先使用它们。
- **RepoMap**：Aider 的仓库地图，把按中心度排序的符号签名（上限 2,048 token）加进指令，每轮计费。

逐仓库成本变化（论文表 6，相对默认；负数表示更省）：

| 仓库 | 默认 Pass@1 | RTK | Serena | RepoMap |
|---|---|---|---|---|
| sklearn | 10/10 | −6.9% | +28.6% | +30.5% |
| SymPy | 10/10 | +7.3% | +30.8% | +9.8% |
| Django | 9/10 | −19.9% | −15.4% | −16.2% |
| Sphinx | 6/10 | +0.6% | +2.1% | −7.5% |
| Matplotlib | 8/10 | −4.9% | −4.8% | +5.0% |
| xarray | 7/10 | −16.8% | +4.7% | −20.2% |

事实编号 F-033 ~ F-038。读法：三者都在 Django 降本、都在 SymPy 升本；scikit-learn 只有 RTK 有效，Sphinx 只有 RepoMap 有效（F-031、F-032）。**没有任何一个固定策略在所有仓库都更便宜**。Serena 在主比较中被排除，因为工具剪枝可能移除它未被使用的 server 而混淆对照，且它是剖析中唯一抬高合并成本的固定策略（F-039）。

## 从观察到设计

论文把三条观察直接映射成三个「自适应决策」，并给了三个术语（F-040）：

| 术语 | 含义 |
|---|---|
| meta-strategy（元策略） | 三条环境无关的过程 |
| policy（策略） | 元策略在某环境中学到的具体决策 |
| fixed strategy（固定策略） | 所有环境套用同一配置 |

对应关系：重复事实 → 决定注入哪些 micro-skills；未用工具 → 决定剪掉哪些工具；失败循环 → 决定何时干预。三者都在每个环境内单独学习策略，而不是全局共用一套配置。

> **洞察**：这里的因果方向容易被讲反。不是「先有三种降本技巧，再去找浪费」，而是先从 60 条轨迹里量出三类可回收成本，再为每一类配一个「可学习、可撤销」的决策过程。这也是 [可迁移模式](08-transferable-pattern.md) 的第一步。
