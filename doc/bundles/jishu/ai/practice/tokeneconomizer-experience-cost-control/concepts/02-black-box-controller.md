# 黑盒外部控制器：状态、三接口与成本口径

## 「黑盒」的精确含义

TokenEconomizer 把 agent 当黑盒：**不改模型权重、不改 agent-loop 代码**（F-041），只通过 harness 已经暴露的三个接口作用（F-042）：

1. **instruction prefix（指令前缀）** —— 在会话开始时加入已激活的 micro-skills；
2. **loaded tools（已加载工具集）** —— 通过 agent 自己的设置文件屏蔽工具；
3. **live event stream（实时事件流）** —— 在轨迹运行中观察工具调用与失败，写入 redirect。

项目页把三条元策略按作用面分成知识 / 接口 / 控制三类，分别对应「任务之间」「任务之前」「rollout 期间」三个时机。这个划分很重要：它解释了为什么三条策略的节省能叠加——它们作用在账单的不同位置，而不是抢同一块 token。

## 优化单元：任务流

优化单元不是单个任务，而是**同一环境内按时间排序的任务序列** τ₁ … τₙ（F-043）。默认执行下，任务 τᵢ 在系统指令 + 任务描述构成的前缀下运行，且加载工具目录里的全部工具。

控制器在每个任务前读取由此前已完成任务蒸馏出的仓库状态 S_{i−1}，产出三个策略量（F-044、F-046）：

```
(ΔP_i, 𝒰_i, B_i) = 𝒞(τ_i, S_{i-1})
```

| 符号 | 含义 |
|---|---|
| ΔPᵢ | 本任务激活的 micro-skills（注入指令前缀的部分） |
| 𝒰ᵢ | 本任务加载的工具集合 |
| Bᵢ | 校准失败循环守卫的轮次预算 |

任务完成后，完成的轨迹 ξᵢ 更新三条元策略，得到下一任务使用的状态 S_{i+1}（F-045）。控制器**可以始终保留默认配置不动作**（F-047）；它自身的模型调用计入触发该调用的任务（F-048），所以「省下的钱」里已经扣掉了控制器开销。

## 四条设计原则

仓库 README「How it works」给出四条原则，可当作评审任何类似控制器的检查表：

| 原则 | 具体做法 | 对应事实 |
|---|---|---|
| 走 agent 已经读的接口 | 事实在会话起始进上下文，工具通过 agent 自身设置移除，不要求 agent 学新工具 | F-042 |
| 按实际计费口径算成本 | 缓存重读占大头，按缓存定价计算，并计入插件自身模型调用 | F-049、F-099 |
| 保护任务成功 | 事实只在重复证据后成立，工具只在长期未用后移除，守卫不打扰仍在推进的 turn | F-053、F-061、F-067 |
| 每个动作可撤销 | 事实被反驳即退休，工具可归还，守卫只 redirect 并把「是否停止」交给人 | F-057、F-063、F-100 |

## 成本口径：为什么不能只看 token 数

附录 E 的式 (4)(5) 定义 cache-aware cost（F-049）：把未缓存输入 token、缓存输入 token、输出 token 按各自权重相加，再叠加控制器自身调用产生的辅助成本 Hᵢ；一个仓库的平均成本是任务流上 C_eff 的均值。

这一步的方法论意义大于公式本身：

- **缓存重读是主要成本**，把「省了多少 token」当成「省了多少钱」会失真；
- **控制器自己的开销必须记账**，否则一个「每轮都调 judge」的控制器能报出漂亮但虚假的节省；
- 论文博客与项目页都明确写了「Reported savings also account for the cost of TokenEconomizer's own model calls」（F-048、F-099）。

优化目标式 (6) 把质量写成约束而不是目标函数的一部分（F-050）：最小化期望平均成本，约束为期望质量不低于默认配置减 ε。这解释了 [结果页](06-results-and-ablations.md) 里「降推理强度省得更多却被排除」的判据——它违反了质量约束。

## 三条元策略的状态流转

```
        ┌────────────── 已完成轨迹 ξᵢ ──────────────┐
        │                                          │
        ▼                                          │
   S_{i-1} ──C──> (ΔP_i, 𝒰_i, B_i) ──> 任务 τᵢ ────┘──> S_{i+1}
                      │        │        │
                 微技能注入  工具剪枝  失败循环干预
                 (任务之间) (任务之前) (rollout 期间)
```

一个容易忽略的细节：三套策略**按仓库分别学习、按 agent 分别维护**（仓库 README「What it does on each agent」：facts、tool evidence、loop guard 对「通常一轮多长」的感觉都是 per agent + per repository，只有 settings 是共享的）。换句话说，同一个开发者在 A 仓库学到的「怎么跑测试」不会被带到 B 仓库——这与 F-018/F-019 的 30% vs 7% 观察一致。

## 与「给模型加记忆」的区别

| 维度 | 常见「记忆 / 技能库」做法 | TokenEconomizer |
|---|---|---|
| 写入对象 | 向量库 / 技能文件 | 三个策略量（注入事实、工具集、轮次预算） |
| 作用时机 | 检索后塞进上下文 | 任务前改配置 + 运行中干预 |
| 是否需要 agent 配合 | 常需要新工具或新调用 | 只用既有接口（F-042） |
| 目标 | 提升任务成功率 | 在质量约束下降低成本（F-050） |
| 错误代价处理 | 多为人工清理 | 每条策略自带反证与恢复（F-057、F-063、F-106） |

> **读法提示**：把 TokenEconomizer 读成「一个更聪明的提示词压缩器」会丢掉一半内容。它同时改了**上下文、接口、停止策略**三处，成本收益也来自这三处叠加（F-088 显示没有任何单策略能达到全栈效果）。
