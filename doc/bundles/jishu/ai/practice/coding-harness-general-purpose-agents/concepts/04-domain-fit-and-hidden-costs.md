# 领域适配与隐性成本：编码偏向、Token 与评测

> 文章给了两句很重的提醒：这些运行时为软件开发设计，系统提示与内置工具会把 agent 往“写代码、跑代码”上带；同时 coding-agent loop 可能消耗大量 token（F-020、F-023）。把 harness 用到文档处理、运营支持或迁移规划时，这两句话就是主要风险。

## 1. 三类偏差

### 1.1 提示偏差

Coding harness 的系统提示通常包含大量软件工程约定：先读文件、再改代码、跑测试、检查 diff、提交。对编码任务是优势，对非编码任务可能是噪声。

表现。

1. 明明只需要提取字段，agent 却想写脚本。
2. 明明只需要回答，agent 却要创建文件。
3. 明明只需要一次调用，agent 却进入多轮“检查—修复”循环。

应对：在系统提示或项目指令里明确“这是非编码任务”“禁止写文件”“输出必须符合某个 schema”（F-021）。

### 1.2 工具偏差

编码 harness 的内置工具以文件系统、shell、搜索为主（F-038）。对文档处理、运营支持来说，真正需要的可能是业务 API、数据库查询、工单系统、邮件与表格工具。

表现。

1. 工具列表里没有业务系统，agent 只能绕道 shell 或文件。
2. 内置工具权限过宽，增加了误操作面。
3. 团队为了“能用”，把业务 API 包成脚本，反而增加了维护成本。

应对：做工具面收敛——只暴露任务需要的最小工具集，业务能力通过 MCP 或自定义工具接入（F-038）。

### 1.3 评测偏差

Coding harness 的默认质量信号来自代码任务：测试通过、编译成功、diff 合理。非编码任务没有这么干净的信号。

表现。

1. 文档抽取“看起来对”，但字段漏了、格式错了。
2. 运营回复“语气不错”，但承诺了不该承诺的事。
3. 迁移方案“结构完整”，但漏了关键依赖。

应对：建立领域评测集，不要用“感觉不错”代替验收（F-030、F-033）。

## 2. 四类成本

### 2.1 Token 成本

Coding-agent loop 的特点是轮数多、工具输出多、上下文长（F-023）。一次任务可能包含：读文件、搜索、执行、检查、修复、再检查。每一轮都要把系统提示、工具定义、历史记录重新发一遍。

成本放大项。

1. 大型内置提示，每轮都在（F-024）。
2. 工具输出冗长，尤其是日志与文件内容。
3. 子代理并行，成倍增加调用。
4. 失败重试，重复消耗。
5. 上下文压缩本身也要调用模型。

### 2.2 延迟成本

多轮 loop 意味着用户等待时间变长。对交互式场景，延迟可能比 token 更早成为问题。

应对。

1. 把长任务放到后台队列，前端只展示进度。
2. 对短任务设置最大轮数与超时。
3. 用流式事件让用户看到进展，而不是干等。

### 2.3 运维成本

会话持久化、沙箱、审批、日志、凭证管理，都是采用 harness 后才出现的运维面（F-012、F-017、F-045）。

应对。

1. 把运行时当生产基础设施，而不是开发工具。
2. 会话存储、日志、审计从一开始就设计。
3. 给 agent 定义版本，随代码一起管理。

### 2.4 组织成本

审批流、权限申请、安全评审、技能维护，都会带来组织协调成本。

应对。

1. 先选一个低风险场景做试点。
2. 用企业级 harness 层统一技能、工具与策略（F-032）。
3. 把“哪些事 agent 可以做”写成明确清单，而不是靠口头约定。

## 3. 领域适配的六层清单

| 层 | 要做什么 | 验收信号 |
|---|---|---|
| 提示层 | 明确任务性质、禁止行为、输出格式 | 不再出现“写脚本解决一切” |
| 工具层 | 只暴露必要工具，业务能力用 MCP/自定义工具 | 工具调用路径最短 |
| 数据层 | 定义输入输出 schema、字段校验、脱敏 | 结构化输出可解析 |
| 评测层 | 建立领域样例集与评分规则 | 每次改动可回归 |
| 成本层 | 设 token/轮数/时长预算与告警 | 单任务成本可预测 |
| 运维层 | 沙箱、审批、日志、回滚 | 出问题可定位、可止损 |

## 4. 评测怎么做

Thoughtworks 的 Harness quality evaluation 给了一个可操作的拆分（F-030、F-033）。

1. **非确定性部分**：技能、提示、插件、子代理行为，用 PluginEval 一类工具评估。
2. **确定性部分**：护栏、校验器、权限规则，用 redproof 一类测试套件做 TDD 式验证。
3. **节奏**：夜间或 CI 定期跑，不要等上线前才测。

对通用任务，评测集至少覆盖。

1. 正常样本：任务能完成，输出符合 schema。
2. 边界样本：空输入、超长输入、缺字段、多语言。
3. 对抗样本：提示注入、恶意指令、越权请求。
4. 失败样本：工具超时、权限拒绝、模型拒答。
5. 成本样本：记录每个样本的 token、轮数、时长。

## 5. 什么时候应该换回 Framework

出现以下信号，说明 coding harness 可能不是最优解。

1. 任务流程高度确定，agent 的“自主决策”反而是风险。
2. 单任务成本被内置提示与多轮 loop 推高到不可接受。
3. 业务系统集成复杂，harness 的工具模型反而增加胶水代码。
4. 需要深度定制记忆、调度、多人协作或审计协议。
5. 组织要求运行时完全自主可控，不能依赖单一厂商。

这时候，agent framework 或直接编排更合适（F-014）。

## 6. 一个低成本试点方案

1. 选一个“有明确输入输出、失败可回滚”的任务，例如文档字段抽取。
2. 用最小 harness 跑通，只开必要工具。
3. 建 20～50 条评测样例，记录准确率、token、时长。
4. 加一层 schema 校验与人工抽检。
5. 连续跑两周，比较“harness 方案”与“人工/脚本方案”的总成本。
6. 再决定是否扩展到更高风险场景。

## 7. 小结

Coding harness 的领域适配，不是改一句提示词，而是把**提示、工具、数据、评测、成本、运维**六层都补齐。编码偏向可以通过提示与工具面收敛解决；token 成本要通过预算、熔断与后台化控制；质量要靠领域评测集，而不是编码任务的测试通过率。下一篇给出完整采用路径。
