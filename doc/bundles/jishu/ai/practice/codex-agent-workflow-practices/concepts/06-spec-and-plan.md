# Spec 与 Plan 工程：需求成型与任务切分的系统化方法

## Spec 写什么

### 核心目标

不是事无巨细（最翔实的 spec 只能是代码本身 [F-027](../article-source.md#F-027)），而是：

1. **把人需要逐字看的关键信息写出来**：high level code review 做多了发现，很多 review 应该前置到 spec 环节，大大提升 MR 接受率
2. **对 agent 做长期任务有帮助的关键信息**：即使反复做 auto compaction 也不会迷路

### Spec 六段结构

| 段落 | 内容 | 作用 |
|------|------|------|
| 背景信息 | 代码中无法体现的外界条件、设计原因 | 防止 agent 迷路 |
| User Story | 需要 review 的核心流程 | 定义"完成"的标准 |
| 解决方案 | 设计方向的重要决策记录 | 约束 agent 设计空间 |
| 测试验收 | 覆盖范围 + 什么是"完成" | 质量门禁 |
| Out of Scope | 本次不做什么 | **防止 scope 膨胀的关键利器** |
| Open Questions | agent 的感想与疑问空间 | 保留 agent 自主性 |

## Spec 怎么写：从多采样对抗到对话式 Plan Mode

### 尝试一：多采样对抗（效果不佳）

最初想法：3 个独立 agent 用不同思路（极简方案、可维护性、创新等）生成不同方案文档，再由 agent 选择综合，进入 spec review + 优化循环 [作者实践]。

**问题**：写出来的 spec 经常与设想对不上。

**原因分析**：

1. **功能设计探索空间太大**：即使是用户登录这种简单功能，背后选择方式也很多，选择路径扩展成巨大决策树，随机探索选中想要的结果无异于买彩票 [作者洞察]
2. **关键决策信息输入是恒定量的**：打造想要的产品形态，需要恒定量的"关键决策信息输入"，不能让模型自我对抗补上 [作者第一性原理分析]
3. **Context 信息充分性影响探索空间**：会议记录、客户拜访、群聊、系统设计等背景信息越充分，agent 探索空间越收敛 [作者观点]

### 成功方案：对话式 Plan Mode

受到产品 plan mode、`/grill-me` skill 启发，采用以下方式 [作者实践]：

```
用户提出"一句话需求"
  → Agent 探索代码库，提出需要决策的问题
  → 每次只提一个问题（前一个问题的选择影响后续）
  → 用户回答
  → 循环直至收敛
  → 基于对话 context 生成 spec 文档
```

**优势**：

- 比起全手写 spec，负担减轻，聚焦在重要决策上
- 比起 agent 先生成 spec 来 review，更能找到真正想要的最优解
- 是一个很好的学习理解过程，体会到对代码项目保持 high level 理解的感觉 [作者感受]

**细致程度因任务类型而异**：

- 模型熟悉的场景（如登录）：需输入的关键决策较少
- 罕见场景（如 agent 产品）：需要更细节的决策指引，否则模型可能写一堆正则表达式来实现设想的"智能场景" [作者实践教训]

## 三段式工作节奏

| 阶段 | 模式 | 人类参与度 |
|------|------|----------|
| 需求探讨和设计 | 同步 | 高——与 agent 持续对话，保持专注 |
| 需求成型后的执行 | 异步 | 低——可有 1 小时以上不需要关注 |
| 最终验收（尤其真实产品体验） | 同步 | 高——切回关注模式 |

> 上一篇文章中追求"一次性让 agent 烧几十分钟 token 再介入"的纯异步方式，想明白"任务中需要投入的决策量是恒定的"之后，转变为三段式 [作者认知演进]。

## 任务切分：垂直切片策略

### 水平切片 vs 垂直切片

| 方式 | 示例 | 问题 |
|------|------|------|
| 水平切片 | 先写 DB 层 → 再写 service 层 → 最后写 API 层 | 反馈迭代速度慢，需等三个任务都完成才能验证 |
| **垂直切片** | 按功能拆分，每个任务交付可端到端验证的功能 | 反馈快，可独立合并 |

### 垂直切片的三个好处

1. **天然引入 feature flag**：未完成功能默认隐藏 [F-019](../article-source.md#F-019)
2. **控制改动量**：每个任务 ≤ 500 行 [F-016](../article-source.md#F-016)
   - 加快反馈迭代速度
   - 先写出功能子集快速验证方案可行性
   - 人类最终 review 时 500 行是舒服的量级
3. **便于独立合并与回滚**：小步快跑，问题定位归因更友好

### Plan 文档

最终形成 plan 文档供 agent 开发：

- Agent 持续更新 plan，描述进度
- 可加入步骤依赖关系，让 agent 自行判断并行环节
- 即使多次 compact 后也不迷失方向 [作者实践]

## 开发自闭环：Execute-Plan Skill

### 核心思路

让 agent 基于 plan 文档自我闭环执行，闭环范围尽可能大 [作者观点]。

### Execute-Plan Skill 流程链

```
tdd → review-change-loop → test-fix-loop → doc-update → create-mr → babysit-mr
```

### 两个关键注意点

1. **隔离 context**：review 和 test 时需要隔离 context 才能达到最佳效果 [作者实践]
2. **证据强制输出**：对指令遵循不够强的模型，必须让它把问题排查、测试验收的证据贴出来，不只口头说已完成 [作者经验]

### 随 agent 能力提升的动态调整

随着 agent 能力增强，需要不断思考：

- 如何提升人类注意力的层级
- 如何让 agent 自闭环范围扩大

> 提及 slock.ai 作为进一步激发 agent 自我管理、集体驱动开发的方式，但碰到与 spec 生成类似的困境——当 agent 能力固定且 context 不变时，很难通过多 agent 多轮交互找到符合预期的 spec [作者尝试与局限]。

## 长程任务推进

有了 feature spec + 可自我闭环的 agent + 垂直切片 plan 后，可以让 agent 自主完成多个子任务：

- 过程基本全程无人值守 [作者实践]
- 关键依赖：Codex + gpt-5.5 的自动压缩功能 [F-015](../article-source.md#F-015)
- 持久化存储记录重要信息（spec/plan 提交到 git，每完成一个 slice 创建独立 MR）
