# 把漏检变成规则，并定期清理规则

## 两条规则化路径

在 Claude Code 仓库里，漏检被转成规则有两条互不替代的路径（F-063—F-066）。

### 路径一：从人的评论与 revert 里抽模式

1. 扫描人工 code review 评论与 PR revert，找出反复出现的问题；
2. 入选门槛有三条：必须在**至少两个 PR** 出现、必须**能从 diff 识别**（F-063）；
3. 候选规则交给 **3 个 agent 试图证伪**（F-064）；
4. 最后由**人在 PR 中评审批准**才生效。

「至少两个 PR」防的是把偶发个例写成全局规则；「能从 diff 识别」保证规则可执行；「三 agent 证伪」是对抗性审查；「人工批准」把最终判断留给人——四步合起来，正好是 [验证循环四要素](00-verification-loops.md) 中「规则回流」的严谨版本。

### 路径二：对已知事故做重放

对关联已知事故的 PR，重放 **3 个 bug finder**（F-065）：若至少 2 个找到该 bug，判为「**可检测 bug**」；若在**小 diff** 上仍被漏掉，这个 gap 就值得写进 `REVIEW.md`（F-066）。

这条路径的判据很讲究：先用多数投票界定「本来就该抓到」，再看 diff 规模——小 diff 上漏掉，说明是注意力/规则问题而非信息过载，才值得固化成规则。这避免了把复杂改动里的正常失误误判为规则缺口。

## flaky 测试与规则清理

**flaky 测试同等待遇**（F-067、F-068）：Agent 不许跳过它、不许加 sleep 或重试到通过；找不到根因就**删除该测试并写下原因**。这与 [三类测试](01-three-test-types.md) 里「flaky 会训练 Agent 重跑而非修代码」形成闭环——不允许用绕过手段把噪声留在信号链里。

最后一条最容易被忽略：**规则也需要清理**（F-069）。测试套件、验证步骤、`.md` 文件只增不减，所以团队例行整理。否则 [门禁治理](04-gate-governance.md) 里「修剪教训让它们值得跑」就只是一句口号。规则库与代码库一样会熵增，且它的熵增更隐蔽——每条规则单看都有来历，合起来却拖慢每一次验证。

## 全局结论：人的工作重新定义

当验证层被当作系统治理之后，人的职责从「读每一个 diff」转为「**定义『done』长什么样 + 审阅证据**」（F-071）。这恰好回到本束起点：只有完成条件被搬进软件、证据可被快速审阅，并行跑很多 Claude 才成为可能（F-004）。

## 可迁移模式总表

| 模式 | 触发场景 | 核心步骤 | 反模式 | 迁移验证 |
|---|---|---|---|---|
| 验证循环四要素 | 准备并行委派 | 信号→证据→迭代→规则回流 | 自评自审、flaky 信号 | 换框架仍四步齐全 |
| 三类测试选型 | 挑验证物 | 治 flaky/慢/重 → 按用户流/不变式/旧系统选 | 只堆单测 | 三判据至少保留一条 |
| `verify` skill | 有可运行产物 | 宿主入口→skill→提交前强制→压测 skill | 只靠 CI 单测 | 冒烟入口与完成条件文本仍在 |
| 检查与改动隔离 | 多人共用仓库 | 规则放受保护分支、评审绑 commit | PR 自带规则修改 | 换平台仍物理隔离 |
| 三态门禁 + 分层 eval | 上线新检查 | observe→复核→enforce→分层召回→停止调优 | 一步到位 enforce | 有对照组与停止条件 |
| 漏检规则化 | 出现事故/revert | 两 PR 门槛→diff 可识别→三 agent 证伪→人工批准 | 个例即立规则 | 有证伪与人工闸门 |
