# 验证循环与委派规模化

## 现象

没有可自动判定的检查时，Agent 在「看起来完成了」就停止（F-004 语境）。此时每一个错误都要等人发现，人本身成了唯一的验证循环。结果是并行度被人的注意力锁死：一次只能跑一两个 Claude。作者给出的对照是——装上验证循环之后，可以并行跑几十到几百个（F-004）。

内部测试给出的量化信号是：在结构化文件生成任务里，让一个**独立的 grader** 按 rubric 检查产出，相比标准 prompting loop，任务成功率最多提升 **10 个百分点**，且最难的问题增益最大（F-005）。注意这里是「独立 grader」，不是让同一个 Agent 自己给自己打分。

## 根因：为什么这一代才成立

关键在于验证的边际成本结构变了（F-006、F-007）：

1. 过去昂贵的验证物——测试、基准、规格、真实端到端运行——现在可以像代码一样由 Agent 快速生成；
2. 生成之后它们是**软件**，反复运行不额外消耗大量 token；
3. 于是「多跑几次验证」几乎不花钱，而「多让人看一遍」始终昂贵。

这三步合起来，才使「把判断搬进软件」在经济上成立。若只看到第 1 步，容易误以为重点是「让 Agent 多写测试」；真正的重点其实是第 2 步——**验证物一旦成为可重复运行的资产，就不再随并行规模线性涨价**。

## 影响

| 维度 | 无验证循环 | 有验证循环 |
|---|---|---|
| 完成判据 | 「看起来完成了」 | 可读的通过/失败信号 |
| 并行规模 | 1–2 个 Agent | 数十至数百个（F-004） |
| 人的角色 | 逐行复查、充当测试 | 定义完成条件、审阅证据（F-071） |
| 错误修复 | 等人发现 | Agent 读结果自行迭代 |

## 建议：验证循环四要素

把原文散落的机制收敛为可迁移的模式（触发场景 + 核心步骤 + 反模式 + 迁移验证）：

- **触发场景**：准备把多个任务同时交给 Agent，或准备让 Agent 无人值守地跑完一段工作。
- **核心步骤**：
  1. 定义**可判定信号**：测试退出码、构建结果、截图对比、属性断言——必须能读成通过/失败，不能是「看起来不错」。
  2. 要求**交出证据**：原文强调让 Agent 展示测试输出、实际命令与返回值，而不是断言成功；审阅证据比自己重跑更快。
  3. 让**结果回流到下一轮**：Agent 读结果 → 修 → 再跑，循环自行闭合。
  4. 把**反复失败的模式固化成规则**：例如某检查反复抓到「日志里含用户数据」，就加 hook 或在 `CLAUDE.md` 写更显式的规则，让问题基本不再发生（F-008）。
- **反模式**：
  - 让写代码的同一个 Agent 兼任唯一的 grader（与 F-005 的「独立 grader」相悖）；
  - 用 flaky 或过慢的检查充当信号——前者训练 Agent 重跑而不是修代码，后者让 Agent 跨批次少跑、难以定位（F-010、F-011）；
  - 把「生成了测试」当成「建立了验证循环」，忽略证据与回流两步。
- **迁移验证**：换一个非 Claude Code 的 Agent 框架，只要仍能提供「可判定信号 + 证据 + 迭代 + 规则回流」四步，模式即成立；缺任一步，并行规模仍会被人的复查量卡住。
