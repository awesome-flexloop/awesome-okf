| 编号 | 事实或声明 | 来源层级 | 核验 |
|---|---|---|---|
| F-010 | flaky 测试会训练 Agent 重跑测试，而非修复失败的代码。 | 作者观点 | 博文单源 |
| F-011 | 慢测试会让 Agent 跨批次减少测试次数，问题定位变困难。 | 作者观点 | 博文单源 |

| F-015 | E2E 难以糊弄：整个功能要么可用要么不可用；具备确定的完成判据，并能具体指出哪里坏。 | 作者观点 | 双源一致 |

| F-018 | E2E 场景中可给 Agent 真实运行系统上的「手和眼」，用 CDP、模拟器或 API harness 让 skill 启动、驱动、检查应用。 | 方法论建议 | 双源一致 |

| F-021 | 属性测试做法：先写一条认为不可能失败的陈述，再用测试库生成数千输入试图证伪。 | 方法论建议 | 双源一致 |

| F-025 | 常见属性之一：idempotency，迁移、归一化、重试做两次与做一次效果相同。 | 博文声明 | 双源一致 |
| F-026 | 常见属性之一：equivalence，优化后代码与朴素但正确的代码产出相同结果。 | 博文声明 | 双源一致 |

| F-030 | 差分测试做法：同一输入分别运行旧系统与新系统，结果不同即存在 bug 或 breaking change。 | 方法论建议 | 双源一致 |
