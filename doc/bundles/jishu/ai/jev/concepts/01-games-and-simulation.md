# 游戏与仿真中的决策分工

> **五例均为微信转述，原帖读取失败，未独立复现。** 下列状态与动作表是教学建模，不声称拿到了原项目的实际schema或源码。原文金额、时长、次数保留归属，不能用作性能承诺。

画面中的角色移动之前，程序需要把环境变成模型能判断的状态，再把结果转换成可执行动作。官方自己的Doom演示也采用结构化文本状态，而非直接图像输入；这能解释架构可能如何组成，不能替代微信五例的原始证据。[F-035、F-039](../references/article-source.md)

## 1 跑酷

微信称Jev同时处理50局地铁跑酷，该次运行不到1美分，但没有给出运行时长、调用数、分数或账单。[F-012](../references/article-source.md)

| 环节 | 教学拆解 |
| --- | --- |
| 状态 | 当前车道、可见障碍、角色运动阶段等文本化信息 |
| 判断 | 在当前允许动作中选换道、起跳、闪避或保持 |
| 输出 | 可以建模为Choice动作与其概率，而非自由按键脚本 |
| 外围依赖 | 游戏状态提取器、实例调度器、按键执行器和结果记录 |
| 回退 | 状态过期或不可判断时由本地确定性策略处理；不能无限等待API |

“50局并行”只说明原文描述的运行形态，不等于50次API同时完成，也不能说明每局都成功。研究价值在于多实例中重复出现相似的短判断；可复现评价需要每局时长、失败率、状态采样频率、调用策略与总费用。没有这些分母，低于1美分无法变成通用成本估计。

## 2 马里奥

原文展示按游戏状态决定移动、跳跃等动作，没有完整schema或测量日志。[F-013](../references/article-source.md) 可将可达平台、危险区域和当前运动状态整理成文本状态，用有限动作集合提出问题，再由游戏桥接程序执行。

与跑酷相比，按键持续时间和动作组合可能影响结果。若允许集合只包含“左、右、跳”却没有时长语义，模型即使返回合法词，也不代表执行器知道该按多久。这是教学提出的接口风险，不是已确认的原项目缺陷。

需要外围地图/状态提取、按键时序管理和碰撞/终止检测。无法从页面确定这些组件如何实现，也不能声称这是一个原生视觉模型或已经稳定通关。验证应对比固定关卡条件下的成功率和失败位置，而非只看一次公开视频。

## 3 杀戮尖塔2

微信称此前使用GPT-6 Astra，换用Jev后的思考约0.7秒；文中人名paulwei与链接账号coolish的关系未核实。[F-014](../references/article-source.md) 这里的动作空间是手牌、目标、资源与规则共同约束的合法选择，不能照搬实时动作游戏的按键模型。

| 环节 | 教学拆解 |
| --- | --- |
| 状态 | 当前手牌、敌我状态、剩余资源及已知规则 |
| 判断 | 从当前合法行动中选择一项，或逐项评价 |
| 输出 | Choice或候选Score，由策略程序解释 |
| 外围依赖 | 规则引擎生成合法动作、回合管理、游戏状态读取 |
| 回退 | 规则先过滤不可用动作；不确定时暂停、转给预设策略或人工 |

0.7秒可能是一次判断，也可能采用其他统计口径，未取得原帖不能确认。即使每步更快，也不说明整局胜率更高；可用的比较应同时固定游戏条件、规则接口、决策预算和评价指标。

## 4 城市交通仿真

原文描述3D城市里的状态、决策、执行、反馈循环，并称搭建不到一小时。[F-015](../references/article-source.md) 这个数字属于演示开发时间，不是车辆反应延迟。

教学上可以把位置、道路规则和周边对象转成状态，用候选驾驶意图提问，再交给仿真控制器执行。外围仍需要地图、对象状态采集、物理更新与安全约束处理。接口延迟或旧状态出现时，应由仿真系统暂停或进入受控状态，不能让模型自行决定是否忽略安全规则。

本例没有真实道路数据、传感器误差、故障注入与安全认证材料。仿真画面展示的是软件世界中的行为，不足以推导现实无人驾驶能力。适合学习模块分工，不适合照搬到实际车辆。

## 5 MuJoCo火箭仿真

原文描述模型参与点火、发动机数与飞行阶段选择，称调整试验12次，成功运行245次API，费用约0.04美元。[F-016](../references/article-source.md) 没有原始日志，无法判断这笔费用仅属于成功运行，还是包含此前试验。

可以将遥测与当前阶段提供给模型，判断候选高层指令，随后由仿真程序及控制逻辑解释和执行。不能据此断定姿态控制、执行频率或每次控制更新都由Jev完成，也不能推算245次调用就是245个固定长度控制周期。

外围依赖包括物理仿真器、遥测编码、合法动作生成、边界保护与终止判定。需要复现时，还应知道初始条件、成功标准、状态字段、模型版本与全部试验分布。单个成功轨迹不足以证明稳定性；这一讨论仅限软件仿真，不提供真实火箭或物理设备控制步骤。

## 跨案例的学习方法

这五例可比较的首先是“判断嵌在哪里”：跑酷和马里奥靠时序动作，卡牌靠合法选择，交通和火箭还依赖仿真中的控制规则。当前材料不支持跨案例速度或费用排名。

选择一例，写出一次判断发生前后有哪些状态变化：哪个组件能保证动作合法？哪个组件判断执行成功？网络超时时谁接管？回答不出来的部分就是仍需补齐的系统设计，而非多写一句提示词能补齐的能力。[官方独立问题语义：F-029、F-038](../references/article-source.md)
