# 可迁移模式（Transferable Patterns）

> G3 质量门通过：每个模式含触发场景 + 核心步骤 + ≥3 反模式 + 迁移验证，经 V 阶段对抗审查修正。

## 模式一：3-File Pattern（文件系统外存模式）

| 要素 | 内容 |
|------|------|
| **触发场景** | 多步骤 AI Agent 任务（≥3 步），尤其是跨多轮工具调用、需要跨步骤保留信息的研究类/构建类任务。不适用于简单问题、单文件编辑、快速查询。 |
| **核心步骤** | 1) 任务开始前创建三文件：task_plan.md（计划 + 进度勾选框）、findings.md（发现记录）、progress.md（会话日志 + 测试结果）<br>2) 每完成一个阶段，在 task_plan.md 勾选对应复选框<br>3) 每次有重要发现，写入 findings.md 而非保留在上下文中<br>4) 每次失败/踩坑，记录在 progress.md 中（含尝试方法和失败原因）<br>5) 停止前，遍历 task_plan.md 确认所有阶段已完成 |
| **反模式** | 1) **单文件混杂**：将计划、发现、进度全写在一个文件里，信息检索困难和结构混乱<br>2) **不更新进度**：创建计划后从不勾选复选框，无法判断完成度<br>3) **不验证完成度**：停止前不检查 task_plan.md，可能遗漏未完成阶段<br>4) **发现留在上下文**：研究发现只存在于对话中，不写入 findings.md，上下文重置后丢失<br>5) **文件无限膨胀**：长期任务中 findings.md/progress.md 无限增长，不定期精简归档，最终自身成为认知负担（V 阶段采纳修正）<br>6) **过度归因**：将 Agent 可靠性提升全部归因于三文件模式，忽视团队/商业模式/时机等多重因素（V 阶段采纳修正） |
| **迁移验证** | SpecWeave 的 Spec Mode 已采用类似模式：spec.md 对应 task_plan.md（规划）、tasks.md 对应 progress.md（进度跟踪）、review.md 对应 findings.md（审查发现）。该模式在知识工作流中验证了可迁移性。OKF bundle 的 facts/insights/patterns/log 四文件结构亦是该模式的变体应用。 |
| **检验标准** | 任务结束时 task_plan.md 所有复选框已勾选；findings.md 包含每个阶段的关键发现；progress.md 记录了所有失败尝试及解决方案；最终输出可直接基于三文件整理，无需回溯完整对话。 |

## 模式二：Hooks 自动化模式（确定性触发模式）

| 要素 | 内容 |
|------|------|
| **触发场景** | 需要 AI 在关键节点（任务开始/阶段完成/停止前验证）执行固定动作的场景，且这些动作的遗漏会造成严重后果（如目标漂移、阶段遗漏、未验证即交付）。不适用于 AI 可以灵活判断的节点。 |
| **核心步骤** | 1) **识别关键节点**：列出 AI 工作流中必须执行固定动作的节点（如开始前建计划、每 N 次操作后存盘、停止前验证）<br>2) **编写 Hook 脚本**：为每个关键节点编写确定性触发脚本（不依赖 AI 读取指令）<br>3) **注册自动触发**：将 Hook 注册到工作流的对应节点，确保自动执行<br>4) **设置回退机制**：当 Hook 触发失败时，有手动触发的回退路径 |
| **反模式** | 1) **依赖 AI 自觉**：将"先建计划""停止前验证"等规则写在提示词中，依赖 AI 读取并遵守，实际执行率不稳定<br>2) **过度自动化**：对所有节点都加 Hook，包括 AI 可以灵活判断的节点，造成流程僵化<br>3) **无回退机制**：Hook 触发失败时无手动触发路径，流程卡死<br>4) **Hook 误触发**：未对 Hook 的触发条件做精确限定（如"重大决策"判定标准模糊），在不应触发的场景误触发，打断 AI 工作流（V 阶段采纳修正） |
| **迁移验证** | SpecWeave 的阶段守卫（phase-guard）当前依赖提示词要求 AI 执行，可改造为 Hooks 机制在阶段切换节点自动触发，提升流程确定性。预提交检查脚本（check-gitignore.py / check-links.py）已具备 Hook 属性，可进一步集成到自动化流水线。降低门槛建议：提供复制即用的 Hook 配置模板，降低初次使用门槛（V 阶段采纳修正）。 |
| **检验标准** | 关键节点的动作执行率达 100%（由确定性代码保证）；不支持 Hooks 的编辑器有结构化检查清单作为回退；Hook 触发条件有明确判定标准，无误触发。 |

## V 阶段对抗审查记录

> V 门通过：4 视角全覆盖，7 条审查意见（每条有具体攻击点），采纳 3 条修正模式文档。

### 视角 1：魔鬼代言人（Devil's Advocate）

| # | 审查意见 | 采纳状态 |
|---|---------|---------|
| V-1 | **20 亿美元归因过度简化**。文章将 Manus 的成功和收购价格归结于"上下文工程"单一因素，但 Manus 被收购的价格取决于多重因素（团队、技术栈、用户基数、商业模式、战略价值）。将 20 亿美金全部归因于一种工作方法是幸存者偏差和过度简化。 | ✅ 已采纳：模式一反模式新增"过度归因"条目 |
| V-2 | **文件膨胀风险**。三个 Markdown 文件在长期任务中可能膨胀到难以管理的大小，findings.md 和 progress.md 在数百轮对话后可能达到数千行，反而成为新的认知负担。文章未讨论文件的清理、归档和精简策略。 | ✅ 已采纳：模式一反模式新增"文件无限膨胀"条目 |
| V-3 | **Hooks 误触发风险**。Hooks 在关键节点自动触发，但若触发条件设置不当（如"每次重大决策前重读计划"中"重大决策"的判定标准模糊），可能在不应触发的场景误触发，打断 AI 的工作流。文章未讨论 Hook 的触发精度和误触发处理。 | ✅ 已采纳：模式二反模式新增"Hook 误触发"条目 |
