# 核心洞察（Core Insights）

## 洞察 1：AI Agent 瓶颈在工程化方法而非模型能力

| 四元组 | 内容 |
|--------|------|
| **陈述** | AI Agent 在复杂任务中的失败（遗忘目标、重复犯错、结构混乱）本质是上下文工程方法的缺失，而非模型智能的不足。planning-with-files 用三个 Markdown 文件加 Hooks 机制就覆盖了 Manus 价值 20 亿美元的工作方法核心。 |
| **证据** | F-008 至 F-011（Manus 收购与上下文工程）、F-015 至 F-018（Context Window 痛点）、F-052 至 F-053（不使用时的遗忘与重复）、F-054 至 F-057（使用后的改善） |
| **反常识** | 业界默认"更强的模型 = 更好的 Agent"，但 planning-with-files 证明：在不改变模型的前提下，仅通过文件系统外存 + Hooks 自动化即可显著提升 Agent 可靠性。挑战了"模型能力是 Agent 瓶颈"的默认假设——瓶颈在工程化方法，而非模型智能。 |
| **行动** | 在 SpecWeave 的 AI Agent 工作流中，对 3 步以上复杂任务强制启用 spec.md + tasks.md + review.md 三文件模式，将关键发现和进度持久化到磁盘而非依赖上下文窗口的隐式记忆。 |

## 洞察 2：RAM-Disk 范式映射是上下文工程底层原理

| 四元组 | 内容 |
|--------|------|
| **陈述** | planning-with-files 的有效性源于一个精确的范式映射——上下文窗口 = RAM（易失、有限），文件系统 = Disk（持久、无限）。这一映射将计算机存储层级理论直接应用于 AI Agent 架构，使"持久化重要信息"成为可操作的工程原则，而非模糊的经验口号。 |
| **证据** | F-023 至 F-026（RAM-Disk 映射与 Manus 原话）、F-019 至 F-022（三文件各自对应不同持久化类型：计划/发现/日志）、F-025（"任何重要的东西都写到磁盘上"） |
| **反常识** | 开发者通常将 AI 对话视为连续的"记忆流"，假设 AI 能自然记住前面的内容。但 RAM-Disk 映射揭示：上下文窗口本质是易失存储，与人类"工作记忆 + 长期记忆"类比是误导性的——人脑有长期记忆，而 AI Agent 的"长期记忆"必须通过文件系统显式构建，不会自然产生。 |
| **行动** | 设计 Agent 工作流时，明确区分"上下文内信息"（临时、会被挤出）与"文件内信息"（持久、可重读），对任何需要跨步骤保留的信息一律写入文件，不依赖上下文窗口的隐式记忆。在提示词中明确标注"以下信息来自 [文件名]"以引导 AI 重读。 |

## 洞察 3：Hooks 自动化降低对 AI 自觉性的依赖

| 四元组 | 内容 |
|--------|------|
| **陈述** | planning-with-files 从文件模板升级为 Hooks 机制（v2.43.0），将"先建计划""每 2 次操作存盘""停止前验证"等规则从"依赖 AI 自觉遵守"转变为"由 Hook 自动触发"，消除了 Agent 行为不可预测的最大来源——对 AI 自觉性的依赖。 |
| **证据** | F-027 至 F-028（Hooks 机制）、F-029 至 F-034（6 个自动动作）、F-035 至 F-038（4 大规则与 Hooks 的对应关系）、F-044（Hooks 为 Claude Code 特有） |
| **反常识** | 社区通常认为"给 AI 更好的指令/提示词就能让它更可靠"，但 Hooks 机制证明：与其依赖 AI 的"自觉性"（读取并遵守指令），不如在关键节点用确定性代码触发固定动作。挑战了"提示词工程是 Agent 可靠性的唯一路径"的假设——提示词依赖 AI 的理解与执行，而 Hooks 提供确定性保障。 |
| **行动** | 在 SpecWeave 中，将阶段守卫、预提交检查等关键质量门从"在提示词中要求 AI 执行"改造为"Hooks 自动触发"，降低对 AI 自觉性的依赖，提升流程的确定性。对不支持 Hooks 的编辑器（如 Cursor），在提示词中用结构化检查清单作为回退方案。 |
