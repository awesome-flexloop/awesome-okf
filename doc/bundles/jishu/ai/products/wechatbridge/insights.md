# 洞察

> 本文是编者对产品事实和官方核验材料的抽取，不是项目方新增说明。官方当前口径与源文时点差异见 [references/verification.md](references/verification.md)。

## 1. 导出式入口降低了集成边界

- **陈述**：让用户主动把合并转发生成的归档交给 Share Extension，可以在不读取微信数据库的前提下完成后续处理。
- **证据**：ZIP 归档与转发链路见 F-013、F-080、F-081；官方隐私边界见 F-082；Share Extension 的沙盒与无网络权限见 F-083。
- **反常识**：能力更少地依赖微信内部接口，反而使入口更容易解释和审计；它并不是后台全量同步。
- **行动**：设计同类工具时，优先定义用户主动导出的文件格式、接收边界和失败兜底，再设计 AI 处理能力。

## 2. 入口矩阵是产品的能力面，而不是功能清单

- **陈述**：十二个内置入口的价值在于把同一份归档路由到不同目标，而不只是增加按钮数量。
- **证据**：官方十二个入口及源文九个入口的时点差异见 F-018、F-041、F-067、F-068；入口组装脚本见 F-096。
- **反常识**：入口数量增长并不自动代表产品能力稳定；六周内的数字变化说明入口矩阵本身需要带时间戳（F-102、F-105）。
- **行动**：维护入口矩阵时记录核验日期、目标类型、默认格式和失败行为，不把旧文章中的数量当作永久接口。

## 3. 本地优先的关键不是“完全不需权限”

- **陈述**：本地处理和隐私边界可以成立，同时仍需要明确列出屏幕录制、辅助功能等系统权限及其用途。
- **证据**：六条隐私约束见 F-082；两类权限的用途见 F-083~F-084；失败时保留剪贴板兜底见 F-035、F-075。
- **反常识**：本地优先并不等于零权限；透明说明“为什么需要权限”比笼统宣称“安全”更可审计。
- **行动**：把权限名称、用途、触发时机和拒绝后的可用路径写入安装说明与验收表。

## 4. 分批收集把平台限制变成可恢复状态机

- **陈述**：当微信侧存在单批上限时，记录页、浮条、续传和重试可以把一次失败转化为多批可恢复流程。
- **证据**：100 条上限与分批收集流程见 F-085~F-087；记录页、浮条和完成并发送见 F-086、F-087。
- **反常识**：分批不是简单地重复点击，而是需要保存“已收集到哪里”的状态，否则用户仍需重新定位和确认。
- **行动**：为批次流程设计明确的开始、追加、完成、失败和重试状态；每个状态都给用户可见反馈。

## 5. Agent 投递与本地知识库沉淀是并列分支

- **陈述**：同一份微信归档可以进入 Agent 处理，也可以沉淀到 Obsidian 或文件夹；两条路径不应被描述成必然串联。
- **证据**：三大能力与目标分支见 F-017、F-030~F-034；官方流程图对 Agent 和笔记路径的区分见 F-081。
- **反常识**：把所有路径画成一条线会掩盖目标应用、权限和输出格式之间的差异。
- **行动**：在产品设计和教程中分别写“投递到 Agent”和“保存到本地”的输入、输出、权限与失败兜底。

## 采用边界

- 这些洞察支持选型和机制设计，不证明某一版本入口数永久不变；当前平台状态仍需按官方材料复核（F-078、F-079、F-102、F-105）。
- examples 来自官方 README 的文档化流程，未在本机实机验证；源文自身没有可照做的操作序列（F-039、F-077、F-088~F-094）。
