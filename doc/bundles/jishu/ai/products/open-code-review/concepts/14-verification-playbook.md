# 可迁移模式与验证手册

本章从 OCR 的官方实现中萃取三个**可迁移**模式——剥离「代码评审」这一具体场景后仍成立的结构，并给出一套零 LLM 成本起步的验证手册。事实编号 F-xxx 指代[官方文档事实清单](../references/official-doc-facts.md)。

## 模式 M1：确定性前置 × 语义后置

### 触发场景

同时满足以下两条时适用：

- 任务输入可被**规则化枚举**（文件、接口、配置项、依赖、变更集）；
- 任务结论需要**语义判断**（这段代码有没有错、这个说法是否越界、这条评论值不值得报）。

典型场景：代码评审、文档质量巡检、契约合规检查、数据管道血缘审查、安全基线核查。

### 核心步骤（7 步）

1. **枚举输入** —— 把任务对象变成清单：路径、状态、增删行数等**元数据**，不带内容。
2. **确定性门过滤** —— 按固定门序（binary → 用户排除 → 用户包含 → 白名单 → 默认路径）剔除不可处理对象，每道门必须能给出**明确的排除原因**。
3. **语义分组** —— 用一次**不喂内容**的 LLM 调用把清单聚成语义相关的组，组大小设上限。
4. **预算拆分** —— 组级预算超限时自动拆为单元素组，避免大组独占资源。
5. **按需前置规划** —— 仅当**量级门槛**（单元素变更量 / 组合计变更量）达标时才跑一次无工具的规划调用，产出清单注入主提示。
6. **语义执行** —— 主循环只做语义工作：检索上下文、读文件、产出结论、按能力调用完成工具收口。
7. **工程化收尾** —— 结论经确定性模块定位（行号、位置）、二次校验、过滤、渲染。

### 反模式（≥3）

| # | 反模式 | 表现 | OCR 的对应设计 |
|---|--------|------|----------------|
| R1 | **把过滤交给模型** | 让 LLM 决定「哪些文件该看」 | 五重门在模型之前完成（F-014 ~ F-017） |
| R2 | **枚举阶段就喂内容** | 分组时把 diff 全文送进模型，成本与噪声同步放大 | 分组只吃元数据（F-021） |
| R3 | **无条件前置规划** | 每次都先规划，小 diff 白付一次调用 | 双阈值门 + 静默跳过（F-025） |
| R4 | **结论无定位** | 模型给结论但不给可核验锚点 | 独立行级定位模块 + 滑动窗口匹配（F-034、F-038） |
| R5 | **无预算前置检查** | 巨大输入直接进模型，撞上限后中途失败 | 三道 token 守卫在调用前 fail-fast（F-018、F-035） |
| R6 | **无元数据回传** | 多轮循环里模型反复发现同一问题 | 已确认评论作为「已发现」上下文回传（F-028） |

### 检验标准

| 检验项 | 判定方法 | 通过线 |
|--------|---------|--------|
| 过滤可解释 | 对每个未处理对象能说出唯一排除原因 | 100% 有原因码，无静默丢弃 |
| 分组不喂内容 | 检查分组调用的请求体 | 只含元数据字段 |
| 分组有上限 | 检查分组常量 | 单组元素数 ≤ 10（F-022） |
| 规划有门槛 | 检查触发条件 | 单元素 ≥ 50 行，或组合计 ≥ 100 行（F-025） |
| 定位可核验 | 检查结论锚点 | 锚点可回指原文；无法锚定时有显式「未锚定」信号而非静默 0（F-034） |
| 预算前置 | 检查是否有调用前 token 检查 | 有，且超限时跳过并记警告 |
| 成本可观测 | 检查是否有 token / 延迟 / 请求数指标 | 有 counter 与 histogram（F-094） |

### 跨场景迁移

- **文档巡检**：枚举 = Markdown 文件树；门 = 二进制 / 大小 / 重复目录 / 扩展名白名单；分组 = 按目录语义；语义执行 = 逐节审查；定位 = 标题锚点 + 行号。
- **API 契约审查**：枚举 = OpenAPI 路径与 schema；门 = 排除生成物目录；分组 = 按资源聚类；语义执行 = 读实现 + 比对；定位 = JSON Pointer。
- **数据管道血缘**：枚举 = SQL / DAG 节点；门 = 排除物化视图；分组 = 按上下游层；语义执行 = 追字段来源；定位 = 列号。
- **安全基线核查**：枚举 = 配置项与权限声明；门 = 排除测试夹具；分组 = 按服务聚类；语义执行 = 逐条比对基线；定位 = 配置行。

**迁移不变的部分**：枚举 → 门 → 分组 → 预算 → 规划门 → 语义执行 → 工程化收尾这七段结构，以及「门必须给原因码」「分组不喂内容」「规划有量级门槛」三条纪律。

## 模式 M2：静默前置检查 × 显式授权门

### 触发场景

把一个 CLI 工具接入**具备行动能力**的宿主 agent（编码 agent、桌面 agent、CI 机器人）时适用。核心矛盾：工具需要自动完成常规设置，但绝不能自动替用户做有后果的决定。

### 核心步骤（5 步）

1. **静默常规设置** —— 缺失的运行时依赖由 agent 直接装好，不打断用户（OCR：CLI 不在 PATH 时自行 `npm install -g`）（F-085）。
2. **显式凭证门** —— 需要凭证时停下询问，展示**两种受支持的配置方式**（环境变量 / 配置命令），绝不编造（F-084）。
3. **上下文补齐** —— 从用户请求中提取业务上下文，结构化传入被调工具（OCR：生成 `--background` 字符串）（F-083）。
4. **按需授权** —— 只有在用户明确表达「同时修复」意图时才动手改代码；否则先询问（F-083）。
5. **分级后渲染** —— 对结构化结论做严重度分级，低置信项丢弃，渲染为人类可读摘要（F-081、F-087）。

### 反模式（≥3）

| # | 反模式 | 后果 |
|---|--------|------|
| R1 | **agent 自行编造凭证** | 用占位 token 触发请求，错误信息淹没真实原因 |
| R2 | **安装依赖时反复询问** | 常规设置被当成决策点打断，交互成本高 |
| R3 | **默认自动改代码** | 在「只评审」场景下产生未授权写操作 |
| R4 | **分级标准藏在实现里** | 调用方无法预期输出形状，只能全量接收 |
| R5 | **低置信评论不丢弃** | 噪声淹没高价值结论，评审者疲劳 |

### 检验标准

- 凭证缺失时是否**停止并展示两种配置路径**（不是编造、不是静默失败）；
- 依赖缺失时是否**静默完成安装**（不是每次询问）；
- 「评审」与「评审并修复」两种意图是否走**不同默认行为**；
- 输出是否**已分级**且低置信项已丢弃；
- 结论是否附带可核验锚点而非仅自然语言。

### 跨场景迁移

- **数据清洗 agent**：静默装依赖（connector SDK）、凭证缺失时问（连接串）、分级后渲染（高置信清洗规则直接执行，中置信入待审清单）。
- **部署 agent**：静默装 CLI（helm/kubectl）、敏感参数缺失时问（凭据）、默认只做 dry-run，收到「执行」才真正 apply。
- **文档发布 agent**：静默装工具链、发布凭证缺失时问、默认只产出草稿，收到「发布」才推远端。

**迁移不变的部分**：「静默的」与「有后果的」必须分类——前者自动化，后者显式授权；凭证永远不编造；分级标准前置到契约里而不是实现里。

## 模式 M3：三档退出条件

### 触发场景

任何「模型驱动的多轮循环」——agent 循环、检索增强生成、多轮工具调用、自动化修复。核心矛盾：循环必须有确定的终止条件，否则成本无上界、失败无归因。

### 核心步骤（5 步）

1. **定义成功出口** —— 明确的完成信号（显式完成工具），不依赖模型「看起来说完了」。
2. **定义预算出口** —— 硬性轮次 / token 上限（OCR：`MAX_TOOL_REQUEST_TIMES` = 100）（F-029）。
3. **定义停滞出口** —— 连续无效轮次上限（OCR：连续 3 轮无有效工具结果）（F-030）。
4. **定义外部取消出口** —— 上下文取消 / 超时信号可打断。
5. **定义降级出口** —— 上下文压缩失败时优雅退出而非崩溃（OCR：`addNextMessage` 返回 false 即退出）（F-030）。

**共同纪律**：无论走哪条出口，**已产生的有效产出全部保留**（OCR：已收集的评论仍被收集并渲染）。

### 反模式（≥3）

| # | 反模式 | 后果 |
|---|--------|------|
| R1 | **只有成功出口** | 模型不收工时无限循环，成本无上界 |
| R2 | **用自然语言判断完成** | 「我觉得差不多了」不可验证，行为不可复现 |
| R3 | **超限即丢弃全部结果** | 一次超限让整批工作归零 |
| R4 | **压缩失败即崩溃** | 长上下文下整轮评审失败 |
| R5 | **退出原因不落日志** | 事后无法归因是预算耗尽还是模型不收工 |

### 检验标准

- 循环代码中能数出**显式的退出条件清单**（OCR 为 5 条）；
- 每条退出条件都有**可观测信号**（工具调用、轮次计数、错误计数、取消信号、压缩返回值）；
- 超限与取消路径**保留部分产出**；
- 退出原因在结构化输出中可查（JSON 模式的 `warnings`、会话 JSONL）。

### 跨场景迁移

- **RAG 检索循环**：命中即停（成功出口）、top-k 耗尽即停（预算出口）、连续 N 轮无新证据即停（停滞出口）。
- **自动化修复循环**：补丁应用成功即停、尝试次数上限、连续失败计数上限、CI 取消、依赖解析失败降级。
- **多 agent 编排**：任务完成即停、子任务预算耗尽、无进展轮次、外部取消、汇总失败降级。

## 验证手册：零 LLM 成本起步的六步

以下流程完全依据官方文档给出的命令设计，**前四步不产生任何 LLM 费用**。

### 第 1 步 —— 确认范围（零成本）

```bash
ocr review --preview
ocr review -c <sha> --preview
```

读两样东西：可审查文件清单与**每个被丢弃文件的原因**。preview 的原因码共 7 种：`binary`、`user_exclude`、`unsupported_ext`、`default_path`、`provider_directory`、`deleted`、`too_large`（F-074）。若预期被评审的文件不在清单里，先看原因码再谈调参。

### 第 2 步 —— 确认规则命中（零成本）

```bash
ocr rules check src/api/UserHandler.go
```

输出会打印匹配的**来源层**（项目 / 全局 / 系统内置）与**glob 模式**（F-046）。若来源层不符预期，多为 `rules` 数组中的声明顺序问题——首条匹配模式生效（F-045）。规则层优先级为 `--rule` > 项目 `rule.json` > 全局 `rule.json` > 内嵌系统规则（F-040）。

### 第 3 步 —— 确认端点连通（零成本）

```bash
ocr llm test
```

官方诊断口径（S9）：取**第一个**完整三元组而非最后一个，因此配置文件里已有全部 `llm.*` key 时环境变量会被忽略；401 / 403 对应 scope 缺失、过期或厂商不匹配——Anthropic 要 URL 以 `/v1/messages` 结尾且 `use_anthropic=true`，OpenAI 兼容要 URL 以 `/v1/chat/completions` 结尾且 `use_anthropic=false`（F-058、F-059）。

### 第 4 步 —— 确认工具能力（零成本）

模型必须支持**原生工具调用**。官方给了一条自检 curl：响应中出现结构化 `tool_calls` 数组即通过；「调用」以文本形式出现在 `content` 里即失败——只在文本里叙述工具调用的模型无论怎么调提示词都无法与 OCR 配合（S9）。

### 第 5 步 —— 小样本试跑（受控成本）

先用小 diff 跑通：单文件、少于 50 变更行时 plan 阶段被静默跳过，走最短路径（F-025）。配合 `--effort low`（1 轮）与 `--concurrency 4`（降低速率限制触发概率）压低首跑成本。

### 第 6 步 —— 打开遥测做归因（可选成本）

```bash
ocr config set telemetry.enabled true
ocr config set telemetry.exporter console
ocr review
```

关注三个 metric（F-094）：`ocr.llm.tokens_used`（counter，标签 model / type）、`ocr.llm.requests_total`（counter，标签 model / status）、`ocr.llm.request_duration_seconds`（histogram，标签 model）。需要仪表盘时切到 `otlp` exporter 指向 collector（F-092）。

## 成本—召回调节杆矩阵

| 调节杆 | 调高 | 调低 | 官方依据 |
|--------|------|------|---------|
| `--effort`（1 / 2 / 3 轮） | 召回↑，耗时与 token↑ | 成本↓，召回↓ | F-027 |
| `PLAN_MODE_LINE_THRESHOLD` | 更少组进入规划 → 更便宜 | 更多组进入规划 → 更贵 | F-025、S9 |
| `PLAN_MODE_GROUP_LINE_THRESHOLD` | 同上；设为 0 会关掉分组闸门 | — | F-025、S9 |
| `--max-tools` | 允许更深探索（只能上调） | 无效（小于模板默认不生效） | F-065 |
| `--concurrency` | 更快，但更易触发速率限制 | 更慢，但更稳 | F-024、S9 |
| `--max-tokens` | 只放宽**提示词**上限 | 收紧提示词；不动输出上限 | F-055 |

**反直觉点**：调高 plan 阈值才省钱（调低反而更贵）；`--max-tools` 只能上调不能下调；`--max-tokens` 不会放大模型输出预算——输出上限由 `MAX_COMPLETION_TOKENS`（16384）单独控制。

## 本章边界

- 三个模式是从 OCR 官方实现中**萃取**的结构性规律，官方文档未使用「可迁移模式」这一表述；模式命名与步骤划分为本 bundle 的抽象。
- 验证手册的命令均取自官方文档，但**未实机执行**；不同平台（Windows / macOS / Linux / WSL）在 shell 引号、`cmd.exe` 差异上有具体表现差异，官方仅就 `api_key_cmd` 给出跨平台提示（F-052）。
- 成本类结论基于官方文档给出的默认值与机制描述，未获得真实账单数据；首页的 token 成本占比为动效占位值，不可引用（E-10）。
