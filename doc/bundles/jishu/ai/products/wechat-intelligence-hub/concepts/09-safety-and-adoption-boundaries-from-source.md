# 09 · 报告安全模型与源码级采用边界

> 本篇补上首轮无法覆盖的两个层面：**报告渲染的安全模型**（首轮完全未涉及，因为当时只读到 README 的产物文件名）与**回复草稿的实际生成机制**（首轮只能标为「图注单源」）。

## 1. 一个 LLM 产品必须回答的问题：报告里渲染的是不可信文本

聊天内容是**不可信输入**——它可能包含 `<script>`、伪造的 HTML 指令、恶意链接。而报告会被人在浏览器里打开。这个场景有一个经典的失效模式：**把聊天文本当指令执行**（prompt injection）或直接渲染原始 HTML。

本项目的处理方式在 `SECURITY.md` 中写得很完整（F-092、F-093）：

| 层 | 措施 | 实现 |
|----|------|------|
| 转换期 | Pandoc **禁用原始 HTML** | 转换阶段就不让原始 HTML 进入文档 |
| 净化期 | 用**显式 nh3 白名单**净化转换后的片段 | `report_security.py` 的 `sanitize_fragment` |
| 链接 | `safe_href(value, allow_parent)` 逐个判定 | 只允许安全协议与必要的父级跳转 |
| 脚本 | 以**基于哈希的 CSP** 限制内联脚本 | `protect_document(document, static)` |
| 网络 | 禁用外部图片与自动网络请求 | 报告不主动外联 |
| 链接语义 | 已知报告链接转**本地导航**；未知文件链接**禁用**；HTTP(S) 源链接保持**手动导航** | 防止「点一下就跳走」 |
| 失败模式 | 缺少 nh3 时 **fail closed**（报错而非降级） | `require_sanitizer()` |

依赖固定为 `nh3==0.3.7`，安装在 Hub 自有 `.venv`，不污染全局 Python；另需本机 Pandoc（F-094）。

**「失败关闭」是这份设计里最值得学的部分**（F-093）。常见的安全设计是「有依赖就用，没有就降级到不净化」——这在长尾场景下会产出**未净化却看起来正常**的页面，用户无从察觉。而本项目选择：没有 nh3 就**明确报错**，宁可不产出报告，也不产出可能带毒的报告。

配套的一句官方提醒也值得记住：「This hardening does not retroactively change existing HTML files.」——**加固不追溯旧文件**，历史 HTML 需要用升级后的渲染器从可信本地 Markdown 重新生成。这意味着安全模型有**版本边界**：升级后旧的报告仍是旧的安全水平。

## 2. 回复草稿：确定性模板，不是模型自由生成

首轮 F-024 把「回复草稿」标为图注单源。本轮源码给出了更精确的事实（F-095、F-096）：

`intelligence_views.py` 的 `_reply_draft(intent, latest_content, relationship, chat_style, minimum_chat_messages=5)` 从一个**意图关键词 → 模板文本**的字典生成输出，共 6 类：

| intent | 触发语义 | 模板（远关系 / 近关系两种措辞） |
|--------|---------|-------------------------------|
| `settlement` | 结算 | 「我核对下结算信息，确认后跟你说」/「收到，我核对下结算信息，确认后回复你」 |
| `review` | 反馈 | 「我按反馈改，完成后发你」/「我按反馈修改，完成后发你审核」 |
| `quote` | 报价 | 「前面是单条价。批量可以按数量重算，麻烦先确认大概每月几条」 |
| `brief` | 需求 | 「我先核对需求，缺的信息我集中确认」 |
| `schedule` | 进度 | 「我先核对进度，确认后给你具体时间」 |
| `general` | 通用 | 「收到了，我确认下再跟你说」/「收到，我确认后回复你」 |

**这修正了首轮的一个隐含假设**。首轮把「生成符合我语气的回复草稿」理解为**模型按用户语气自由生成**；源码表明它更接近**「识别意图 → 套用语气模板」**。

这个区别很实际：

- 它意味着草稿**高度可预测**，不会出现「本该一句话回复却扩写成方案书」的情况——`skills/wechat-intelligence-hub/SKILL.md` 明确要求「不要默认给『推荐版、简短版、争取时间版』三套模板，也不要把一两句微信扩写成方案书」（F-098）；
- 它也意味着**语气个性化来自有限模板 + 关系距离**两个维度，而非任意语言能力——`_reply_relationship` 决定用哪套措辞，`chat_style` 影响用词。

## 3. 语气学习的来源与边界

`skills/wechat-intelligence-hub/references/reply-style.md` 规定了「学我说话」的取样口径（F-098）：

| 项 | 规则 |
|----|------|
| 样本窗口 | 安装者**最近 30 天**跨联系人私聊的聚合特征，不限于重点标签 |
| 优先级 | 当前会话的称呼、语气与关系证据**优先于**全局习惯 |
| 兜底 | 未配置本人昵称或样本不足时使用**中性草稿**，不冒充已经学会 |
| 可覆盖 | CLI `reply` 的 `--style-days` 可覆盖 Profile 中的风格窗口天数 |
| 数据边界 | 原始聊天与学习结果只留本机；开源包不得携带任何姓名、联系人、绝对路径、聊天原文、个人统计、关系标签或学习结果 |

**「样本不足时用中性草稿，不冒充已经学会」**是这条规则里最有分量的部分。它承认了一个能力边界：**语气模仿需要足量样本**，在冷启动时诚实地降级，比硬凑一个像模像样的语气更可靠。

「跨联系人聚合、不限于重点标签」也解决了一个实际的设计冲突：如果只从重点联系人学习，学到的语气会偏向某类关系；跨联系人聚合才能学到**本人**的通用表达习惯，而当前会话的上下文再覆盖它。

**采用建议（源码级修订版）**：

1. **可放心日常部署的部分**：`wechat-cli` + `wechat-intelligence-hub` 两个 Skill 的日常使用是纯只读的，安装与日报链路不触发任何获取动作（F-091）；
2. **需要单独授权评估的部分**：macOS 上跑 `rion_wechat_access.py` 取钥——它**明确不是只读**，可能重启微信并重签名影子副本；
3. **必须自己核对的部分**：金额、日期、报价与承诺——官方把这一步写成使用者责任（F-099）；
4. **需要重新生成的部分**：升级后旧的 HTML 报告仍处旧安全水平，须用升级后的渲染器从可信 Markdown 重新生成（F-092）。

## 5. 可迁移模式

**模式 M7：把「不可信文本渲染」当成一等安全问题设计，而不是事后补丁。**

本项目的安全设计有三处可迁移的决策：

1. **在转换入口就掐断**——Pandoc 禁用原始 HTML，让危险语法根本没有进入中间态的机会；
2. **失败关闭而非失败降级**——缺依赖时报错，宁可不产出，也不产出「看起来正常但未净化」的产物；
3. **显式区分三类链接**——本地导航 / 禁用 / 手动外链，让「点开报告会不会跳走」成为设计决策而非默认行为。

补充一条**元模式**：安全加固**不追溯历史产物**，所以任何安全声明都必须绑定**版本边界**（哪一版渲染器产出的产物才享有该保证）。这条容易被忽略——文档里若只写「报告是安全的」而不写「由 X 版本渲染器生成的报告是安全的」，就是不完整的。
