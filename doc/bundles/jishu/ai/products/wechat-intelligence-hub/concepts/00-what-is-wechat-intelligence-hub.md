# 00 · 项目身份、热度时点与信源距离

## 1. 一句话定位

**WeChat Intelligence Hub** 是一个**本地优先的微信个人情报库**：把本机已有的微信聊天记录，只读地整理成可检索、可核查、可行动的个人情报（F-005、F-010、F-044）。官方英文描述为 "Local-first WeChat intelligence system with a read-only CLI, Codex skills, searchable chat history, daily briefings, follow-ups and opportunity tracking."（F-043）。

博主把它概括为「微信界的情报中台」（F-025）——这是**作者观点**，不是项目官方定位，引用时须带此标注。

它要解决的是博主开篇描述的痛点：聊天记录像「塞满纸条、从不归档的抽屉」，群里哪句是商机、谁答应过什么、上周要跟进的客户到哪一步了，靠翻记录拼不出全貌（F-004，作者比喻）。

## 3. 星标口径与时点（最容易被误引的一组数字）

| 口径 | 数值 | 时点 | 性质 |
|------|------|------|------|
| 博文标题 | 「2000 星」 | 2026-09-24 发文时点 | 取整口径（F-007） |
| 博文正文与结尾 | 「1976 颗星」「1976 星不到一周」 | 2026-09-24 发文时点 | 精确口径（F-006、F-008） |
| 官方现值 | **2,764** | 2026-11-06 API 快照 | 动态数字（F-042），另有 fork 2,754、open issue 10 |
| 增长窗口 | 「5 天」/「不到一周」 | 仅博文单源 | **未独立核验**（本次未取 star 时序接口） |

三条引用纪律：

1. 1976 与 2000 **不是互相矛盾**，是同一时点的精确值与取整值（F-007）。
2. 2,764 与 1,976 的差距是**约 43 天的时效差**，不是「博文写错」（勘误②）。
3. **绝不能把「5 天」写成「仓库创建后 5 天」**：API 显示仓库创建于 2026-09-04，与发文日相隔约 20 天（F-041、F-002）。二者描述的是不同时间轴，只能表述为「博文口径的星标增长窗口，未独立核验」。

## 4. 四层信源距离地图

读本束的任何一句，都应先判断它站在哪一层：

| 层 | 内容 | 可信度处理 |
|----|------|-----------|
| ① 官方一手 | GitHub REST API 元数据、main 分支 README（F-041~F-057） | 可直接作为事实；动态数字仍需带时点 |
| ② 官方截图经博文转述 | 四个入口名、视图风格 A~D、移动端视图（F-011~F-013、F-016~F-018） | 加「博文/图注口径，官方未逐字核验」前缀 |
| ③ 第三方推介转述 | 能力清单、检索维度、安全声明（F-005~F-036 中的 O 类） | 已尽量回源到 ①；未回源者标单源 |
| ④ 博主评价 | 抽屉比喻、「情报中台」「克制反而让人敢用」（F-004、F-025、F-037~F-040） | 标为作者观点，不作为产品事实引用 |

博文全文**没有给出仓库 URL**，只写「去 GitHub 把仓库 clone 下来」（F-003、F-040）；本束用官方地址补全（F-048）。这一点本身也说明：博文是推介文本，不是可照做的技术文档。
