# 02 · 别聊需求，定验收

> 本篇的核心是**方法论**，不是模型评测。博文中所有对 Kimi K3.1 Pro 的评价（F-037、F-038、F-040、F-060）均为**作者观点**或媒体转述，本束不对其能力下结论。

## 1. 作者实际做了什么（事实层）

作者自述用法只有两步：**「先让它写计划，再让它自己跑」**（F-043，作者观点），且「我没有上来就让它写代码」（F-043）。拆开是六个动作：

| 步 | 动作 | 出处 |
|----|------|------|
| 1 | 先把产品形态讲清楚：中转站怎么收、怎么存、怎么投，哪些能做、哪些 iOS 做不了 | F-044、F-046 |
| 2 | 要求产出「交给任何一个 Agent 都能照着做完」的开发文档 | F-045 |
| 3 | 提示词①让模型**先确认理解**、列疑问、不要猜，再定方案 | F-046 |
| 4 | 提示词②让模型产出**两份可对齐编号**的文档（开发规格 + 档期），并声明「写完我看一遍，没问题就开工」 | F-047 |
| 5 | 人审阅后把文档交给模型，按任务编号逐个做，每完成一个汇报一次 | F-054 |
| 6 | 模型在验收时自找 bug、自修并记进验收记录 | F-056、F-057 |

作者给出的结论是「**别跟它聊需求，跟它定验收**」（F-059，作者观点）；他自评「这份计划里最值钱的，倒不是排期，是**验收规则**」（F-051 附近）。

## 2. 两段提示词的结构（可复用骨架）

**提示词①（定方案，不写码）** 的关键约束（F-046）：

- 给定背景与既有资产：Mac/Windows 已有版本，核心代码在 `macos/Sources/WeChatBridgeCore`，**iOS 要复用，不要另写一套**。
- 指向两份既有输入文档：`docs/design/ios-feature-baseline.zh-CN.md`（真机实测结论）与 `ios-relay-v1.zh-CN.md`（产品设计）——官方 tree API 确认二者存在（F-071）。
- 把范围钉死：v1 只做收 / 存 / 投三件事，逐条写明交互形态。
- **提前暴露平台限制**：分享扩展不能直接打开别的 App、不能自动粘贴、部分 App 不收 ZIP、微信一次最多 100 条要分批合并。
- 收尾要求「先跟我确认一下你理解的对不对，有疑问直接列出来问我，**不要自己猜**」。

**提示词②（出两份可交付文档）** 的关键约束（F-047）：

- 开发规格须含：工作规则、环境前提与检查方法、输入数据规格、架构与工程配置（Bundle ID / App Group 写死）、逐模块规格、**分模拟器（S）与真机（R）两类的编号化验证**、T0–T9 依赖顺序任务清单、交付定义、待决问题、**不在 v1**。
- 档期文档须含：按里程碑拆、每个写工期与日期与**出口闸门**、关键路径与可并行任务、需要人亲自做的事、风险与应对、**固定进度汇报格式**。
- 两份文档的**任务编号与验证编号必须对齐**。
- 最后一句是人工闸门：「写完我看一遍，没问题就开工」。

> 这两段提示词的逐字复现与运行前置条件见 [examples/00](../examples/00-reproduce-the-two-prompts.md)。注意：它们来自博文，**非官方模板**，本知识包未实机验证。

## 3. 为什么有效（I 阶段洞察，非博文事实）

**观察**：官方产物确实存在且与提示词要求一一对应——dev-spec 有 S1–S11 / R1–R7 / T0.1–T9.2 / 交付定义 9 条 / 待决 Q1–Q5 / 不在 v1 14 项（F-077），schedule 有 M0–M6、出口闸门、7 行汇报格式（F-078），验收记录有 9 项自修问题与两次复跑（F-079/F-080）。

**机制（洞察/推断）**：把「什么叫做完」外化成可观察的通过条件后，Agent 获得了**终止判据**与**自检信号**；没有验收定义时，模型只能以「代码写完了」为终止条件，边界 bug 不会进入反馈回路。三条具体杠杆：

1. **编号对齐**：S/R/T/M 编号在两份文档间互引（F-047、F-077、F-078），让「任务 → 验证 → 闸门 → 汇报」形成闭环，进度可被机器和人同时检查。
2. **留白合法化**：「待真机」「不许标通过」（F-053、F-073）给不可验证项一个**显式状态**，避免模型用推测填补证据空缺。官方验收记录 R3–R6 至今挂着「待真机」（F-080），正是这一纪律生效的证据。
3. **回归基线**：改到 `macos/` 必须跑 `swift test` 且 186 个测试 0 失败（F-053、F-073），使「新平台开发」不能牺牲既有平台。

**可迁移条件**（G3 门）：① 任务能拆出可观察的输入/输出或状态变化；② 存在不被本次改动破坏的回归基线；③ 能区分「可自动验」与「必须人/真机验」，且允许后者留白；④ 需求边界在人审阅文档时已经冻结。

**反例/边界**：需求本身未定型、探索性研究、以审美或主观偏好为交付目标的任务，写死 S/R 只会把不确定性伪装成确定；验收定义**不等于**验收完成——本例 R3–R6 仍待真机（F-080）。

## 4. 作者的归因，以及需要补上的那一半

作者把顺利归因为「Kimi K3.1 Pro 的强模型加持」**加上**「我们的产品形态是确定的」（F-058，作者观点/因果分析）：微信流在 Mac/Windows 已跑通，收/存/投三件事早已想清楚，剩下的只是「把『什么叫做完』写清楚」。

从第一性原理补上另一半：**可复用核心 + 已验证的产品语义**才把搜索空间从「设计产品」压缩到「移植与验收」。官方 README 显示 iOS 复用 `WeChatBridgeCore`（F-067），dev-spec §5.2 规定以本地 Swift 包引用 `../macos`（F-076/F-077），提示词①也明确禁止另写一套（F-046）。缺少这些前提时，同样的两段提示词不会复现作者自述的 6 小时（F-039、F-055）。

> **口径提醒**：6 小时是作者自述的净运行时长且与官方记录跨 10-23/10-24 两天存在张力（V-14）；18 个工作日是含真机验收与 2 天缓冲的全职档期（F-050、F-078）。二者不可相除，见 [verification.md 勘误②③](../references/verification.md)。

## 5. 与七概念方法论的对应

| 七概念 | 本文对应物 |
|---|---|
| R 事实 | 提示词①要求先读两份基线文档、先确认理解、不自己猜（F-046） |
| F 第一性原理 | 先定产品形态与平台限制，再谈实现（F-044、F-046） |
| I 洞察 | 「最值钱的是验收规则」（F-051）、「别聊需求定验收」（F-059） |
| E 抽取 | 两份编号化文档（F-047、F-072、F-078） |
| V 对抗审查 | S/R 编号验收、出口闸门、不许标通过（F-051~F-053、F-077、F-078） |
| A 原子化 | 每个 T 任务单独提交、标题 `[AI]` 开头、不 push（F-073） |
| C 原子提交 | 同上；进度汇报固定 7 行（F-078） |

这套对应关系是**本知识包的解读**，不是作者或项目官方的说法。完整可迁移模式与采用边界见 [05 篇](05-transferable-patterns-and-boundaries.md)。
