# 03 · 验收控制面：规格、档期、编号与闸门

> 本篇依据**官方仓库一手文档**（F-071~F-080），不是博文转述。博文只提到「700 多行」「7 个里程碑」「18 个工作日」「11 条验收」（F-048~F-052）；编号细节与大量约束由核验补充。

## 2. 四件套：S / R / T / 交付定义

| 件套 | 编号范围 | 出处 | 作用 |
|------|---------|------|------|
| S（模拟器可自动验） | S1–S11 共 11 条 | F-052、F-077、F-079 | 每条写死操作步骤与预期结果；官方验收记录逐条给出证据 |
| R（必须真机验） | R1–R7 共 7 条 | F-077、F-080 | 由用户操作、Agent 记录；未做的一律标「待真机」 |
| T（任务清单） | T0.1–T9.2 共 21 个 | F-047、F-077 | 按依赖顺序编号，每个任务 = 代码 + 测试 + 列出的验证全过 + 一个 `[AI]` 提交 |
| 交付定义 | 9 条 | F-077 | 全部打勾才算 v1 完成 |

**S 编号的三条博文举例均可在官方找到对应**（F-052、F-077、F-079）：

- 0 字节文件必须提示失败、不能存入 → S4，验收记录为「通过（修复后）」，修复提交 `cfbced3`（F-079）。
- 删除卡片 5 秒内撤销必须恢复 → S10（F-079）。
- 杀掉 App 再分享一次、重新打开必须看到新卡片 → S11（F-079）。

**交付定义**（§10，9 条，F-077）中值得单独记住的四条：Mac 回归全过且测试数 ≥ 186；S1–S11 全通过并写入验收记录；R1–R5 由用户真机完成并记录、R6/R7 有结论；仓库里没有用户真实聊天内容（真机样本与未打码截图）。最后一条把**数据合规**也写成了交付条件。

## 3. 工作规则：把「人」留在回路里

dev-spec §0 的七条规则（F-073）：

1. 只在指定 worktree（分支 `feat_ai_ios_relay`）里改代码，不碰主检出。
2. 每个 T 任务完成并通过验收后**单独提交**，标题以 `[AI]` 开头。
3. **不 push、不开 PR**，除非用户在对话里明确要求。
4. 改到 `macos/` 必须跑 `cd macos && swift test`，结果 186 个测试（含 1 个跳过）0 失败；新增测试后基线数相应增加。
5. 真机步骤无法自动完成时，在验收记录里标「待真机」，**不要标通过**。
6. 界面简体中文、代码注释英文，注释解释「为什么」不复述代码。
7. 不做画中画、剪贴板监听、自定义键盘、iCloud、Handoff、邮件、云端积分、`wcb`、Shortcuts、小组件（详见 §12）。

档期文档另有三层人机分工（F-078）：**关键路径**（T1.1 → T2.1 → T3.1 → T3.2 → T5.3 → T6.1 → T7.1 → T8.x → T9.1）、**需要用户亲自做的事**（同意安装 iOS 平台、回答付费签名账号、准备多人群样本与装好各 App 的 iPhone、按清单做真机测试）、**风险与应对表**（磁盘不足、免费签名无 App Group、豆包/千问丢文本、大 ZIP 超扩展内存上限等）。

## 4. 档期与出口闸门

档期文档日期 2026-10-23，原文「**计划交付：2026-11-18；最晚 2026-11-20。开发和验收共 18 个工作日，另加 2 天缓冲**」（F-078）。

| 里程碑 | 内容 | 工期 | 出口闸门（示例） |
|---|---|---|---|
| M0 | 环境与骨架 | 2 天 | iOS 26.5 平台已装、`verify.sh` 退出码 0、`xcodegen generate` 成功、空白 App 能启动 |
| M1 | 收：分享扩展进收件箱 | 2 天 | S1 S3 S4 S11 通过 |
| M2 | 存：中转站列表与详情 | 3 天 | S2 S5 S10 通过 + 两个单测类通过 |
| M3 | 投：ZIP 与 TXT+图片两条路线 | 3 天 | S6 S7 S8 通过 + Mac 回归通过 |
| M4 | Obsidian、文件夹、场景 | 3 天 | S9 通过 |
| M5 | 收集、引导、打磨 | 2 天 | §10 交付定义除真机项外全部打勾 |
| M6 | 真机验收与修正 | 3 天 | R1–R5 已记录、能力表按结果更新、§10 全部打勾 |
| 缓冲 | — | 2 天 | — |

进度汇报固定 7 行（F-078）：`[任务]` `[状态]` `[提交]` `[验证]` `[未验证]` `[下一步]` `[需要用户]`。每完成一个任务报一次，每个里程碑结束时追加到验收记录；阻塞超过半天立刻汇报并切换到不依赖该任务的工作。

## 5. §12「不在 v1」：范围控制比功能清单更重要

官方 §12 列 14 项（F-077）：云端账号和积分、云端执行技能、手机作为 Mac `wcb` 的审批端、iCloud 同步、`Shortcuts / App Intents`、小组件、**灵动岛**、画中画、剪贴板监听、自定义键盘、Handoff、邮件、英文界面、iPad 布局。§11 另有 Q1–Q5 待决问题，其中 Q3 明确「分享扩展是否要发本地通知…v1 不做，R7 只做技术验证」，Q2 记「上架中国区需要 App 备案」仍待决。

这组「不做清单」是本束 `flagged` 判定的直接依据之一：博文写了灵动岛入口（F-019），而官方把它逐字排除在 v1 之外（V-22）。它也解释了为什么「18 个工作日」不是可以随意压缩的数字——档期里含 M6 真机验收与缓冲（F-078）。

## 6. 抽象成可复用四件套

把上表抽掉 iOS 细节，得到可用于任意 Agent 长程任务的模板（**本知识包的抽象，非官方模板**）：

```
① 可自动验清单 S：编号 + 操作步骤 + 可观察预期结果
② 需人/真机验清单 R：编号 + 由谁操作 + 记录什么 + 允许「待验」状态
③ 任务清单 T：按依赖排序，每任务绑定所属 S/R 与一个原子提交
④ 交付定义：全部勾选项 + 回归基线 + 数据/合规约束 + 「不在本期」清单
```

配套三件：里程碑出口闸门（未过不得进下一阶段）、固定进度汇报格式（含「未验证」与「需要用户」两行）、不做清单。演练方式见 [examples/01](../examples/01-design-your-own-acceptance-gates.md)。

> **反例**：需求未定型、以审美为主观目标、没有回归基线的探索性任务，套用此模板会把不确定性伪装成确定（见 [05 篇](05-transferable-patterns-and-boundaries.md)）。
