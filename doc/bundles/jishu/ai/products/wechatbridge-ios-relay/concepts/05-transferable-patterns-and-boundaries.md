# 05 · 可迁移模式、洞察四元组与采用边界

> 本篇是本知识包的**解读层**。所有「机制」段落均为洞察/推断，与 [article-source.md](../references/article-source.md) 的事实层严格分离；作者本人的因果分析（F-058）同样只算待检验的作者洞察。

## 1. 四条洞察（G2 四元组）

### 洞察 1 · 验收定义是长程 Agent 任务的控制面

- **观察**：先要「交给任何一个 Agent 都能照着做完」的文档（F-045）；产物含 S1–S11 / R1–R7 / T0.1–T9.2 / 交付定义 9 条（F-077/F-078）；验收记录有 4 项「通过（修复后）」与 9 项自修问题（F-079）。
- **机制（洞察）**：可观察的通过条件为 Agent 提供终止判据与自检信号；否则只能以「代码写完」为终止条件，边界 bug 不进入反馈回路。
- **可迁移条件**：任务可拆出可观察状态变化；有不被破坏的回归基线；能区分可自动验与必须人验并允许后者留白。
- **反例**：需求未定型、探索性研究、以审美为主观目标的任务；R3–R6 至今「待真机」（F-080）也说明验收定义 ≠ 验收完成。

### 洞察 2 · 「6 小时」的隐藏前提是产品形态已确定

- **观察**：作者自己归因于「模型 + 产品形态确定」（F-058）；iOS 复用 `WeChatBridgeCore`（F-046/F-067）；档期按 1 人全职估 18 工作日 + 2 天缓冲（F-050/F-078）。
- **机制（洞察）**：可复用核心与已验证语义把搜索空间从「设计产品」压缩为「移植与验收」；6 小时是净运行时长口径，18 工作日是含真机验收的全职档期口径。
- **可迁移条件**：存在可复用核心、明确的不做清单（§12 共 14 项，F-077）、人可审阅的规格。
- **反例**：从零定义新产品、无回归基线；官方验收记录日期跨 10-23 与 10-24（F-079/F-080），「一个下午加一个晚上」（F-055）是叙事化表达。

### 洞察 3 · 二手产品文的「完成态」必须以仓库一手件收窄

- **观察**：博文称 iOS「开发完成 / 正在提审」（F-009/F-010）与灵动岛入口（F-019）；官方 README 仍「iOS 版正在开发中」、`[ ] iOS 版`（F-065/F-066），§12 排除灵动岛（F-077），R3–R6 待真机（F-080）。
- **机制（洞察）**：发布文案描述作者期望的状态，仓库文档描述当前可验证的状态（有日期、编号、提交 SHA）；冲突时取后者，并把差异登记为「时点 + 口径」，而不是替作者"改正"。
- **可迁移条件**：项目开源、文档入库、有路线图或验收记录等状态件。
- **反例**：闭源产品无一手件可查，只能标「仅博文单源」；README 也可能滞后，故结论须写成「截至核验时点的官方口径」并设 `stale_after`。

### 洞察 4 · 成效数字的错误多不是造假，而是三轴口径缺失

- **观察**：1.7k vs 2024（F-006/F-063）；6 小时 vs 18 工作日（F-039/F-050）；10-27「开源」vs 11-04 权重公开（F-037/F-081）；「有点贵」vs「便宜约 80%」（F-061/F-084）。
- **机制（洞察）**：失真集中在**时间轴**（取值时点）、**主体轴**（谁统计/谁体验）、**定义轴**（净运行时长 vs 全职档期、承诺开源 vs 权重开放、绝对支出 vs 相对价格）。去掉任一轴的限定词，两个不可比数字就会被读成因果或倍数。
- **可迁移条件**：任何跨时点、跨主体的二手内容 → 可信知识库转化；操作化为「勘误四张清单」（日期/版本、成效溯源、口径对照、引文逐字）。
- **反例**：不带时点的定性描述不适用；也不能因发现口径差异就推断造假——官方验收记录反而印证了自修 bug、186 测试、图文合一 PDF 等多数技术叙述（F-079/F-080）。

## 2. 三个可直接搬走的做法

| 做法 | 出自 | 搬到你的项目时 |
|---|---|---|
| 「先确认理解，不要自己猜」作为提示词收尾 | F-046 | 任何长任务开工前，先让 Agent 复述范围与限制并列出疑问，人确认后再动手 |
| 「待验」作为一等状态 | F-053/F-073/F-080 | 验收表允许「待真机 / 待用户 / 待数据」三态，禁止用推测填补证据空缺 |
| 两份文档编号对齐 | F-047/F-077/F-078 | 规格与档期共用一套任务/验证编号，进度汇报模板固定含「未验证」「需要用户」两行 |

具体演练见 [examples/00](../examples/00-reproduce-the-two-prompts.md) 与 [examples/01](../examples/01-design-your-own-acceptance-gates.md)。

## 3. 采用边界（谁不该照抄）

1. **不要把 iOS 版当可安装产品**：官方 README 只提供 macOS 14+ 与 Windows 安装包（F-065），iOS 状态见 V-21；[examples/02](../examples/02-ios-usage-walkthrough.md) 是流程说明，不是安装教程。
2. **不要把「6 小时」当效能基准**：无独立出处，且隐藏前提是已有 Mac/Windows 核心（V-14）。
3. **不要把博文观点当官方结论**：「最强国产开源模型」「别聊需求定验收」「Astra 类比」「有点贵」均为作者观点（F-037、F-059、F-060、F-061）。
4. **不要照搬「哪家都能吃」**：官方 R2 明确豆包/千问的限制与「视频和压缩包仍发不了」（F-080）。
5. **合规前置**：仅处理本人有权使用或已获合法授权的聊天记录，转发第三方 AI 前脱敏（F-035）；官方交付定义也把「仓库里没有用户真实聊天内容」列为完成条件（F-077）。
6. **本束未实机验证**：所有命令、提示词、操作流程均来自博文或官方文档，知识包本身未运行。
