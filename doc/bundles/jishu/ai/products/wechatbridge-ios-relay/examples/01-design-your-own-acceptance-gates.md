# 01 · 为任意 Agent 任务设计一套验收闸门

> ⚠️ **非官方模板 / 未实机验证**：下面的四件套是对官方 dev-spec 与 schedule 的**抽象**（F-077、F-078），由本知识包编写，不是 WeChatBridge 项目或任何模型厂商发布的规范。示例任务是虚构的，用于演示填空方式。

## 1. 从官方产物抽象出的四件套

| 件套 | 官方形态 | 通用定义 |
|---|---|---|
| S 清单 | S1–S11，模拟器可自动验（F-077/F-079） | 编号化的**可自动验证**步骤：操作 + 可观察预期结果 |
| R 清单 | R1–R7，必须真机、由用户操作（F-077/F-080） | 编号化的**需人/真实环境验证**步骤：谁操作 + 记录什么 + 允许「待验」 |
| T 清单 | T0.1–T9.2 共 21 个，按依赖排序（F-077） | 任务编号，每个绑定所属 S/R 与一个原子提交 |
| 交付定义 | 9 条，全部打勾才算 v1（F-077） | 完成条件：回归基线 + S 全过 + R 有结论 + 数据/合规约束 |

配套三件（F-078）：里程碑**出口闸门**、固定**进度汇报格式**、**不在本期**清单（官方 §12 共 14 项，F-077）。

## 2. 模板（可直接复制）

```text
# <任务名> · 验收规格（非官方模板）

## 不在本期
- <明确排除的能力 1>
- <明确排除的能力 2>

## 回归基线
- 命令：<例如 npm test / pytest -q>
- 期望：<测试数> 个通过、<跳过数> 个跳过，0 失败；新增测试后基线数相应增加

## S · 可自动验（每条：操作 → 可观察预期结果）
| 编号 | 操作 | 预期 |
|---|---|---|
| S1 | … | … |
| S2 | … | … |

## R · 需人/真实环境验（每条：谁操作 → 记录什么 → 允许「待验」）
| 编号 | 内容 | 由谁 | 记录 | 状态 |
|---|---|---|---|---|
| R1 | … | … | … | 待验 / 通过 / 不通过 |

## T · 任务清单（按依赖顺序，每任务绑定 S/R）
| 编号 | 任务 | 依赖 | 绑定验证 | 提交要求 |
|---|---|---|---|---|
| T0.1 | … | — | — | 单独提交，标题 <前缀> 开头，不 push |

## 交付定义（全部打勾才算完成）
- [ ] 回归基线通过，测试数 ≥ <N>
- [ ] S1–S<N> 全部通过并写入验收记录
- [ ] R1–R<K> 有明确结论（通过 / 不通过 / 明确不做），未验项标「待验」
- [ ] 所有提交符合要求，工作区干净，未经同意没有 push
- [ ] 仓库中没有真实用户数据 / 未脱敏截图

## 里程碑与出口闸门
| 里程碑 | 内容 | 闸门 |
|---|---|---|
| M0 | … | <哪些 S/R 与单测通过才能进入 M1> |

## 进度汇报格式（每完成一个任务报一次）
[任务] [状态] [提交] [验证] [未验证] [下一步] [需要用户]
```

## 3. 填空演练（虚构任务，非博文内容）

**任务**：为一个已有的 Markdown 知识库工具新增「按标签批量导出」功能。

| 件套 | 填写示例 |
|---|---|
| 不在本期 | 不做云端同步、不做标签自动推断、不做 PDF 导出 |
| 回归基线 | `pytest -q`，现有 214 个测试 0 失败；新增测试后基线数相应增加 |
| S1 | 输入两个标签 → 导出目录出现 1 个 zip，内含且仅含同时命中两标签的文件 |
| S2 | 输入不存在的标签 → 明确报错，不生成空 zip |
| S3 | 文件名含空格与非 ASCII → 解压后文件名逐字节一致 |
| R1 | 由人在真实知识库（≥1000 文件）上执行一次，记录耗时与内存峰值 → 允许「待验」 |
| T0.1 / T1.1 / T1.2 | 环境检查 → 参数解析 → 导出实现；T1.1 绑定 S2，T1.2 绑定 S1/S3 |
| 交付定义 | 回归 ≥214、S1–S3 全过、R1 有结论、无真实笔记入库、提交不 push |
| 出口闸门 | M1（参数解析）需 S2 通过；M2（导出实现）需 S1/S3 + 回归通过；M3 需 R1 有结论 |

**演练要点**：S 写「可观察预期结果」而不是「功能正常」；R 允许留白而不是补推测；每个 T 绑定验证编号；「不在本期」先写，避免范围 creep。

## 4. 与官方原型的差异（必须知道）

| 维度 | 官方 WeChatBridge iOS 文档 | 本模板 |
|---|---|---|
| 环境粒度 | Xcode 26.6、iOS 26.5 平台、XcodeGen 2.x、付费签名团队（F-074） | 泛化，不绑定任何工具链 |
| 输入规格 | 逐字节定义微信导出 ZIP / `聊天记录.txt` 与占位写法（F-075） | 抽象为「输入规格」占位 |
| 架构约束 | 分享扩展只收存、120 MB 内存上限流式复制、主 App 唯一删除者（F-076） | 未覆盖，需按项目补写 |
| 数据合规 | 交付定义含「仓库里没有用户真实聊天内容」（F-077） | 保留为通用约束 |
| 验证状态 | R3–R6 至今「待真机」（F-080） | 用「待验」三态模拟 |

> 抽象会损失细节。真实项目请回到 [03 篇](../concepts/03-spec-schedule-and-acceptance-gates.md) 看官方四件套的原始形态，再决定保留哪些约束。

## 5. 何时不要用这个模板

- 需求还在澄清期：先做探索与原型，写死 S/R 会把不确定性伪装成确定。
- 交付目标为主观审美或开放式研究：没有可观察的「通过」信号。
- 没有回归基线：模板第 4 条交付定义会形同虚设。

对应 [05 篇洞察 1](../concepts/05-transferable-patterns-and-boundaries.md) 的可迁移条件与反例。
