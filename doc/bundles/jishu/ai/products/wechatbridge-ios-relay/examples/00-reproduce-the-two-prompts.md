# 00 · 两段提示词复现

> ⚠️ **非官方内容 / 未实机验证**：以下两段提示词逐字来自博文（F-046、F-047），不是 WeChatBridge 项目官方模板，也不是任何模型厂商推荐用法。本知识包**没有**运行过它们，不保证在不同模型/仓库状态下得到相同产物。
> **前置事实**：官方仓库中确实存在提示词①引用的两份输入文档与产出的两份文档（F-071），且开发规格首句与博文引文逐字一致（F-072、F-048）——这证明「产出存在」，不证明「照抄提示词即可复现」。

## 1. 运行前置条件（缺一不可）

| 条件 | 说明 | 出处 |
|---|---|---|
| 有一个已跑通的产品与可复用核心 | 本例为 Mac/Windows 版 + `macos/Sources/WeChatBridgeCore`，官方 README 记 `ios/ … 复用 WeChatBridgeCore` | F-046、F-067 |
| 有两份基线文档可读 | `docs/design/ios-feature-baseline.zh-CN.md`（真机实测）、`ios-relay-v1.zh-CN.md`（产品设计） | F-046、F-071 |
| 目标平台限制已由人预先摸清 | 分享扩展不能代开 App/自动粘贴、部分 App 不收 ZIP、微信一次最多 100 条 | F-046、F-075 |
| 有 Agent 执行环境与人审阅环节 | 提示词②末句「写完我看一遍，没问题就开工」 | F-047 |
| 有回归基线 | `cd macos && swift test`，186 个测试（含 1 个跳过）0 失败 | F-053、F-073、F-079 |

> 没有这些前提时，该流程最接近**洞察 2 的反例**：从零定义产品、无回归基线的任务不会复现作者自述的 6 小时（F-039、F-055，作者自述未独立核验）。

## 2. 提示词①：先定方案，不写代码

原文逐字（F-046；`●●●` 为公众号排版符号，复现时可省略）：

```text
我们要把微信流做成 iPhone 版，先别写代码，先把方案定下来。背景：
- 微信流现在有 Mac 版和 Windows 版，核心代码在 macos/Sources/WeChatBridgeCore，iOS 要复用它，不要另写一套。
- 我在真机上测过：微信 iOS 可以「转发 → 合并转发 → 其他应用 → 选择手机中的应用」，把聊天记录导出成一个 ZIP（里面是 聊天记录.txt + 图片、视频、文件）。测试结论在 docs/design/ios-feature-baseline.zh-CN.md，产品设计在 docs/design/ios-relay-v1.zh-CN.md，你先读这两份。
产品形态：iOS 版是一个「中转站」，v1 只做三件事：
1. 收：微信里转发过来，分享扩展把文件存进收件箱，弹个小卡片就回微信，不打断人。
2. 存：App 里按卡片列出来，点开能像微信一样看聊天记录，图片内联显示。
3. 投：挑一批（或者多批合并），选场景，投给 ChatGPT、豆包、千问、WorkBuddy、Claude、DeepSeek、Obsidian、文件夹或者任意 App。
iOS 做不到的事情你要提前标出来，别等写完了才发现：
- 分享扩展不能直接打开别的 App，也不能自动粘贴，最后一下只能让用户在分享面板里点目标。
- 有的 App 不收 ZIP（豆包、千问），要自动改成 聊天记录.txt + 图片。
- 微信一次最多转 100 条，超过的要能分批收、最后合并。
你先跟我确认一下你理解的对不对，有疑问直接列出来问我，不要自己猜。
```

**可观察的预期输出**：模型先复述产品形态与三条平台限制、列出疑问，**不产出代码**；人确认后才进入提示词②。若模型直接写代码，视为流程偏离。

## 3. 提示词②：产出两份编号对齐的文档

原文逐字（F-047）：

```text
理解没问题。现在帮我出两份文档，放在 docs/design/ 下：
一、开发技术文档 ios-dev-spec.zh-CN.md
目标是：交给任何一个 Agent，只读这一份加上档期文档，就能把 iOS v1 做完并验证交付。
要包含：
- 给执行者的工作规则：只在 .worktrees/ios-relay 里改；每个任务单独提交，标题以 [AI] 开头；不 push；改到 macos/ 必须跑 swift test，Mac 不能退化；做不到验证的写「待真机」，不许标通过。
- 环境前提和怎么检查、怎么补。
- 输入数据规格：微信 iOS 导出的 ZIP 和 TXT 长什么样，图片、表情、链接、视频号的占位写法。
- 架构、目录、工程配置（XcodeGen），所有 Bundle ID、App Group 写死，不要另起名字。
- 每个模块的规格：分享扩展、收件箱、中转站列表、详情、目标能力表、投递规划、投递面板、Obsidian、场景、合并收集、首次引导。
- 验证方法：分模拟器能自动验的（编号 S1、S2…）和必须真机验的（R1、R2…），每条写清楚怎么操作、看到什么才算过。
- 任务清单，按依赖顺序编号，从 T0 排到 T9。
- 交付定义：全部打勾才算 v1 完成。
- 待决问题：需要我回答的列出来，不要自己猜。
- 不在 v1 的东西也写明。
二、档期文档 ios-schedule.zh-CN.md
- 按里程碑拆（M0 环境骨架、M1 收、M2 存、M3 投、M4 知识库与场景、M5 收集打磨、M6 真机验收），每个写工期、日期，以及出口闸门：哪些 S/R 验证和单元测试通过才能进下一个。
- 关键路径，哪些任务可以并行。
- 什么时候需要我亲自做什么（装平台、真机测试、签名账号）。
- 风险和应对。
- 进度汇报格式：每完成一个任务，按固定格式报一次：任务、状态、提交、验证结果、没验证的、下一步、需要我做的。
两份文档里的任务编号、验证编号要对得上。写完我看一遍，没问题就开工。
```

**自检结论写法建议**：不要写「复现成功」，只写「产出的编号体系与官方真实产物在 X 项上对齐 / 在 Y 项上不同」——不同模型、不同仓库状态下产出必然有差异。

## 5. 为什么这个示例不算「实机验证」

- 本知识包没有克隆仓库、没有调用任何 Agent、没有运行 `swift test`（F-070 的命令仅作路径说明）。
- 官方 README 的构建命令需要 macOS 14+ / Xcode 16 或兼容 Swift 6 的 Command Line Tools，dev-spec §1 另要求 Xcode 26.6 与 iOS 26.5 平台（F-070、F-074）。
- 因此本文是**可照做的流程说明**，不是经过本知识包验证的实战记录；这一点与「操作可复现性两问」的判定边界一致（见根 [index.md](../index.md) 的内容性质声明）。
