# 洞察

> 本文的“洞察”和“行动”是编者抽取，不等同于官方路线图或产品承诺。iOS 当前状态、四项 ❌ 与待真机项必须以 [references/verification.md](references/verification.md) 为准。

## 1. 完成态必须由交付定义和真机结果共同证明

- **陈述**：产品“开发完成”不能只由博文发布口吻证明，还需要官方交付定义、路线图和验收记录形成闭环。
- **证据**：博文的完成与提审表述见 F-009~F-010；官方 README、路线图、交付定义和 R3~R6 状态见 F-065、F-066、F-077、F-080。
- **反常识**：功能描述很完整、计划很具体，并不等于 App 已经完成上架；“待真机”本身是验收状态，不应被填成通过。
- **行动**：发布判断至少同时检查版本可用性、交付定义、模拟器/真机结果和上架证据；任何缺项都保留“待验证”。

## 2. 验收文档把 Agent 编码从对话转为控制面

- **陈述**：两段提示词的核心价值不在于让 Agent“自由发挥”，而在于将需求、任务编号、汇报格式和验收条件固定下来。
- **证据**：作者的两段提示词与方法论观点见 F-043、F-046、F-047、F-059；官方 `docs/design/`、S/R/T 编号和交付定义见 F-071、F-072、F-077、F-078。
- **反常识**：更长的需求描述不一定更可执行；没有编号化任务、出口闸门和记录，Agent 的“完成”难以复核。
- **行动**：为 Agent 任务先建立规格、计划、任务编号、验收闸门和汇报模板，再允许执行；把“未验证”作为合法状态。

## 3. 证据状态应成为交付物的一部分

- **陈述**：验收记录不仅记录通过项，还应记录部分通过、待真机、失败项及其复跑条件。
- **证据**：官方验收记录的 S/R 结果、自修问题与复跑信息见 F-073、F-079、F-080；四项核验失败及其分布见 F-081~F-084。
- **反常识**：把不确定项隐藏起来会让文档更“完整”，但会降低交付可信度；“待真机”比猜测一个通过结论更有价值。
- **行动**：每个验收条目增加证据状态、环境、复跑命令或待办条件；发布前检查是否存在未经证据支持的“已完成”。

## 4. 动态数字必须同时记录时间、主体和定义

- **陈述**：Star、耗时、档期和“开源”都可能因时间点、统计主体和定义不同而不能直接比较。
- **证据**：Star 双时点见 F-006、F-063；6 小时与 18 工作日的口径见 F-039、F-050、F-055、F-078；模型权重公开时点见 F-081。
- **反常识**：把两个数字放进同一张表，不代表它们可相除或可以证明提效；相同词语也可能对应不同发布阶段。
- **行动**：记录数字的日期、主体、统计范围和定义；禁止把“净运行时长”与“含验收的工作日”计算成提效倍数。

## 采用边界

- 可迁移的是“规格—任务—验收—记录”的控制面，不是 iOS 已上架或灵动岛能力等产品结论（F-065~F-080）。
- examples 只用于提示词、验收模板和证据状态练习；不提供 IPA、签名或 TestFlight 安装步骤，因为 iOS 仍处于官方记录的开发/待真机状态（F-065、F-066、F-080）。
