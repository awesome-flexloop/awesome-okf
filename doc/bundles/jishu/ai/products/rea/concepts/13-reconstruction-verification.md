# REA 重建验证与比较器可信度

东方重建博客 W17 记录了历史工程与比较器失效。它为“精确匹配”补上了数据、初始化、共享状态与原平台行为的约束；其中旧项目还使用专用 bridges/scripts，不能将所有成果改署为 REA 产出（F-173~F-178）。

## 匹配对象

先写清要恢复的对象：一条计算规则、一个函数、完整函数 extent，还是整程序。TH04 教学 `aimed_ring_angle` 摘要解释角度计算；503 字节 helper body、517 字节包围 span 与历史 2139 字节 bullet-add extent 是三个不同计数对象（F-171/F-172）。

```text
规则解释 -> 指令和引用数据 -> 历史编译器产物 -> 原平台整程序 -> 语义重建 -> 现代移植
```

这是博客后来总结的推荐阶段顺序，不是 TH08 最初按此顺序执行的历史记录。TH08 早期 portable releases 先于部分历史平台审计（F-177）。

## 比较器失效

旧 TH08 比较器修正指令中的重定位地址，再比较指令字节，却未检查它们引用的浮点数据。`ItemManager::OnUpdate` 中源码 0.0 对目标 128.0 曾被判通过（F-175）。因此，指令一致无法单独证明引用常量一致。

上游后续审计 1548 个 floating-literal references，并修复另 12 个 stale references，涉及 5 个已 accepted 函数。这些数字分别是引用次数、额外陈旧引用与函数数，不是 1548 个独立常量（F-176）。本轮仅阅读证据，未重新运行该审计。

检查器也须有应失败的输入：故意改坏常量值、声明或表示，确认它会拒绝；再检查重定位、引用数据和目标区段。一个恒为通过的比较器能产生漂亮报告，但没有区分正确与错误的能力。

## 两条验证路径

历史编译器路径回答“在指定 compiler、flags、ABI 和数据布局下，候选是否复现了目标”。原平台路径回答“程序是否能启动、运行、正确处理共享状态、时序与用户操作”。两者互相补充。

| 层级 | 判据 | 不覆盖 |
|---|---|---|
| 代码和引用数据 | 已审重定位、常量、MAP 与完整比较范围 | 整程序初始化及运行 |
| 函数行为 | 明确输入集、正负例、边界 | 未测试输入与外部系统 |
| 原平台整程序 | 启动、正常路径、异常、保存等实际记录 | 未观察路线与未来平台 |
| 语义命名 | producer/consumer 与状态生命周期证据 | 仅凭名称推断的归属 |
| 现代移植 | 新平台行为及历史语义保持 | 仅凭旧字节匹配自动放行 |

TH04 Normal 路线、结局与存档是维护者人工 Windows 观察，64 位移植仍开发。不能把这些写成官网新增自动测试或现代移植完成（F-178）。

## 目标出处与数字

TH04 的目标出处为 `candidate-local-attested`，尚未添加独立 pristine 来源证明（F-172）。比较范围越精确，越需要记录原始工件身份、来源与是否可能由候选产生；哈希固定只说明字节身份，不补足来源独立性。

博客的耗时按 UTC commit committer 时间差除 86400 算 calendar days。它不是工作人时、计算量或受控提效实验；函数分母会随审查变化，因此不使用跨游戏完成率排名（F-173）。

## 实践约束

从一个可定位函数开始，保存目标哈希、地址、证据来源与外加假设。检查函数行为时写明输入域；检查编译字节时写明数据和重定位范围。加入至少一个明确应失败的候选，最后按声明范围安排原平台测试。

不要把“函数匹配”写成“游戏恢复”、把“编译器通过”写成“源码名称正确”、把“演示可用”写成“原应用已验证”。这些反例也适用于非逆向工作：迁移数据库时，schema 比较和真实查询行为是不同验证；序列化回归中，字段存在和原始数据语义也须分别核对。
