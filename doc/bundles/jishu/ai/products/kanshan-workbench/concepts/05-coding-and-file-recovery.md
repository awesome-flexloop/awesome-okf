# Coding 任务与文件恢复：能改代码，但没有后悔药

## 1. Coding 任务能做什么

官方列出五项能力（F-090、F-003）：

1. **阅读、搜索和修改代码**：在用户授权的项目目录中操作；
2. **执行测试**：使用项目已有的测试框架；
3. **安装 Node.js 等项目依赖**；
4. **启动本地开发服务并检查运行结果**；
5. **使用 Git 查询提交历史、比较改动和定位问题**。

这五项覆盖了「读—改—测—跑—查」的日常开发闭环，但它不是完整的 IDE：没有内建文件历史面板，也没有操作级回滚（F-093）。

## 2. 三条运行边界

### 2.1 本地开发服务会被回收

本地开发服务会在当前会话结束后被运行环境回收，不能作为长期运行的公开服务（F-091）。

含义：

- 适合「启动服务 → 跑测试/看页面 → 结束会话」的短周期验证；
- 不适合把看山启动的服务当作持续在线的 API、Webhook 接收端或公网演示；
- 需要长期运行的服务，应使用独立的进程管理器、容器或云托管。

### 2.2 Python 依赖要装进受管环境

Python 依赖需要安装到受管的 Python 运行环境中；直接通过 Bash 安装到宿主环境，可能无法在任务沙箱中使用（F-092）。

原文没有给出受管环境的路径、Python 版本、包管理器或预装包清单（F-119）。实操建议：

1. 先让看山执行 `python -c "import sys; print(sys.executable)"` 或等价的只读命令，确认当前解释器路径；
2. 用该解释器对应的 `pip`/包管理器安装依赖；
3. 安装后在同一会话中立即跑一次导入测试，确认沙箱可用；
4. 不要假设宿主环境的 `pip install` 对任务沙箱生效。

### 2.3 没有内建历史面板

看山工作台没有内建的文件历史面板，也不提供操作级回滚或自动快照（F-093、F-098、F-107）。文件能否查看历史或恢复，取决于两个前提（F-094）：

- 当前目录是否为 Git 仓库；
- 修改前是否已经保留备份。

## 3. Git 仓库中的查看与恢复

### 3.1 只读查看

在 Git 仓库中，看山可以通过 Bash 工具运行只读命令，查询提交历史、文件演变和当前改动（F-056、F-095）：

```bash
git log --oneline -20        # 最近提交
git diff                     # 当前未暂存改动
git diff --cached            # 已暂存改动
git show <commit>:<path>     # 某次提交中的文件内容
git status                   # 工作区状态
git blame <path>             # 逐行定位改动来源
```

这些命令不改变仓库状态，属于安全操作。

### 3.2 恢复指定文件

恢复指定文件时，看山会先检查仓库状态并征得用户确认，再通过 Git 恢复（F-057、F-096）。官方描述的保护流程是（F-058）：

1. 先通过 `git status` 检查仓库状态；
2. 如需保护未提交的工作，先征得用户同意；
3. 再创建备份或使用 Git 暂存方案；
4. 最后执行恢复。

### 3.3 高风险命令必须确认

以下命令可能丢失未提交改动，必须由用户明确确认（F-099）：

```bash
git reset --hard
git checkout -- .
git clean -fd
```

看山不会自动执行 `git push`、强制推送、删除远端分支或重写已推送历史（F-100）。

## 4. 非 Git 目录：只能靠备份

非 Git 目录的边界更窄（F-097、F-107）：

- 只能回溯**当前会话中**由看山执行的改动；
- 如需恢复文件，必须已经存在备份副本；
- 没有内建的文件历史面板；
- 不支持操作级回滚与自动快照。

这意味着：**在非 Git 目录里让 AI 批量改文件，风险显著高于 Git 仓库**。如果必须操作，先手动复制一份备份，或先 `git init` 建立最小版本控制。

## 5. 安全操作流程（建议固化）

| 阶段 | 动作 | 依据 |
|---|---|---|
| 开工前 | 确认目录是 Git 仓库；`git status` 干净或已提交 | F-058、F-095 |
| 开工前 | 重要文件另存备份，或创建一次提交 | F-098、F-101 |
| 任务中 | 只让 AI 做只读探查与小步修改；每次修改后 `git diff` 复核 | F-095 |
| 任务中 | 高风险命令逐条确认，不接受「自动清理」 | F-099、F-100 |
| 完成后 | 跑项目测试；检查关键文件与公式 | F-090、F-101 |
| 完成后 | 由用户决定是否提交；不自动 push | F-100 |

一个可复制的开工提示词：

```text
在 ~/projects/demo 中执行任务，遵守以下纪律：
1. 先运行 git status 和 git log --oneline -5，确认仓库状态。
2. 只做读取与最小修改；每次修改后展示 git diff。
3. 不执行 git reset --hard、git checkout -- .、git clean -fd，除非我逐条确认。
4. 不执行 git push、强制推送、删除远端分支或重写历史。
5. 修改完成后运行项目已有测试，并报告失败项。
6. 需要安装 Python 依赖时，先确认当前解释器路径，再安装到该环境。
```

## 6. 一页检查表

- [ ] 项目目录已授权，且是 Git 仓库（F-094）。
- [ ] 开工前 `git status` 干净或已提交，重要文件有备份（F-058、F-098）。
- [ ] 本地开发服务只用于会话内验证，不作为长期公开服务（F-091）。
- [ ] Python 依赖装进受管环境，并在同一会话验证导入（F-092、F-119）。
- [ ] 高风险 Git 命令逐条人工确认（F-099）。
- [ ] 不自动 push、不强推、不删远端分支、不重写历史（F-100）。
- [ ] 完成后跑测试并复核关键改动（F-090、F-101）。
