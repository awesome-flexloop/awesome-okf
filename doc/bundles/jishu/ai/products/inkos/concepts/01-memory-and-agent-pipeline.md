# 记忆与 Agent 流水线——InkOS 怎么做到"写到百万字还记得住"

这篇文章是理解 InkOS **为什么能写长篇小说** 的核心。一节写 8000 字不难，难点在于写到第 200 章时，角色还记得第 3 章从哪拿了武器、埋伏笔在第 5 章还没回收。InkOS 靠**「一章由多个 Agent 接力 + 一套持久化记忆」**解决这个问题。

## 一章是怎么写完的：10 角色接力，零人工干预

官方把每一章的生成描述为一条**由多个 Agent 接力完成的流水线，全程降人工干预**（F-033）。简化后的主回路是：

```
雷达(可选) → 规划师(本章意图) → 编排师(选上下文) → 建筑师(章节结构)
         → 写手(生成正文) → 观察者(提取9类事实) → 反射器(JSON delta)
         → 归一化器(字数治理) → 连续性审计员(33维校验) → 修订者(修复)
                          └────── 审计不通过 → 自动进入 "修订→再审计" 循环 ──────┘
```

关键点：**写手不是最后一步**。写完正文后，系统还要**观察、反射、审、改**这四步，才认为一章"完成"。这意味着 InkOS 把"写"和"保证质量/连续性"分成了明确的两类 Agent——这正是它区别于"一个 LLM 输出整章"的 AI 写作机器人的地方（F-033、F-048）。

## 记忆三层：JSON 权威态 + Markdown 投影 + SQLite 时序库

博文（F-024）用"三层记忆"概括，与官方 README 的长期记忆设计**完全对应**（F-035、F-038）：

| 层 | 载体 | 作用 | 官方依据 |
|---|---|---|---|
| **第一层：结构化状态** | `story/state/*.json`（Zod schema 校验） | **权威事实源**：当前世界状态、伏笔、章节摘要等；每次写入前经结构校验 | 0.6.0 起真相文件权威源从 markdown 迁移到 JSON（F-035） |
| **第二层：Markdown 投影** | 7 个 `*.md` 真相文件 | **给人看的记忆**：打开可读、可改；保持人类可读性 | README"markdown 投影仍保留"（F-035） |
| **第三层：时序记忆库** | `story/memory.db`（SQLite，Node 22+） | **本地全文检索**：写到一两百章时，规划师/编排师从库里按相关性检索历史事实与伏笔，喂给写手当上下文，**避免全文注入导致上下文膨胀** | F-038 |

> **为什么分三层？** 纯 Markdown 适合人读，但 LLM 直接写 Markdown 容易出现格式漂移、漏字段，且全量注入会爆上下文。InkOS 的做法是：**让 LLM 输出 JSON delta，代码层用 Zod schema 校验后再 immutable 写入**（反射器 Reflector 的职责），Markdown 只是给人看的"投影"；而当书很长时，用 SQLite 做**相关性检索**而不是全量塞给写手。三层各司其职，是"记得住"的工程基础（F-035、F-038）。

## 7 个"真相文件"：唯一事实来源

无论记忆怎么分层，事实的"真相"收敛在 **7 个文件**上（F-035）：

| 文件 | 记录 |
|---|---|
| `current_state.md` | 世界状态：角色位置、关系网络、已知信息、情感弧线 |
| `particle_ledger.md` | 资源账本：物品、金钱、物资数量及衰减追踪 |
| `pending_hooks.md` | 未闭合伏笔：铺垫、对读者的承诺、未解决冲突 |
| `chapter_summaries.md` | 各章摘要：出场人物、关键事件、状态变化、伏笔动态 |
| `subplot_board.md` | 支线进度板：A/B/C 线状态、停滞检测 |
| `emotional_arcs.md` | 情感弧线：按角色追踪情绪变化和成长 |
| `character_matrix.md` | 角色交互矩阵：相遇记录、信息边界 |

连续性审计员**对照这些文件检查每一章草稿**（F-037、F-048）——如果角色"记起"了从未亲眼见过的事，或拿出了两章前已丢失的武器，审计员会捕捉并让修订者修复。

## 可靠性设计：不是"让 AI 随便写"

- **状态写入受 Zod 校验**：反射器输出 JSON delta → 代码层 `applyRuntimeStateDelta` immutable 更新 + `validateRuntimeState` 结构校验；坏字段（如 `lastAdvancedChapter` 非整数、伏笔 `status` 非法）直接拒绝，不滚雪球（F-035）。
- **审计→修订闭环**：审计不通过自动进入"修订 → 再审计"循环，直到**关键问题清零**；关键问题自动修复，次要问题标记给人工（F-048、F-023）。
- **字数治理**：`draft`/`write next`/`revise` 共享保守型字数治理——`--words` 指定目标字数、系统推导允许区间、最多只追加 1 次纠偏归一化，不硬截断正文。
- **版本与回滚**：每章自动创建状态快照，`inkos write rewrite` 可回滚任意章节（F-040 配套）。
- **并发安全**：文件锁防止并发写入；写手输出自检表（上下文/资源/伏笔/风险）、写完输出结算表，审计员交叉验证。

> **执行者洞察（机制层，单源假设）**：InkOS 的记忆设计把"人工可读（Markdown）+ 机器权威（JSON 校验）+ 检索可扩展（SQLite）"三者分开，本质上是**把 LLM 状态外化为「可信文件系统 + 校验层」**——这与"靠 prompt 里塞越老越多的历史对话"的做法相比，换得更稳的长期一致性，代价是引入了事件溯源式的状态管线复杂度。此观察基于单一开源实现，标注为机制层假设。

## 对创作流程的意义

博文作者（F-019，**作者观点**）认为：写小说最不值得一提的环节是"具体写"，更重要的**新书框架搭建与内容审计**——这样才能保证一部书不出现"设定 BUG"。这与官方把 10 个角色中的 **7 个**（规划/编排/观察/反射/归一/审计/修订）都投向"写之外"的架构相吻合（F-033）。理解这层，才不至于把 InkOS 当成"一个能写小说的对话框"，而是理解它本质是一套**「AI 协同的记叙文版本控制系统」**。
