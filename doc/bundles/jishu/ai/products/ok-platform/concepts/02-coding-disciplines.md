# 手术刀式编码：AI 写代码的三条纪律

## 背景

AI 写代码最大的坑是：**写得出，但写得不对、写得过度**。方案对了不代表代码就对了——从方案到可运行代码之间有大量细节可出错 [F-049]。

开发 AI 在 feature 分支上编码，**编译 + 单测 + 创建 MR 通过**才算一次开发结束 [F-048]。平台运营总结出三条硬纪律 [F-049]。

## 纪律一：简单优先，抵抗过度设计

AI 和人一样有把事复杂化的冲动，而且更明显——为一个只用一次的操作设计"通用框架"，为三行逻辑抽象"可扩展的策略模式"[F-049]。

开发阶段注入明确的简单优先原则 [F-049]：

- 先写最简单、显而易见正确的版本。
- 写完自问：能不能更少行？这个抽象值不值？
- 三行重复代码，好过一个过早的抽象。
- 只为当前需求写，不为臆想中的未来需求过度设计。

> 效果：注入"简单优先"约束后，审查中**架构过度复杂类问题出现频次下降约一半**（作者运营观察，`single-source/flagged`，见 [verification V6](../references/verification.md)）[F-050]。

## 纪律二：范围纪律，只碰该碰的

方案里已列出需要改动的文件。开发 AI **必须且只能**改动方案列出的文件 [F-049]。

但 AI 极容易"顺手清理"相邻代码——"命名不规范顺手改一下""函数可优化顺手重构一下"。每个顺手都是潜在的 bug 引入点和审查噪声 [F-049]。

OK 平台加入 **"发现但不碰"** 机制：AI 在开发中发现范围外值得改进的点，必须记到变更摘要的"发现但不碰"部分，**而不是自行动手**。既保留发现问题的价值，又避免顺手改出问题 [F-049]。

## 纪律三：关键路径先写测试，再实现

不是所有代码都需要先写测试。但对**核心业务逻辑**——新增的判断分支、关键计算、状态流转、幂等逻辑——开发 AI 必须遵循 **"先写一个会失败的测试 → 再实现使其通过"** [F-049]。

这不是在追求测试覆盖率数字，而是**把验收标准固化成测试**：测试通过时，不是"感觉对了"，而是"确实对了" [F-049]。

> 数据佐证：约 49 条需求（约 17%）在自动开发阶段经历超过 1 轮"代码审查 + 修复"，其中相当一部分因"编译通过但单测失败"而在早期暴露逻辑漏洞，避免了进入代码审查后的更大返工 [F-051]。换算 49/254≈19% 与文章"约 17%"存在轻微出入，作者用"约"处理，本包标 `single-source/flagged`（见 [verification V7](../references/verification.md)）。

## 可迁移要点

- 把**确定性工程约束**硬编码进 Agent 执行策略，比反复调 prompt 更有效（见 [知识地图 I-2](../references/knowledge-map.md)）。
- 三纪律与审查标准配合形成闭环：简单优先 → 范围纪律 → 先测后编，共同压低审查返工成本。
