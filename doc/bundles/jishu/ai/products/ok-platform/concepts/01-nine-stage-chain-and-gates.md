# 九阶段全链路与质量门：需求即交付

## OK 平台定位

OK 平台是 AI 驱动的端到端研发平台，核心理念"需求即交付"——用户提交需求描述，AI Agent 自动走完 **需求评审 → 仓库匹配 → 技术方案 → 编码 → Code Review → 部署** 的全链路 [F-024][F-025]。文章称其为"九阶段全链路"，各阶段有明确的 AI 角色、输入、输出和质量门 [F-033]。

- 其余为策略需求、数据需求，或超出端到端能力范围，**转人工**处理 [F-029]。

- **人力不变**时团队可承接更多需求；常规需求由 AI 消化后，人聚焦在更复杂、更高风险、更有价值的策略需求与架构决策 [F-032]。

## 第一道门：需求质量决定交付成败

作者给出反直觉的运营结论：**瓶颈不在开发侧，在需求侧** [F-036]。需求写得多清楚，AI 就做得多准确；需求一旦模糊，代码再快也是返工 [F-037]。

**不是让人把每个细节写清楚**——那既不现实也不公平。真正的问题是让 AI 在需求不完整时**主动追问补背景**，而非闷头干到最后漏东西 [F-038]。

### 需求评审 AI 的访谈式深挖（非清单式校验）[F-038]

1. **先复述理解**：任何追问前，AI 先把核心意图用自己的话复述一遍，请提需求者确认有没有偏——这是最高效的纠偏点。
2. **顺着回答继续挖**：基于用户上一轮回答，挖出新暴露的模糊点，接近资深 PM 的访谈方式。
3. **发散收敛**：对极模糊需求，列出 2~3 种"可能是想要什么"的合理解释让用户选或补充，而非直接驳回。
4. **区分必须/建议**：**放行的必要条件四项 = 做什么、为谁做、关键业务规则、验收标准**；优先级、异常场景等为建议补充而非强制 [F-039]。

### PM 需求收集池

平台为 PM 单独设计需求收集池，独立于端到端流水线：PM 提一个很粗的想法，由 AI 负责补全到"可以开发"的质量——把需求变成 AI 可执行的规格，本身是 AI 能做的事 [F-040]。

### 可行性评估：7 维打分（保护机制，非通关游戏）

可行性评估 AI 对 7 个维度打分（0~100）[F-041]：

| 维度 | 权重 |
|---|---|
| 需求清晰度 | 20% |
| 仓库匹配度 | 20% |
| 改动范围 | 15% |
| 技术复杂度 | 15% |
| 外部依赖 | 10% |
| 风险等级 | 10% |
| 交付形态 | 10% |

总分 **≥60** 才能进入开发流水线。作者强调：不是通关游戏，是**保护机制**——把注定在开发阶段卡住的需求拦在上游 [F-042]。

## 第二道门：技术方案是质量的前置卡口

**方案阶段改方向，成本最低；开发阶段发现方向错了，代价最高** [F-043]。方案质量对最终代码质量的影响是整个链路最大的，一个好方案不是提纲，是施工图。

技术方案 AI 遵循四条硬纪律 [F-044]：

1. **按依赖图排序，不按重要性排序**——实现步骤按依赖自底向上（数据/存储 → 协议/接口 → 业务逻辑 → 调用方/前端），任何步骤不依赖尚未在前序创建的物件。
2. **垂直切片优先**——按一条完整功能路径切（建表 + 接口 + 最小可用逻辑 = 一个可验证切片），每片完成后系统可编译、可验证。
3. **任务粒度控制**——单步预计触碰 >5 个文件或跨 ≥2 个独立子系统则拆分；步骤标题出现"并且/同时"意味着其实是两步。
4. **插入检查点**——每 2~3 步明确写验证节点（如"此处应能 `go build ./...` 通过"）。

### 找茬式自审 + 待确认问题提前暴露

- 对关键决策（跨模块修改、断言编译器无法验证的属性如并发安全/幂等/不变量、不可逆变更），方案 AI 做一次找茬式自审：站在"假设作者过度自信"的视角，问"这个方案最可能错在哪？有没有未言明假设？未处理边界？"[F-045]。价值在于把问题消灭在方向还便宜修正的时候。
- 方案里不确定、需人拍板的点收进"待确认问题"（产品/技术两类），用户在管理端逐题回答（选择/开放题）[F-046]。
- 核心原则：**不确定的事提前暴露，不让模糊进入开发**[F-047]。
