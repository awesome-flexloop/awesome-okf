# 多任务协作中的注意力与研究边界

用户让 AI 同时处理代码、资料和审查时，仍可能需要切窗口、重述背景、确认哪个任务已经完成。小枫coding 的导读从这些协调动作切入，把人的注意力视为需要纳入架构设计的资源。[事实 F-004 至 F-005](../references/facts.md)

“AI 能完成单项任务”与“人能轻松管理一组任务”是两类观察。前者可按结果正确性和执行时间评估；后者还需要观察人的打断次数、重复输入和结果核对负担。后面的评估建议是本教程的分析，不是源文已完成的测量。

## 四项目标的含义

下表对媒体记录的 continuity、efficiency、proactivity、persistence 作教学解释，不声明原型全部实现。[F-006、F-019](../references/facts.md)

| 目标 | 学习时关注的行为 | 需要反问的边界 |
|---|---|---|
| 连续性 | 不同入口仍能衔接相关任务背景 | 身份、权限与上下文能否正确区分 |
| 效率 | 多任务推进时，用户无需逐一盯住会话 | 协调开销是否超过并行收益 |
| 主动性 | 环境变化可以触发相关工作 | 谁授权了这类动作，何时应保持安静 |
| 持续性 | 长时间工作和中断后恢复 | 什么状态可靠保存，重复执行如何避免 |

这些是设计方向，不是性能证明。把“长期在线”直接理解成“永不故障”会遗漏恢复、预算和停止条件。

## 阅读后的判断练习

选择一个真实但不含敏感数据的工作任务，写出用户当前要做的协调动作。再标出哪些只是传递进度，哪些是必须由人决定的取舍。如果只是把更多消息自动推给用户，尚不能证明协调负担下降。

填写示意，非源文案例：修复一个错别字时，“告诉执行者文件在哪”是补背景，“询问是否完成”是追进度，“同意公开发布”是授权。练习输出为“动作、需要的信息、谁决定、完成证据”四列；不能把收到进度消息当作发布授权。后续各篇可复用同一个任务。

这是一项纸面分析练习，不是 Super-agent 原型运行实验；不提供虚构测试结果。继续阅读[双层架构](01-router-worker.md)，理解协调动作可以如何分配。
