# 协调分工的知识地图与迁移模式

## 三层地图

| 层 | 本包内容 | 证据边界 |
|---|---|---|
| 事实层 | 导读元信息、设计描述、媒体转述，F-001 至 F-030 | 来源清楚，不等于效果已核实 |
| 机制层 | 职责分离、事件归属、恢复与授权的解释 | 执行者提出的机制假设 |
| 迁移层 | 对现有工作流划分接待、执行、订阅、观察与停止责任 | 建议与纸面练习，非实测结论 |

操作可复现性两问：有没有可照做的操作步骤？有没有可核对的作者实测条件和输入输出？导读未提供这些材料，两问未同时通过，因此不建 `examples/`，概念页的练习不得伪装为原型实验。

## 洞察四元组

每项洞察分成现象、工作根因假设、影响和建议，避免把机制解释混入事实。

### 交互与执行分责

- 现象：导读同时描述统一入口与独立 Worker。[F-007 至 F-009](../references/facts.md)
- 工作根因假设：把用户交互和任务过程混在同一上下文，可能增加背景切换与信息筛选负担。
- 影响：分工可能简化用户协调，但共享目标丢失也可能增加返工；尚未测量净收益。
- 建议：先写清 Router 与 Worker 各自需要的信息，再评估真实工作中的重复输入。

### 订阅转移协调成本

- 现象：后续相关消息可送到 Worker。[F-010](../references/facts.md)
- 工作根因假设：消息已有任务归属时，不必每次重新派工；代价转移到订阅生命周期管理。
- 影响：过期订阅、重复事件和错误归属可能抵消收益。
- 建议：给订阅定义建立、撤销、重开和去重规则；本次未确认原型实现。

### 恢复与授权共同约束主动性

- 现象：来源同时讨论主动响应、持续在线和 Watchdog。[F-006、F-012 至 F-013](../references/facts.md)
- 工作根因假设：后台任务持续推进时，异常、重复副作用和权限边界更难仅靠用户即时监督。
- 影响：减少打断的设计若缺授权与停止规则，也可能降低人的控制。
- 建议：先确定可自动完成的动作，再定义异常上报和人工判断时点。

## 协调分工模式

成熟度：单案例待验证。仅基于同一架构的导读与报道，不认定多案例实证，不登记为通用成熟模式。

适用于：任务可区分、事件有归属、结果可核对的多任务协作设计评审。不适用于：把强耦合任务任意拆开、需连续人工授权的高风险操作，或没有停机预算的常驻自动化。

1. 找出用户正在承担的协调动作。
2. 区分统一接待与具体任务执行。
3. 明确后续事件归属和订阅寿命。
4. 留下恢复所需的状态与外部结果证据。
5. 单独设置授权、预算、停止和人工判断。
6. 同时记录结果质量、系统开销与人的投入。

检验标准：能够解释每条事件去哪、每个结果谁核对、每个外部动作谁授权；真实验证必须有相同任务和基线。没有数据时写“待验证”，不填写模拟提效数字。

模式升级还需要真实案例：在结果质量不降低、权限约束满足的前提下，比较人的协调投入与周期总成本是否净减少。若反复错派、重复发布或净成本增加，应修订或否定对应步骤；单个成功案例不解除跨场景待验证限定。

反模式是依据本次证据缺口提出的风险提醒，**不是已发生的原型失败案例**：把独立上下文当安全隔离；把 Watchdog 当不会失败的恢复保证；把合成负载当真实团队效果；把研究提案当现成产品。

跨场景迁移示意：客户支持可区分接待、单个问题处理和后续消息归属，但退款等动作仍要另行授权。此例为教学假设，无用户数据、无生产验证。
