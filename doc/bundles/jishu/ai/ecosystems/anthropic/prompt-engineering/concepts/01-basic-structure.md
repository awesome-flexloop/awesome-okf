# 基础提示词结构（入门Ch1-3）

入门篇聚焦于三个最基础但最重要的技巧，掌握它们就能解决 60% 以上的提示词失败问题。

---

## Ch1: 基础提示词结构

### 核心原则：最简有效提示词公式

一个有效的提示词通常包含三个部分（不必每次都全，但这是很好的起点）：

```
任务描述（Task）：你希望 Claude 做什么
    +
上下文（Context）：背景信息、相关数据、用户情况
    +
约束（Constraints）：输出格式、长度、风格、禁忌等
```

**记忆口诀：说清做什么，给足背景，讲明要求。**

### 技巧说明

#### 1. 任务描述放在最前面

开门见山，让 Claude 一开始就知道这是什么类型的任务。

#### 2. 提供必要上下文

不要假设 Claude 知道你的具体情况。如果你是在处理特定文档、特定行业、特定用户，都需要说明。

#### 3. 明确输出约束

想要什么格式（列表/段落/JSON）、多长、什么语气、不要什么——这些都要说清楚。

### 正反示例对比

**❌ 坏的提示词（缺少结构）：**

```text
帮我处理一下这个
```

问题：没有说"处理"是什么意思、处理什么、想要什么结果。

**✅ 好的提示词（完整三要素）：**

```text
任务：将以下客户反馈总结为3个要点，每个要点不超过20字。

上下文：以下是某SaaS产品NPS调研中的1条用户反馈。

约束：用中文，使用动宾结构，保持客观，不要添加反馈中没有的信息。

<feedback>
产品功能很强大，但是界面太复杂了，新人上手要花很久。希望能出个新手引导教程，还有能不能把常用功能放在更显眼的位置？
</feedback>
```

### 常见失败模式与修复

| 失败现象 | 原因 | 修复方法 |
|---------|------|---------|
| 输出太泛泛、不够具体 | 缺少上下文 | 添加背景信息，说明你的具体场景 |
| 输出格式不对 | 没有约束格式 | 明确指定 Markdown/JSON/列表等格式 |
| 输出太长/太短 | 没有长度约束 | 指定字数、段落数、要点数 |
| 答非所问 | 任务描述模糊 | 重新组织语言，直接说你要什么 |

## Ch2: 清晰直接

### 核心原则

Claude 不会读心术。**你说得越清楚直接，结果越好。** 模糊和委婉是提示词的大敌。

### 技巧说明

#### 1. 使用肯定句，避免否定句

直接说"要什么"，而不是"不要什么"。

❌ 不要："不要写得太正式，也不要太随意，不要太长。"
✅ 要："用友好、对话式的语气，控制在200字以内。"

#### 2. 具体量化

"简短"是模糊的，"100字以内"是具体的。"几个要点"是模糊的，"3个要点"是具体的。

❌ 不要："简短总结一下"
✅ 要："总结为3个要点，每个要点一句话"

#### 3. 避免双重否定和复杂句式

❌ 不要："我不希望你不提到这个问题，除非在不需要提及的情况下。"
✅ 要："除非我明确要求，否则不要讨论价格问题。"

#### 4. 把最重要的放在前面或最后

模型对提示词开头和结尾的内容关注度最高（首因效应和近因效应）。重要的约束可以考虑在开头和结尾各提一次。

#### 5. 有歧义时直接问

如果你的需求有多种可能的解释，不要让 Claude 猜——要么在提示词中消除歧义，要么让 Claude 先提问再回答。

### 正反示例对比

**❌ 坏的提示词（模糊）：**

```text
帮我写点关于产品的东西，别太长，差不多就行。
```

问题："关于产品的东西"是什么？"别太长"是多长？"差不多就行"是什么标准？

**✅ 好的提示词（清晰直接）：**

```text
请为我们的产品"云笔记Pro"写一段产品介绍文案。

要求：
- 目标用户：职场白领
- 用途：放在官网首页的产品简介区
- 长度：150-200字
- 风格：专业但不生硬，突出"高效"和"跨设备同步"两个核心卖点
- 结构：一句话定位 + 两个核心功能说明 + 一句行动号召
```

### 常见失败模式与修复

| 失败现象 | 原因 | 修复方法 |
|---------|------|---------|
| Claude "想太多"，过度解读 | 指令模糊，给了想象空间 | 缩小范围，明确边界 |
| 输出总是偏题 | 指令不够直接 | 开头第一句就说清楚核心任务 |
| 多次尝试风格都不对 | 风格描述抽象 | 给出具体示例或参考物（如"像苹果官网的风格"） |
| 包含你不想要的内容 | 只说了"不要X"没说"要什么" | 用肯定句描述期望，必要时才补充禁忌 |

## Ch3: 角色分配（Role Prompting）

### 核心原则

给 Claude 分配一个具体的角色（Persona），可以引导它进入特定的专业视角，使用对应的知识体系、说话风格和思考方式。

### 什么时候用角色

角色提示在以下场景特别有效：

- 需要专业知识的任务（法律、医疗、财务、编程等）
- 需要特定语气或风格（客服、教师、教练、编剧等）
- 需要特定视角思考（产品经理、用户、面试官等）
- 简单提示效果不好，输出不够"专业"时

### 什么时候不用角色

- 非常简单直接的任务（翻译、简单摘要、格式转换）
- 角色反而会增加不必要的限制时
- 你只需要事实性答案而非特定风格时

### 角色设定模板

```text
你是一位[具体角色]，拥有[X年/什么领域]的经验。
你的专长是[具体能力]。
你的说话/写作风格是[具体描述]。
在回答时，你应该[具体行为1]、[具体行为2]。
你不应该[具体禁忌]。
```

### 正反示例对比

**❌ 没有角色的提示词：**

```text
帮我看看这段代码有什么问题。

[code]
def calculate_total(items):
    total = 0
    for item in items:
        total += item.price
    return total * 1.1
[/code]
```

**✅ 有角色的提示词（效果更好）：**

```text
你是一位资深Python工程师，有10年后端开发经验，擅长代码审查和重构。
你的审查风格是：先肯定做得好的地方，然后按严重程度（Bug→性能→可读性→最佳实践）列出问题，每个问题说明"问题是什么→为什么是问题→如何修复"。
语言简洁直接，不客套，给出可直接复制的修复代码。

请审查以下代码：

[code]
def calculate_total(items):
    total = 0
    for item in items:
        total += item.price
    return total * 1.1
[/code]
```

带角色的版本会得到更结构化、更专业、更可执行的代码审查结果。

### 更多角色示例

| 场景 | 角色提示示例 |
|------|-------------|
| 客服回复 | "你是一位电商平台的资深客服代表，以耐心、友好、解决问题为导向，语气亲切但专业..." |
| 教学解释 | "你是一位擅长把复杂概念讲简单的物理老师，面向高中生，善用类比和生活例子..." |
| 产品经理 | "你是一位互联网B端产品经理，思考问题从用户场景、业务目标、数据指标三个维度出发..." |
| 文案写作 | "你是一位有10年经验的广告文案，写的文案简洁有力、有记忆点、突出用户价值而非功能..." |
| 法律咨询 | "你是一位专精于合同法的律师，回答时先说明风险点，再给出合规建议，最后提示需要咨询专业律师的情形..." |

> ⚠️ **重要提示**：角色提示是引导视角和风格，不是让 Claude 真的"成为"那个角色。涉及法律、医疗、财务等专业领域时，Claude 的输出不能替代专业人士意见，必须加上免责声明。

### 常见失败模式与修复

| 失败现象 | 原因 | 修复方法 |
|---------|------|---------|
| 角色效果不明显 | 角色太泛（如"你是一个专家"） | 把角色具体化——什么领域、多少年经验、风格是什么 |
| 输出太啰嗦、过度表演 | 角色描述太复杂 | 精简角色设定，保留最关键的1-3个特征 |
| 被角色限制住，反而答错事实 | 角色设定与任务冲突 | 简单事实性任务不要加复杂角色 |
| 专业度不够 | 只分配了角色没给行为指引 | 在角色后补充"你应该如何回答"的具体行为规范 |

## 入门篇 80/20 技巧总结

这是入门篇最重要的几个技巧，掌握它们收益最大：

1. **三要素公式**：任务 + 上下文 + 约束
2. **清晰直接**：用肯定句、具体量化、开门见山
3. **角色加持**：专业任务给具体角色和行为指引
4. **首因/近因效应**：重要约束放开头或结尾
5. **从简单开始**：先写最简版本跑通，再逐步添加优化

## 练习建议

1. 找一个你之前写过的"效果不好"的提示词，用本章技巧重写
2. 对比两个版本的输出差异
3. 养成习惯：写完提示词后读一遍，问自己——"一个完全不了解背景的人看了这个，知道要做什么吗？"
