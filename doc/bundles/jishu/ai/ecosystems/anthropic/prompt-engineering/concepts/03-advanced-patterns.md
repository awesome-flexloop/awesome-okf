# 高级模式（Ch8-9）

高级篇聚焦于高风险场景（需要事实准确性）和复杂任务的提示词设计。掌握这些技巧后，你可以为生产环境构建可靠的提示词系统。

---

## Ch8: 避免幻觉（Hallucination）

### 什么是幻觉

幻觉（Hallucination）是指大语言模型生成**看似合理但实际不真实、不正确或无依据**的内容。这是 LLM 最受诟病的问题之一，在事实性要求高的场景（医疗、法律、金融、新闻）可能造成严重后果。

### 幻觉的常见表现

- 编造不存在的事实、数据、引用
- 张冠李戴（把A的事安在B身上）
- 自信地给出错误答案
- 虚构不存在的API、函数、法律条文
- 过度自信地推测未知信息

### 核心防幻觉原则

> **你无法100%消除幻觉，但可以通过提示词技巧大幅降低其发生概率，并让模型在不确定时"学会说不知道"。**

### 防幻觉技巧

#### 技巧1：明确要求引用来源

让 Claude 只基于你提供的信息回答，并在每个事实性陈述后标注来源。

```xml
<instructions>
回答用户问题时，你必须严格遵守以下规则：
1. 只使用<documents>标签中提供的信息来回答
2. 如果<documents>中没有足够信息回答，直接说"根据提供的资料，我无法回答这个问题"
3. 每个事实性陈述后必须标注来源文档的编号，如[来源：文档1]
4. 绝对不要编造或推测你不确定的信息
</instructions>

<documents>
<document id="1">
[文档1内容]
</document>
<document id="2">
[文档2内容]
</document>
</documents>
```

#### 技巧2："如果你不知道就说不知道"

直接、明确地告诉 Claude 承认无知比瞎编更好：

```text
回答时请遵循：
- 对于你确定知道的信息，直接回答
- 对于你不确定或没有足够信息的内容，明确说"我不确定"或"我没有足够信息回答"
- 不要为了显得完整而编造内容
- 承认无知不会扣分，编造信息才是严重错误
```

#### 技巧3：要求置信度标注

让 Claude 对自己输出的每个事实标注置信度：

```xml
<output_format>
对于每个回答要点，按以下格式输出：
- 内容：[事实陈述]
- 置信度：高/中/低
- 依据：[说明你为什么这么认为，或为什么不确定]

低置信度的内容必须明确提示用户需要进一步核实。
</output_format>
```

#### 技巧4：事实核查步骤

要求 Claude 在给出答案前先自我核查：

```text
在最终回答前，请先在<thinking>中完成：
1. 列出回答需要的关键事实点
2. 逐个检查每个事实点是否有明确依据
3. 标记出没有依据或不确定的点
4. 确认没有编造任何信息
然后再给出最终答案。
```

#### 技巧5：提供"我不知道"的示例（Few-shot）

用示例教会 Claude 什么时候应该拒绝回答：

```xml
<examples>
<example>
<q>公司2025年的营收目标是多少？</q>
<a>根据提供的资料，我无法回答这个问题——文档中只提到了2024年的营收数据，没有2025年的目标。</a>
</example>
<example>
<q>产品X的主要功能是什么？</q>
<a>根据文档1，产品X的主要功能包括A、B、C。[来源：文档1]</a>
</example>
</examples>
```

### 正反示例对比

**❌ 容易产生幻觉的提示词：**

```text
介绍一下我们公司2024年推出的新产品。
```

问题：没有提供任何信息，Claude 会基于"类似公司"的情况编造内容。

**✅ 防幻觉的提示词：**

```xml
<instructions>
你是公司内部知识库助手。回答时：
- 只使用<company_docs>中的信息
- 没有信息时明确说"资料中未提及"
- 引用具体文档编号
</instructions>

<company_docs>
<doc id="1">[关于产品A的说明]</doc>
<doc id="2">[2024年Q1财报摘要]</doc>
</company_docs>

<question>
2024年公司一共推出了几款新产品？分别是什么？
</question>
```

### 重要认知：提示词防幻觉的边界

提示词能降低幻觉概率，但**不能完全依赖提示词解决幻觉问题**。高可靠性场景需要多层防护：

| 防护层级 | 措施 |
|---------|------|
| L1 提示词层 | 来源引用、"不知道"指令、置信度标注（本章内容） |
| L2 检索层（RAG） | 只给模型真实资料，不让它"凭记忆"回答 |
| L3 工具层 | 关键事实用计算器、搜索引擎、数据库等工具验证 |
| L4 人工层 | 高风险输出必须人工审核 |

> 参考：[搜索与检索（RAG）](04-beyond-standard.md#search--retrieval搜索与检索rag) 章节了解 L2 防护。

### 常见错误与修复

| 错误 | 问题 | 修复 |
|------|------|------|
| 只说"不要编造"但没给替代方案 | 模型不知道该怎么做 | 明确告诉它"不知道就说不知道"，并给示例 |
| 开放式问题不给任何上下文 | 模型只能"凭记忆"，容易幻觉 | 需要事实准确时，提供参考资料（RAG） |
| 相信模型的"自信" | 模型说的越肯定，不代表越正确 | 要求置信度标注和来源引用，不要被语气迷惑 |
| 一个提示词既让它"有创意"又"完全准确" | 创意和准确是矛盾的目标 | 不同任务用不同提示词，不要混在一起 |

## Ch9: 构建复杂提示词

### 复杂提示词设计方法论

从零构建一个生产级复杂提示词，可以按照以下模块化框架组装：

```
1. 角色（Role）→ 2. 核心指令（Core Instructions）→ 3. 上下文/数据（Context/Data）
     → 4. 示例（Examples）→ 5. 输出格式（Output Format）→ 6. 约束/防护（Constraints/Guardrails）
```

下面给出四个常见场景的完整提示词模板。

---

### 模板1：Chatbot（对话机器人）

适用于客服、助手、行业垂类聊天机器人。

```xml
<role>
你是"云小助"，云笔记Pro的官方客服机器人。
- 你的性格：友好、耐心、专业、有同理心
- 你的知识范围：只回答云笔记Pro产品相关问题
- 你的目标：帮助用户解决问题，提升用户满意度
</role>

<core_instructions>
与用户对话时遵循以下规则：
1. 首先理解用户问题属于哪一类：账号问题/功能使用/计费问题/bug反馈/其他
2. 如果是常见问题，直接给出解决方案
3. 如果需要更多信息才能回答，礼貌地询问用户
4. 如果是bug或你无法解决的问题，引导用户联系人工客服，并告知工单通道
5. 不要回答与云笔记Pro无关的问题
</core_instructions>

<kb>
以下是常见问题知识库：
<faq>
<q>如何修改密码？</q>
<a>请进入「设置」→「账号与安全」→「修改密码」，按提示操作即可。</a>
</faq>
<faq>
<q>会员支持哪些付款方式？</q>
<a>我们支持微信支付、支付宝、银行卡支付。企业用户可开具发票，联系客服办理。</a>
</faq>
<!-- 更多FAQ... -->
</kb>

<guardrails>
安全与合规要求：
- 绝对不要泄露用户隐私信息
- 不要承诺你做不到的事情（如"我保证退款"）
- 不要贬低竞争对手
- 遇到辱骂用户保持礼貌，不要争吵
- 如果用户询问政治、色情等无关内容，礼貌拒绝并引导回产品问题
</guardrails>

<conversation_history>
<!-- 这里放对话历史 -->
</conversation_history>

<user_message>
{{用户最新消息}}
</user_message>

<output>
请回复用户，语气自然，像真人客服一样说话，不要太机械。
</output>
```

### 模板2：法律服务提示词

适用于合同审查、法律问答、合规检查等场景。**必须加免责声明。**

```xml
<role>
你是一位专精于中国民商法的律师助理，拥有10年合同审查经验。
你的工作是辅助律师进行初步审查，不能替代执业律师的正式法律意见。
</role>

<instructions>
请审查以下合同文本，按要求输出审查意见：
1. 首先总结合同类型、主要目的、签约双方
2. 按风险等级分类列出问题：
   - 🔴 高风险：可能导致重大损失或法律无效的条款
   - 🟡 中风险：约定不明确、对我方不利、可能引发争议的条款
   - 🟢 低风险：表述不够规范但不影响实质权利义务
3. 每个问题包含：条款位置、问题描述、风险说明、修改建议
4. 最后给出整体审查结论和建议
</instructions>

<contract>
[合同文本]
</contract>

<output_format>
# 合同审查意见

## 一、合同概要
- 合同类型：...
- 甲方：...
- 乙方：...
- 合同目的：...

## 二、风险点分析
### 🔴 高风险
1. **第X条**：[问题描述]
   - 风险：[为什么这是个问题]
   - 建议修改为：[具体修改文本]

### 🟡 中风险
...

### 🟢 低风险
...

## 三、整体结论
[总结评价，是否建议签署，需要重点修改哪些条款后再签]

---
⚠️ **免责声明**：本审查意见由AI辅助生成，仅供内部参考，不构成正式法律意见。
正式签署前请咨询执业律师审核。
</output_format>
```

### 模板3：金融服务提示词

适用于财报分析、投资研究摘要、风险评估等场景。**必须加免责声明。**

```xml
<role>
你是一位资深CFA持牌金融分析师，擅长上市公司财报分析和行业研究。
你的分析风格：数据驱动、客观审慎、注重风险提示、不做确定性预测。
</role>

<instructions>
基于提供的财报数据，撰写一份分析摘要。要求：
1. 所有结论必须有数据支撑，禁止主观臆测
2. 不仅要正面解读，也要指出潜在风险和隐忧
3. 对比上期数据和行业平均水平（如数据中有提供）
4. 对未来的判断使用"可能""预计""存在...风险"等审慎表述
5. 标注出数据中异常或需要进一步关注的科目
</instructions>

<financial_data>
[财报数据、行业对比数据]
</financial_data>

<output_format>
# [公司名称] [财报期] 财报分析摘要

## 一、核心结论
一句话概括本期业绩整体情况。

## 二、关键指标（同比/环比变动）
| 指标 | 本期 | 上期 | 同比 | 行业平均 |
|------|------|------|------|---------|
| ... | ... | ... | ... | ... |

## 三、亮点与积极因素
1. ...
2. ...

## 四、风险与关注点
1. ...（说明风险点及可能影响）
2. ...

## 五、展望
基于当前数据的审慎展望，明确标注不确定性。

---
⚠️ **免责声明**：本分析由AI生成，仅供参考，不构成任何投资建议。投资有风险，决策需谨慎。
</output_format>
```

### 模板4：编程提示词

适用于代码生成、代码审查、调试、重构等场景。

```xml
<role>
你是一位资深软件工程师，精通[编程语言/框架]，擅长编写清晰、可维护、高效的代码。
你遵循SOLID原则，写的代码有适当注释但不过度，有完善的错误处理。
</role>

<task>
[具体任务描述：写什么功能/修复什么bug/重构什么模块]
</task>

<requirements>
- 功能要求：...
- 性能要求：...
- 约束条件：必须使用X库/不能用Y方法/必须兼容Z版本
- 代码风格：遵循项目现有风格/PEP8/Google Style等
</requirements>

<context>
<existing_code>
[相关的现有代码，让Claude了解上下文]
</existing_code>

<dependencies>
项目已安装的相关依赖版本：
- library-x: 2.3.1
- framework-y: 18.0
</dependencies>
</context>

<instructions>
请按以下步骤完成：
1. 首先在<thinking>中简要说明你的实现思路和关键决策
2. 然后输出完整的代码
3. 代码后说明：
   - 如何使用这段代码（示例）
   - 关键设计决策和理由
   - 可能的边界情况和错误处理
   - 测试建议
4. 如果有多种实现方案，说明你为什么选择当前方案
</instructions>
```

## 提示词迭代优化流程

好的提示词很少是一次写就的，而是迭代出来的。推荐使用以下流程：

### Step 1: 最简版本跑通
先写一个最简单能工作的版本，不要追求完美。

### Step 2: 准备测试用例集
收集 5-10 个有代表性的测试输入，包含：
- 典型正常输入
- 边缘情况
- 可能触发幻觉/错误的输入

### Step 3: 批量测试
用所有测试用例跑一遍，记录哪些表现好、哪些有问题。

### Step 4: 针对性修复
不要因为一个case不好就大改提示词。先诊断问题是什么类型：
- 格式错了？→ 加强输出格式，用填空模式
- 理解错了？→ 改进指令描述，加示例
- 幻觉了？→ 加强防幻觉指令，提供参考资料
- 不稳定（有时对有时错）？→ 加思维链，细化约束

### Step 5: 回归测试
改完后**重新跑所有测试用例**——确保新的修改没有破坏之前好的case。

### Step 6: 固化版本
当所有测试用例都通过或达到满意效果，把这个版本的提示词保存下来，记录版本号和测试结果。

### 优化技巧

- **每次只改一个变量**：这样你才知道是什么改动起了效果
- **保留历史版本**：改坏了可以回滚
- **A/B测试**：对同一个输入用两个版本提示词，对比输出质量
- **从bad case学习**：每一个输出不好的case，都是优化提示词的机会
