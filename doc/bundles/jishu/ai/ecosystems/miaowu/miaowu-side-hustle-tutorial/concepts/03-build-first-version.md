# 第 2 步：用 Meoo 做出可交付的首版

> **目标**：做出一个能打开链接、跑通**一个**核心闭环的版本，并且店员不看你写的说明也能用。
> **通过判据**：店员在真实营业中 3 分钟内完成一次「找桌 → 核销 → 结账」，全程不需要你在旁边提示。
> **性质**：范围判据、数据模型、提示词结构、自测清单为编者推断（T-019–T-028）；工具能力与「功能能跑只是开头」为源文口径（F-021、F-024、F-025）。

## 1. 先定「不做」，再定「做」

首版失败的头号原因不是做不出来，而是**做得太多**。用三层表把范围钉死：

| 层 | 内容 | 判据 |
|---|---|---|
| **必须做（闭环）** | 一个角色、一个时段、一条主流程能从头走到尾 | 少任何一项，流程就断 |
| **可以延后（支撑）** | 让闭环更省事的辅助信息（列表、状态色、简单统计） | 不做也能完成闭环，只是慢一点 |
| **明确不做（明面清单）** | 多店、多角色权限、会员营销、硬件对接、报表导出 | 写进「暂不做」清单，给店主看 |

案例可以反证这一点：在线预约、数据仪表盘、套餐设置并没有出现在最初的开发里，而是在**驻店试用之后**才补齐（F-039–F-041）——说明它们属于「用了才知道要不要」的一层。文章也提醒：功能能跑起来还只是开头（F-021）。作者的建议同样是「不用急着把功能做全」（F-056）。

## 2. 首版范围示例（以门店计费场景为例）

| 层 | 首版内容 | 说明 |
|---|---|---|
| 必须做 | 桌位列表（含状态）· 计时与到点提醒 · 一次核销 · 一次结账 | 覆盖「找桌—看时间—核销—收钱」 |
| 可以延后 | 当日流水合计 · 桌位筛选 · 简单搜索 | 不影响主流程 |
| 明确不做 | 在线预约 · 经营仪表盘 · 套餐配置中心 · 多店切换 | 案例中都是试用后补的（F-039–F-041） |

> 把「明确不做」写成清单交给店主，比口头说「以后会做」更能建立信任，也能挡掉后面 80% 的加需求。

## 3. 最小数据模型

四张表足够跑通上面的闭环（推断，按 F-027 的功能归纳）：

| 表 | 关键字段 | 为什么要它 |
|---|---|---|
| 桌位 `tables` | 桌号、状态（空闲/使用中/待结账）、开始时间 | 「桌位即状态」是整个界面的骨架 |
| 套餐 `packages` | 名称、时长、价格 | 结账要核对套餐与加钟（F-016） |
| 订单 `orders` | 桌号、套餐、开始/结束、应付、实付、核销渠道 | 核销与结账的凭据 |
| 核销记录 `redemptions` | 订单号、渠道（美团/抖音）、时刻、操作人 | 两个平台分别核销（F-014）必须留痕 |

字段只留**店员每天会用到的**。任何「以后可能有用」的字段都不进首版。

## 4. 用 Meoo 的构建顺序

同库产品束把 Web 应用构建整理为「需求描述 → 参考设计 → AI 生成 → 交互优化 → 数据与发布」的主线（S3），与本文的场景对应关系是：

| 阶段 | 你要给出的输入 | 判据 |
|---|---|---|
| 需求描述 | 第 01 步的假设卡（角色、时刻、动作、字段） | 描述里没有「好看」「智能」这类词 |
| 参考设计 | 一两个你熟悉的同类界面，指明「像这个的哪一部分」 | 店员看一眼就知道点哪 |
| 生成与交互优化 | 真实数据量（三四十张桌子，不是一个） | 高峰期不卡、不错行 |
| 数据与发布 | 表结构与初始数据；发布后拿到可访问链接 | 手机能打开、能登录、能保存 |

> 工具替你处理服务器、数据库与部署，并生成访问链接（F-024、F-025）。这意味着**你的时间应该花在流程与字段上**，而不是环境上。

## 5. 五要素提示词

一条能用的需求描述，至少包含五要素：

```text
【角色】给门店 3 名店员用，不是给老板看的后台。
【场景】营业高峰，店员站在桌边用手机操作，单手可用。
【对象与字段】桌位（桌号/状态/开始时间）、套餐（名称/时长/价格）、
              订单（桌号/套餐/应付/实付/核销渠道）、核销记录（渠道/时刻/操作人）。
【主流程】打开首页看到桌位墙 → 点某桌看到剩余时间 → 点「核销」选渠道 →
          点「结账」自动带出套餐与加钟 → 完成后桌位回到空闲。
【验收标准】三四十张桌子同时使用时不串行；一次核销不超过 3 次点击；
            金额不需要手算；刷新后数据不丢。
```

写完后检查两件事：**有没有一个动作是你自己编的**（删掉）；**有没有一个字段是店员不会填的**（删掉）。

## 6. 发布前自测清单

| # | 检查项 | 通过标准 |
|:-:|---|---|
| 1 | 手机端首屏 | 3 秒内看到桌位墙，无需滚动 |
| 2 | 真实数据量 | 导入 40 张桌位不卡顿 |
| 3 | 主流程 | 找桌→核销→结账 ≤3 次点击/步 |
| 4 | 误操作 | 核销可撤销，且有确认 |
| 5 | 刷新与断网 | 刷新不丢；断网有明确提示 |
| 6 | 金额 | 加钟、套餐外消费自动算，不靠心算 |
| 7 | 多端 | 两台手机同时操作不互相覆盖 |
| 8 | 权限 | 店员看不到与己无关的配置项 |
| 9 | 链接 | 微信里点开可访问，不需要装 App |
| 10 | 兜底 | 出问题时能回到纸笔流程，不阻塞营业 |

## 7. 可交付的定义

「做完了」不是指功能齐了，而是指下面三件东西同时存在：

1. **一个链接**：手机点开就能用（F-025）；
2. **一页操作卡**：三步以内说清「开台—核销—结账」，贴在收银台；
3. **一个账号与一条回滚路径**：谁负责、出问题怎么退回手工。

第 3 件最容易被忽略，却决定了试用期店主敢不敢真的用。

## 8. 反模式

| 反模式 | 后果 | 纠正 |
|---|---|---|
| 先做会员/营销 | 核心流程没跑通，附加功能全是负担 | 回到三层表，只留闭环 |
| 先做「好看的仪表盘」 | 老板看一眼，店员不用 | 仪表盘属于「可以延后」 |
| 一次支持多店多角色 | 权限与数据隔离拖长工期 | 首版单店单角色，写进「暂不做」 |
| 用示例数据自测 | 一上真实数据就崩溃 | 用 40 行真实规模的数据压一遍 |
| 没有撤销 | 一次误点毁掉一天的账 | 所有写操作都要可撤回或可更正 |
