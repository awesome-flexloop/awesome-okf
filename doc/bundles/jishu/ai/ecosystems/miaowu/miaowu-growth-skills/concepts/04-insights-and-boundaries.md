# 洞察、可迁移模式与边界

> 本文件是执行者洞察层，**不是文章原文**。每条洞察都标注了对应事实编号；凡超出事实的推断，均以「假设」标注。

## 1. 三层知识结构

| 层 | 内容 | 来源 | 可靠性 |
|---|---|---|---|

## 2. 六条洞察（现象 / 工作原因 / 影响 / 建议）

### 洞察 1：数量不是冲突，而是聚合层级；命名不是错乱，而是身份分层

- **现象**：同一篇文章出现 24、22、25 三个技能数量（F-066、F-012、F-073），创作者名字在文章与市场之间也不一致（F-076、F-079–F-094）。
- **工作原因（假设）**：数量差异来自**聚合层级**——22 是精选行、24 是集合卡片（多算空格 2 个平台变体）、25 是广场条目（再算一起Vibe 1 条重复投稿）；名字差异来自**身份分层**——文章写共创博主显示名，市场写技能作者 handle。
- **影响**：读者若把三者当互斥集合，会误判「技能到底有几个」；若只记一个名字，会在市场搜不到或装错技能。
- **建议**：数量按层级读（22 精选 / 24 集合 / 25 广场）；检索用「共创者 + 技能名 + @作者」三元组；引用时注明层级与身份层。

### 洞察 2：Skill 的差异化在「交付物」，不在「生成能力」

- **现象**：六个示例的产出分别是报告、6 张图 + 文案包、用户画像 + 计划、诊断报告、两套图文稿、商业化报告（F-042–F-060）。
- **工作原因（假设）**：通用大模型也能生成文字，但增长工作的瓶颈是「产出能否直接进入下一步」，而不是「有没有内容」。
- **影响**：以「能不能生成」为标准的技能评估会失真；以「交付物能否被验收」为标准更接近真实价值。
- **建议**：安装前先问「它会给我什么文件/表格/计划，验收信号是什么」；答不出来就先不装。

### 洞察 3：六例共享「先定位、再产出、后验证」的增长纪律

- **现象**：每个示例都先定位问题（需求/发布/获客/诊断/商业化），再给交付物，最后给验证信号或后续核对项（F-044、F-047、F-050、F-053、F-060）。
- **工作原因（假设）**：增长失败多来自「动作与阶段错配」，而不是「动作不够多」。
- **影响**：把技能当「万能文案机」会得到一堆无法验收的素材；按阶段用则会形成连续的证据链。
- **建议**：每次使用技能前写一句「我在哪一段、这次要验证什么」，再选技能。

### 洞察 4：「缺数据不估」是增长诊断的分水岭

- **现象**：花叔示例在缺少留存数据时明确写「留存率填不出来，不估」，而不是补一个估算值（F-053）。
- **工作原因（假设）**：增长报告最常见的失真来源是「用看起来合理的数字填空」，后续决策会建立在伪精确上。
- **影响**：承认缺口会降低报告的「完整感」，但提高了可复检性；硬估则会把团队引向错误的优先级。
- **建议**：所有增长交付物都加一栏「本报告不能回答的问题」，并标注需要补采的数据。

### 洞察 5：平台市场是分发面，教程只能做「选型层」

- **现象**：文章只给技能标签与演示，真正的输入契约、权限、收费在平台详情页（F-013、F-061、F-077）。
- **工作原因（假设）**：平台技能会持续上架、改名、调权限，任何静态教程都无法替代详情页。
- **影响**：把教程当操作手册会失败；把教程当选型地图则仍然有效。
- **建议**：教程写「怎么选、看什么、验收什么」，详情页写「怎么装、怎么填、什么权限」，两者分工。

### 洞察 6：内容推广的可复用资产是「简报 + 对照」，不是单篇爆款

- **现象**：冲浪 Skill 的工作简报冻结了目标受众、期望行动、账号身份、可用素材，并给出 A/B 两套稿件与效果观察方法（F-055–F-057）。
- **工作原因（假设）**：内容效果高度依赖上下文；每次重述背景会造成风格漂移，单篇也无法判断是选题还是执行的问题。
- **影响**：只追单篇爆款会让下一轮从零开始；有了简报与对照，下一轮可以只改一个变量。
- **建议**：把「简报」作为长期资产维护；每轮至少保留两套可对照的稿件。

## 3. 三个可迁移模式

### 模式 A：场景 → 技能 → 交付物 三层选型卡

- **触发场景**：面对一长串工具、Skill、插件或服务清单，不知道从哪开始。
- **核心步骤**：
  1. 用「当前情况」列（不是工具名）描述问题；
  2. 为每种情况只映射 1 个候选技能；
  3. 为每个候选写清「交付物 + 验收信号」；
  4. 安装前回详情页核对名称、权限与输入要求。
- **反模式**：按技能名或热度选；一次装全套；没有验收信号就开始用。
- **迁移验证**：适用于任何 Skill 市场、插件市场、内部工具目录；本案例的 7 行速查表与 22 条清单即原型（F-010、F-019–F-040）。

### 模式 B：模拟数据标注法

- **触发场景**：用虚构产品、样例数据或演示账号做教程、售前演示、培训。
- **核心步骤**：
  1. 在示例开头标明「模拟产品/模拟数据」；
  2. 在每张截图或表格旁重复标注；
  3. 在教程正文用单独段落声明「不可当真实数据引用」；
  4. 给出真实数据时应替换的字段清单。
- **反模式**：把演示数字混入真实汇报；只在小字标注；用「示例」二字代替明确声明。
- **迁移验证**：本案例的六例均标注模拟产品（F-069、F-071），且本教程在每处引用时重复限定（核验项 19）。

### 模式 C：缺口优先诊断

- **触发场景**：数据不全，但业务方要求给出增长判断或优先级。
- **核心步骤**：
  1. 先列出「要回答这个问题必须有的数据」；
  2. 对照现有数据，标出缺口；
  3. 缺口对应的结论一律写「不估/待补」，不填估算值；
  4. 把「补数据」列为独立行动项，并给采集口径。
- **反模式**：用行业均值硬套；用「大概/可能」掩盖缺口；把补数据当成报告的附录而不是行动项。
- **迁移验证**：花叔示例的「留存率填不出来，不估」是直接原型（F-053）；可迁移到经营复盘、投放复盘、产品数据分析。

## 4. 为什么本束不设 `examples/`

按可复现性两问判定：

| 问题 | 判定 | 理由 |
|---|---|---|
| 是否有明确的输入、步骤与可观察输出？ | 部分 | 文章给了示例输入与输出描述，但没有各技能的完整输入契约与安装步骤（F-013、F-061） |
| 独立执行者能否重复并验证结果？ | 否 | 需要 Meoo 账号、安装具体技能、技能版本与权限可能变化；本教程无法保证同一输出（F-077） |
| 结论 | **不设 `examples/`** | 避免把「演示」写成「可复现教程」；示例拆解放在 `concepts/02-six-skills-in-practice.md`，并逐处标注模拟 |

> 这与同库既有束 `miaowu-bounty-plaza` 的处理一致：广场层只给一句话说明，不设 `examples/`（F-073）。

## 5. 边界与使用限制

### 5.1 单源、归一模型与命名覆盖

- 22 条清单、技能标签、六个示例的输入输出，均为文章单源（F-019–F-060）。
- 24/22/25 已归一为**层级模型**（22 精选 + 空格 2 变体 = 24；再 + 一起Vibe 1 条重复投稿 = 25），但 24 的集合卡片为登录后页面，未直接观测，标 `modeled`（核验项 23）。
- 命名统一为**两层**：文章共创博主显示名 ↔ 市场技能作者 handle；15/22 已匹配，7 行仅文章口径（F-095、核验项 24）。
- 塔斯海条目仍标 `likely`：市场同主题技能为「GitHub星标增长器」@常成，但广场另有「内容选题咨询顾问」，不能写成唯一归属（核验项 16）。

### 5.2 平台依赖与时效

- 技能安装、权限、收费、数据留存政策以 Meoo 技能详情页为准（F-013、F-061、F-077）。
- 文章称技能市场暂仅支持电脑访问（F-063），未做移动端实测（核验项 22）。
- 清单与技能状态易变，`stale_after` 设为 2027-04-24；到期前应复核技能是否仍可检索、名称是否变更。

### 5.3 数据与合规

- 六例均为模拟产品/模拟数据，禁止把其中数字写入真实业务汇报（F-069、F-071）。
- AI 生成的图文在发布前必须补真实产品截图、体验链接，并核对图片内容（F-047、F-071）。
- 本束不保存文章全文、不保存原始配图；只保留转述与事实编号，遵循公开文章的原创改写边界。

### 5.4 成熟度

- **L1-draft**：单一案例、单一信源、无独立实测；三个模式可迁移但尚未在第二个场景验证。
- **口径与命名模型为 L1.5**：22→24→25 的层级模型与两层命名映射已用公开市场 252 张卡片交叉验证（15/22 匹配），但 24 集合卡片未直接观测、7 行未匹配；升级到 L2 需补齐集合页证据与剩余 7 行的平台身份。
- 升级到 L2 的条件：至少再用一个 Skill 市场/工具目录复现模式 A；用真实（非模拟）项目复现模式 B/C 各一次。
