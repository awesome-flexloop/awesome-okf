# WorkBuddy 开放平台：四类开放能力、核心概念与时效边界

本篇回答三个具体问题：WorkBuddy 开放平台对外暴露哪几类能力？调用它需要先理解哪些核心概念？使用这套接口时又有哪些必须知道的时效边界？事实取自白皮书 §7 开放能力概述（F-110 ~ F-118）。

## 一、四类开放能力与调用凭据

开放平台以 REST API 形式暴露四类能力：助理管理、任务生命周期、本机执行、积分与签到（F-110）。这四类能力串起了从「建角色」到「派任务」，再到「本机动作」与「权益发放」的完整链路。

这些接口均以用户身份调用，凭据是 OAuth 2.0 授权后颁发的个人票据（access_token）（F-111）。换言之，接口不是以合作方应用身份、而是以最终用户身份操作，返回的资产也归属该用户——这一点直接决定了后文「用户标识」与「票据保管」两项设计的必要性（F-111）。

四类能力覆盖了合作方使用 AI 能力时最常需要做的动作：先以 Assistant 定义角色，再以 Task 发起执行，需要时启用本机能力，涉及权益时使用积分与签到（F-110、F-115、F-116、F-117）。

## 二、正式上线声明及其时序不自洽

白皮书 §7 在「已正式上线」框中声明：平台已于 2026 年 9 月 2 日正式发布，即日起可申请接入，无需等待排期（F-112）。

**必须显式提示**：本白皮书页脚所载发行日期为 2026 年 08 月（F-002），早于此处声称的正式发布日 2026-09-02，二者**时序不自洽**（勘误 E-1）。本束对两处事实并列登记、不作裁决（F-002、F-112）。该问题属于白皮书内部不一致，而非被外部证据证伪；因此本束在对外引用时保持这一限定，不把该日期当作上线时间的确定结论。也正因如此，引用本束技术内容时，**不得据此断言接口在某一具体日期之后一定处于可用状态**。

## 三、时效边界：以官网为准 + 官网入口未核验

- **接口以官网为准**：白皮书明示，第 7–10 章所述全部接口清单、鉴权方式、示例代码与联调流程，均以官网开发者文档的最新版本为准（F-113，`以官网为准`）。这意味着本知识包中的接口快照是白皮书发行日的记录，而非权威最新口径；若要按最新口径对接，须自行访问官网开发者文档，本知识包不替代官方文档（F-113）。
- **官网入口未核验**：开放平台官网入口为 `https://open.workbuddy.cn/`，在官网可完成注册应用、获取凭证、下载对接文档、提交硬件接入意向（F-114，`未核验`）。本束采集期间未访问、未注册该官网账号（未核验项 O1），因此官网当前的实际能力清单与白皮书快照之间的差异，本束无法对照（F-114）。

## 四、能力构成：三项基础构件

开放平台的能力由三项基础构件组成（F-115 ~ F-117）：

| 构件 | 说明 |
| --- | --- |
| Assistant（助理） | 用户拥有的 AI 角色，支持 local（本机端）与 cloud（云端）两种部署位置，提供创建、查询、更新、删除与激活（F-115） |
| Task（任务） | 对指定助理发起的一次执行，返回回复内容、工具链、产出物与状态（F-116） |
| 本机能力 | 当用户 PC 上装有 WorkBuddy 客户端时，可通过任务接口读取桌面文件或运行本机任务（F-117） |

三项构件的具体调用方式见 [接口调用](06-assistant-and-task-apis.md)。三者的关系是：Assistant 是角色载体，Task 是执行单元，本机能力则是 Task 在 local 执行位置上的一种可选形态（F-115、F-116、F-117）。

## 五、核心概念五项

要理解开放平台的调用，需要先记住五个核心概念（F-118）：

| 概念 | 作用 |
| --- | --- |
| access_token（个人票据） | 代表用户身份，用于调用所有开放接口（F-118） |
| openid | 用户在合作方 App 下的唯一标识，用于数据隔离（F-118） |
| asst_id | 助理 ID，创建 Assistant 后返回（F-118） |
| task_id | 任务 ID，创建 Task 后返回（F-118） |
| execution_target（任务执行位置） | cloud 走云端执行环境，local 走用户本机客户端（F-118） |

其中 access_token 的获取路径（OAuth 2.0 授权码 + PKCE）属于授权登录范畴，见 [OAuth 授权](05-oauth2-authorization-flow.md)；openid 与另外两级用户标识（unionid、uid）的差别，同样在该篇的用户标识三级表中说明（F-131）。这五个概念分别对应身份、用户隔离、两个资源标识与执行位置，几乎贯穿后续每一条接口的请求与响应（F-118）。
