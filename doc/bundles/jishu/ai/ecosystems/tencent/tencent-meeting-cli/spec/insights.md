# 腾讯会议 CLI（tmeet）Insights

> 8 条核心洞察，每条遵循四元组结构（陈述 / 证据 / 反常识 / 行动），证据均回引 [facts.md](facts.md) 编号事实。洞察一至四基于首批 8 信源（v1.0.18 截面），洞察五基于 2026-06-25 腾讯文档用户手册（s-qqdoc）加入后的跨日期信源比对，洞察六至八基于第三轮源码主体学习（s-code，tag v1.0.18 @ e631b35，2026-10-04）。

## 洞察一：安全边界在「Skill 提示词层」而非「CLI 代码层」——手与脑是两个可分离组件

**陈述**：tmeet 的安全模型是分层的——CLI 二进制（Go，经 npm 包装）只负责注入 OAuth Token 并透传开放平台 REST API（F-096），它本身不在本地拦截写操作；真正约束 AI「取消会议前必须问人」「踢人必须取自参会列表」「不许向用户显示 meeting_id」的，是随仓库分发的 `SKILL.md` 提示词契约（F-072~F-076）。CLI 是「手」，Skill 是「脑」，二者通过 `npx skills add` 分别安装（F-012），官方安装指南把 Skill 标注为「必需」。

**证据**：F-072（9 个二次确认命令清单全部出自 SKILL.md 而非 command.md 的参数约束）、F-071（踢人 open_id 来源硬约束是提示词规则，CLI 接口本身接受任意 openid）、F-066（通讯录场景白名单只存在于 SKILL 描述文本）、F-096（CLI 侧职责仅为 Token 注入与 REST 转发）、F-097（官方风险提示把模型幻觉/提示词注入列为用户自担风险）。

**反常识**：用户直觉认为「官方出品的命令行工具自带官方安全兜底」，但 tmeet 的写操作确认是**提示词级**约束——它只在宿主 Agent 忠实加载并执行 Skill 时生效；绕过 Skill 直接敲命令（或不遵守 Skill 的 Agent）依然可以无确认取消会议。安全不是被代码强制执行的，是被写给模型读的自然语言规则「请求」执行的。这是 Agent 时代软件分发的一个结构性转向：策略（policy）与机制（mechanism）分离，策略以 Markdown 文本为载体。

**行动**：① 使用者务必同时安装 CLI 与 Skill 两件套并重启 Agent（F-012、F-019），不能只装 npm 包；② 企业/团队引入时，应在宿主 Agent 侧另加一道不可绕过的写操作审计（如网关层对 cancel/update/kick 的拦截），不能把 SKILL.md 文本当作安全边界；③ 敏感会议（高管/保密）场景优先用独立账号并通过 `auth logout` 及时收口（F-031）。

## 洞察二：「纪要」是两套权限模型不同的独立产物——检索必须按权限分流并双向兜底

**陈述**：一场腾讯会议可能产生两类互不从属的纪要：元宝纪要（会中 ASR 生成，参会者人人可取，无逐字稿）与录制纪要（依附录制文件，创建者所有、需权限、有逐字稿）（F-062）。官方 Skill 为此设计了权限驱动的分流路由：已知会议先用 `meeting get` 顺带拿 `permission_status`，`can_view` 走录制纪要、其余走元宝纪要、录制侧失败再降级（F-063）；跨会议搜索则两条链路都执行、按会议去重、逐条标注来源（F-064）。

**证据**：F-062、F-063、F-064（双纪要体系与分流规则）；F-057/F-058（录制侧 smart-minutes 与 transcript-* 命令族）；F-060/F-061（元宝 minutes search/get 独立命令族及其内容开关）；F-059（录制权限申请 prepare/commit 两阶段，证明录制内容存在正式权限审批流）。

**反常识**：「把昨天那个会的纪要给我」在传统软件里是一次确定查询，在 tmeet 里是一道**权限推断题**——命令名里都带 minutes 字样的两套东西，数据源、所有权、是否有逐字稿完全不同。更反直觉的是官方明确禁止「一条搜空就报告没有」：AI 总结会概括掉具体数字与某人原话，而逐字稿里可能保留（F-064）。同时，「按时间找纪要」的正确入口是 `minutes search --start/--end`，而不是先 `meeting list-ended` 再逐场取纪要的 N+1 调用（SKILL.md 路由规则）。

**行动**：① 教程必须把「双纪要权限分流」作为独立概念讲透，不能把 record 与 minutes 混为一个域；② Agent 作者应复用官方三段决策（permission_status 分流 → 失败降级 → 双向兜底）而非按命令名字面匹配；③ 用户要「原话/准确记录」时直接走 transcript-*，并明白元宝纪要本身是 AI 加工品。

## 洞察三：CLI 的第一用户是模型而非人——输出契约处处为「机器可组合性」优化

**陈述**：tmeet 的接口设计优先级明显面向 Agent/脚本管道消费，而非人类终端阅读：统一 `{trace_id,message,data}` JSON 信封（F-036）、`--compact` 由服务端按命令下发精简字段列表以裁剪 token（F-077）、游标分页 `--page-token` 全命令统一（F-039）、全部时间参数强制 ISO 8601 带时区（F-038）、event 族严格 stdout（NDJSON 业务流）/stderr（ready/exit 诊断）分离并规定退出码 0/1/2 语义（F-081）。

**证据**：F-035~F-039（全局输出/分页/时间契约）、F-077（compact 中间件与模型解析场景默认开启的指引）、F-078（翻页 5 页/200 条征询阈值，专为控制 Agent 上下文膨胀设计）、F-079~F-081（bus + NDJSON + ready 标记的管道契约）、F-085（jq_root_path 错配会静默丢事件，要求先 schema 再 jq）。

**反常识**：传统 CLI 追求「人敲着顺手」（交互式 prompt、彩色表格、自由文本），tmeet 刻意反其道——`auth login` 阻塞前台且不适合后台（F-023）是少数例外，其余全部为「被程序调用」设计：event consume 甚至完全不读 stdin，使 nohup/setsid/后台天然兼容（F-084）。判断一个 CLI 是否「Agent-native」，可看它是否把 token 预算（compact）、流式就绪信号（ready marker）、退出码分支、幂等游标当作一等公民——tmeet 四条全中。

**行动**：① 在自己的 Agent 工作流中默认对查询命令加 `--compact`，需要原始字段时才取全量；② 编排 event 自动化时以 stderr ready 行作为启动同步点、按退出码 2 写健康检查分支、订阅前先 `event schema` 确认 jq_root_path；③ 借鉴其「信封+精简字段白名单+游标」三件套作为设计企业内部 Agent CLI 的模板。

## 洞察四：能力缺口与实时事件都被「产品化」——CLI 自带反馈回流管道与 per-host 事件总线

**陈述**：tmeet 把两件通常散落在客服与运维侧的事收进了 CLI：其一，Agent 找不到工具/工具报错/能力不足时，可用 `tshoot feedback` 按 5 类 category 直接把「原始意图+已尝试动作+阻塞点」结构化上报平台（F-091），且上报前二次确认、强制隐私脱敏、同问题去重（F-092）；其二，v1.0.18 新增 per-host bus 守护进程，多个消费者复用一条 WSS 长连接订阅实时会议事件，bus 存活探测基于进程级独占文件锁，logout 时通过 ResourceReleaseHook 两阶段清理（F-079、F-082、F-032）。

**证据**：F-090~F-092（日志导出与反馈回流）、F-079~F-086（event/bus 全套机制：共享 WSS、NDJSON fan-out、orphan/stale_owner 状态机、隐藏 _bus、不回放历史）、F-009/F-010（v1.0.18 版本与变更记录密度，两版本间隔仅 2 天）、F-098（事件错误码体系）。

**反常识**：多数官方 CLI 是「能力的终点」——命令发出去、结果返回来，产品方对 Agent 在哪里卡住是盲的；tmeet 把「我想做但你的工具做不到」设计成一条**由 Agent 自主触发的结构化遥测命令**，形成使用侧→平台侧的能力缺口回流闭环。而 per-host bus 模式也与常见「每消费者一条 WebSocket」的直觉相反：它在本机引入一个隐藏守护进程做连接复用与 fan-out，并配套了 stale_owner/orphan 自愈状态机和 logout hook——这是把「Agent 长期驻留、多任务并发监听」当作默认运行形态来设计的基础设施。

**行动**：① 团队构建自己的 Agent 工具链时，可直接复刻「feedback 命令 + category 枚举 + 脱敏模板 + 二次确认」四件套，把 Agent 失败变成可统计的产品输入；② 需要实时事件驱动的场景用 `event consume` 批处理模式（`--max-events`/`--timeout`）做定时采集，避免自写轮询；③ 运维上把 `event status --fail-on-orphan`（退出码 2）纳入健康检查，账号切换后用 `event stop --force` 清理残留 bus。

## 洞察五：三套带日期的信源构成「文档时间差」证据链——对外命令契约纯增量、安全契约在提示词层独立加厚

**陈述**：关于 tmeet 的命令面，知识包现有三套带明确日期的官方文本：腾讯文档用户手册（最后保存 2026-06-25，19 命令，F-099/F-104）、腾讯云文档（页面更新 2026-07-08，同为 19 命令口径，F-034）、仓库 `docs/command.md`（对应 v1.0.18，2026-09-11，44 子命令，F-009/F-033）。将最早一套的 19 个命令名与最新一套逐一比对，19 个全部保留、无一重命名或移除，新增的 25 个全部落在新命令名或 contact/control/minutes/app/event 五个新域（F-105）。同期安全侧的证据是：2026-06 用户手册写二次确认仅覆盖 create/update/cancel 三个写命令，而 v1.0.18 的 SKILL.md 清单已扩展到 9 个（F-106、F-072）。

**证据**：F-099/F-104（用户手册的日期与 19 命令逐名表）、F-105（19 旧名在 v1.0.18 全部存活、44=19+25 纯增量的逐一核对）、F-034（云文档 2026-07-08 仍是 19 口径，证明滞后窗口以「月」计）、F-106（确认清单 3→9 的加厚轨迹）、F-009（v1.0.18 日期）、F-107（同一句中 AES 与 Keychain 并列，顺带证明早期「凭证存储口径冲突」其实是同一事实的两面）。

**反常识**：「文档不一致」通常被当作噪声或笔误处理（本束最初也把 Node 14/16、19/44 标记为口径差异），但当信源带有可核对的日期时，差异本身是**版本演化的直接证据**：①它证明这个 CLI 对 Agent 的外部命令契约是严格向后兼容的——新增能力靠新命令/新域承载，旧命令名不破坏，这对自动化资产（脚本、Skill、教程）的存续是关键承诺；②安全策略的加厚发生在 SKILL.md 提示词层（3→9）而命令层保持稳定，与洞察一的「策略/机制分离」互为印证：策略文本可以高频修订而无需改变二进制契约。真正的风险不在「文档有差异」，而在读者把滞后文档（19 命令、≥16）当作当前事实——云文档滞后窗口约两个月，用户手册至今（2026-10）仍停留在 19 命令面。

**行动**：① 引用 tmeet 任何命令/参数时必须标注信源日期与版本，参数级问题只信带版本号的仓库 `docs/command.md` 与 CHANGELOG，用户手册只用于理解「官方想让普通用户知道什么」；② 编写自动化时可放心依赖 19 个旧命令名（已验证跨版本存活），新域命令（event/app/control 等）则要预期继续变动并锁版本；③ 评估同类 Agent-native CLI 的成熟度时，把「旧命令名存活率」「策略层（Skill/规则文本）与机制层（二进制）的修订频率差」作为两个可观察指标；④ 本束 stale 到期重抓时，优先复查用户手册是否已跟进新命令域，以量化官方文档的滞后期。

## 洞察六：「薄 CLI」架构——命令是手写 cobra 壳，唯一被远程驱动的是输出契约而非命令定义

**陈述**：源码证伪了「38 个 ApiCmd 常量 + compact-schema 接口 = schema-driven 命令框架」的第一印象。事实是：38 个 ApiCmd* 字符串（F-129）既不生成 cobra 命令也不生成 flag，全部 flag 手工 StringVar 系列声明、REST 路径硬编码在各叶子命令的 Run 中（F-130、F-131）；ApiCmd 只有两个消费者——请求头 Tmeet-Cli-Name 与 compact 字段表的拉取参数（F-130）。整个二进制是「手写 cobra 壳 + 洋葱中间件（middleWare.Chain）」的薄装配层（F-128），远程 `/v1/api/compact-schema` 能动态决定的只是**输出时保留哪些字段**（F-133），命令的存在性、参数形态、调用哪个 API 全部在编译期固化。

**证据**：F-129/F-130（38 常量的定义位置与仅有的两个用途，关键计数已经 Grep 机械复核）、F-131（EnumValue 全仓仅 2 处使用，证明连枚举校验都没走「schema 自动生成」路线）、F-133（compact 远程化仅限输出裁剪，且 filecache + 服务端 TTL + 失败透明放行）、F-132（一个叶子命令承载多 ApiCmd 的切换也是手工 FlagSwitch）、F-135（HintProvider 接口零 import、靠同签名方法结构化装配——同一种「不依赖抽象框架、手工对接」风格的旁证）、F-115（连构建期变量注入都只做了 Version 一半，BuildTime 的 -X 指向不存在的符号）。

**反常识**：看到名为 api_schema 的文件和一个返回 schema 的服务端接口，工程师很容易脑补出「服务端下发 schema → 客户端动态生成命令/参数」的现代插件化架构（类比 AWS CLI 的 model-driven 设计）；tmeet 实际选择了相反的极端——**变化最快的东西（给模型看的字段精简表）远程化，变化最慢的东西（命令契约）发版固化**。这与洞察一/五形成闭环：命令契约是对自动化资产的兼容性承诺（19 旧命令全存活），所以不敢远程驱动；token 预算字段表是运营调优项（哪些字段模型最常用、哪些最占上下文），所以必须能不发版热调。架构分层不是按「技术上能不能动态」切的，是按「变化频率与兼容性承诺」切的。另一个细节同样反直觉：Makefile 一本正经地注入 BuildTime，但 Go 侧根本没有该符号——发布工具链里存在纯装饰性的链接参数，且因 Go 链接器静默忽略而从未被发现。

**行动**：① 二开 tmeet（如内部封装）时不要试图复用 ApiCmd 常量做命令反射——它不包含路径/参数信息，应直接读各 Run；② 设计自己的 Agent CLI 时可复用这条切分原则：命令面手工固化保兼容、输出面白名单远程化保 token 运营空间，并务必实现「远程 schema 失败透明放行 + 本地缓存」否则一次配置故障会瘫痪全部查询；③ Code review 同类项目时，把「命名像 schema 的东西是否真的驱动行为」列为必查项，命名暗示的架构要以调用点 Grep 验证；④ 构建脚本审计应检查每个 `-X` 目标符号是否存在（可加一条 `go tool nm` 断言），防止装饰性注入。

## 洞察七：凭证安全是「主密钥分层托管 + AAD 绑定 + 原子文件」的平台自适应体系——官方「Keychain」说法只在 macOS 字面上成立

**陈述**：用户面文档统一说「AES-256-GCM 加密、存入系统 Keychain、与设备绑定」（F-024、F-025、F-107），源码显示真实结构是三层：①数据层**加密原语**三平台一致——UserConfig JSON 经 AES-256-GCM 加密、明文从不落盘（F-155、F-150），但**存储载体分叉**：macOS/Linux 写 `<open_id>.enc` 文件，Windows 把密文 base64 后写注册表值（同一 `HKCU\Software\TmeetCli\keychain` 键，全程无文件操作、业务值不经 DPAPI）（F-149）；②主密钥层按平台自适应托管——macOS 主密钥进系统 Keychain、Linux 主密钥就是 0600 权限的 `master.key` 文件（不用任何系统 keyring）、Windows 进注册表并经 DPAPI 保护（F-149、F-152）；③防搬运层——GCM AAD 绑定 open_id 字节防止跨账号替换密文（文件或注册表值），且保留 nil-AAD 解密路径自动迁移历史密文（F-151）。配套原语包括 filelock 跨进程互斥、filecheck 拒符号链接/非属主文件（unix）、tmp+Sync+Rename 原子写、0700 目录（F-144、F-153、F-154），登出时再用 ResourceReleaseHook 保证资源释放成功后才删凭证（F-145）。

**证据**：F-149（keychain.go 三平台分叉与 darwin 注释，对 F-025 的直接口径深化）、F-150/F-151（crypto.go 算法参数与 AAD、SEC-009 注释）、F-152（Windows DPAPI entropy 组成与坏 key 自愈）、F-153/F-154/F-144（锁、文件校验、原子写三件套）、F-141/F-142（token.lock 包裹登录写盘、三份配置结构分离）、F-147（设备指纹 .machine_id 首写者胜，支撑「与设备绑定」宣称）、F-192（panic 不出 coredump，避免栈/内存泄敏）。

**反常识**：①「存入系统 Keychain」在三分之二的平台上是假的——Linux 用户机器上并没有系统级 keyring 兜底，安全强度等价于「0600 文件 + 运行用户隔离」，root 或同权限进程可读；这不是缺陷而是刻意的跨平台一致性取舍（macOS Keychain 与 Windows DPAPI 有原生 API，Linux 没有事实标准），但文档用 macOS 的措辞掩盖了平台差异。②密钥设计刻意「不聪明」：32 字节随机主密钥、无 KDF、无口令派生——好处是没有弱口令面、加解密零延迟，代价是密钥文件泄露即全泄露，整个体系的物理边界就是用户主目录权限。③AAD 绑定与「fallback 到 nil AAD」是一对矛盾共存：前者防替换攻击，后者为了兼容旧密文自动迁移，等于在新版本里永久保留了一条降级路径（迁移完成前该路径无法安全删除）。

**行动**：① Linux 部署 tmeet 的运维方应自行补偿主密钥文件强度——全盘加密、限制 home 目录访问、避免多用户同机；安全审计时把「文档宣称 Keychain」与「0600 文件 / Windows 注册表」的差异写进评估报告；② 备份/迁移时须知：macOS/Windows 密文与设备绑定不可搬（文档口径正确；Windows 业务密文虽在注册表但 AES-GCM 主密钥受 DPAPI 绑定），Linux 上 .enc + master.key 一起拷走即可解密——恰因后者没有系统托管；③ 借鉴该设计做跨平台密钥管理可直接复用分层模板（加密原语统一 / 存储后端与主密钥分平台 / AAD 绑账号 / 原子写 / filecheck），但应给 AAD-fallback 设迁移截止期而非永久保留；④ 排障凭证问题时按 F-142 的三份配置（config.json/agent.json/业务密文——macOS/Linux 为 `<open_id>.enc` 文件、Windows 为注册表同名值）+ master.key 逐项核对，不要寻找一个不存在的「统一 config」。

## 洞察八：per-host bus 是一个完整的「单机 IPC 微内核」——alive-lock 选举、owner 哈希隔离、硬编码事件注册表与字符串退出语义

**陈述**：v1.0.18 的事件系统不是「CLI 里内嵌了个 WebSocket 客户端」，而是一个分层完整的单机微内核：source 层独占一条 WSS 长连（应用层心跳、指数退避、token 轮换鉴权）（F-167~F-169），bus 层做 Hub fan-out 与引用计数订阅（0→1 才发 SUBSCRIBE、1→0 刻意不发 UNSUBSCRIBE 而靠服务端 TTL 回收）（F-163、F-175、F-176），transport 层是 unix socket / Windows 命名管道上的 NDJSON 八类消息协议（F-164、F-170），spawner 以再 exec 自身隐藏命令 `event _bus` 的方式完成守护进程化（F-165），busdiscover 用 `bus.alive.lock` 的非阻塞 TryLock 而非 PID 探活做选举与存活判定（F-166）。多用户安全靠 hello 帧的 `sha256(openId)[:12]` owner 哈希（F-172）；事件类型是**编译期硬编码的 8 个注册表项**（F-173、F-174）；消费者生命周期用字符串 reason（limit/timeout/signal/shutdown）与仅两处生效的退出码 2 表达（F-180）；登出以 owner 匹配 → 3s 优雅期 → 按 PID 强杀的钩子闭环收口（F-183）。

**证据**：F-163~F-166（分层、IPC 端点、自举方式、存活锁）、F-167~F-169（wsspb 协议帧、25s 应用层心跳、10s/5min/1-30s/30 次退避参数）、F-172~F-174（owner hash、8 个 RegisterKey 与 recording.failed 未注册的反例）、F-175~F-178（引用计数、drop-oldest、30s 空闲退出、512 TraceID 去重环）、F-179~F-183（consume 的 frameCh/ready 行/落盘 0600/stop 三件清理/登出强杀）、F-079~F-086（用户面契约与源码逐条对应）。

**反常识**：①「alive 判据是文件锁而不是 PID」反运维常识——PID 会被系统回收复用、pid 文件会残留，而内核保证持锁进程死亡后锁必然释放；pid/meta 文件在这套设计里只是诊断信息，bus.pid 存在完全不代表 bus 存活（所以才有 orphan 状态）。②事件注册表是封闭的：头注释提到的 recording.failed 都不注册，`event list` 不是「服务端能力发现」而是「二进制版本指纹」——用户无法订阅新事件，能力边界严格等于客户端版本；这牺牲了扩展性，换来 jq_root_path/params 全部可本地静态查询（F-083）与零信任服务端推送。③协议设计全面偏爱「字符串人类可读」而非枚举数字：IPC 消息类型、退出 reason 全是字符串，但退出码又极克制（2 只留给 status/stop 两个分支），说明设计者明确区分「给机器判读的少量分支码」与「给日志/人读的原因描述」。④Windows 自举刻意不用 DETACHED_PROCESS 而用 CREATE_NEW_PROCESS_GROUP + HideWindow，是为了保留进程组信号语义（对应 unix Setsid）——跨平台守护进程化做的是语义对齐而非 API 对齐。

**行动**：① 在 Agent 自动化中把 bus 当系统服务对待：先 `event status --fail-on-orphan` 判存活（退出码 2 分支）、消费 stderr ready 行再下发业务、账号切换后 logout 或 `event stop --force` 收口；② 排障「bus 起不来/事件不来」按层诊断：IPC 三件（sock/pid/meta）+ alive lock → WSS 状态文件 ws.state（auth_failed/auth_expired vs 网络重连）→ 8 个 key 拼写与 jq_root_path `.payload[0]`，不要跨层猜；③ 需要类似「单机长连复用 + 多消费者」架构时可整套照搬其决策序列（TryLock 选举、owner hash 鉴权、引用计数订阅、有界队列 drop-oldest + 1s 聚合 dropped、去重环吸收重连重复），但事件目录若要可扩展应把注册表改成配置/服务端发现并接受相应信任成本；④ 安全注意：命名管道无显式 SDDL（默认 ACL），多用户 Windows 主机上的隔离主要靠 owner hash 而非 OS 强制，高敏环境应评估同机用户探测管道的风险。
