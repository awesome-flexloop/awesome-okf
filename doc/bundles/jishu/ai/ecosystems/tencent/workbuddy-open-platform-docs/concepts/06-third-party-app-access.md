# 第三方应用接入：三类并列形态、OAuth 授权与分享能力

> 本篇归纳 WorkBuddy 开放平台开发者文档 D9「第三方应用」页（2026-10-16 采集，服务端渲染 `/docs/` 页正文，核验时点 2026-10-16），事实区间 **F-269～F-354**。另引用 **F-366、F-367**（来源代号 `D9、D10` 与 `D10`，为跨来源事实，仅用于并列登记凭证有效期口径，故本篇来源列出 D9 与 D10）。信源为**厂商单源**开发者文档；**未在本机实跑**任何应用注册、授权、签名、唤起或接口调用流程。

## 一、三类并列的第三方应用形态

开放平台**当前支持三类第三方应用**，面向不同接入场景（F-272）：

| 应用类型 | 说明 | 可申请权限 | F 编号 |
| --- | --- | --- | --- |
| **硬件接入** | 面向硬件设备厂商与合作伙伴开放 API 能力。硬件设备（如智能眼镜、车机等）通过开放平台接入 WorkBuddy，取得用户授权后可调用本地助理对话、云端任务、会话产物等 Open API | 全部权限（按业务需要申请） | F-273 |
| **Buddy 应用** | 面向行业伙伴开放垂直行业 AI Harness 能力。伙伴将行业 know-how 封装进 WorkBuddy，取得用户授权后可调用 Open API，为用户提供开箱即用的行业 AI Harness | 部分权限（按业务需要申请） | F-274 |
| **积分应用** | 面向开发者和合作伙伴开放积分权益 API 能力。应用取得用户授权后，可通过卡券或兑换码为用户兑换 WorkBuddy 积分（credits），适用于积分发放等场景 | 部分权限（如积分与权益类） | F-275 |

**并列关系声明**：上述三项为**并列的应用类型**——硬件接入、Buddy 应用、积分应用**并非同一种能力**，而是三条独立接入路径（F-272、F-273、F-274、F-275）。因此「硬件接入」与「积分兑换（积分应用）」是并列类型，不可互相替代或混同。

## 二、平台概述、核心能力四域与术语

- **平台概述原话**：WorkBuddy 开放平台基于 **OAuth 2.1 规范**进行用户身份验证和获取用户授权，同时面向开发者及生态合作伙伴提供了一套基于 **HTTPS 协议**的 Open API（F-269）。第三方应用访问用户数据前需**显式地向用户征求授权**；用户授权后平台遵循 OAuth 规范派发第三方票据，第三方应用可获取票据并与平台进行所需操作（F-270）。
- **核心能力四域**（F-271）：

| 能力域 | 说明 |
| --- | --- |
| 本地助理对话 | 通过 API 与 **PC 端本地助理**进行消息交互 |
| 云端任务管理 | 创建并管理云端 AI 任务，支持移动端/应用会话 |
| 产物管理 | 会话产物的拉取、增量更新与媒体文件下载 |
| 兑换码核销 | 通过卡券或兑换码为用户兑换 WorkBuddy 积分（credits） |

- **术语定义**（F-276）：

| 角色 | 说明 | 信任边界 |
| --- | --- | --- |
| Resource Owner | 资源拥有者，通常是 WorkBuddy 用户 | 决定第三方应用或连接器可访问的资源范围 |
| Third Application | 常规第三方应用，开发者基于 WorkBuddy 开放平台开发 | 用户授权后可调用 Open API |
| WorkBuddy | 代表用户执行任务、发起工具调用的智能体运行环境 | 调用前应换取短生命周期凭据 |
| Open Platform | 开放平台，负责应用注册、授权确认、令牌签发、Scope 管理和审计 | 平台级可信边界，所有开放调用的权限源头 |

## 三、应用注册与授权认证

**接入流程概览**：步骤一为**创建应用并完成配置**——在开放平台一次性填写应用基本信息、权限管理信息和回调地址配置，完成后提交审核（F-277）；步骤二为**从用户授权到调用接口**——应用引导用户完成 OAuth 2.1 授权，服务端换取访问凭证后即可调用 Open API，整体分为三个连续阶段：① 三方应用发起用户授权；② 用户完成授权后由应用服务端换取访问凭证；③ 应用使用访问凭证调用所需的 Open API（F-278、F-279）。

**应用基本配置**（6 步）：

- 硬件接入：登录 WorkBuddy 开放平台 → 点击「硬件接入」→ 填写基本信息 → 配置权限管理信息 → 配置 OAuth 回调地址 → 提交审核（F-280）。
- 积分应用：登录开放平台 → 点击「其他 > 积分兑换」→ 填写基本信息 → 配置权限管理信息（**仅开放积分与权益类 Scope**）→ 配置 OAuth 回调地址 → 提交审核（F-281）。

**应用状态**（F-282）：审核中（配置已提交，等待平台审核）／已启用（审核通过并发布，可以调用已授权的 Open API）／已驳回（审核未通过，需按反馈修改后重新提交）。

**应用凭据**：应用创建后进入审核状态，平台生成 `client_id` 和 `client_secret`；`client_secret` **仅在应用创建成功后明文展示一次**，请妥善保管，不要在前端或客户端代码中暴露，遗失请联系平台处理（F-283）。

**授权认证**：应用审核通过并启用后需引导用户完成 OAuth 2.1 授权以获取 `access_token`；授权流程涉及两类接口——`GET /authorize`（请求用户授权）、`POST /token`（换取/刷新 Token）（F-284）。

### Token 类型一览（F-285，D9 页口径）

| Token 类型 | 用途 | 有效期 | 备注 |
| --- | --- | --- | --- |
| access_token | 调用 Open API 的凭证 | 24 小时 | 通过「换取访问凭证」获取；过期后需重新获取。 |
| refresh_token | 刷新 access_token | 60 天 | 通过「换取访问凭证」获取；需安全存储在服务端，不得暴露在前端或客户端代码中。 |

> 本表 `access_token` 的「24 小时」与 D10 换取接口响应体示例的 `expires_in: 3600`（秒）**口径冲突**，见第五节并列登记。

### Scope 权限列表与申请（F-286～F-288）

| 分类 | Scope | 权限名称 | 描述 |
| --- | --- | --- | --- |
| 用户资料 | user.profile.readable | 读取个人资料 | 读取用户的昵称和头像 |
| 用户资料 | user.contact.readable | 验证联系方式 | 校验调用方提供的手机号是否与用户的手机号一致 |
| 积分与权益 | user.credit.exchange | 卡券兑换积分 | 使用卡券或兑换码为用户兑换WorkBuddy积分 |
| 云端任务 | user.task.invokable | 创建并执行云端任务 | 允许应用按照用户的指令创建并执行云端任务 |
| 云端任务 | user.task.readable | 读取任务列表与详情 | 允许应用读取用户的云端任务列表及任务详情 |
| 本地助理 | user.localassistant.invokable | 向本地助理发送消息 | 向本地助理（用户 PC 端）发送消息，驱动用户本机 Agent 执行任务 |
| 本地助理 | user.localassistant.readable | 读取本地助理在线状态与消息历史 | 读取本地助理（用户 PC 端）的在线状态与会话消息历史 |

权限申请步骤 3 步：在应用管理页面选择需要申请的 Scope → 说明使用场景和必要性 → 提交审核（F-287）。**最小权限原则**：仅申请应用功能所需的 Scope；用户授权时仅请求当前操作所需的 Scope；避免申请超出业务需求的权限（F-288）。

## 四、分享能力接入

### 4.1 功能介绍与端边界（原话口径）

- **功能定义原话**：WorkBuddy 分享是指第三方应用通过接入该能力，让用户可以从自己的应用把**文本、图片、音频、文件、资源链接**等内容一键分享到 WorkBuddy（F-289）。
- **开放对象与开通路径**：分享功能**已向通过企业认证的开发者开放**；开发者在开放平台创建分享应用（按「基础配置 → 应用平台信息」两步填写），提交审核后即生成应用 ID，审核通过后生成密钥，即可获得分享接入权限（F-290）。**企业认证是分享能力的开放门槛**。
- **端边界原话 A**（F-291）：「WorkBuddy 分享当前支持 **PC 端**接入（Windows 应用 / macOS 应用）；**移动端**（Android / iPhone / 鸿蒙应用）**后续开放**」。
- **端边界原话 B / 版本门槛**（F-292）：「请确认用户使用的 WorkBuddy 客户端为 **5.8.0 及以上**版本，更低版本**无法唤起**分享；移动端（Android / iPhone / 鸿蒙）接入方式与分享 SDK **后续开放**」；《PC 端开发手册》适用版本同为 **WorkBuddy 5.8.0 及以上**（F-321）；错误处理表亦要求核对「是否安装且为 5.8.0 及以上」（F-353）。
- 移动端开放**时间点官方未给**（仅表述为「后续开放」，F-291、F-292），不得写成已支持。

### 4.2 接入前准备（F-293～F-306）

需在 WorkBuddy 开放平台**创建分享应用、通过审核并生成密钥**（F-293）。入口路径：开放平台「第三方接入 → 分享功能接入」→ 点「创建应用」，按 **基础配置 → 应用平台信息** 两步填写，支持随时「存草稿」；提交审核后立即生成应用 ID 并进入审核（**7 个工作日内**）；审核通过后到应用详情生成密钥，即可按《PC 端开发手册》接入（F-294）。

- **第一步：基础配置**（F-295）——字段：应用名称（必填，全平台唯一）、应用 logo（必填，不小于 96×96px、不大于 100KB、支持 JPG/PNG）、应用简介（必填）、应用官网（必填）、申请说明（否）。
- **第二步：应用平台信息**（F-296）——先勾选接入端（Windows 应用 / macOS 应用），**至少一个**，勾中的端各展开一张信息卡。
  - Windows 应用字段 5 项（F-297）：Windows 应用标识、代码签名主体、代码签名证书指纹（40 位十六进制，去掉每两位之间的空格）、应用已上架、开发方式（固定 deeplink 接入）；PowerShell 取证示例见 F-298；**应用须使用代码签名证书签名后发布（OV / EV 证书需企业实名申请），自签名或未签名的应用无法通过审核**（F-299）。
  - macOS 应用字段 4 项（F-300）：Bundle ID、Team ID（Apple 分配给开发者团队的 10 位标识）、应用已上架、开发方式（固定 deeplink 接入）；终端取证示例见 F-301；Team ID 取自 Apple Developer Program 会员资格页，同一团队下所有应用共用（F-302）。
  - **字段用途**（F-303）：桌面端唤起时**不校验发起方的应用签名**；Windows 代码签名主体与指纹、macOS Team ID 用于**登记、唯一性校验与审核核验**；填错不会导致唤起失败，但会在审核阶段被驳回。
- **提交与审核**（F-304～F-306）：必填项缺失时提交按钮不可用；应用 ID 提交后立即生成、状态为「审核中」（此时可查看应用 ID 但还不能生成密钥）；审核 7 个工作日内完成，审核期间可「撤回申请」回到编辑态（F-304）。审核结果经**开放平台通知中心、WorkBuddy 端内消息中心、开发者邮箱**三渠道通知，驳回含原因、可修改后重新提交且应用 ID 不变（F-305）。通过后应用状态变为「已开通」，到应用详情「安全配置」生成密钥后按《PC 端开发手册》集成分享能力（F-306）。

### 4.3 生成密钥（F-307～F-314）

密钥在应用审核通过后生成，创建应用阶段不提交密钥（F-307）。生成入口为应用详情点击「随机生成密钥对」，**仅主体超管可操作**（F-307）。

- **生成方式**：在浏览器本地生成非对称密钥对（RSA-2048，私钥为 PKCS#8 PEM 格式，**签名算法 RSAwithSHA256、PSS 填充**），私钥不经过平台服务端（F-308）。
- **密钥标识 `kid`**：生成后展示该密钥对的标识 `kid`，调用分享能力时需随签名参数传入；WorkBuddy 按 `kid` 取对应公钥验签；生成即生效，无需保存（F-309）。
- **私钥保管**（F-310）：弹窗展示公钥与私钥，私钥支持一键复制并提示「私钥仅本次展示，关闭后不再显示，请立即复制保存」；平台**不保存你的私钥**，丢失需重新生成一对；私钥请保存在你的服务端，不要放入网页、桌面应用或移动应用安装包。
- **密钥数量**（F-311）：同时有效的密钥**最多 10 对**，达到上限时先删除不再使用的密钥再生成。
- **多对并存**（F-312）：多对可同时有效、每对有独立 `kid`，可平滑轮换（先生成新的、把签名切到新 `kid` 后再删除旧的）。
- **删除密钥**（F-313）：删除即时生效，该公钥不再参与验签；删除后该 `kid` 失效，仍用旧 `kid` 签名的调用将验签失败。
- **公钥**（F-314）：列表逐对展示 `kid`、公钥指纹、生成时间与最近使用时间，公钥可随时复制；私钥仅在生成弹窗中出现一次。

**（冲突并列）签名填充算法口径**：同页存在两处口径，均按原文并列登记、不择一：

| 口径 | F 编号 | 来源章节 | 原话摘要 |
| --- | --- | --- | --- |
| 口径一 | **F-308** | D9「生成密钥」 | 生成方式为浏览器本地生成非对称密钥对（RSA-2048，私钥 PKCS#8 PEM，签名算法 **RSAwithSHA256、PSS 填充**），私钥不经过平台服务端 |
| 口径二 | **F-346** | D9「签名生成：详细步骤」 | 签名算法为 **RS256，RSA PKCS#1 v1.5 填充、SHA-256 摘要**；使用与 `kid` 配套的 RSA-2048 私钥（PKCS#8 PEM）生成签名 |

> 另见《PC 端开发手册》快速开始示例 `sign.cjs`：其 `crypto.sign('sha256', …, { padding: crypto.constants.RSA_PKCS1_PADDING })`（F-326）与口径二一致。两处口径并列保留，**不合并、不择一、不替官方判定**（处置依据见[核验报告 · 四、跨页口径不一致并列登记](../references/verification.md)）。

### 4.4 标识冲突、品牌标识与常见问题（F-315～F-320）

- **标识冲突校验**（F-315）：应用名称全平台唯一，重名时提示「该应用名称已被占用，请更换」；各端应用标识与签名信息在同一端下全平台唯一、只能归属一个主体，冲突时拦截并提示可申诉。
- **申诉**（F-316）：标识或名称确为你所有时，发送邮件至 `openworkbuddy@tencent.com`，说明被占用的应用名称或标识、你的开发者主体名称，并附证明归属的材料（软件著作权证书、应用市场后台截图等）；平台核实认证主体后处理归属。
- **品牌标识**（F-317～F-319）：接入后需在自己应用内唤起分享的入口展示 WorkBuddy 标识（分享面板的分享目标项、设置页的接入标识位），须遵守 WorkBuddy 品牌设计指南（品牌中心入口见原始页）；品牌标识规则含使用范围、素材、净空与背景、配色、视觉层级、文案、关系表述共 **7 类**（F-318）；平台会在应用审核与线上巡查中核验标识使用情况，未按规范使用时平台可要求整改并暂停分享能力（F-319）。
- **常见问题**（F-320）：证书指纹格式错误、取不到签名主体或指纹、找不到 Team ID、同一公司多产品共用一张签名证书、应用尚未上架任何市场、没有代码签名证书、私钥丢失，共 **7 条**。

### 4.5 PC 端开发手册（F-321～F-354）

**能力概览**（F-322、F-323）：第三方应用构造分享消息，使用应用私钥生成签名包，再通过 **PC 端 HTTPS 中间页或移动端 SDK** 交给 WorkBuddy；WorkBuddy 校验请求后将内容**预填**到任务输入区，用户可以检查、编辑并发送。**唤起成功或内容预填成功，不等于用户已提交任务**（F-322）。当前分享场景值统一为 `newTask`；若新建任务输入框中已有内容，分享内容将覆盖当前任务输入区，否则创建新任务并填充到任务输入区；`newTask` 是协议场景名称，不表示每次分享都强制创建全新任务（F-323）。

**传输签名包 7 参数**（F-334、F-335）：

| 参数 | 传输类型 | 格式与含义 |
| --- | --- | --- |
| `appId` | `string` | 开放平台分配的应用标识 |
| `kid` | `string` | 与本次签名私钥配套的密钥标识 |
| `message` | `string` | UTF-8 JSON 的标准 Base64；原始 JSON 最多 16,384 字节 |
| `nonce` | `string` | 安全随机生成 16 字节后得到的 32 位小写十六进制字符串，仅含 `0–9`、`a–f` |
| `scene` | `string` | 当前固定为 `newTask` |
| `timestamp` | `string` | Unix 秒级时间戳的十进制字符串；不是毫秒数 |
| `sig` | `string` | RS256 签名二进制的标准 Base64；本身不参与签名串 |

前六项参与签名，加上 `sig` 共七项；无需传验签公钥（F-335）。`message` 在传输时为 `string`，解码后才是 `WorkBuddyMessage` 对象（F-336）；移动端 SDK 的实际入参形式以其正式接口文档为准（F-336，移动端 SDK 属**规划态**，F-292）。

**`WorkBuddyMessage`**（F-337）：`title`（string，不超过 50 字）、`description`（string，不超过 200 字）、`payload`（`TaskPayload` 对象）。16 KiB 限制针对**原始 JSON**，不是 URL 长度，也不是 Base64 编码后的字符串长度；若嵌入多媒体 `data`，这些字符也计入 JSON 字节数（F-338）。

**`TaskPayload`**（F-339、F-340）：`action`（string，当前支持 `start`）、`promptContentBlocks`（`ContentBlock[]`，有顺序、可混排）、`connectorIds`（`string[]`）。指定的连接器应已发布、且与分享应用所属主体一致；用户是否已授权仍影响资源读取（F-340）。

当前消息负载使用 `TaskPayload`，其内容块可承载**文本、图片、音频、文件资源与资源链接**；**各端对本地资源和内嵌数据的支持存在差异**（F-324），接口形态层面的支持矩阵见下节 `ContentBlock`，此处不重复。

**`ContentBlock` 类型与端差异（内嵌 `data` 支持矩阵，F-341）**——逐字照抄原文：

| `type`值 | 内容类型 | 已知字段及类型 | 端差异 |
| --- | --- | --- | --- |
| `text` | 文本 | `text: string` | 文本内容 |
| `image` | 图片 | `data?: string`（图片 Base64）、`uri?: string`、`mimeType?: string` | 内嵌 `data`：移动端支持，PC 端不支持 |
| `audio` | 音频 | `data?: string`（音频 Base64）、`uri?: string`、`mimeType?: string` | 内嵌 `data`：移动端支持，PC 端不支持 |
| `resource` | 文件资源 | `data?: string`（文件 Base64）、`uri?: string`、`mimeType?: string` | 内嵌 `data`：移动端支持，PC 端不支持 |
| `resource_link` | 资源链接 | `name?: string`、`uri: string`、`_meta?: object` | 需确认链接可访问及必要的连接器授权 |

**`ContentBlock` 逐字示例**（F-345）：文本块 `{"type":"text","text":"分析这个仓库"}`；资源链接块 `{"type":"resource_link","name":"产品文档","uri":"https://example.com/docs","_meta":{"og:title":"产品文档"}}`。

**内嵌 `data` 支持矩阵**：image / audio / resource **三类**均为「**内嵌 `data` 移动端支持、PC 端不支持**」（F-341）。对应 PC 端约束原话：「对 PC 端**不要**依赖将图片、音频或文件以 `data` 直接嵌入消息的方式」（F-351）。表中 `?` 仅表示不同来源可能不提供该字段，**不构成字段组合或必填规则的承诺**（F-342）；资源路径或链接能否由 WorkBuddy 读取取决于目标端的访问能力，第三方应用可访问的本地 `file://` 路径不一定能由 WorkBuddy 访问（F-343）；字段组合、大小上限和各端完整支持矩阵需以正式 SDK／协议为准（F-344）。

**签名生成：详细步骤**（F-346～F-350）：签名算法为 **RS256：RSA PKCS#1 v1.5 填充、SHA-256 摘要**（F-346），共 **9 步**（F-347）；待签名串格式（逐字照抄原文，F-348）：

```
appId=Base64(appId)&kid=Base64(kid)&message=message&nonce=Base64(nonce)&scene=Base64(scene)&timestamp=Base64(timestamp)
```

第 9 步时效要求：`-30 ≤ 平台当前时间 − timestamp ≤ 300`（单位秒）；同次分享重试保留原包；发起新分享或包过期后重新生成 `nonce`、`timestamp`、`sig`；同一 `appId + nonce` 最多允许应用内验签成功 3 次（F-349）。调试签名失败时先比较双方使用的待签名串原文，再检查 `kid` 与私钥是否配套；不要将私钥或完整真实分享链接提交到问题工单（F-350）。

**PC 端完整链接与快速开始**（F-325～F-333）：对外提供 HTTPS 中间页 `https://workbuddy.cn/app/open-deeplink`（F-329）；快速开始示例用 Node.js 在服务端签名并生成中间页链接，示例文件 `sign.cjs` 需 `appId`、`kid` 与私钥（`private-key.pem`，不要提交到代码仓库）（F-325）；示例要点含 16 KiB 校验、`nonce = crypto.randomBytes(16).toString('hex')`、待签名串拼接与 `crypto.sign('sha256', …, RSA_PKCS1_PADDING)`（F-326）；运行方式（F-327）；**请在用户发起分享时生成签名包，不要提前生成并长期复用链接**（F-328）；示例链接由临时密钥生成，`app_demo`、`kid_demo` 未在平台登记、时间戳会过期，**不可用于真实分享**（F-331）。上述示例代码**未在本机实跑**。

- **传输参数编码**（F-330）：对传输参数使用 `URLSearchParams` 进行 URL 编码，**不要手动拼接** Base64 中的 `+`、`/`、`=`。
- **解码验证示例**（F-332）：示例 `message` 经 URL 解码、再按标准 Base64 解码后，UTF-8 JSON 形如 `{"title":"Demo", …}`。

**资源与连接器分享 / 错误处理与上线检查**（F-351～F-354）：对 PC 端不要依赖内嵌 `data`（F-351）；需连接器时在 `TaskPayload.connectorIds` 填写应用主体**已发布**的连接器（F-352）；错误处理 **6 行**（无法唤起客户端、应用不可用、接入端不可用或身份不符、验签失败、请求过期或重复、资源或连接器不可用、内容未预填）（F-353）；上线前至少验证纯文本分享、未安装客户端、错误私钥、过期请求、重复请求、身份不符与不可访问资源（F-354）。
