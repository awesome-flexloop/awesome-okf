# 从场景评估到知识治理

一个任务可以先用普通流程改进，也可以增加检索、模型生成或工具执行。Kanzan 的场景评估文章主张在开发前看清问题、流程、数据、团队条件，随后以小范围验证决定投入。这是作者的方法建议，不是经过独立对照试验证明的成功公式。[F-008、F-009](../references/facts.md)

## 把任务写成可判定的输入输出

“用 AI 管理企业资料”范围过宽。教学设计可以把它收敛为“依据已批准制度回答员工问题，注明适用版本，无法确定时交给负责人”。后者能明确谁提供资料、什么算答对、哪些问题不允许自动答复。

以下为本包设计模板，非 Kanzan 官方表单或实测案例：

| 项目 | 要填写的内容 | 判定作用 |
|---|---|---|
| 任务 | 谁在什么情况下需要什么结果 | 避免把工具名称当需求 |
| 当前做法 | 输入来自哪里，由谁处理 | 找到真正的耗时或差错环节 |
| 输入条件 | 必需资料、允许读取范围、缺失处理 | 区分可解决与不可解决的请求 |
| 输出条件 | 格式、引用、业务规则、审核人 | 用业务结果评价，不只看流畅程度 |
| 失败条件 | 必须拒绝、转人工或停止的情形 | 为不确定性留合法出口 |
| 验收样本 | 真实正常样本及历史难题 | 保留与现有做法的比较基准 |
| 维护安排 | 规则变更、资料更新、责任交接 | 避免原型无人持续管理 |

首次练习可以不用连接任何产品。以下为虚构教学情境，不是实验数据：任务卡写“根据已批准制度定位答案”；输入为带生效日期的制度和一条问题；输出为答案、出处、适用版本或拒答理由；裁定人为制度负责人。若问题所需规则在材料中不存在，输出应是“资料不足，转负责人”，不补写规则。

练习交付一张填好的任务卡，人工判断一个正常请求和一个缺资料请求。能够说明前者的依据、后者为何不能答，并指定裁定人与维护人，即完成这次纸面练习；它不证明自动系统可用或效率提升。

开始时选一个边界清楚、资料足够、有人能判定结果的任务。若资料和权责尚不明确，先整理流程可能比接模型更有价值。若错误后果很高，则应先限制输出用途与写入权限。

## 知识库的资料责任

企业知识库文章列出来源、更新时间、责任人、术语与权限，也讨论使用反馈和维护。[F-010、F-011](../references/facts.md) 这些项目决定一条答案能否用于某个业务情境，不能只靠文本相似度解决。

| 治理对象 | 教学建议 | 常见风险 |
|---|---|---|
| 来源 | 保留原文位置与发布主体 | 复制材料丢失出处 |
| 版本 | 明确生效、失效与替代关系 | 新旧规则混在同一答案 |
| 责任人 | 指定能裁定争议的人 | “AI 说的”无人负责 |
| 术语 | 建立本组织用法及近义词 | 同名字段含义不同 |
| 权限 | 在检索和工具读取时检查身份 | 先取全文再让模型“保密” |
| 反馈 | 保留错误类型、处理与资料修订 | 重复错误只靠改提示词 |

治理数据不全时，可先做引用辅助或资料定位，避免直接生成具有执行效力的决定。权限控制需要由实际系统实施，表格声明或提示词不能替代授权检查。

## CMS 里的内容流程

Kanzan 的 CMS 文章讨论结构化内容与 API 复用，并提出草稿、审核、版本、权限和审计。[F-013、F-014](../references/facts.md) 对知识维护而言，结构化字段允许程序识别标题、有效期、责任人和状态；“可读取”与“可发布”仍是两种权力。

教学流程可以是：资料提交后形成草稿，Agent 建议改稿，人类或确定性规则审核，发布后记录版本，错误反馈再进入修订。每一步应保存谁改了什么、依据什么批准；是否需要人工审核取决于风险，不必所有内容一律全自动或一律手工。

## 把培训接到任务上

培训文章主张围绕岗位高频任务、输入输出与风险设计学习，并使用流程模板和人工审核。[F-012](../references/facts.md) 一次培训可以使用与试点相同的资料，比较学员能否解释来源、识别冲突、处理失败和独立完成任务，而不只检查会不会输入提示词。

建议让学员先人工判断一份样本，再使用系统，最后解释为什么接受或拒绝结果。若只能复述 AI 答案而说不清业务依据，培训尚未转化为可独立使用的能力。

## 最小试点的结束条件

这是一组本包建议的判定问题，未承诺具体收益：

1. 正常、缺资料、冲突资料和越权请求是否都有处理结果？
2. 输出能否回到原始依据，由指定责任人判定？
3. 将审核、返工和维护算入后，是否仍优于当前做法？
4. 谁能暂停系统、恢复人工流程并修正资料？

满足这些条件后再扩大场景；没有满足时，应记录失败类型和需要补齐的前置条件，而非靠增加模型调用次数掩盖问题。
