# AI 任务成本与生产交付

Kanzan 的成本文章按任务讨论费用，并把系统集成、治理和培训纳入项目投入。[F-025～F-027](../references/facts.md) 对使用者而言，需要衡量的是一次被接受的业务结果花了多少，而不仅是一次模型响应的账单。

## 分项计费与有效结果

以下是本包核算框架，不是当前服务报价。各项单价、单位、币种和缓存计费规则应取自实际供应商账单与对应时点官方价目表：

```text
模型费用 = 未缓存输入量 × 对应单价
         + 缓存读取量 × 对应单价
         + 缓存写入量 × 对应单价（供应商单独计费时）
         + 输出量 × 对应单价

每个有效结果的成本 = 全部任务投入 / 被验收接受的结果数
```

“全部任务投入”还可能包括工具调用、检索存储、集成、人工审核、返工、培训和维护。若没有被接受的结果，不能以总调用量作分母宣称有效成本很低。相同任务的比较应使用相同验收标准，并记录失败与重试。

文章给出的 181 条回复及 token 数属于作者匿名内部样本，本次没有取得日志；历史价格也没有独立核准，不能据此计算当前预算或行业平均成本。[F-025、F-026](../references/facts.md)

| 要记录什么 | 用于判断什么 |
|---|---|
| 任务类型、输入与验收要求 | 是否比较同一种工作 |
| 输入、输出、缓存、工具费用 | 哪一项真正占主要开销 |
| 接受、拒绝、返工和人工时间 | 调用便宜是否转化为结果便宜 |
| 初始集成与后续维护 | 试点成本与长期运行成本的差异 |
| 费用时点、币种与单位 | 防止旧价格、不同口径混算 |

## 作者流水线的结构

部署文章使用 Next.js、Node 22、pnpm、GitHub Actions、SSH、PM2 与 Prisma，是 2026-07-08 作者环境的实践自述，本包未复现。[F-036～F-039](../references/facts.md) 文章将 PR 检查与生产发布分开：前者判断变更是否满足检查，后者把产物部署并确认运行状态。

| 环节 | 作者描述 | 教学审查重点 |
|---|---|---|
| 发布前版本 | 工作区自动增加 patch，参与构建 | 构建版本、源提交和最终版本提交的关系 |
| 产物构建 | pnpm 构建与部署包 | 锁文件、运行时、环境配置是否可追踪 |
| 远端部署 | 备份 `.next`、上传和解包 | 备份究竟覆盖哪些恢复对象 |
| 依赖与数据库 | 生产依赖安装、迁移、客户端生成 | 失败时代码与 schema 是否兼容 |
| 进程与健康 | PM2 重启与 `/api/health` 轮询 | 超时必须失败，健康响应覆盖什么 |
| 成功后记录 | 提交版本变更，用 `[skip ci]` 防递归 | 是否与分支保护和必需检查相容 |
| 可选通知 | OPC Feed 部署事件通知可失败 | 通知失败与部署失败的区别 |

表内审查重点是本包建议，不是文章已验证全部解决的事项。本文不提供可直接执行的生产脚本：完整环境、应用、锁文件、秘密注入和回退前置条件没有在本任务中取得并验证。

## 版本和秘密边界

博文中的 `pnpm prisma migrate deploy` 与直接 HTTP 读取官方页面所得 ORM 8 的新 `db migrate` 体系不同；同日 WebFetch 仍返回旧迁移说明。[F-049](../references/facts.md) 差异短摘录和 canonical 定位保存在[核验记录](../references/verification.md)。应先确认目标项目的 Prisma 版本与锁文件，再查对应版本文档；不能把当前命令替换进旧流水线并假定等价，也不能认为旧命令在所有版本均失效。Node 22 也是作者环境，不是本包推荐的统一最低版本。

生产 `.env`、访问令牌与数据库凭据不应进入公开仓库或不受控产物。若部署过程需要携带配置，需另行验证注入方式、访问范围、日志脱敏、有效期和轮换。秘密可被部署机读取不意味着可被所有构建参与者读取。

## 四种完成证据

以下分层为本包验收设计：

1. 构建通过：编译与检查完成，并且进程正式退出。
2. 发布成功：预期产物到达目标，版本与提交可核对。
3. 应用就绪：应用能回应健康请求，进程持续存活。
4. 业务可用：认证、数据库、后台任务与目标业务读写实际完成。

健康接口返回成功和 commit，只能证明接口覆盖的项目，不能自动证明数据库、队列或完整业务正常。备份 `.next` 不等于备份数据库；代码回退也不自动撤销数据库迁移。生产发布前需要单独设计兼容迁移与恢复演练。[作者流程 F-038](../references/facts.md)

本包建议在生产放行前指定恢复负责人，约定 RPO（可接受的数据损失范围）与 RTO（目标恢复时间），并保存数据库备份还原、代码与 schema 兼容性、恢复后业务读写的验收记录。恢复演练未达到约定目标时不放行；这些目标须由业务风险决定，不由本包统一给数值。

GitHub 文档说明跳过的必需工作流检查可能阻碍 PR 合并。[F-040](../references/facts.md) 防递归方案必须结合实际触发器和分支保护测试。可选通知失败可以记录后继续，构建、迁移、健康或业务验收失败则应按各自停止与恢复规则处理，不能统一加“忽略错误”。
