# 三个示例与外部依赖

> 三个示例的作用是**说明能力边界**，不是可复现的操作教程：公告未给版本号、实际站点链接、构建日志与耗时（见 [缺口登记](../references/verification.md)）。因此本包不设 `examples/` 目录，示例只作场景解读。

## 三个示例一览

| 示例 | 技术形态 | 演示的能力 | 依据 |
|------|----------|-----------|------|
| ① 记账本 | 已有 React 项目 | 存量项目上线、私有转公开、原地改版 | F-022~F-025 |
| ② 活动报名 | Node.js + 后端接口 + 外部 Webhook | 全栈小应用、占位配置、二次部署 | F-026~F-032 |
| ③ 今日天气 | Node.js + 公开 API | 外部数据接入、排障路径 | F-033~F-036 |

## 示例一：把存量 Demo 发出去

流程最短但也有信息量：

| 步 | 动作 | 依据 |
|----|------|------|
| 1 | 指令「把这个项目部署上线。」 | F-023 |
| 2 | 点开链接自查 | F-008、F-024 |
| 3 | 说「把这个站点设为公开」 | F-010 |
| 4 | 分享链接 | F-010 |
| 5 | 原对话里「把主色换成绿色，标题改成「我的小账本」」 | F-012 |
| 6 | 「重新部署」→ 原链接生效 | F-013、F-014 |

关键点：**项目已有**（F-022）。这条路径说明"一键部署"不要求项目由 TRAE 从零生成——本地已有的 React 工程同样可以接进来。

## 示例二：全栈小应用 + 外部通知

这是三段示例里信息密度最高的一段，公告给出的指令包含四个要素：

```text
用 Node.js 做一个「活动报名」网页。            ← 技术栈 + 产物形态
用户填写姓名、手机号和参加场次后提交，         ← 表单字段（F-027）
由后端接口 /api/signup 校验，                  ← 接口契约（F-028）
再通过飞书群机器人发送报名通知。               ← 外部依赖（F-029）
Webhook 地址先在 server/config.js 里留个占位，  ← 配置约定（F-030）
我之后自己填。做完直接部署，给我一个公开链接。
```

| 要素 | 价值 |
|------|------|
| 指定 `/api/signup` | 接口路径由人定，而非 AI 自选，后续对接成本可控 |
| Webhook 走 `server/config.js` 占位 | 密钥不写进提示词、不写进代码仓库，是**签名凭据与代码分离**的基本纪律 |
| 「我之后自己填」+「再部署一次」 | 承认部署是可重复动作：先留占位跑通，再填真实凭据重部署（F-031） |

### 飞书群机器人的可核验口径

公告只用一句话提到飞书群机器人（F-029、F-032）。官方文档的口径要细得多（F-045、F-048~F-052）：

| 项 | 口径 | 出处 |
|----|------|------|
| 接入方式 | 群内添加「自定义机器人」，默认提供 Webhook 地址 | F-045 |
| 调用方 | 服务端向 Webhook 发起请求即可把消息推到群 | F-045 |
| 安全方式 | 自定义关键词 / IP 白名单 / 签名校验，**可设一种或多种**，官方"强烈建议"添加 | F-045 |
| 权限面 | 添加后即可用，**无需租户管理员审核**；**不具有任何数据访问权限**，只能发消息 | F-052 |
| 频率 | 单租户单机器人 **100 次/分钟、5 次/秒**；整点/半点易触发 `11232` 限流 | F-051 |

#### 三种安全方式的实际差别

| 方式 | 生效条件 | 上限 | 能防什么 | 防不了什么 |
|------|----------|------|----------|------------|
| 自定义关键词 | 消息内容须含至少一个关键词 | 最多 10 个 | 误把测试消息推到正式群；低成本的随机投递 | 知道关键词的人照样能发（关键词不是秘密） |
| IP 白名单 | 仅白名单内 IP 可请求 | 最多 10 个，支持 `123.12.1.*`、`123.1.1.1/24` 等段 | Webhook 泄露后从其他机器发起的调用 | 与白名单共享出口 IP 的其他服务 |
| 签名校验 | 请求须通过 `timestamp + sign` 校验 | 无条目上限 | Webhook 泄露后的重放与伪造（`timestamp` 限 1 小时内） | 拿到密钥的一方 |

- **关键词的关键限制**：只对 `text`、`title` 这类文本参数值生效（F-048）。富文本里的超链接标签 `{"tag":"a","text":"请查看","href":"..."}` 只过滤 `text`，**`href` 不参与过滤**——这意味着关键词挡不住"看起来合规、链接指向别处"的消息。
- **签名的算法**（F-050）：把 `timestamp + "\n" + 密钥` 当作签名字符串，用 HmacSHA256 计算**空字符串**的签名，再 Base64；请求体额外带 `timestamp` 与 `sign`。时间戳超过 1 小时会返回 `sign match fail or timestamp is not within one hour from current time`。

```python
# 官方算法示意（非公告内容）：timestamp + "\n" + secret 作 key，对空串做 HMAC-SHA256 再 Base64
import base64, hashlib, hmac, time

def gen_sign(secret: str, timestamp: int) -> str:
    string_to_sign = f"{timestamp}\n{secret}".encode()
    digest = hmac.new(string_to_sign, b"", digestmod=hashlib.sha256).digest()
    return base64.b64encode(digest).decode()

ts = int(time.time())
sign = gen_sign("你的密钥", ts)   # 请求体里带 {"timestamp": str(ts), "sign": sign, ...}
```

> ⚠️ **公告省略了整个安全设置环节**。Webhook 地址等同于"向该群发消息的凭据"，一旦泄露，任何人都能往群里推消息。最低限度应启用签名校验（能防伪造与重放）；若服务端出口 IP 固定，叠加 IP 白名单成本更低。关键词校验只适合过滤误触，不要当作鉴权手段。
>
> 另需注意：报名场景会在群里出现**真实手机号**（F-027），而自定义机器人无数据访问权限、也无读取消息的能力（F-052）——数据一旦推进群聊就脱离了应用的控制范围，留存与删除要靠群管理与多维表格侧处理。

### Open-Meteo 的可核验口径

| 项 | 完整口径（核验补充） | 出处 |
|----|----------------------|------|
| 认证 | 无需 API Key、无需注册、无需信用卡 | F-044 |
| 免费额度 | 非商业用途**每日 10,000 次**以内 | F-044 |

| 商用 | 需订阅计划（更高额度与优先支持） | F-044 |

公告的"无需 API Key"是准确的，但省略了**额度上限**与**署名义务**两件事。做一个自用天气页无所谓；若这个页面要对外并挂广告，署名与商用条款就得先读清楚。

## 三段提示词共同的结构模式

把公告里三段指令并排看，可以抽出一个稳定的骨架（本包归纳）：

```
【技术栈 + 产物形态】  +  【数据/交互契约】  +  【外部依赖与配置约定】  +  【交付形态】
   "用 Node.js 做        "填写姓名/手机号/      "通过飞书群机器人发送"      "做完直接部署，
    一个报名网页"          场次，由 /api/signup     "Webhook 先在 config     给我一个公开链接"
                            校验"                   里留占位"
```

四个位置各自解决一类模糊性：

| 位置 | 不定清楚会怎样 |
|------|----------------|
| 技术栈/产物形态 | AI 自选框架，可能选到平台不支持静态导出的方案 |
| 数据契约 | 字段名、接口路径各写一套，后续对接要重命名 |
| 外部依赖 | 密钥被硬编码进源码或写进对话 |
| 交付形态 | 得到一堆代码文件，而不是一个地址 |

这个骨架不依赖具体产品：换成任何"对话式生成 + 部署"的工具，同样的四段式都能显著减少来回。它是本包从公告示例中提炼的**可迁移模式**，不是 TRAE 官方规范。
