## P1 三层改造面

**一句话定义**：把「改一个 AI 系统」拆成记忆、技能、程序三层，按生效成本从低到高选择落点。

**适用**：可配置的 Agent 产品（有记忆、有技能/提示词资产、有可改的程序）。
**不适用**：完全黑盒的 SaaS；或改动必须跨三层同时生效的场景。

**核心步骤**：

1. 写下需求，判断它是「偏好」「流程」还是「界面/能力」。
2. 偏好 → 记忆层；流程 → 技能层；界面/能力 → 程序层。
3. 优先在最低成本层实现，验证不满足再上升一层。
4. 每上升一层，先确认回滚方式（技能保留旧版、程序保留备份）。
5. 记录每层改动的生效方式与验证方式，形成自己的对照表。

**检验标准**：能用一句话说明「这次改动落在哪层、多久生效、怎么验证」。

**反模式**：

- 一上来就改程序，把配置问题当代码问题。
- 三层同时改，失败时无法归因。
- 改程序前没备份记忆与技能（卸载会清数据）。

**跨域迁移**：企业系统配置——先改字段与流程配置，再改插件，最后才改核心代码。

**升级条件**：在两个不同产品（手机 Agent、桌面助手或工单系统）上各走一遍五步，升 L1。

## P2 四问成技

**一句话定义**：用「何时开始、怎么做、怎么检查、哪里要确认」四个问题，把口头流程固化成技能。

**适用**：重复发生、有明确触发语、结果可观察的任务。
**不适用**：一次性任务；结果无法观察的任务；触发条件还在变化的任务。

**核心步骤**：

1. 写触发：用户会说哪句话，或到哪个时间点。
2. 写步骤：先读什么、再做什么、最后交什么。
3. 写检查：做完去哪看（页面、列表、记忆、通知），没做到要如实说。
4. 写确认：付款、删除、对外发送前必须停下来问。
5. 补红线：不能做什么，写死。
6. 用同一句话复测，对比改前改后。

**检验标准**：任意第三人读这份技能，能说出「它在哪停、回来给你什么、你怎么验收」。

**反模式**：

- 只有目标没有步骤（「帮我安排好」）。
- 没有检查点，验收靠感觉。
- 只有正向要求，没有红线。
- 一次写十条规则，失败无法定位。

**跨域迁移**：给外包或实习生写 SOP——四问与交接单结构完全通用。

**升级条件**：在三个不同任务类型上验证通过，升 L1。

## P3 试改验循环

**一句话定义**：改任何配置化行为前先跑一次基线，改完用同一输入复测，只让一个变量变化。

**适用**：提示词、技能、规则、配置的迭代。
**不适用**：首次搭建（没有基线可对比）；无法重复触发的场景。

**核心步骤**：

1. 先跑一次，记录输入原话与输出表现。
2. 只改一处（一条规则或一个检查点）。
3. 发布改动（技能 lint + push；程序构建 + 安装）。
4. 用同一句话原样复测。
5. 对比前后差异，判断是否达到预期。
6. 不达预期则回退，再进入下一轮。

**检验标准**：能说出「这次只改了什么、输入没变、输出变了哪里」。

**反模式**：

- 换一句话复测，混淆了输入变化与规则变化。
- 一次改五处，成功了也不知道哪条起作用。
- 把「lint 通过」当作「行为正确」。
- 改完不复测，直接进入下一个需求。

**跨域迁移**：A/B 测试与灰度发布——控制变量、单一改动、可回滚，三者同构。

**升级条件**：在两类系统（Agent 配置、Web 功能开关）上各验证一次，升 L1。

## P4 证据先行

**一句话定义**：失败时先取运行证据，再定位，再做最小修改；禁止无证据重试。

**适用**：多步执行、跨设备、结果不确定的自动化任务。
**不适用**：确定性脚本的编译错误（直接看报错更快）。

**核心步骤**：

1. 留下改前版本，必要时先回退。
2. 取三件套：运行 ID、最后几步日志、当前截图。
3. 让 AI 先解释失败在哪一步，不直接改。
4. 写一个能复现问题的测试或最小复现步骤。
5. 做最小范围修改，一次只改一处。
6. 保留成功标准，禁止把未完成改写为完成。
7. 改完说明校验、安装与复测方式。

**检验标准**：能指出失败发生在第几步，并说明这次改动为什么能消除它。

**反模式**：

- 反复重跑同一任务，期待偶然成功。
- 让 AI 直接改，改完仍不知道原因。
- 顺手重构，引入与问题无关的变更。
- 把「没跑通」写成「已实现」。

**跨域迁移**：线上故障排查——先取证（日志/指标/链路），再定位，再最小变更。

**升级条件**：在两个不同系统上各完成一次「取证 → 定位 → 最小修复 → 复测」闭环，升 L1。

## P5 单产出拆分

**一句话定义**：多 Agent 拆分时按「一段一个可验收产出」切，用六字段交接单约束上下游。

**适用**：步骤多、可并行、每段有可检查产出的复杂任务。
**不适用**：强顺序依赖、无可检查中间产出、只有一两步的任务。

**核心步骤**：

1. 列出全流程动作与每个动作的产出。
2. 按四条规则切段：单一产出；在人工确认处切开；触发时间不同就分开；同一产出合并。
3. 为每段写六字段交接单：目标、输入、能改什么、不能做什么、交回什么、怎么验收。
4. 标注人工关口（如选题、定稿、发布）。
5. 先跑最费劲的一段，跑稳再接下一段。
6. 两三段稳定后，才交给调度角色串联。
7. 调度角色按「怎么验收」自核，不过就退回、不往下传。

**检验标准**：每段能独立验收；任一段失败只影响自己，不污染下游。

**反模式**：

- 单条工作流没跑稳就拆。
- 交接单缺「怎么验收」，下游无法判断。
- 坏结果继续下传，导致整链返工。
- 按人数拆而不是按产出拆。

**跨域迁移**：软件流水线与内容生产线——按产物切分、按验收门交接，而非按人头切分。

**升级条件**：在一个真实多段任务上完整跑通（含至少两次打回），升 L1。

## P6 双闸门

**一句话定义**：把不可逆动作的确认写两遍——规则层写「应该确认」，能力层写「不确认就执行不了」。

**适用**：会执行付款、发送、删除、安装、登录等不可逆动作的自动化系统。
**不适用**：纯只读系统；所有动作都可回滚的系统。

**核心步骤**：

1. 列不可逆动作清单。
2. 在流程/技能层写入确认步骤与话术。
3. 在程序/平台层实现能力闸门（缺参数则无法执行）。
4. 用示例数据分别验证两层：改坏规则层，能力层是否仍能拦住。
5. 记录每道闸门的位置与验证方式。

**检验标准**：故意绕过规则层时，能力层仍能阻止不可逆动作。

**反模式**：

- 只在提示词里写「不要付款」，没有能力约束。
- 闸门只覆盖付款，漏掉发送与删除。
- 把确认做成「可一键跳过」的弹窗。
- 让 Agent 自己输入密码或凭据。

**跨域迁移**：数据库权限与审批流——应用层校验之外，数据库权限与审批流是能力层兜底。

**升级条件**：在一个系统中完成「改坏规则层仍被拦住」的反证测试，升 L1。

## 使用建议

这六个模式可以串起来：**P1 定位落点 → P2 写成技能 → P3 迭代 → P4 排障 → P6 守闸门 → P5 再谈拆分**。顺序也可反转：做多 Agent 设计时，先用 P5 切段，再用 P2 把每段写成技能，最后用 P4 与 P6 收口。
