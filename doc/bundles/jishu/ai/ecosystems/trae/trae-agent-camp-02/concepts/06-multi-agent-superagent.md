# 多 Agent：从「一个助理」到「一支小队」

## 两种形态

课程只给了两种形态，没有把「多 Agent」神秘化（F-084）：

| 形态 | 怎么跑 | 适合什么 |
|------|--------|----------|
| 单 Agent 串行 | 一个助理按技能步骤往下走，每走一步检查一次 | 步骤不多、在一部手机上能办完的事 |
| 多 Agent 并行 | 调度者把大任务拆开，分给几个助理同时做，最后收回来汇总、检查 | 要同时查资料、写内容、做操作的复杂任务 |

本节课的五个场景全部属于第一种。**这不是能力不足，而是顺序正确**：先把一条工作流跑稳，再谈拆分。

## 讲师的五条原则

讲师自述其助理小队的五条做法（F-086，【讲师口径】）：

| # | 原则 | 对应到本课的哪一层 |
|---|------|--------------------|
| 1 | 先单后多 | 五个场景先各自跑通 |
| 2 | 每一步留下能检查的结果 | 四问里的「怎么检查」 |
| 3 | 交接写清楚：交什么、要回什么格式 | 交接单六字段 |
| 4 | 人守住关键关口：付款、发送、删除、拍板 | 技能确认 + 程序闸门 |
| 5 | 失败了先留证据：运行 ID、截图、最后几步日志；先分析再改，一次只改一处 | 证据链排障 |

这五条不是并列的「最佳实践」，而有依赖顺序：**没有第 2 条，第 1 条的「单」不可验收；没有第 3 条，拆出去的任务收不回来；没有第 5 条，第 1 条会退化成反复重试。**

## superagent-lead：给 TRAE 用的「总管」

讲师把五条原则写成了一个技能 `superagent-lead`，放在独立仓库 https://github.com/aduoge/superagent-lead（F-087、F-088）。

装上以后，遇到步骤多、能拆开分头做的任务，TRAE 当大管家：**自己不动手，只管拆、派、验**，具体活交给几个执行者。

### 怎么装

1. 打开仓库，Code → Download ZIP 下载解压（会用 git 的直接 clone）。
2. 把里面的 `superagent-lead` 文件夹复制到项目的 `.trae/skills/` 下。
3. 想所有项目都能用，就复制到全局技能目录：国内版是用户目录下的 `.trae-cn/skills`，国际版是 `.trae/skills`。
4. 打开 TRAE 设置 → 规则和技能，能看到它就装好了。

> **可达性提示**：课程提供了该仓库地址，但本次公开检索未独立确认可达；文档评论区有用户反馈「打不开了」「私有仓库？」，2026-11-18 复读时又新增「有梯子也打不开了」（F-118、F-123）。源码核验进一步确认：本仓库与 `camp/xiaoman` 分支中都没有 `superagent-lead` 目录或引用（S-052），它是独立仓库。遇到打不开，先按课程渠道反馈，不要自行寻找同名仓库替代。

### 怎么用

```text
用总管模式帮我做：给我的小满加一个“每周复盘”功能，一块查现有的记忆和技能怎么存，一块写新技能，一块写测试。
先给我看任务总表和交接单，我同意后再派。
```

流程（F-091）：

1. 它先把任务总表与每张交接单拿给你看。
2. 你同意后，按它说的开几个新对话，每个对话贴一张单。
3. 执行者交回来，再回到大管家这个对话里让它验收。

## 公众号小队：一次完整拆分

课程给了一个真实案例（F-092）：做公众号的同学每天要刷热点找选题、写稿、排版、做封面、掐点发布，发完还要统计，大半天就过去了。

按四条规则拆分（F-093）：

| 规则 | 含义 |
|------|------|
| 单一产出 | 一段只产出一个文件或一个结果 |
| 在人工确认处切开 | 需要人拍板的地方就是段边界 |
| 触发时间不同就分开 | 定时触发与即时触发不混在一段 |
| 同一产出合并 | 多个动作写同一个文件时并成一段 |

拆成五段，每段对应一个技能；由 superagent-lead 当大管家，五个助理当执行者（F-094）。大管家拆、派、验，进度表只有它能改；执行者各管一段，只拿交接单与上一段文件，只写自己的产出。

多出来的四个关口是：**选题、定稿、封面、发布**。大管家把结果推到手机，等你确认才继续（F-095）。

### 交接单六字段

以写稿助理的交接单为例（F-096）：

```text
目标：按你确认的选题写一篇初稿
输入：选题清单.md 里你选中的那一条
能改什么：只写 草稿.md
不能做什么：不发布、不改选题清单、不编数据
交回什么：草稿.md，开头写明用的是哪条选题
怎么验收：1500 到 2500 字；每个数据都带来源链接
```

| 字段 | 作用 | 缺了会怎样 |
|------|------|------------|
| 目标 | 这一段的唯一产出 | 执行者会顺手多做几件事 |
| 输入 | 从哪读，读哪一条 | 读错版本，后面全错 |
| 能改什么 | 写权限边界 | 互相覆盖对方的文件 |
| 不能做什么 | 红线 | 越界发布、改上游数据 |
| 交回什么 | 交付格式 | 下游接不上 |
| 怎么验收 | 可判定的标准 | 大管家无法判断过不过 |

### 验收与打回

大管家按「怎么验收」自己核对（F-097）：

- **过了**：在进度表打勾、记下证据，再派下一段；
- **没过**：打回给执行者重做，不往下传。

这条规则的关键在「不往下传」。坏结果一旦流入下一段，后面所有段都要返工。

## 落地顺序

课程给的建议很务实（F-098）：

1. 不要一口气全做完。
2. 先挑**最费劲的一环**（例如「每周数据小结」），用四问写成一个技能跑通。
3. 再接下一环。
4. 等两三环都跑稳了，再交给大管家把它们串起来。

## 什么时候不该拆

| 情况 | 为什么不该拆 | 更合适的做法 |
|------|--------------|--------------|
| 单条工作流还没跑稳 | 拆开后无法判断问题在哪一段 | 先按四问把单技能跑通 |
| 步骤之间强顺序依赖 | 并行没有收益，只增加交接成本 | 单 Agent 串行 |
| 没有可检查的中间产出 | 交接单的「交回什么」写不出来 | 先补检查点 |
| 只有一两步 | 拆分的管理成本大于执行成本 | 直接做 |

> 上表为**本包判断**，课程只给了「先单后多」的原则与适用形态（F-084、F-086），没有列出不该拆的清单。
