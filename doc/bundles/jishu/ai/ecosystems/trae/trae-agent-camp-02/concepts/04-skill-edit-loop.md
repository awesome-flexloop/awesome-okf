# 试改验循环：先让它在手机上跑一次

课程把五个场景统一成同一个三步流程（F-042）。这不是为了整齐，而是为了让**改动前后可比**——不先跑一次，你不知道自己改的到底是哪一处行为。

## 三步法

| 步骤 | 在哪做 | 你做什么 | 为了看什么 |
|------|--------|----------|------------|
| 1 先试一次 | 手机 | 把需求原样发给助理 | 改之前它会怎么做、哪里不满意 |
| 2 改技能 | 电脑上的 TRAE | 把提示词发给 TRAE，让它写进技能再推到手机 | 规则有没有写进 SKILL.md、手机有没有收到 |
| 3 验收 | 手机 | 把第 1 步那句话**原样**再发一次 | 前后回复有没有变、规则是否真的生效 |

**适用**：有明确触发语、能在手机上看到结果的重复性任务。
**不适用**：一次性任务；结果无法在手机端观察的任务；触发条件本身还在变的任务——这三种情况先别写技能，手工做一遍更划算（本包判断，课程未直接讨论）。

## 第 2 步里 TRAE 替你做了什么

每段提示词最后都有一句「完成后帮我校验并推送到手机」。TRAE 改完技能后会接着做两件事（F-043）：

1. **lint**：检查技能文件格式对不对。
2. **push**：通过 adb 把技能复制进手机。

对应的两条命令（由 TRAE 运行，你不需要敲，F-046）：

```bash
python cli/xiaoman.py lint skills/examples/<技能名>
python cli/xiaoman.py push skills/examples/<技能名>
```

回复里出现 `0 problem(s)` 与 `pushed`，表示校验通过且已推送。

想单独再推一次，直接对 TRAE 说「把 skills/examples/today-plan 推送到手机」（F-044）。

> **前提**：第二部分那座「桥」已经搭好——数据线或 Wi-Fi 都行（F-043）。

## 什么叫「改成了」

课程给了一个很容易被忽略的判据：**lint 通过不算成功**（F-100）。真正的成功标准是：

- 手机上的回复按新规则变化；
- 检查点对得上（页面、闹钟列表、记忆条目或通知）；
- 没有越界动作（加购、下单、发消息、删数据）。

所以验收必须回到手机、用**同一句话**复测。在电脑上看到 `0 problem(s)` 只说明文件格式没问题。

## 为什么必须「原样复测」

| 做法 | 问题 |
|------|------|
| 换一句话再问 | 分不清是规则生效，还是新问法恰好触发了别的行为 |
| 只看 TRAE 的总结 | TRAE 总结的是「它改了什么」，不是「手机上变成什么」 |
| 只看 lint 结果 | 只证明格式合法，不证明行为对 |

原样复测把变量降到最低：输入相同、设备相同、只有技能变了。这就是控制变量。

## 失败时的分岔

| 现象 | 可能原因 | 下一步 |
|------|----------|--------|
| 回复完全没变 | 技能没被选中，或没推成功 | 确认 push 输出 `pushed`，再确认触发语与技能匹配 |
| 部分规则生效 | 规则写得含糊，或互相冲突 | 把规则改成可判定的一句，减少条数 |
| 行为对了但显示不对 | 显示属程序层 | 见 [05 程序层改造](05-program-layer.md)（表格渲染就是这类） |
| 结果时好时坏 | 页面加载、识别不稳定 | 在技能里加「看不清就写页面未显示」这类兜底 |

课程在淘宝比价的排错录屏里演示了第三种：技能补全后 lint/push 即生效，回复变成四列表格；但表格的渲染方式改在 App 程序里，必须重新构建安装 APK 才生效（F-063、F-104）。

## 一次改一处

课程在多助理部分强调「一次只改一处」（F-086），这条对单助理同样成立：

- 一次只加一条规则，或只改一个检查点；
- 改完立刻原样复测；
- 失败时能定位到刚改的那一句。

一次改五条规则再复测，成功了不知道哪条起作用，失败了不知道哪条冲突。

## 验收清单

- [ ] 第 1 步的原话已经记下来（后面要原样复测）
- [ ] 提示词里包含四问的四块：触发、步骤、检查、确认
- [ ] TRAE 回复里有 `0 problem(s)` 与 `pushed`
- [ ] 手机上原样复测，行为按新规则变化
- [ ] 检查点（页面/列表/记忆/通知）逐项核对过
