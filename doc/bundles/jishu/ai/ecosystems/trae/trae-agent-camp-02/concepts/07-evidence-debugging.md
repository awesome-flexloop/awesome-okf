# 证据链排障：把失败定位到某一步

手机上的结果不对，最常见的错误反应是「改提示词再试一次」。课程给的是另一条路：**先取证，再定位，最后做最小修改**（F-101~F-103）。

## 三件套

课程要求交三样东西给 TRAE（F-101）：

| 证据 | 作用 | 从哪来 |
|------|------|--------|
| 本次运行 ID | 定位这一次执行 | `python cli/xiaoman.py logs` 每行开头 |
| 最后几步日志 | 看它在哪一步停下 | 同上，取最后几行 |
| 当前截图 | 看屏幕上实际是什么 | 手机截图 |

运行 ID 与日志不用自己翻（F-102）：让 TRAE 在终端运行 `python cli/xiaoman.py logs`，每行开头那一串就是运行 ID；再运行 `python cli/xiaoman.py traces show 运行ID`，就能把这次每一步做了什么列成表。

> 这两条命令由 TRAE 运行。你只需要知道：**运行 ID 是这次执行的身份证，traces 是这次执行的分步记录。**

## 交给 TRAE 的排错模板

```text
我的目标是……，实际停在……。这是本次运行 ID、最后几步日志和当前截图。
请先解释失败在哪一步，再写能复现问题的测试，然后做最小范围的修改。
保留成功标准，不能把没做完改成成功。修改后告诉我怎么校验、安装和重新验证。
```

这段模板有四条硬约束（F-103）：

| 约束 | 防的是什么 |
|------|------------|
| 先解释失败在哪一步 | 防「直接改代码」，改完也不知道改对了没有 |
| 先写能复现问题的测试 | 防修完无法确认、下次复发 |
| 做最小范围修改 | 防顺手重构引入新问题 |
| 保留成功标准，不能把没做完改成成功 | 防把「没跑通」写成「已实现」 |

最后一条最值得单独记：它不是技术约束，而是**对 AI 汇报的约束**。模型倾向于给出「已完成」的结论，尤其在只改了一半时；把「不能把没做完改成成功」写进模板，是把验收权收回人手里。

## 一个真实案例

淘宝比价的排错录屏（F-063、F-104）：

1. **现象**：回复里没有店铺名，也没排成表格。
2. **取证**：把截图、运行 ID、执行轨迹交给 TRAE。
3. **定位**：技能里的输出要求不完整。
4. **修改**：技能补全要求，lint、push。
5. **复测**：回复变成四列表格，看不到的信息写「页面未显示」。
6. **剩余问题**：表格的显示方式属程序层，要重新构建、安装 APK 才生效。

这个案例把第二课的三层讲全了：**有的问题改技能就好（秒级生效），有的问题必须改程序（分钟级 + 重装）**。排障时先判断落在哪一层，再决定改哪里。

## 先回退，再取证

课程在现象排查表里给了一条顺序（F-100）：改坏了先退回改之前的版本，再按上面的做法把现象和证据交给 TRAE。

为什么先回退：

- 回退后你能确认「原版本是好的」，缩小问题范围；
- 带着坏版本继续改，容易在错误基线上叠加改动；
- 有备份时，回退是最快的对照实验。

回退的前提是**改之前留了一份版本**。这一点在技能层是源码的 `skills/examples/<技能名>`，在程序层是安装包与记忆/技能的备份（见 [05 程序层改造](05-program-layer.md)）。

## 多设备时的定位

手机连了好几台时，先用 `adb devices -l` 查到目标设备的序列号，再在命令后面加 `--serial 设备序列号`（F-100）。推送推错设备，现象会是「手机上什么都没变」——这类问题不需要改技能，只需要指定设备。

## 排障的顺序清单

- [ ] 先确认现象：哪一步、屏幕上是什么、期望是什么
- [ ] 判断层级：技能问题、程序问题，还是配置/权限问题
- [ ] 留证据：运行 ID、最后几步日志、当前截图
- [ ] 让 TRAE 先解释失败在哪一步
- [ ] 先写复现测试，再做最小修改
- [ ] 技能改完 lint + push；程序改完构建 + 安装
- [ ] 手机上原样复测，核对检查点
- [ ] 分享日志/截图前，去掉个人信息并给 Key 打码
