# 五条洞察：改造一个 Agent 的真实杠杆

> 事实在 [课程事实登记](references/course-source.md)，本页只写「从事实推出什么」。凡属本包推断而非课程原文的，明确标出。

## I-1 改造面决定生效成本，先选层再动手

**陈述**：记忆、技能、程序三层的差别，首先不是「能改什么」，而是「改完多久生效、怎么验证」。

**证据**：课程把改造归为三层（F-005）；技能推送后同名替换、无须重装（F-040）；技能改动 lint + push 即生效，而表格渲染等程序改动要重新构建安装 APK（F-043、F-063、F-104）；回退到课程版还需卸载重装并备份数据（F-081）。

**反常识**：直觉是「改程序最彻底，所以最优先」。实际相反——**程序层的反馈周期以分钟到十分钟计，且伴随数据风险**；记忆层说完即生效，技能层一次 lint + push 即生效。

**行动**：拿到需求先问「这件事能不能用一条偏好表达？不能，能不能用一份技能表达？」两层都不行，再动程序。顺序：记忆 → 技能 → 程序。

## I-2 技能不是更长的提示词，而是可检查的流程契约

**陈述**：一份技能之所以比一句提示词稳定，是因为它把「触发、步骤、检查、确认」四件事固定成了结构。

**证据**：课程用四问定义技能（F-036、F-037）；五个场景的技能都包含触发语、步骤、检查点与确认点（F-049、F-054、F-060、F-066、F-072）；技能被选中后按步骤执行（F-034）。

**反常识**：多数人写不出好技能，第一反应是「再加点形容词，让模型更努力」。但课程里真正起作用的，是「看不清写页面未显示」「不足 3 条如实说明」「答前不给答案」这类**可判定的约束**，而不是语气。

**行动**：每份技能至少写一个可观察的检查点（去哪看、看什么）和一条红线（不能做什么）。检查点写不出来，说明这件事还不适合做成技能。

## I-3 可靠性的分界线是证据，不是模型能力

**陈述**：Agent 能不能改好，取决于每一步有没有留下可检查的结果；排障能不能收敛，取决于有没有拿到运行证据。

**证据**：四问里的「怎么检查」要求做完去页面、闹钟列表、记忆或通知核对（F-037）；讲师的第二条原则是「每一步都留下能检查的结果」（F-086）；排障要求交运行 ID、最后几步日志与截图（F-101、F-102）；课程明确「lint 通过不算成功」（F-100）。

**反常识**：结果不对时，直觉是「改提示词再试一次」。但没有证据的重试只是换随机种子——**同一句提示词改三次，可能三次都不同，而你无法解释哪次为什么对**。

**行动**：遇到失败先取证（运行 ID + 日志 + 截图），再让 TRAE 解释失败在哪一步，最后做最小修改、原样复测。一次只改一处。

## I-4 闸门要下沉到能力层，规则层只是第一道

**陈述**：把确认写进技能，是「规则约束」；把「没有确认就存不进」写进程序，是「能力约束」。只有后者不可绕过。

**证据**：四问要求「哪一步交给你确认」（F-036）；程序层改造把确认关卡写在程序里，不管技能怎么写，没有「确认」就存不进手机（F-078）；验收要求「保存之前一定先给你看、要你确认」（F-079）；课程重申付款、发送、删除前一定先问（F-105）。

**反常识**：通常把「确认弹窗」当成体验负担，想着以后能不能关掉。但在这套设计里，**确认是自动化的前提**——正因为不可逆动作有人兜底，才敢让 Agent 走得更远。

**行动**：列一张不可逆动作清单（付款、发送、删除、卸载、登录），逐个检查：确认点是在技能里，还是在程序里？涉及数据与钱的，尽量下沉到程序层。

## I-5 多 Agent 的前置条件是单 Agent 的可验收

**陈述**：能不能拆，不取决于任务多大，而取决于**每一段有没有可检查的产出**。

**证据**：课程把形态分为单 Agent 串行与多 Agent 并行，并强调「先单后多」（F-084、F-086）；拆分按四条规则（单一产出、在人工确认处切开、触发时间不同分开、同一产出合并，F-093）；交接单要求写清目标、输入、能改什么、不能做什么、交回什么、怎么验收（F-096）；大管家按验收标准自核，不过就退回、不往下传（F-097）。

**反常识**：并行常被当作「更快」的同义词。但没有可检查产出的拆分，只会把「一个地方失败」变成「几个地方同时失败且互相污染」——**并行放大的是吞吐，也放大不可查性**。

**行动**：先挑最费劲的一环，用四问写成技能并跑稳（F-098）；再拆第二环；两三环稳定后，才交给调度技能串联。
