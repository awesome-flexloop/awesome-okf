# 任务设计：把一句话写成可验收的任务书

Agent 的能力上限由模型决定，但**这一次任务的成败**由任务书决定。同一台手机、同一个模型，任务书写法不同，结果可能一次成功、一次绕十步。

## 四要素

课程给的规则只有一句：自己写任务，说清四件事（F-054）。

| 要素 | 要回答的问题 | 不写的后果 |
|------|--------------|------------|
| 做什么 | 在哪个 App、找什么东西、达成什么结果 | 它会自己选一个理解，通常不是你要的 |
| 条件 | 预算、规格、时间、颜色、数量 | 它会挑第一个符合字面描述的，可能是最贵的 |
| 停在哪一步 | 停在商品页 / 停在结算前 / 直接完成 | 它会一路走到付款或提交，把决定留给你收拾 |
| 回报什么 | 店名、规格、价格、链接，或一句结论 | 你拿到「已完成」，但不知道该核对什么 |

## 两个官方示例的拆解

**示例一：淘宝买笔记本**（F-051）

```text
帮我在淘宝挑一本20元以内的A5笔记本，选好后给我确认。
```

| 要素 | 对应文本 |
|------|----------|
| 做什么 | 在淘宝挑一本笔记本 |
| 条件 | 20 元以内、A5 |
| 停在哪一步 | 选好后给我确认 |
| 回报什么 | 隐含在「给我确认」里——确认时你自然能看到店铺、规格、价格 |

这个示例的回报项写得比较松，因为它把验收放在了确认弹窗上。适合第一次跑通。

**示例二：淘宝抽纸，停得更早**（F-055）

```text
在淘宝找一提 30 元以内、3 层的抽纸，停在商品页，把店名、规格和价格告诉我，
不要加购、不要下单。
```

| 要素 | 对应文本 |
|------|----------|
| 做什么 | 在淘宝找抽纸 |
| 条件 | 30 元以内、3 层、一提 |
| 停在哪一步 | 停在商品页 |
| 回报什么 | 店名、规格、价格 |
| 额外红线 | 不要加购、不要下单 |

第二个示例多了一样东西：**否定式红线**。「不要加购、不要下单」把可能的越界动作提前排除了。写红线比写期望更有效，因为模型对「不要……」的约束遵循通常比对「尽量……」更稳定。

## 可复制模板

```text
在【App 名称】里【做什么】。
条件：【预算/规格/时间/数量】。
停在【具体页面或动作】之前，不要【越界动作1】、不要【越界动作2】。
完成后回来告诉我：【需要核对的信息清单】。
如果遇到【验证码/登录/权限】先停下来告诉我，不要自己处理。
```

最后一行是建议加上的：课程说明遇到滑块或验证码要本人手动处理，再回来说「继续」（F-053）。把它写进任务书，可以少一次「它卡住但没告诉你」的等待。

## 模糊与明确的对照

| 模糊写法 | 问题 | 改写 |
|----------|------|------|
| 帮我买个笔记本 | 没有预算、规格、停点 | 20 元以内、A5、选好后给我确认 |
| 找最便宜的抽纸 | 「最便宜」需要全平台比价，步数不可控 | 30 元以内、3 层、停在商品页、把前三名的店名与价格告诉我 |
| 帮我整理一下相册 | 没有完成判据 | 把截图类图片移到一个名为「截图」的相册，移完告诉我移了多少张 |
| 看看有没有便宜的机票 | 没有日期、航线、舱位 | 查 12 月 20 日北京到上海、经济舱、直飞，把最低三档价格与航班号告诉我 |

改写的共同点：**把形容词换成数字，把「帮我做」换成「做到哪一步停下」**。

## 长任务要拆步

课程说明淘宝这类长任务有十几二十步，每一步都要发一张截图给模型（F-064、F-068）。步数直接对应成本与失败概率，所以长任务应该拆：

1. **先侦察**：只让它打开 App、搜索、停在列表页，把前三条结果报给你。
2. **再选定**：你确认目标商品后，让它进入详情页核对规格与价格。
3. **最后决策**：你决定买不买；买的话让它停在结算页，你核对后自己付。

三步各自可验收，任何一步失败都只损失一步的成本。相反，一句「帮我买好」把所有不确定性压进一次长循环，失败时你不知道错在哪一步。

## 求助也要用任务书

卡住时，课程给的模板同样遵循四要素（F-074）：

```text
我在用课程里的 Agent 助理（小满），发的任务是：……
它停在了这一步：……（附截图，Key、手机号、地址已打码；有报错就把报错原文贴上）
请先用大白话告诉我可能的原因，再按从简单到复杂的顺序列出我该检查什么。
先只分析，不要修改任何文件。
```

这里有两个细节值得学：

- **「先只分析，不要修改任何文件」**：与 [06 用 TRAE 读项目](06-trae-read-project.md) 的「只讲不改」是同一条纪律。
- **「按从简单到复杂排列」**：避免一上来就让你重装配环境。多数问题出在配置与权限，不在代码。

## 五条反模式

| 反模式 | 典型写法 | 后果 | 改法 |
|--------|----------|------|------|
| 无停点 | 帮我买好 | 一路走到付款 | 明确「停在确认前」 |
| 无预算 | 挑个性价比高的 | 选品不可控 | 给数字上限 |
| 多目标混写 | 顺便看看有没有优惠券，再比比价，然后下单 | 循环变长、失败点变多 | 拆成三个任务 |
| 依赖隐含偏好 | 按我的习惯来 | 每次都要重新推断，成本高且不稳定 | 把偏好写成显式条件 |
| 让它处理验证码 | 遇到验证码自己过 | 违反平台规则，且通常过不去 | 任务书里写明「先停下来告诉我」 |

## 验收清单

写完任务书，用四个问题自查：

- [ ] 它知道在哪个 App、做什么吗
- [ ] 条件里有没有可判定的数字或枚举
- [ ] 停点是一个具体页面或动作吗
- [ ] 回来时你要核对的信息，是否已经列出来

四问都能答「是」，再发出去。
