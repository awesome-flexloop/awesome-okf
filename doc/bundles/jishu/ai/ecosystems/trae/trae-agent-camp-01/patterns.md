## P1 底座二次开发

**一句话定义**：不重写系统，先在成熟底座上跑通，再按最小改动逐层定制。

**适用**：目标能力与底座高度重合；时间有限；你更需要「能用」而不是「完全可控」。
**不适用**：底座缺少关键能力（如必须对接只对公开放的系统）；许可或合规不允许二次开发（缺口 G-07）。

**核心步骤**：

1. 确认底座能跑通最小闭环（本课的安装 + 自检）。
2. 用「只讲不改」勘察目录，找到改动落点。
3. 按「记忆 → 任务书 → 技能 → 界面 → 操作层」的顺序尝试最小改动。
4. 每改一处，在真实环境验证一次。
5. 记录改动点与回滚方式。

**检验标准**：能在不修改核心操作层的前提下，完成一次个性化改动并验证。

**反模式**：

- 一上来就改核心操作层（hands），改动面不可控。
- 没有基线就跑通之前先改代码，导致分不清「本来就坏」与「改坏了」。
- 把底座当框架重写，成本反超自建。

**跨域迁移**：企业内部工具建设——先在成熟 SaaS 上配置，再针对差异做插件式开发，而不是自研全套。

**升级条件**：在第二个底座（不同项目/不同团队）上重复一次同样的五步，即升 L1。

## P2 只讲不改勘察

**一句话定义**：让 AI 首次接触陌生代码库时只做解释、不做修改，以「零改动」作为验收条件。

**适用**：任何第一次把 AI 引入既有项目的场景。
**不适用**：已经建立基线、且有版本控制与测试保护的小范围改动。

**核心步骤**：

1. 明确三问：关键模块在哪、一次请求经过哪几步、改某类行为该动哪里。
2. 在提示词结尾写死「先只讲解，不要修改任何文件」。
3. 让 AI 用非开发者能懂的话复述。
4. 人工核对它的说法与目录是否一致。
5. 用版本控制的变更列表确认零改动。

**检验标准**：能回答三问，且工作区无改动。

**反模式**：

- 只写「先看看」，没写「不要改」。
- 把「讲解」当成「改完再解释」。
- 不做零改动核对，靠感觉判断。

**跨域迁移**：新成员入职——先让其画系统地图并口头讲解，暂不分配改动任务。

**升级条件**：在三个不同项目上完成，且每次都拦下过至少一次误改，升 L1。

## P3 四要素任务书

**一句话定义**：把「帮我做某事」写成做什么、条件、停点、回报四项齐全的任务书。

**适用**：一切交给 AI 执行的、有外部副作用的任务。
**不适用**：纯问答、纯生成、无需验收的探索。

**核心步骤**：

1. 写「做什么」：哪个环境、哪个对象、达成什么结果。
2. 写「条件」：预算、规格、时间、数量，全部换成可判定的数字或枚举。
3. 写「停点」：停在哪一页、哪一个动作之前。
4. 写「回报」：回来时要核对哪些信息。
5. 补一行红线：不要做哪些越界动作。
6. 发出去之前用四问自查。

**检验标准**：任意第三人读任务书，能说出「它会在哪停下、回来给你什么」。

**反模式**：

- 只有目标，没有停点（「帮我买好」）。
- 用形容词代替阈值（「便宜点」「性价比高」）。
- 多目标混写，失败时无法定位。
- 依赖隐含偏好，每次都要重新推断。

**跨域迁移**：给外包或实习生派活——四要素同样适用，停点即交付边界。

**升级条件**：在三个不同任务类型（采购、信息收集、内容处理）上验证通过，升 L1。

## P4 分链排障

**一句话定义**：先判断故障落在「理解链」还是「执行链」，再进入对应检查表，避免盲改配置。

**适用**：多组件系统（模型 + 工具 + 权限 + 运行时）的故障定位。
**不适用**：单组件故障（如纯 API 报错），直接看错误码更快。

**核心步骤**：

1. 用一条最小指令验证理解链（如「介绍一下你自己」）。
2. 用一条最小指令验证执行链（如「打开 Wi-Fi 页面」）。
3. 按结果落到四条分支之一：只理解不执行、只执行不理解、两条都不通、执行中途停。
4. 每条分支只查该分支的三个固定项。
5. 修完重跑两条最小指令，确认没有把另一条弄坏。

**检验标准**：能说出「这次坏在哪条链、改了哪一项、另一条链是否仍通」。

**反模式**：

- 一报错就重装。
- 同时改三个配置，成功也不知道哪个起作用。
- 只看错误码不看现象（有回复但不动，往往不报错）。

**跨域迁移**：网络排障——先分层（物理/链路/网络/应用），再在单层内做替换验证。

**升级条件**：在两类异构系统（如手机 Agent 与浏览器自动化）上各验证一次，升 L1。

## P5 截图成本裁剪

**一句话定义**：多模态 Agent 的成本与失败率随「看屏幕次数」增长，用任务设计裁剪步数比换模型更有效。

**适用**：以截图为主要输入的 GUI Agent、浏览器自动化、手机自动化。
**不适用**：纯文本 API 调用；有结构化接口可直接取数的场景。

**核心步骤**：

1. 估算任务步数（一次搜索、一次筛选、一次详情页各算一步）。
2. 把长任务拆成「侦察 → 选定 → 决策」三段，每段单独验收。
3. 每段把条件写成可判定的数字，减少来回比较。
4. 把停点提前：能停在列表页就不进详情页。
5. 记录每次任务的步数与费用，形成自己的基线。

**检验标准**：同一目标在第二次执行时步数下降，且结果仍可验收。

**反模式**：

- 用「找最便宜的」这类需要全量比较的表述。
- 一个任务里同时做搜索、比价、下单。
- 只看单次费用，不看失败重试的累计成本。

**跨域迁移**：RAG 检索——减少无效检索轮次比换更大模型更能降本。

**升级条件**：在两个不同 GUI 环境（手机 App、网页）上得到同向数据，升 L1。

## 使用建议

这五个模式可以串起来用：**P1 决定路线，P2 建立地图，P3 写任务，P5 控制成本，P4 处理故障**。顺序反过来也成立——排障时先用 P4 定位，再回到 P3 改任务书。
