# 产品能力层：一键部署与画中画各自解决什么问题

> 周报给的是「是什么」，本篇补的是「为什么这样设计、边界在哪、官方日志把它精确到了哪一版」。所有能力描述均为厂商口径，**非独立实测结论**。

## 一、一键部署：把「上线」收进对话框

### 周报口径

「一键部署」上线 TRAE 插件市场，升级桌面端至最新版本即可限时免费体验（F-004、F-005）；适用场景是把已有 Demo 发给朋友或从零做网站上线（F-006）；在对话框里告诉 TRAE 想部署哪个项目即可（F-007），TRAE 识别项目类型、准备代码、发起部署并生成可分享链接（F-008）。

### 它补的是哪一环

从「写出代码」到「别人能打开一个网址」之间，通常还隔着构建、托管、域名、发布四段操作。周报描述的是把这四段压缩成一次对话指令（F-007、F-008）。这是**发布链路的收口**，不是新的编程能力。

### 硬边界（周报未提）

- 限免的起止时间、结束后的计费规则未给出（见 [核验报告缺口登记](../references/verification.md)）。
- 无客户端版本号，「最新版本」无法定位具体构建（F-036）。
- 本包不提供可复现部署步骤：周报无输入输出、无构建日志、无实际站点链接（F-033）。完整的能力边界（支持形态、可见性模型、Node.js 运行时）见 [trae-one-click-deploy](../../trae-one-click-deploy/index.md)。

### 图文层与官方社区教程的口径落差（2026-11-19 新增）

编号海报 01 写「一键部署 限免体验！**把手上的 Demo 做成正式上线的网站**」（F-052），是正文文本层没有的能力承诺。同日发布的官方社区教程 R9（Damond，11-12）给出的却是相当硬的边界（F-064~F-071）：

| 维度 | 海报／周报口径 | R9 官方社区教程口径 |
|------|---------------|---------------------|
| 可部署形态 | 「正式上线的网站」「生成一个可分享的访问链接」 | 仅 StaticWeb（有 `index.html`／确定性静态产物）与 FunctionWeb（Node.js 20 服务进程、明确生产启动入口） |
| 明确拒绝 | 未提 | Python／Java／Go／PHP 等运行时、数据库迁移、多独立服务、常驻后台任务、启动入口或产物目录不明 |
| 资源与域名 | 未提 | 单日 10 GB 流量、100 QPS；静态最多 99 文件／50 MB；不支持自有域名与备案、不满足内网隔离 |
| 可见性 | 「可分享的访问链接」（F-008） | **默认私有**，仅站点所有者可见；须显式说「所有人可访问」才切公开，同一链接即时生效 |
| 可核对实例 | 无 | 真实案例站点 `https://37j97v5w1ieuvqe5pqj.traesite.cn`（StaticWeb、17 文件约 260 KB、私有），项目内 200 MB 模型未随站点上传 |

两者并列登记，**不判海报为错误**：海报是营销位的一句话概括，教程是能力规格。但读者若只按海报预期「正式上线」，会撞上运行时与可见性两类硬约束。R9 另给出安装路径「插件市场 → 推荐 → 一键部署 → 安装 → 使用」、自然语言发起话术、AI 后台四阶段（识别与准备 → 站点与可见性 → 创建与监控 → 校验与交付）与「我的站点」四个页签（观测数据／站点管理／部署历史／日志）。

> **骨架不改判**：R9 虽含可照做的步骤与真实站点，但它属于**外部官方社区教程**，不是本周报正文的流程。按操作可复现性两问，本包仍不设 `examples/`；此处只作能力边界补证，且 R9 仍属厂商一方，不是独立第三方验证。

## 二、画中画：把「等待」变成「并行」

### 周报口径与精确时点

周报说「10 月底」增加画中画（F-009）；官方更新日志精确到 **2026-10-30 v3.4.12** 的新增功能「支持在浏览器预览页面上使用画中画模式，将 AI 操作的浏览器页面悬浮展示在桌面上」，同版本另有「优化画中画模式下编辑器标签栏的展示，隐藏正在悬浮预览的浏览器标签页以减少干扰」（F-034）。

### 触发与交互链路

| 环节 | 行为 | 出处 |
|------|------|------|
| 触发 | AI 判断任务需要浏览器或电脑控制 → 自行调用并唤起小窗；用户不需提前打开面板或安排步骤 | F-012、F-013 |
| 位置 | 小窗位于 TRAE 主窗口之旁，显示 Agent 操作的实时画面 | F-010、F-011 |
| 并行 | AI 在浏览器点击／填表时，用户仍可在主界面继续其他操作 | F-014 |
| 只读 | 小窗是**只读**的；需要接管点击输入时，一键切回侧边栏内置浏览器，操作完可一键切回小窗态 | F-047 |
| 版式 | 可拖拽位置、缩放宽高、置顶，可拖出应用窗口放到另一显示器；不想看时可最小化到侧边工具栏 | F-047 |
| 退场 | 任务结束后伴随退出动画收起：先保留最后画面显示「预览已结束」，再以电视关闭效果收起 | F-047 |

### 机制层：为什么「切换」不等于「重开」

官方专文说明小窗与内置浏览器指向**同一个页面**，靠三项处理维持状态连续（F-048）：

1. **后台渲染**：隐藏侧栏后页面仍持续渲染，把原页面画面送到小窗，同时避免隐藏页面接收用户输入。
2. **任务／Tab 关联数据**：记录页面所属任务、选中 Tab、展示状态与分组；返回内置浏览器时激活原任务页面。
3. **按需同步画面**：小窗收起时暂停画面传输但任务继续；恢复展示后经消息通道同步最新画面，配合限速与背压控制只保留最新帧。

```{mermaid}
stateDiagram-v2
    [*] --> 内置浏览器: AI 调用浏览器/电脑控制
    内置浏览器 --> 画中画小窗: 自动唤起(只读实时画面)
    画中画小窗 --> 内置浏览器: 一键接管(需点击/输入)
    画中画小窗 --> 最小化: 用户暂不想看
    最小化 --> 画中画小窗: 恢复展示(同步最新帧)
    画中画小窗 --> [*]: 任务结束(预览已结束 → 收起)
```

### 厂商自述数字与平台边界

- 官方专文称「经过性能压测，macOS 和 Windows 的画中画对电脑的影响几乎可以忽略（高帧率下 CPU 占用通常低于 5%）」（F-049）。**这是厂商自述，无第三方实测，且不在本周报正文**，本包不把它写成结论。
- 同文注明「画中画功能现已登陆 macOS，Windows 版本正在陆续开放体验」（F-049）。周报未提平台差异，属**省略而非错误**；读者在 Windows 上可能暂不可用。**2026-11-19 复查**：官方日志与专文均无 Windows 全量开放的更新（RV-08 ⚠️）；11-13 第三方自媒体自述实测（R10，F-077）无版本号与测量数据，且称「11-13 官方微博新功能」，与官方日志 10-30 v3.4.12 的落地时点不一致，属渠道复述，不作进度依据。
- 官方日志 11-08 v3.4.16「体验优化」另含「优化 macOS 浏览器预览在任务结束后的收尾体验，短暂保留最后画面并平滑关闭」（F-063），与专文退场动画描述同向。专文 01 图内嵌的 Agent 会话截图（MCP OAuth 检索、Mac 日历日程、IM69D130 数据手册）属演示素材，非带测量数据的实测（F-076）。
- 实现层：官方称通过原生代码处理窗口与画面呈现（F-048）。

## 三、两个能力的共同设计取向

周报用一句话概括了设计意图（F-015）：「让你看进展时少切一次 Tab，让正在写的代码不被打断，让一段原本只能等待的时间，可以用来推进另一件事」；结语是「开头那些不起眼的『小石子』，值得我们认真地一颗颗移开」（F-016）。

把两项能力放在一起看，共同点是**减少人机协作中的切换成本**：一键部署减少「IDE → 托管平台」的上下文切换，画中画减少「主任务 → 查看 Agent 进展」的窗口切换。这是官方定位表述，不是本包的因果推断。

## 洞察（四元组）

1. **陈述**：画中画的关键设计不是「悬浮窗」而是「只读 + 同一页面状态连续」。**证据**：F-047、F-048。**反常识**：容易把它理解成第二个浏览器窗口。**行动**：评估同类功能时先问「能否免重开地接管」。
2. **陈述**：更新日志里的【灰度中】是能力边界的一部分，且灰度状态本身会随时间变化。**证据**：F-035（11-08 两条标灰度）、F-060（11-17 未标灰度）、F-059（版本号精确化）。**反常识**：看到日志条目就当作全量可用，或把一次快照的灰度状态当成永久属性。**行动**：登记版本侧证据时同时抄录版本号、灰度标记**与抓取日期**。
3. **陈述**：跨 bundle 结论冲突不应就地改写他人文档。**证据**：F-050 与 `trae-one-click-deploy` 核验表第 3 项。**反常识**：发现「过时结论」时的本能是顺手修正。**行动**：新建独立「须复核」登记项，保留原束的信源边界与可审计性。
