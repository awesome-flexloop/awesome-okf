# 从官方评测到本地任务评估

官方在 Agents' Last Exam v1 上报告的部分数值如下。它们来自发布文图表，尚未独立复测，不是本束实验结果。[F-031 至 F-034]

| 模型 | effort | 得分 | 图中 Cost（美元） |
|---|---|---:|---:|
| GPT-6.1 Terra | medium | 57.6% | 0.29 |
| GPT-5.6 Terra | medium | 42.6% | 0.84 |
| GPT-6 Astra | medium | 57.6% | 4.82 |
| GPT-6.1 Terra | max | 60.0% | 1.01 |
| Claude Opus 5.5 | 图中未取得 effort 标注 | 63.2% | 8.82 |

medium 的 Terra 与前代相差 15 个百分点，0.29 / 0.84 约为三分之一。这是对图值的算术核对，不是重新运行 benchmark。Astra 与 Terra 的 medium 得分相同，也只能说该评测这个设置上的得分相同，不能推出全面能力、失败类型或可靠性相等。正文使用 cost per task，但本次未取得成本覆盖范围、失败计入及聚合方法。[F-031] 图值比值不能直接换算本地每成功任务总成本。

官方还给出较快完成任务的声明。[F-035] 若没有复现环境、重复次数和耗时分布，本束不将其扩展为产品 SLA 或个人使用效率。

## 写作任务

本束建议用真实但可公开或脱敏的工作材料，固定目标读者、语气和禁止事项，对输出盲评。评判事实遗漏、约束违反、语气合适程度和人工修订量。“Personality”与“细腻理解”对应的是可评价的文本行为，而不是模型自称理解了请求。[F-003]

不要只问“哪个写得更好”。例如，给一封需要拒绝请求又保持合作关系的邮件，明确不得新增承诺，逐句核对有没有擅自承诺交期、付款或责任。这是建议的测试情境，不是 Terra 成功案例。

## 视觉与电脑操作任务

在应用副本中处理发票或图纸时，分别检验“看对”“填对”“改对”。图像字段识别正确、写入正确记录和保存到正确位置，是三个可分开的验收点。若最后只拿到模型的完成自述，任务仍未完成验证。

记录截图或脱敏输入、初始应用状态、允许动作、人工确认点与最终回读结果。不以模拟点击代码冒充电脑操作实测。没有安全执行器时，先做字段理解或文本产物测试，暂不开放外部写入。

一个验收设计示例：以脱敏发票的人工核对版本为基准，要求票号、日期、金额、币种与目标记录逐项一致，保存后重新打开仍一致，且未改动其他记录。任一字段不一致、保存后丢失或出现额外改动，都判该任务失败并登记原因；部分字段正确只作诊断，不记为全任务成功。这是设计示例，未执行 Terra 实测。

## 编码任务

从一个有现成测试、易回滚的局部任务开始，同时核对测试通过、非目标文件改动和依赖变更。若错误代价高或需要跨模块推理，可以保留 Sol / Astra 作为候选；官方明确仍推荐它们处理最复杂编码任务。[F-041]

比较时固定仓库版本、测试集、端点、执行器版本、工具权限、effort 与终止条件。把失败重试和人工修复算入成本，才能连接到[成功任务成本](02-economics.md)，而不是用 benchmark 最高分替代工程验收。

## 试验记录

以下为空白记录设计，不含虚构实验结果。

| 应记录的项 | 用途 |
|---|---|
| 任务 ID、输入版本、模型、effort | 让比较可以重放 |
| API 端点、宿主与执行器版本 | 区分接口和运行环境变化 |
| 工具与权限范围 | 解释成功来自模型还是环境 |
| 预先确定的验收条件 | 避免看过结果后改变标准 |
| 最终产物与外部状态回读 | 区分自述完成与实际完成 |
| 时间、token、工具费、重试与人工修订 | 汇总真实总成本 |
| 未完成原因及风险事件 | 看见平均分掩盖的失败 |

本束没有模型账户实验、套餐额度实测或桌面动作演示，所有试验方案均待验证。
