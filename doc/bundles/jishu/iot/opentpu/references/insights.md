# openTPU 架构洞察四元组

基于 F-001~F-123（[事实登记表](facts.md)）与 8eaa4806→ffe997e 二十条对账（[源码地图](source-code-map.md)）。四元组格式：**陈述 / 证据 / 反常识 / 行动**。这些是单仓源码归纳的教程性结论，不是跨项目验证的普遍定律。

## I-1 契约对拍：正确性来自「同一份逐位契约 × 多实现对拍」，不是单点测试

- **陈述**：openTPU 的正确性基础设施是一份写死到位级别的三方契约（docs/isa.md：编码、存储语义、fp32 舍入、近似函数固定序列、权重编码），compiler.py、isasim.py、RTL 三个实现必须写出相同的位；模型级再用 validate.py 的四行对照表（device vs W+A、device vs fp32、W+A vs fp32、W+A~ ulp floor）把「实现正确性」与「量化质量」拆成两个可分别归因的问题。
- **证据**：F-010、F-077、F-045、F-091~F-097；对账 R3-09（232 commits 后 exp2 系数与 recip/rsqrt 魔数零漂移）。
- **反常识**：token 相同不证明运算一致（logits 整体偏移后 argmax 可以不变）；设备偏离 fp32 也不证明硬件错（量化本就改变输出）。位级一致只是「已执行测试上的证据」，不是形式化证明。
- **行动**：学习任何一层前先读契约；做模型质量评估时四行表分开读；复用该方法时先固定提交、输入、数值格式与执行配置。

## I-2 限制隐式行为：刻意简单的顺序机器让「每次数据搬运」成为可教学的指令

- **陈述**：机器无 cache、无乱序、无隐藏调度，sequencer 按程序序把指令发进 WIN=16 的足迹窗口（依赖跟踪而非重排），每次 DRAM 搬运都是显式指令；性能问题由此压缩为「等 DRAM / 等计算 / 等依赖」三类可在 trace 中直接定位的状态。
- **证据**：F-004、F-016、F-079、F-090、F-099、F-056。
- **反常识**：WIN=16 不是「乱序发射窗口」；ACT_ROWS>MCOLS 时 MXU 对每 MCOLS 行组 replay 流数据，但结果不依赖 MCOLS/ACT_ROWS（F-012）——硬件可以在不改变可见语义的前提下重复流数据。「预取/窗口/replay」容易被误读成隐藏缓存层。
- **行动**：先建立「顺序完成」心智模型再读流水；把生产点（S=1/MCOLS=4/WIN=16）与 09-23 设计稿（S=2/MCOLS=8/WIN=32）当作演进而非矛盾来读。

## I-3 修复配反例：契约演进的最小证据单元是「固定点反例 + 跨层联动 + 能杀死 mutant 的边界测试」

- **陈述**：数值/协议修复不是一行改动，而是「固定点反例 → Python 模型 → RTL → isa.md → 测试」同步演进，反例直接钉住曾经出错的输入：recip(1)、负零、35B 连续 embedding 的 WAITW 乱序。
- **证据**：F-035（exp2 Taylor 在 f=1 偏 13 ulp 的文档记录）、F-036（无 FMA 时纯 Newton 驻点低 1 ulp，recip(1) 曾为 0.99999994）、F-098（waitw.py 精确限定竞争场景）、F-101、F-009（贡献契约）。
- **反常识**：文档保留「这个算法曾经错在哪、朴素实现为什么不够」比只写最终公式更有价值——它是未来移植者的反例库；「测试全绿」的证据强度低于「故意改坏负零的 mutant 被测试拦截」。
- **行动**：每次契约变更同时更新实现、边界测试与对应层级证据；读近似函数章节时连带读修复史。

## I-4 量化是 ISA 的一等公民：尺度不是元数据，而是指令字段和累加器移位

- **陈述**：量化不是部署期离线变换——量化器是执行单元（QACT/QST 是 opcode），激活两级块尺度（Sa + 4 个 8-bit da）驻在 ACT RAM 每行每块；MM 在精确整数累加后按权重/激活偏移做幂次移位再做三次舍入乘法；RMSNorm 的列/行尺度折叠进 QACT（CSCALE/RSCALE）免一次向量遍；权重四格式（int8/int4/FP4/NVFP4）由 WF 字段与 scale 行布局在 ISA 层裁决。
- **证据**：F-015、F-042、F-045、F-046、F-048~F-053、F-055、F-054。
- **反常识**：「4-bit 权重」不是全模型 4 bit——LM head 保 int8，E4B 是按层混合；4.25 bits 是 FP4 值加两级尺度的加权结果，NVFP4 为 4.5 bits；4-bit 提速 40-45% 的直接原因是 DRAM 流量下降（decode 带宽受限），不是算力提升。
- **行动**：读 MM 之前先读 ACT RAM 的尺度记录；引用 bits/提速数字时带「口径+镜像+日期+作者报告」标签。

## I-5 归属与口径分离：读高速演进仓的两类「不能合并的数字」

- **陈述**：①「AI 开发」是仓库自述，公开仓库不能证明逐行作者——工程产物与生成归属必须分开引用；②性能表存在多套不可互换口径（512 prompt+64 greedy 且主机 argmax 在环 vs 96-token 卡自选取且 logits 流式；device vs wall；不同镜像与日期；作者报告 vs 第三方复现），且 232 commits 间配置从 7 行扩到 18 行、模型从 6/7 个扩到 10 个。
- **证据**：F-102~F-104、F-084~F-085；对账 R3-15、R3-16（7 个数字逐字保留但表范围扩展）、R3-12、R3-20（第三方运行数字与 HN/star 无法由源码静态确认）。
- **反常识**：同一模型同一权重在同一 README 里可以出现两个吞吐数（LFM2 4bit：85.8/82.1 与 89.5/84.5）——这不是勘误，是计时边界不同；把它判成「口径不一的错误」反而是读者错误。
- **行动**：全束数字引用必带四标签；不收录任何 HN/star/第三方运行数字为事实；引用演进中的仓库固定全 hash 而非浮动分支。
