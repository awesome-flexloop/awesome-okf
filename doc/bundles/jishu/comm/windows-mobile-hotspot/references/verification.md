## 二、勘误明细

### 勘误 1（源自 C2，实质性）—— 源文注意事项④

**源文口径**：「真正的路由器可以长期运行，支持防火墙、DHCP、端口转发等功能；而 Windows 11 的移动热点更适合临时应急共享网络」。

**问题**：该句把「防火墙、DHCP、端口转发」三项并列对比，读者会自然理解为后两项是路由器专属、Windows 移动热点不具备。

**官方依据**：

| 断言 | 官方原文要点 | 编号 |
|---|---|---|
| 移动热点具备 DHCP | ICS 通过提供本地私有网络服务（名称解析与地址分配）简化小网络配置 | F-016 |
| 移动热点具备 DNS 代理 | ICS 扮演 DHCP 服务器并充当 DNS 代理 | F-019 |
| 移动热点具备状态防火墙 | Windows 防火墙在 ICS 主机上启用时保护 ICS 客户端；官方建议始终启用 | F-016 |
| 移动热点不做端口转发 | ICS 对报文做的是源地址改写，不是端口映射 | F-018 |

**修正后口径**（已在[总览](../concepts/overview.md#三勘误索引本包最重要的一条)、[ICS 机制](../concepts/ics-mechanism.md)、[边界与风险](../concepts/boundaries-and-risks.md)三处就地写入）：

> Windows 11 移动热点**自带** DHCP 地址分配、DNS 代理与状态防火墙——这些不是「专业路由器才有的东西」。它与家用路由器的真实差距在于：依赖主机常开不休眠；提供 NAT 共享出口而非端口转发；缺少访客网络、设备分组、家长控制、QoS 等管理面。

**为什么这条必须改在正文**：错误归因会直接误导排障动作——相信「热点没有 DHCP」的读者会去查防火墙开关或重装驱动，而真实故障点在 ICS 服务与 UDP 67/68 的放行。

### 勘误 2（源自 C3，证据层级）—— 「8 台设备」

**源文口径**：「Windows 11 这个热点最多可连接 8 台设备，对于日常使用完全够用。」

**问题**：以确定语气陈述一个**从未出现在产品文档中**的数字；且把它当作不可变的硬上限。

**修正后口径**：

> 移动热点的**默认连接上限为 8 台设备**，Windows 设置界面**不提供**调整入口。存在官方社区答复提及的注册表调整项 `icssvc\Settings\WifiMaxPeers`（F-023），但其**跨版本、跨驱动的实际效果未获微软官方文档确认**（U-3）。此外无线网卡驱动自身还有并发上限，不受 ICS 侧参数影响（F-037）。

### 勘误 3（源自 C4，规范完整性）—— 密码长度

**源文口径**：「密码：要求至少 8 个字符。」

**修正后口径**：官方 schema 明确 **8 到 63 个 ASCII 字符（码位 32–126）**；无法映射到 ASCII 的 Unicode 字符会被拒绝（F-020）。

### 勘误 4（源自 C5，证据冲突）—— 6 GHz

**媒体口径**：KB5050094 为 Windows 11 24H2 引入 6 GHz 移动热点支持（F-035，L6）。

**冲突**：官方 KB 条目清单未列该项（F-033，L1）；官方社区答复称该功能尚未开始推出（F-034，L3）。

**修正后口径**：**本包不对 6 GHz 移动热点的可用性作任何断言**，登记为未闭环项 U-1，并给出实机验证作为唯一可靠路径。

## 四、可迁移模式：共享出口型能力归因校验

> **模式名**：共享出口型能力归因校验（Shared-Egress Capability Attribution Check）
> **来源**：本包 C2 勘误的抽象化，适用于「操作系统做不到 X」这类断言的普遍性检验。

### 触发场景

看到一份教程/文档/同事的说法形如「**XX 很简单，但不支持 A、B、C 这些专业功能**」，且：

- 这些「专业功能」在操作系统层**可能已有独立组件提供**；
- 该说法会被读者**直接转成操作动作**（例如「所以我不需要检查防火墙 / 不需要检查 DHCP」）；
- 断言的后果是**排障方向被带偏**，而不是单纯的知识偏差。

### 核心做法（5 步）

1. **拆项**：把被否定的能力清单逐项拆开，不要让它们打包成一句话。源文把「防火墙、DHCP、端口转发」并列，这一步就是勘误的入口。
2. **定位责任组件**：为每项能力找到操作系统层的责任主体（服务名 / 驱动要求 / 注册表键）。本例中 DHCP 与 DNS 代理的责任主体是 ICS（`SharedAccess` / `icssvc`）。
3. **查该组件的官方文档**，确认它是否**确实提供**该能力，以及启用时是否**自动完成配置**。本例中 ICS 启用时会自动配置防火墙放行规则——这解释了为什么用户不该去手动开关防火墙。
4. **区分「未启用」与「不具备」**：本例中「没有端口映射」是**真的不具备**，「没有 DHCP」是**误判**。两者混为一谈是错误归因的主要成因。
5. **把勘误写回正文对应段落**，而不是在文末加一条勘误块——错误留在正文里，读者就会照着错的那句做。

### 反模式（≥3）

| 反模式 | 本例中的表现 |
|---|---|
| 把社区 Q&A 口径当产品文档条款引用 | 「8 台上限」被当作确定的产品条款，而产品文档从未写过这个数字 |
| 用过时技术的探测命令判断新功能可用性 | `netsh wlan show drivers` 的 Hosted Network 行被当作热点可用性判据 |
| 把「默认关闭/未暴露入口」与「不具备」混为一谈 | ICS 的 DHCP 与防火墙是内建能力，只是没被文档显眼地讲出来 |
| 只在文末加勘误块而不改正文 | 错误断言仍在正文原位，读者仍会照着做 |
| 把二手报道当官方结论 | 6 GHz 热点：多家媒体一致报道，但官方 KB 未列、官方社区称未推出 |

### 检验标准

- 教程中每条「不支持 X」的断言，都能指向一个**组件级证据**，或已被删除；
- 每条能力断言都标注了**证据层级**（L1~L6），读者能自行判断可信度；
- 勘误条目在正文**对应段落**就地可见，不是集中在文末；
- 社区口径类事实**不被升格**为官方结论，且带复核触发条件。

### 跨领域迁移示例

**示例 1 · 容器内嵌 DNS**。常见说法：「Docker 容器默认无法通过服务名互相解析，只能用容器 IP」。实际 Docker bridge 网络内置了一个 DNS 服务器（默认 `127.0.0.11`），并由 Docker 的 DNS 代理提供服务名解析——这与「操作系统不具备 DNS」是完全相反的归因。同一条纪律：**先查该能力是否由独立组件提供，再判断有无**。判据与本例同构：查组件官方文档 → 确认启用时是否自动配置 → 区分未启用与不具备。

**示例 2 · 同一功能两代技术并存时的探测命令**。本例的 Hosted Network 与移动热点是「同代功能的两套实现」。可迁移的通则是：**当一项功能在软件栈里存在两代技术时，探测命令属于哪一代，决定了它能否作为判据**。同类场景：Android 的 Wi-Fi AP 与 Wi-Fi Direct、Bluetooth PAN 与经典蓝牙网络栈。

**status 决策**：`draft`。

理由：
1. 机制层结论（C2 的 ICS 能力）有 L1/L2/L4 三层官方证据支撑，可靠度高；
2. 但存在 **1 处实质勘误已回写**、**5 项未闭环**（U-1~U-5）、**3 处社区口径**（F-036、F-037 及 `WifiMaxPeers` 效果）未获官方确认；
3. 操作层未实测（G4），UI 措辞随时可能随 Windows 更新变动；
4. 故不标 `stable`，也不标 `flagged`——信源本身是公开且可核验的，未闭环项**已逐条标注层级与复核触发条件**，读者可安全地按层级引用。
