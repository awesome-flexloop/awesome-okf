# 洞察与可迁移模式

> 本文件是 R→I→E→V 链路的 I/E/V 产出。事实编号见 [facts.md](facts.md)；信源与核验见 [sources.md](sources.md)。

## 1. 洞察（四元组）

### I-1 编译器不会消失，但「编译」会退化为「表示 + 分析 + 验证」

| 维度 | 内容 |
|------|------|
| 现象 | Agent 已能直接生成 CUDA/PTX，社区却在此时重建编译基础层 [F-019][F-016] |
| 根因 | 代码生成可被替代，但**正确性验证**不能依赖生成者自述；验证需要精确定义的结构化语义 [F-017][F-018] |
| 影响 | 编译器的价值重心从「变换与优化」转向「表示、分析与验证」；优化交给后端或上层 harness |
| 建议 | 评估编译器项目时，先问它提供什么**可验证语义**，再问它有多少优化 Pass |

### I-2 真正的架构变量是「稳定性与变化速率」，不是「功能模块」

| 维度 | 内容 |
|------|------|
| 现象 | TIRx 把项目切成「最小核心 / 可预测工具 / 动态扩展 / 上层 harness」 [F-004][F-024] |
| 根因 | kernel 可分钟级生成并丢弃，底层却需要长期兼容；按功能分层会让快变模块拖慢稳定模块 |
| 影响 | 维护对象从「代码」变成「分层契约」；扩展可以独立发版，不必跟随核心 |
| 建议 | 设计任何 Agent 参与的系统时，先画「变化速率轴」，再决定哪些进核心、哪些做插件 |

### I-3 语言不是架构，是局部实现细节

| 维度 | 内容 |
|------|------|
| 现象 | TIRx 同时支持 Python/C++/Rust，且允许同一扩展用两种语言实现 [F-012][F-027] |
| 根因 | 不同模块的最优语言不同：原型要快、热点要性能、安全关键要内存安全 |
| 影响 | 统一 ABI 成为关键；语言选择从「全局约束」降级为「模块决策」 |
| 建议 | 多语言系统的第一优先级是统一对象/调用 ABI，而不是统一语法或工具链 |

### I-4 「动态扩展」是对构建时间的直接攻击

| 维度 | 内容 |
|------|------|
| 现象 | TIRx 用运行时注册表让新类型/算子无需重编译核心 [F-015] |
| 根因 | Agent 写代码快，但「改—编—测」循环中的构建时间占比反而上升 [F-023]；静态 visitor 又要求预知全部节点 [F-031] |
| 影响 | 扩展生态成为可能；核心只需保持最小稳定 |
| 建议 | 把「新增一个算子需要多久」作为架构健康度指标；超过分钟级就要考虑插件化 |

### I-5 传播口径会制造「能力幻觉」

| 维度 | 内容 |
|------|------|
| 现象 | 中文文章称 Rust「较完美支持」，官方博客标为 work in progress [F-030][F-006] |
| 根因 | 作者视角（愿景）与官方文档（交付状态）承担不同责任；传播链缺少状态标注 |
| 影响 | 读者可能高估成熟度，做出错误的技术选型 |
| 建议 | 对 beta 项目，一律以「包版本 + 官方 README/文档状态标记」为准，文章表述只作意图参考 |

### I-6 性能证据有代际归属，不能跨代引用

| 维度 | 内容 |
|------|------|
| 现象 | 2026-06 第一代给出 54 配置 B200 基准；2026-11 第二代未给基准 [F-081][F-040] |
| 根因 | 两代包名、文档、API 与代码基不同；传播时经常省略「哪一代」 [F-097] |
| 影响 | 读者可能把 1517/5930 TFLOPS 当作 `tvm-tirx` 0.1.0b1 的能力 [F-099] |
| 建议 | 引用性能必须带四要素：代际 + 硬件 + baseline commit + 计时方法 |

### I-7 抽象边界是演化节奏，不是一次性设计

| 维度 | 内容 |
|------|------|
| 现象 | 新硬件先以 intrinsic 立即使用，模式稳定后再晋升为 tile primitive [F-072] |
| 根因 | 编译器无法预判所有新硬件 pattern；过早抽象会把未成熟的假设锁进核心 |
| 影响 | 核心保持小，后端库随硬件世代增长；新增 intrinsic 不破坏已有功能 |
| 建议 | 用「晋升条件」设计扩展，而不是一次性定义通用 API |

### I-8 文档范围 ≠ 架构范围

| 维度 | 内容 |
|------|------|
| 现象 | README 只承诺 CUDA + host LLVM；源码注册了 10 个内置后端 [F-004][F-112] |
| 根因 | 对外承诺保守，内部架构为多后端预留；两者服务不同读者 |
| 影响 | 只读 README 会低估架构；只读源码会高估可用性 |
| 建议 | 区分「已注册 / 已构建 / 已测试 / 已承诺」四档，引用时标明档位 |

### I-9 「无启发式」是口径问题，不是零 pass

| 维度 | 内容 |
|------|------|
| 现象 | 官方说 compile 不施加启发式；源码有 dispatch/layout/向量化/展开/CSE/校验流水线 [F-022][F-110] |
| 根因 | 「启发式」指搜索式/代价模型式调优，不是所有确定性变换 |
| 影响 | 误以为零 pass 会在调试与性能预期上判断错误 |
| 建议 | 看到「无启发式」时追问：哪些 pass 仍固定执行？顺序是什么？ |

## 2. 可迁移模式（E）

### P-1 稳定内核 + 动态插件

| 项 | 内容 |
|----|------|
| 触发场景 | 系统需要长期稳定，同时上层需要高频试错；Agent 或多人并行开发 |
| 核心步骤 | ① 识别「一旦确定就很少变」的最小语义；② 把它做成小核心；③ 为变化部分设计运行时注册/加载机制；④ 插件独立仓、独立发版；⑤ 核心只保证兼容与验证工具 |
| 反模式 | 单体大仓每次改一行全量重编译；或反过来「一切动态」导致无稳定语义可依赖 |
| 迁移验证 | 可用于插件化 IDE、规则引擎、数据管道算子体系；判据是「新增一个能力是否需要重建核心」 |

### P-2 统一 ABI，语言自由

| 项 | 内容 |
|----|------|
| 触发场景 | 同一系统需要脚本层快速迭代 + 原生层高性能 + 安全关键模块 |
| 核心步骤 | ① 定义跨语言对象模型与调用约定；② 让所有语言绑定共享同一对象表示；③ 允许模块级选择语言；④ 用同一套测试验证跨语言一致性 |
| 反模式 | 「主语言 + wrapper」；每种语言各维护一套 IR；跨语言靠序列化复制 |
| 迁移验证 | 适用于编译器、数据库扩展、推理引擎；判据是「同一对象能否在两种语言间零拷贝传递」 |

### P-3 先表示，后验证

| 项 | 内容 |
|----|------|
| 触发场景 | 由 AI/Agent 生成代码、配置或策略，且错误代价高 |
| 核心步骤 | ① 把生成结果强制落到结构化表示；② 在表示上做廉价静态检查；③ 再做测试/对拍；④ 高价值场景引入形式化语义 |
| 反模式 | 只跑测试就上线；或直接相信模型自述「已验证」；或一上来就做完整形式化导致成本失控 |
| 迁移验证 | 适用于 IaC 配置、SQL 生成、工作流编排、硬件描述；判据是「错误能否在编译前被结构化检查捕获」 |

### P-4 intrinsic → primitive 晋升

| 项 | 内容 |
|----|------|
| 触发场景 | 新硬件/新算子频繁出现，编译器无法提前为每个特性设计抽象 |
| 核心步骤 | ① 先用薄封装 intrinsic 让用户立即可用；② 收集跨 kernel 的重复模式；③ 补 layout helpers、legality checks 与 dispatch；④ 晋升为 tile primitive 并沉淀入库 |
| 反模式 | 一开始就设计「通用 primitive」导致过度抽象；或永远停留在 intrinsic，重复代码扩散 |
| 迁移验证 | 适用于数据库算子、图像处理、推理后端、硬件驱动；判据是「新模式是否先在 2–3 个真实用例中重复出现」 |

### P-5 对外承诺与架构能力分账

| 项 | 内容 |
|----|------|
| 触发场景 | 平台/框架支持多后端、多语言、多部署形态，但成熟度不一 |
| 核心步骤 | ① 列「已注册」清单；② 标「已构建」开关；③ 标「已测试」矩阵；④ 对外只承诺「已测试且稳定」的子集；⑤ 文档显式说明差异 |
| 反模式 | README 罗列所有后端造成过度承诺；或只写两个后端让架构能力被低估 |
| 迁移验证 | 适用于推理引擎、数据库连接器、云 SDK、跨平台框架；判据是「读者能否一眼分清可用与可试」 |

## 3. V 对抗审查（六视角）

### 3.1 魔鬼代言人

**攻击**：如果 Agent 能直出 PTX 并自带测试，IR 基础层只是多一层负担。

**回应**：对一次性 kernel 成立；但当需要跨项目复用分析、跨语言共享表示、长期维护与独立验证时，自建脚本会重复造轮子。**部分反驳已解决**：第一代已给出 54 配置 kernel 基准，证明低边界 DSL 能达到 SOTA 邻域 [F-081]~[F-086]；**仍未解决**：没有「Agent + TIRx vs Agent 单独」的效率对照数据 [F-040]。

### 3.2 新人视角

**攻击**：TIRx/TVM-FFI/TIR/`tvm::tirx` 术语密集，新手极易把两个 TIRx 混为一谈。

**回应**：本包在 [00-overview](../concepts/00-overview.md) 用对照表显式区分，并在术语表标注。**遗留风险**：官方文档本身未强调这一区分，读者仍可能误读。

### 3.3 老板视角

**攻击**：第二代项目 2026-10 创建、`0.1.0b1`、Rust WIP，凭什么进入生产？

**回应**：第二代不应直接进入生产关键路径；合理定位是「跟踪 + 试验 + 学设计」。第一代 `apache-tvm` 0.25.0 已有发布、课程与基准，可作为第一代能力参考，但仍不能替代第二代的评估 [F-095][F-099]。

### 3.4 未来视角

**攻击**：若 MLIR 成为 Agent 生成 IR 的事实标准，TIRx 的差异何在？

**回应**：TIRx 的差异是极简核心、动态类型/算子注册、三语言低边界与 <1 MB 运行时 [F-004][F-028]。但这些是否足以形成生态，取决于社区采用速度，而非技术优劣本身。

### 3.5 基准审计视角

**攻击**：54 配置是官方自测，baseline 选择、形状覆盖与计时方式都可能对自身有利。

**回应**：官方固定了 baseline commit 与 Proton 计时参数，结果多为 0.95×–1.00×，属于「接近」而非「碾压」[F-081]~[F-086]。**未解决**：没有第三方独立复现；且测试对象是第一代，不是第二代 [F-099]。

### 3.6 源码审计视角

**攻击**：本包此前基于文章与文档，可能把「官方叙事」当成「代码事实」。

**回应**：本次用本地 commit `cdc7a377` 核对了后端矩阵、lowering 顺序、构建依赖与 API 形态，修正了三处认知（见 [11](../concepts/11-source-repo-tour.md) 第 7 节）。**仍未解决**：未构建、未跑测试，源码结论是静态阅读；非 CUDA 后端未实测 [F-100][F-108]。

## 5. 一页总结

> **TIRx 的启示不是「去学一个新编译器」，而是「把系统按变化速率切开」**：稳定的部分提供语义与验证，易变的部分交给 Agent 快速试错。这个判断可以迁移到任何「AI 参与生产」的系统设计里。
