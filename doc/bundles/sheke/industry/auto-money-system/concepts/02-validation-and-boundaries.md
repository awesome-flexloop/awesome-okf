# 验证与边界：不把建议误读成收益承诺

## 把数字还原为假设

文章中的“20% 替代”“500 个粉丝”“被问过十次”“19.9/29.9 元”分别对应效率、受众、需求频率和价格假设（F-007、F-009、F-013、F-014）。验证时应改写为问题：

1. 任务完成时间是否下降，返工是否增加？
2. 内容模板在没有本人实时编辑时是否仍能工作？
3. 重复提问是否足以形成明确交付边界？
4. 用户是否愿意在当前平台和支付方式下完成购买？

只有在真实用户、真实交付和明确记录下，这些假设才可能被支持或证伪。

## 四类边界

### 平台边界

公众号自动回复、支付、下载和消息触达受平台能力与规则影响（F-015）。平台接口、审核策略和文件存储方式会变化，不能把某一篇文章的建议视为长期稳定的产品能力。

### 用户边界

个人 IP 的内容模板可能提高复用性，但不能消除定位、信任和售后问题（F-008、F-010）。粉丝数量本身不是支付意愿、留存或交付质量的替代指标。

### 交付边界

轻产品减少人工参与，不等于没有更新、退款、版权、隐私和错误纠正责任（F-011、F-012、F-015）。这些责任必须在产品说明中先写清楚。

### 时效边界

文章发布于 2026-08-12（F-002），对“2026 年”的判断是时间截面观察（F-003）。工具、平台和用户行为会变化，当前 bundle 在 2026-12-31 前复核。

## 可迁移模式

**触发条件**：面对“自动赚钱/自动化变现”类宽泛建议，需要将其变成可验证的工作流假设。

**核心步骤**：

1. 把方向拆成任务、模板、结果和反馈；
2. 把数字门槛改写成待验证假设；
3. 明确人工检查点、平台限制和售后责任；
4. 用一条流程和一类用户先做小范围验证；
5. 记录支持、证伪和停止条件。

**反模式**：

- 把作者观察写成行业定律；
- 把示例价格写成推荐价格；
- 只自动化发送，不设计更新、退款和异常处理；
- 用粉丝量或曝光量替代支付与完成数据。

**迁移验证**：该模式可迁移到课程、模板、咨询、数字下载和内部运营自动化；每次迁移都必须重新验证平台规则与用户付费行为。
