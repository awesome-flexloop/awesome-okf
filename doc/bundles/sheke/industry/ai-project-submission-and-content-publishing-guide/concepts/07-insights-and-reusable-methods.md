# 三条机制洞察与两项候选方法

以下为基于规则结构的解释和方法候选，未观察用户参赛结果，未经获奖、收益或独立V验证。每条解释只使用[底账](../references/facts.md)已登记证据；官方没有表达这些方法论结论。

## I-001 工具资格先于内容包装

**陈述**：作品是否满足真实工具链约束，不能靠介绍文章更换平台用语来补救。

**现象与证据**：知乎要求全程对应工具、一作品一工具一赛道（F-012/F-014），WorkBuddy要求使用WorkBuddy创作并提供真实创作对话（F-035/F-042）；知乎重复或跨赛道轻改可取消资格（F-022）。外部跨投仍未知（G-003/G-016/G-017）。

**解释假设**：这些要求让创作过程成为资格证据，而不只是成品展示。此为规则结构推断，不声称知道评委如何识别混用，也不推导未公布的检测算法。

**反常识**：直觉会把“同一应用能跑”当成多平台可用；已取得规则却还限定了怎样创作和怎样投，功能质量不能证明工具资格。

**影响**：先开发再改赛道声明，可能留下无法诚实补齐的过程证据；同代码跨赛不可作默认复用路径。

**行动建议**：选题前记录实际工具链和目标入口，核双方同作品定义。冲突时选择一个符合真实过程的入口，或分别做合规的新作品；不事后伪造单工具过程。

## I-002 公开表达有独立的时间成本

**陈述**：把正文放进公开Wiki或社媒是发表动作，不宜只当可逆的草稿整理。

**现象与证据**：头条站外先发及实质相似简单改写非首发（F-062/F-063），删重发不自动恢复（F-066/F-079），72小时按小时而非日期（F-061/F-064）。知乎与WorkBuddy活动截止见F-002/F-030，Git/Wiki/代码表达边界仍缺（G-023）。

**解释假设**：内容准备、公开可检索和平台声明是不同状态；先公开可能产生另一平台无法消除的历史条件。对Wiki的具体裁定尚无依据，不能推断所有代码或所有目录标题都是文章先发。

**反常识**：直觉认为“我自己的稿，换平台或等三天就能首发”；已取得规则仍记录原先发表及相似性，等待不会删除历史。

**影响**：赛事宣传与首发窗口可能冲突；为了归档先公开正文，可能提前花掉未确认的首发资格。

**行动建议**：在私有写作区保留实际正文及发表记录，公开包只给指南。用真实`t0+72小时`与截止比较，缺协议/时区不算许可；冲突时分开独立论证、少选一个入口或不声明首发。

## I-003 核验范围决定证据能支持多大的话

**陈述**：一项检查成功，只能支持它实际比较的字段和对象，不能自动扩展到全面合规。

**现象与证据**：W-R当前/旧版细则字符串一致，但W-H链接提示更新（F-043；C-002/E-002）；服务协议与隐私正文未读（G-019）。知乎CLI片段非全文（C-001），头条百科全文已得但实际入口仍未确认，协议读取片段非全文（C-007/G-020/G-022）。

**解释假设**：把来源身份、读取完整度、比较对象、适用范围合成“已经核验”，会丢掉关键边界。这是证据管理解释，不把当前未读项认定为违法或永远不可得。

**反常识**：直觉认为“官方规则没变，所有流程都没变”；实际细则比对与表单更新可以同时成立，协议适用也须另证。

**影响**：过宽表述会误导新人，以为体验链接、许可或收益资格已确认；重复官方来源也可能被误写成独立多源。

**行动建议**：每次结论写四项：谁检查、检查哪份材料、截至何时、仍不覆盖什么。来源更新按字段重核，未取得入口就保留缺口，不用相关百科补成适用协议。

三条分别聚焦工具资格、发表时序、证据范围；不以同一观点换名凑三条。

## M-001 三对象分账

一句话定义：把作品、文章和宣传分别记录来源、工具、许可与发表状态，再判各平台路径。

**成熟度：L1-draft。** 仅本次三入口规则整合首成型，未经实际投稿、获奖或独立迁移验证；不登记到仓库外方法论模式库。

### 适用边界

适用于同一主题需要应用、文章、社媒等多种交付，且存在工具绑定或首发、授权限制的场景。

不适用于给出法律意见、替用户接受协议、用一张表证明允许跨投；没有实际来源、资格或开发链时只能列缺口。

### 核心步骤

1. 列出每项作品、文章和宣传素材，记录同一性关系，不先把三者当成一份稿。
2. 为作品登记真实工具链、原创/实质改造证据与目标赛事要求。
3. 为文章登记独立读者问题、论证和发表历史；实际未发表正文留私有区。
4. 为宣传素材登记商标、界面、引用与第三方许可，以及平台和用途。
5. 逐对象判断已确认条件、缺口、冲突和保守分支；缺口不写成许可。
6. 修改或公开前回核关联对象，保存真实版本与发表记录。

### 检验标准

每个对象能回答“是什么、由什么工具产生、权限从哪来、在哪何时公开、还缺什么”。事实与意见分栏；任何跨发决定能指到已取得条款或明确的待确认分支。第三人能发现缺项，不以“已完成”一句话代证。

### 反模式

| 反模式 | 为什么失效 | 替代动作 |
|---|---|---|
| 一份代码、一份稿件三处投，只改标题 | 工具绑定、作品同一性与文章先发是三个条件 | 分作品链、论证和发表状态核对 |
| 用非独占许可证明所有外部用途合法 | 非独占不确认目的赛事资格、主办IP或其他协议 | 分许可主体、范围和目的平台 |
| 以库规模或平台知名度选择方案 | 总量不证明任务可体验或过程可举证 | 选一个能跑且有真实证据的任务 |
| 把商业素材、主办界面和纯自有代码混成一类 | 不同权利和授权前提会被省略 | 逐素材登记来源与用途 |

### 跨域迁移检验

候选迁移到科研论文配套Demo：论文正文、代码仓、宣传材料分别列许可及公开历史；核目标会议的预印本政策与数据许可，不能套头条72小时。当前只做桌面可行性检验：若能逐对象写清适用规则与缺口，方法可继续试用；本次未执行真实会议投稿。

升级L1须至少两项独立真实交付记录，对对象区分和缺口处理有第三人复核；升级L2需多案例、规则变更回核及错误处理证据。获奖不是唯一指标，更不能用候选方法反推获奖概率。

## M-002 证据时序门

一句话定义：每个不可逆公开动作，须同时核证据就绪、适用资格与时间条件；任何一项未知就保留暂停或退路。

**成熟度：L1-draft。** 来自本次规则结构与时序演算，未经真实审核周期、获奖或跨域实际交付验证。

### 适用边界

适用于有活动截止、审核、首发窗口或权限依赖的创作任务，尤其是公开动作不能简单恢复的场景。

不适用于预测审核耗时、把统一固定缓冲当SLA，或用“超过72小时”替代全部合同审查。

### 核心步骤

1. 为每条条件登记来源、版本、时点、已读范围和未知项。
2. 分资格、作品、发布三线列节点，标明可自控动作与外部依赖。
3. 用实际时刻和明确时区算窗口；截止缺钟点或时区时拒绝输出精确最晚时间。
4. 把体验、截图、对话、正文事实与对应版本核对，不把预计结果当完成证据。
5. 公开或提交前同时检查时间、适用资格、许可及材料；有冲突就缩范围、改独立内容或停止该分支。
6. 保存当时检查范围与真实结果；来源或版本变动后只回核受影响项，不抹掉既有失败。

### 检验标准

每项公开动作均有时间依据、真实证据状态和缺口处置；计算可由第三人复算；未知没有被转换成确定工期或许可。一次检查成功所支持的对象和未覆盖范围写在同一记录中。

### 反模式

| 反模式 | 为什么失效 | 替代动作 |
|---|---|---|
| 提前两天必够、跨过三天就是72小时 | 审核无SLA，日期不是小时差 | 记录外部依赖、用明确时刻算，保留失败分支 |
| ruleHTML一致就宣称整个平台流程已核验 | 表单、服务协议与实际入口未被该比较覆盖 | 按检查对象限定结论 |
| 用公开Wiki存实际首发正文，稍后删掉 | 公开历史与相似内容可能仍影响资格 | 正文留私有区，公开仅指南 |
| 权限申请后24小时视为必开通 | 原文是“可尝试”，不是承诺 | 取得实际权限再推进依赖 |

### 跨域迁移检验

候选迁移到资助申请：资格审批、材料准备、公开预告分三线，所有截止用机构当期时区，保密与公开条款用资助方规则；不借赛事工作日或头条窗口填空。仅检验表结构能承载实际依赖与未知，未提交真实申请。

升级L1须在至少两项独立真实任务中留下窗口计算、依赖失败和第三人复核；升级L2须多案例含版本更新和不可逆动作后的复盘。没有这些证据就保持L1-draft。
