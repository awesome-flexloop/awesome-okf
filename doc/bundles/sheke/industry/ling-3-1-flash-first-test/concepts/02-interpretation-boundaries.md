# 怎么读这篇评测：边界与迁移

## 三类陈述要分开读

| 陈述 | 例子 | 可信层级 |
|---|---|---|
| 规格/发布事实 | 560B、权重未开放（F-005、F-008） | 文章单源，待官方核实 |
| 测试观察 | 小地图 bug 1 分半修完（F-010） | 单次任务采样，非基准 |
| 作者观点/感慨 | “没熟”“放在一年前都是 SOTA”（F-016、F-018） | 主观判断，不是事实 |

混读三种会得到错误结论——例如把“地铁 FPS 卡顿”当成“模型整体卡顿”，或把“对标 DeepSeek”当成已证实的排序。

## “对标 DeepSeek”是个问号，不是结论

文章用「能否对标 DeepSeek」做标题和钩子（F-001），正文给出的只是一次游戏开发测试的印象与“越做越大”的路线对照（F-007）。它既无官方基准对比，也无独立复现，因此应读作**待验证的比较问题**，不是已完成的能力排序。

## 可迁移的评测方法（去场景化）

原文的具体结论会过时，但“如何评测一个生成模型”可迁移到其他工具/模型的选择：

1. **多任务采样**：不只看一个题，覆盖常规、代码、空间/3D 等不同任务（F-009 的思路）。
2. **区分首稿与修正**：给反馈后看收敛速度，而不只比首稿完成度（F-012）。
3. **标注任务上下文**：把结果记成“任务 × 表现”，不写成“通用能力”（本概念第 2 节）。
4. **先验真伪后下判断**：权重/API 未开放时，一切数字都当“转述”，不升级为事实（F-008、见核验报告）。
