# 03 · 机制洞察

> **本页全部为执行者洞察（假设），不是平台公告。** 四条洞察都以「现象挂 F 编号」开头，原因部分为结构性推断；事实层可核对，机制层需验证。验证方式见文末。

## I1 · 入口化：把应用生产收进对话入口

| 四元组 | 内容 |
|---|---|
| **现象** | 用户在千问App内用一句自然语言描述需求即可开始建应用（F-005、F-008）；应用搭建、数据库配置与部署由 Meoo 承接（F-039、F-041）。 |
| **可能成因（洞察）** | 把生成能力放进已有高频入口，比要求用户学习独立开发平台更能扩大使用面；入口方无需自建云体系，后端交给专业平台（F-043）。 |
| **影响** | 应用生产的门槛从「会工具」降到「会描述」；供给数量上升，但用户对「应用」的预期会被示例抬高，实际能力受模板、配额与审核约束（F-046）。 |
| **建议** | 分开评估「入口」与「运行时」：入口决定谁能用、怎么开始；运行时决定能做什么、数据留多久、能否迁走（F-042、F-046）。 |

**边界**：这是对产品结构的解读，不是对生成质量的评价。公告没有披露入口层的模型、上下文长度、生成次数限制（G8），因此「入口更强/更弱」无法从本文判断。

## I2 · 后端平台化：OpenAPI 把存储、数据库与发布变成可嵌入能力

| 四元组 | 内容 |
|---|---|
| **现象** | Meoo 通过 OpenAPI 向 AI 产品提供应用预览、发布上线、数据存储能力，合作方可选是否展示 Meoo 品牌（F-043）；本次「我的应用」由 Meoo 提供云端服务（F-041）。 |
| **可能成因（洞察）** | 生成一个页面容易，让它「长期可用」难——缺的是文件存储、数据记录、用户区分与对外发布（F-042）。平台把这四件事打包，合作方不必自建云服务体系（F-043）。 |
| **影响** | 合作方可以快速获得全栈能力；代价是**平台绑定**：数据、发布链路与计费都落在 Meoo，迁移成本取决于导出能力。官方计费表显示**代码下载导出仅 Lite 及以上支持**（F-047）。 |
| **建议** | 在投入真实数据前，先确认三件事：能否导出代码/数据、能否绑定自有域名、是否有可调用的 API（F-047；G10）。把「能否离开」当作选型的一等指标。 |

**反证条件**：若千问Go 侧提供独立的数据导出与迁移工具，或 Meoo 开放免费档代码导出，则「绑定」判断需下调。

## I3 · 场景模板化：用样板降低「我能做什么」的想象成本

| 四元组 | 内容 |
|---|---|
| **现象** | 公告用五类场景 + 16 张截图展示能力（F-012、F-013），而不是参数表或功能清单；每类场景都给出一个具体例子（F-016、F-019、F-022、F-025、F-027）。 |
| **可能成因（洞察）** | 新品类首先要解决「我为什么要用」，场景比参数更容易让用户映射到自己的任务；具体例子还能降低「不知道能做什么」的空白感。 |
| **影响** | 用户倾向模仿示例，早期供给会集中在活动页、约课、导览等形态；长尾需求仍需要用户自己把任务描述清楚。示例也可能造成「只能做这些」的误解。 |
| **建议** | 从自己的**高频重复任务**反推（记录、统计、提醒、分享、报名），而不是照抄五个示例；示例只用于理解能力边界（F-015~F-029）。 |

**边界**：公告没有说这些场景是模板，也没有说只能做这些类型；Meoo 官网列出的应用类型更宽（F-049），但千问Go 侧实际开放范围未知（G8）。

## I4 · 邀测制：供给控制与真实数据学习的组合

| 四元组 | 内容 |
|---|---|
| **现象** | 「我的应用」与「云端Pro」处于邀测，用户需在千问App内排队申请（F-034、F-035）；资格「正加速向申请用户开放」，但没有时间表或名额（F-036）。 |
| **可能成因（洞察）** | 限量开放可以控制算力成本与内容审核风险，同时收集真实使用数据来迭代；稀缺感也会提升申请意愿。 |
| **影响** | 可用性不确定，**不适合作为关键业务依赖**；早期参与者可能获得反馈红利，但也承担功能变更、配额调整与停服风险（G4、G10）。 |
| **建议** | 以非关键试点参与：不影响主业务、可随时退出、数据可删除；不要把邀测功能写进对外承诺或合同（F-034~F-036）。 |

**反证条件**：若官方公布正式开放时间表、SLA 与配额，则「不确定」判断应下调；若长期停留在邀测，则应上调。

## 五、四条洞察的关系

```
I1 入口化（谁来做）
   │  需要后端能力
   ▼
I2 平台化（在哪里跑）—— 决定绑定与迁移成本
   │  需要通过场景教育需求
   ▼
I3 场景化（做什么）—— 决定早期供给形态
   │  需要控制供给与风险
   ▼
I4 邀测制（什么时候能用）—— 决定可用性预期
```

四者不是并列功能，而是一条**从分发到运行、从需求教育到供给控制**的链。任何一环的证据不足，都会让「产品已成熟」的判断站不住。

## 六、如何验证这些假设

| 假设 | 可观察信号 | 验证方式 |
|---|---|---|
| I1 入口化带来增量用户 | 非开发者占比、首次建应用转化率 | 官方披露或第三方调研（当前无） |
| I2 平台绑定真实存在 | 导出限制、域名限制、API 权限 | 申请邀测后逐项测试；对照 Meoo 计费表（F-047） |
| I3 场景影响供给形态 | 公开应用的类型分布 | 产品广场/分享链接抽样（当前无公开样本，G7） |
| I4 邀测是阶段性策略 | 开放节奏、配额变化、SLA 发布 | 跟踪官方公告与计费文档（S4、S5） |

> 在获得上述证据前，本页四条只能作为**分析框架**，不能作为结论引用。
