# 00 · 反馈延迟归零表

> **依据**：见 [../concepts/01-stage-craft.md](../concepts/01-stage-craft.md)。核心判断是——**反馈延迟是能力杀手**，因为人对延迟反馈的响应是衰减的。
>
> **本表的目标**：**把你所在领域的反馈延迟从「数月」压到「当场」。**

## 一、延迟分级表

先给你所在的事打分（推断层分类）：

| 级别 | 反馈延迟 | 典型领域 | 失败成本 | 成长速度 |
|---|---|---|---|---|
| **L4** | **当场** | 现场演出、直播、面对面授课、当面推销 | 高 | **最快** |
| **L3** | 1–3 天 | 会议现场、当天交付、当天发布 | 中高 | 快 |
| **L2** | 1–4 周 | 项目交付、代码上线、论文投稿 | 中 | 中 |
| **L1** | 1–6 月 | 影视作品、书籍出版、大型产品发布 | 低（可重拍/可改） | **最慢** |
| **L0** | 6 月以上 | 年度考核、长期项目评价 | 极低 | **几乎不成长** |

> **本包的判断（推断）**：
>
> **L1 的隐蔽危害最大**——它看起来「很专业」（作品要打磨），但实际上它提供了**虚假的安全感**：因为可以重拍，所以不需要真的进步。
>
> **「可剪辑」是环境的属性，不是你的属性。** 当环境允许重拍时，人会自动降标准——这不是意志问题，是结构问题。

## 二、六个降低延迟的具体动作

按可行性排序（推断层）：

### 动作 1：把「准备好的东西」今天发出去

| 领域 | 改造前 | 改造后 |
|---|---|---|
| 写作 | 改到满意再发 | **今天发一版**，收反馈 |
| 设计 | 内部评审到完美 | **今天给一个人看** |
| 代码 | 本地跑通就安心 | **今天上线一个功能** |
| 方案 | 反复讨论 | **今天找一个人讲一遍** |

> **成本**：几乎为零。**收益**：反馈从数周变成当天。

### 动作 2：找一个「不能 NG」的场合

**四个替代方案**（推断层，不限于表演）：

| 方案 | 说明 | 适合谁 |
|---|---|---|
| **A. 站上讲台** | 面对真人讲，不许重来 | 所有人 |
| **B. 直播/录播** | 有观众即时反应 | 有表达需求的人 |
| **C. 现场交付** | 当面把东西交给对方并当场确认 | 做服务/咨询的 |
| **D. 实战场景** | 去真实的环境里做（不是模拟） | 有条件型工作的 |

> **为什么是这四个**（推断）：它们的共同点是**有真人在场，且不能暂停**。
>
> **注意 D 的特殊价值**：它对应胡歌的青海环保（F-HG-072）——**你不捡垃圾，垃圾就在那里**。这是最强的反馈，因为**环境本身给出反馈，不需要任何人评价**。

### 动作 3：把「大项目」拆成一个 L3 动作

**示例**：

| 原计划 | 拆成 | 延迟 |
|---|---|---|
| 写一本书 | 今天写 500 字发给一个人 | L3 |
| 做一次公开演讲 | 今天在三人小会上讲 5 分钟 | L3 |
| 上线一个产品 | 今天给一个人演示原型 | L3 |
| 学完一门课 | 今天讲给一个人听 10 分钟 | **L4** |

> **最后一行是本包最推荐的一条**（推断）：**「学完讲给人听」同时满足 L4 + 输出验证 + 暴露理解漏洞。**
>
> 这与陶行知的「教学做合一」第三步（见 [../../taoxingzhi-life-education/concepts/01-three-propositions.md](../../taoxingzhi-life-education/concepts/01-three-propositions.md)）和游本昌教孩子的「还能是什么」（A 级 F-YB-088）都指向同一件事。

### 动作 4：给自己找一个「更强的对象」

**依据**：见 [../concepts/01-stage-craft.md](../concepts/01-stage-craft.md) 第 4 节「慢功夫第三条特征」。

```
自己练 → 有重复无反馈 → 变成机械练习
与更强的人合作 → 有对比 → 反馈自动产生
```

**可操作的三种找法**：
1. 找一个比你强的人，请他看你的东西（**注意**：他要真的看，且要给出具体意见）
2. 加入一个有高手的社群/项目
3. 如果找不到人——**去一个真实的环境里做**（对应动作 2 的 D）

### 动作 5：把「成功标准」从「无失误」改成「有反馈」

> **这是本表最重要的一条**（推断）。
>
> ```
> 旧标准：这件事不能出错 → 因此要多练 → 因此延迟交付
> 新标准：这件事要拿到反馈 → 因此可以粗糙地做 → 因此快速交付
> ```

**填写**：

```
我当前正在做的事：
  ______

我现在设定的成功标准是：□ 不出错  □ 完美  □ 有反馈
  （勾一个）

如果改成「有反馈」，我最早可以在第几天交出去？第 ___ 天
```

### 动作 6：每月做一次「延迟审计」

见下节。

## 三、每月检查表

```markdown
## 反馈延迟审计（第 N 月）

### 1. 我本月的产出分别是什么级别？
| 产出 | 延迟级别 | 是否拿到真实反馈 |
|---|---|---|
| | L__ | □ 是 □ 否 |
| | L__ | □ 是 □ 否 |

### 2. 本月有没有一件事是「当场拿到反馈」的？
  □ 有 → 是：______
  □ 没有 → 说明本月完全在 L1/L2 区，需要在动作 1/2 中选一个执行

### 3. 我有没有跟一个「比我强的人」一起做事？
  □ 有 → 是：______
  □ 没有 → 说明本月无对比反馈（动作 4）

### 4. 我本月有几次「粗糙地先发出去」？
  ___ 次
  （0 次 = 本月的延迟完全没有被压缩）

### 5. 下月要压缩的一件事
  我选择压缩 ______ 的反馈延迟，从 L__ 到 L__
```

## 四、六个月后的判断

| 问题 | 回答 | 判断 |
|---|---|---|
| 本月产出的平均延迟级别是否下降了一级？ | □ 是 □ 否 | 机制是否建立 |
| 我是否已经能接受「粗糙地交付」？ | □ 能 □ 不能 | **心态是否转变**（这是最难的一项） |
| 我是否有过「当场拿到反馈」的经历？ | □ 有 □ 无 | 环境是否改造过 |
| 我是否有一个「比我强的人」在持续合作？ | □ 有 □ 无 | 对比反馈源是否存在 |

> **最难的一项是第二问**（推断）：**降低延迟的关键障碍不是方法，是「允许自己交出不完美的东西」的心理承受力。**
>
> **一个可操作的小技巧**（推断）：把交付标准显式写下来并加上时间戳——**「v0.1，2026-XX-XX，目标是拿反馈不是拿好评」**。写下来之后，交出粗糙版本就不再是「失职」，而是「按计划执行」。
