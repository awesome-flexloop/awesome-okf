# GraphQL 概览与五大设计原则

## GraphQL 是什么

GraphQL 是一种用于 API 的开源查询语言和服务端运行时（server-side runtime）。它通过提供直观且灵活的语法与系统来描述客户端的数据需求与交互，以构建客户端应用（F-001、F-613）。

GraphQL 服务通过定义类型及其字段、然后为每个字段编写提供所需数据的函数来创建（F-620）。它使用自定义类型系统（type system）来执行查询，提供强类型 schema 定义数据之间的关系，使 API 更灵活和可预测（F-613、F-619）。

理解 GraphQL 的三个关键边界（F-001~F-003）：

1. **不是通用编程语言**：GraphQL 不能进行任意计算，它专注于数据查询与交互描述。
2. **不绑定实现语言**：不强制要求实现它的应用服务使用特定的编程语言或存储系统，可与现有代码和数据协同工作。
3. **不绑定数据库或存储引擎**：GraphQL 不要求特定数据库，可由现有代码、数据库、REST API 或第三方服务支撑。

GraphQL 规范于 2015 年开源，现已在多种编程语言中实现。它最早在 Facebook 移动应用中自 2012 年起投入使用，现由 GraphQL 基金会支持，该基金会自 2018 年起由非营利组织 Linux 基金会托管（F-614、F-619）。

## 五大设计原则

GraphQL 的设计围绕五个核心原则（F-004、F-615），这些原则共同塑造了语言的语法、类型系统和运行时行为。

### 1. Product-centric（产品中心）

GraphQL 由视图和编写视图的前端工程师的需求驱动，从他们的思维方式和需求出发构建语言和运行时（F-005）。它不是由存储层或后端架构约束塑造的，而是由产品消费数据的方式塑造的——客户端需要什么数据、以什么形状消费，决定了查询语言的设计。

### 2. Hierarchical（分层）

GraphQL 请求本身是分层结构的，请求的形状与其响应中的数据形状一致（F-006）。嵌套选择集对应嵌套响应对象，形成自然的树状同构关系。客户端可构造镜像所需数据结构的 GraphQL 查询，单次请求获取预期形状的数据，无需关心底层数据源（F-622）。

### 3. Strong-typing（强类型）

每个 GraphQL 服务定义一个应用特定的类型系统（F-007）：

- 请求在该类型系统的上下文中执行；
- 工具可以在执行前（开发时）确保操作在语法上正确且在该类型系统中有效；
- GraphQL 服务接收查询后首先检查查询，确保它仅引用 API 已定义的类型和字段，然后运行提供的函数生成结果（F-621）。

类型系统不是辅助文档，而是客户端与服务端之间可执行、可验证的契约。

### 4. Client-specified response（客户端指定响应）

GraphQL 服务通过类型系统发布客户端允许消费的能力，由客户端负责指定如何消费这些能力（F-008）：

- 请求以字段级粒度指定；
- 响应恰好包含客户端所请求的内容，不多不少。

这一原则带来了 GraphQL 的核心优势：精确获取所需数据，无过度获取（over-fetching）或获取不足（under-fetching）；单次请求即可跟随数据间关系获取多个资源（F-616）。

### 5. Self-describing（自描述）

GraphQL 服务的类型系统可通过 GraphQL 语言本身查询，其中包含可读的文档（F-009）。服务围绕类型和字段而非 endpoint 构建，确保数据一致性和自文档化（F-616）。这一特性支撑了 GraphiQL、代码生成、IDE 自动补全等整个工具生态。

## 与 REST 的对比

基于上述设计原则，GraphQL 与传统 REST API 在多个维度上形成对比：

| 维度 | GraphQL | REST（典型模式） |
|------|---------|-----------------|
| 数据获取 | 客户端通过选择集指定所需字段，响应恰好包含请求内容（F-008） | 服务端预定义每个 endpoint 返回的数据结构，常出现过度获取或多次请求 |
| 请求结构 | 分层嵌套，单次请求跟随数据关系获取多个资源（F-006、F-616） | 通常需多次请求访问不同 endpoint 聚合数据 |
| 契约 | 强类型 schema 作为可执行契约，开发时即可验证查询有效性（F-007） | 契约依赖外部文档（如 OpenAPI），运行时才发现不匹配 |
| 自描述 | 类型系统可通过 GraphQL 语言本身查询，支持交互式工具（F-009、F-618） | 需额外文档体系，工具集成依赖规范同步 |
| 版本演进 | 添加新字段和类型不影响现有查询，通过 `@deprecated` 弃用过时字段（F-623） | 常通过 URL 版本号（如 `/v1/`、`/v2/`）管理破坏性变更 |

GraphQL 不要求特定序列化格式或传输机制，这与 REST 通常基于 HTTP 动词和 URL 的模式不同。GraphQL 服务通常通过单个入口接收查询，由查询本身决定操作类型和数据需求。

## 三阶段管线全局图

本规范描述语言及其语法、类型系统、用于查询类型系统的内省系统，以及执行和验证引擎及其算法（F-010）。GraphQL 请求处理遵循严格分层的三阶段管线：

```
客户端请求
    │
    ▼
┌──────────┐    验证失败     ┌──────────────┐
│  验证     │ ────────────── │ request error │（无 data）
│ Validation│                └──────────────┘
└────┬─────┘
     │ 验证通过
     ▼
┌──────────┐    执行错误     ┌──────────────┐
│  执行     │ ────────────── │ execution     │（部分 data）
│ Execution│                │ error         │
└────┬─────┘                └──────────────┘
     │
     ▼
┌──────────┐
│  响应     │
│ Response │
└──────────┘
```

1. **验证（Validation）**：GraphQL 服务不仅验证请求语法正确，还确保其在给定 schema 上下文中无歧义无错误。服务接收查询后首先检查查询，确保它仅引用 API 已定义的类型和字段（F-621）。只有通过所有验证规则的请求才应执行；已知验证错误应在响应中报告且请求必须不执行。

2. **执行（Execution）**：验证通过后，服务运行提供的函数生成结果。执行流程为：确定要执行的操作 → 强制转换变量值 → 按操作类型（query/mutation/subscription）分派执行。执行期间，字段解析、参数强制转换、值完成按选择集递归进行。

3. **响应（Response）**：GraphQL 服务必须返回格式良好的响应，描述成功执行的结果或请求期间引发的错误。响应必须包含 `data` 条目；执行引发错误时还需包含 `errors` 条目。

验证失败产生 request error（无 `data`），执行失败产生 execution error（可能有部分 `data`），二者的响应结构截然不同。

三种操作类型在执行阶段有不同语义：
- **query**：只读获取，字段可并行执行；
- **mutation**：先写入后获取，顶级字段串行执行以防止竞态条件；
- **subscription**：长连接请求，随时间事件序列获取数据，返回事件流。

## 生态概览

GraphQL 的生态系统建立在自描述原则之上，围绕类型系统形成了丰富的工具链和社区（F-616、F-618）：

- **GraphiQL**：社区构建的开源交互式查询编辑器，支持自动补全（Ctrl+Space）和运行查询（Ctrl+Enter），使开发者能即时探索 schema 并测试查询。
- **代码生成**：利用自描述类型系统，工具可从 schema 自动生成类型化客户端代码，实现端到端类型安全。
- **数据共置（Data Colocation）**：GraphQL fragments 支持在组件附近定义每个组件的数据需求，并通过单个查询满足，使前端组件与其数据依赖紧密关联（F-617）。
- **多语言实现**：规范已在多种编程语言中实现，服务端和客户端库覆盖主流技术栈（F-619）。
- **无版本演进**：API 可通过添加新字段和类型持续演进而不破坏现有查询，通过 `@deprecated` 指令标记弃用，待确定不再使用后移除（F-623）。
- **存储无关集成**：GraphQL 可集成数据库、REST API 和第三方服务到统一数据层，客户端无需关心底层数据源（F-616、F-622）。

规范本身描述了从查询编写到验证、执行、响应的完整管线定义，是所有实现的权威参考（F-010）。
