## 统一决策框架

Jupyter 所有治理机构（EC、SSC、各子项目 Council、常设委员会、工作组）都必须遵循**统一的决策制定流程**。这确保了个人跨多个决策机构工作时体验一致。

核心原则：**协作、包容参与、响应式决策**。

## 两阶段决策流程

```
┌──────────────────────────────────────────────────────────┐
│  阶段1：非正式共识寻求（Informal Consensus Seeking）       │
│  · 讨论完善提案                                           │
│  · 考虑替代方案                                           │
│  · 权衡取舍                                               │
│  · 所有利益相关者有发言机会                                │
│  · 达成共识 → 直接记录并执行                              │
└──────────────────────────┬───────────────────────────────┘
                           │ 讨论成熟，任何成员可发起投票
                           ▼
┌──────────────────────────────────────────────────────────┐
│  阶段2：正式投票（Formal Vote）                           │
│  · 发起者总结提案 → 另一成员附议                          │
│  · 7天投票期（全员在场时可缩短）                           │
│  · 二选一：简单多数；多选项：排序复选制                    │
│  · 50%法定人数；始终包含"空白"选项                        │
│  · 结果公开记录                                           │
└──────────────────────────────────────────────────────────┘
```

### 阶段1：非正式共识寻求

决策始于讨论，目标是：
- 完善提案
- 考虑替代方案
- 权衡取舍
- 找到非正式共识

关键要求：
- **所有利益相关者必须有发言机会**：Council 必须主动为相关利益相关者提供输入机会
- 不假设沉默即同意
- 达成非正式共识后，可立即记录并执行决策

### 阶段2：发起投票

当共识阶段的讨论成熟后，任何 Council 成员可发起投票：

1. **发起**：发起者（sponsor）总结当前提案
2. **附议**：另一名 Council 成员附议（second）后进入投票期
3. **投票期**：成员有**7天**时间投票；全员在场时可缩短；特殊情况可延长
4. **提案更新**：发起者可在投票期内更新提案，此时投票期重置
5. **结果判定**：
   - **二元决策**（批准/否决）：非空白票的简单多数通过
   - **多选决策**（多个选项中选一个或多个）：使用排序复选制（ranked choice）

## 投票参与率要求

- **最低参与率**：所有 Council 成员每年必须参与至少 **2/3** 的正式投票
- **自动卸任**：未达标者在年底自动被要求卸任，但未来可重新加入
- 低活跃度项目可自行定义具体的统计方式

## 法定人数

- 所有正式投票的法定人数为 **50%**
- 始终包含**"空白"（blank）选项**
- 空白票计入法定人数，但不计入结果计算
- 各 Council 可自行制定更严格的规则

## 决策记录

决策做出后（无论是共识阶段还是投票），Council 必须公开记录决策：
- 使用 GitHub Team Compass issues 或等效的公开可见机制
- 记录内容应清晰可查

## 可选最佳实践

以下是推荐但非强制的指南：

1. **不要用投票短路讨论**：如果讨论仍在有效探索想法和反馈，不应发起投票
2. **主动征求意见**：不要假设沉默即同意，应主动联系利益相关者
3. **双向门 vs 单向门**：
   - **双向门**（Two-way door）：容易逆转的决策 → 可快速推进
   - **单向门**（One-way door）：难以或不可能逆转的决策 → 需要格外谨慎，确保广泛参与
4. **软件项目建议**：
   - 在 issue 和 PR 模板中添加决策指南链接
   - 使用 `seeking consensus`、`vote`、`decision made` 标签
   - 投票时在 issue/PR 描述中附上投票成员清单
   - 主要实施工作开始前，开独立 issue 总结问题并号召投票
   - PR 实施决策时链接到相关 `vote` issue

## EC 干预

在以下情况下，EC 可介入或被理事会成员呼吁介入：
- 流程模糊不清
- 违反决策流程
- 需要流程例外的特殊情况

## 反常识要点

- **投票不是默认决策方式**：Jupyter 强烈偏好共识决策，投票是共识无法达成时的升级机制，而非日常决策手段。
- **空白票有意义**：空白票计入法定人数，意味着成员可以通过投空白来表达"我参与但不站队"，同时不阻止投票达到法定人数。
- **提案可在投票中修改**：发起者可以在投票期内更新提案（投票期重置），这允许投票过程继续完善提案。
- **2/3参与率是硬指标**：不参与投票的成员会被自动清退，这确保治理机构始终由活跃成员组成。
