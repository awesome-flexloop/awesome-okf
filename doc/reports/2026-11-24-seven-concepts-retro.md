## 2. 洞察（I）

### I-01 跨包对比的第一步是版本对齐，不是功能对比

- **陈述**：两个知识包同日生成、同一 `stale_after`、互相链接，但父主题基线相差两个小版本；对比结论的有效性以版本对齐表为前提。
- **证据**：F-08、F-09、F-10；对比报告 §1.2、§4-I-06。
- **反常识**：同组、同日、互相引用的文档容易被当作同一时间切片；本次两个包描述的是 `0.25.0dev0` 与 `0.23.0` 两个不同对象。
- **行动**：任何跨包/跨版本对比，第一节固定写"版本对齐表"，并在每条结论旁标注"适用于哪个版本"。

### I-02 导出层的返工由格式契约决定，与内容质量无关

- **陈述**：本次 6 处返工中，4 处发生在 Markdown→DOCX 的格式契约（标题重复、TOC 空域、CLI 参数编码、表格竖线），2 处发生在内容层的交叉引用编号。
- **证据**：F-17~F-21、F-27、F-28。
- **反常识**：报告质量的主要瓶颈不在分析与写作，而在"同一份源在两种渲染器下的语义差异"；这类问题不会在 Markdown 预览里暴露。
- **行动**：把导出检查固化为脚本：标题唯一、TOC 静态可读、表格列数一致、中文参数不进 CLI、导出后校验表数与标题数。

### I-03 对抗审查的收益主要来自证伪自己

- **陈述**：6 条审查质疑中 4 条针对本次报告的初判并被证伪，直接改写 3 个章节的结论；审查后报告的证据密度高于初稿。
- **证据**：F-22~F-24；对比报告 §6.1。
- **反常识**：对抗审查常被当作"挑别人的错"；本次实际产出是删掉了 4 条看似合理但站不住的判断（如"SBT 缺版本切换器"）。
- **行动**：对比类报告强制增加"被证伪的自身判断"清单，作为交付物的一部分，而不是内部草稿。

### I-04 脚本化审计的成本远低于人工逐页检查

- **陈述**：结构审计脚本一次运行覆盖 53 个文件的文件数、行数、标题、表格行、frontmatter 与链接可达性；首次误报 1 处，修正后为 0 断链。
- **证据**：F-05~F-07、F-25、F-27。

## 3. 模式萃取（E）

### P-01 跨包对比四步法

**触发场景**：需要在两个及以上同源/同类知识包之间做可信对比。

**结构**：

```text
① 版本对齐（基线、依赖、维护状态）
      ↓
② 结构审计（脚本：文件/行/表/链接/frontmatter）
      ↓
③ 逐维对比（固定维度表，逐项给证据编号）
      ↓
④ 自身证伪（列初判 → 逐条攻击 → 改写结论）
```

**步骤**：

1. 先产出版本对齐表，标注"不适用"的结论。
2. 用脚本产出可复现的结构指标，不靠目测。
3. 维度表固定后再填内容，避免"哪边材料多就多写"。
4. 单列"被证伪的自身判断"，作为可信度凭证。

**反模式**：直接按文档目录顺序写"读后感"；用事实条数代替质量评价；对比结论不标版本。

**迁移验证**：套到"两个前端框架"或"两个云服务"的选型报告，检查是否仍能产出可回查的版本对齐表与证伪清单。

### P-02 单一正文源 + 双格式交付契约

**触发场景**：同一份报告需要 Markdown 与 Word/PDF 两种交付。

**结构**：

```text
report.md（唯一正文源，含静态目录）
    ├── 校验：标题层级 / 表格列数 / 链接
    ├── 导出：pandoc → docx（无 TOC 域、无重复标题）
    └── 复核：表数、标题数、段落数、代码块数
```

**步骤**：

1. 正文只维护一份 Markdown，目录写成静态列表。
2. 导出前剥离 YAML frontmatter，避免 Title 与正文 H1 重复。
3. 中文参数不通过 CLI 传递，改用文件内容或默认值。
4. 导出后校验：表数、各级标题数、TOC 域数量为 0。
5. 把上述检查写成脚本，随交付一起运行。

**反模式**：用 Word 域生成 TOC 却不填充缓存；在命令行传中文标题；表格单元格里写裸竖线。

**迁移验证**：套到任意"Markdown → PDF"流水线，检查是否能用同一套校验项覆盖。
